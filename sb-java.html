Annotations — notes someone else reads

lab2-complete · entity/Product.java · lines 8–18

Eight annotations in eleven lines. An annotation is a note attached to a class, a field, a method or a parameter. On its own it does nothing: no code runs because a note is there. Something else reads the note and acts on it. In your project there are three kinds of reader, at two different times.

Who reads itWhenIn your code
the compilerwhile compiling@Override — "check that this really overrides something" (CustomUserDetailsService, line 20)
Lombokwhile compiling, inside the compiler@Getter, @Setter, @NoArgsConstructor, @AllArgsConstructor, @Builder, @RequiredArgsConstructor — "write this code for me"
Spring and its librarieswhile your app runs@Service, @RestController, @GetMapping, @Value; Hibernate reads @Entity, @Id, @Table; the validator reads @NotBlank, @Size

Retention: how long a note is kept

Every annotation type says how long its notes survive, with @Retention. SOURCE notes are read during compiling and then dropped; they are not in the .class file at all. @Override and every Lombok annotation are SOURCE. RUNTIME notes are written into the .class file and can still be read while the program runs. Spring's and JPA's annotations are RUNTIME, because Spring reads them only when your app starts. (There is a third, CLASS — kept in the file but not readable at run time. It's the default, and none of your annotations use it.) So when you meet a new annotation, ask two questions: who reads it, and when? The answer tells you what it can and can't do.

Be Spring for a minute

How can a note on a method make that method answer a URL? Here is the idea in 30 lines of plain Java. It invents an annotation @Get, puts it on two methods, then does what Spring does at start-up: looks through the class for notes, and calls the methods that have one.

// MiniSpring.java import java.lang.annotation.*; import java.lang.reflect.Method; import java.util.*; public class MiniSpring { public static void main(String[] args) throws Exception { Object controller = new ProductController(); Map<String, Method> routes = new TreeMap<>(); for (Method m : ProductController.class.getDeclaredMethods()) { Get get = m.getAnnotation(Get.class); // read the note, if there is one if (get != null) { routes.put(get.value(), m); } } for (String path : routes.keySet()) { System.out.println(path + " -> " + routes.get(path).invoke(controller)); } // /api/products/count -> 3 // /api/products/get-all -> [Laptop, Wireless Mouse, Mechanical Keyboard] } } @Retention(RetentionPolicy.RUNTIME) // try SOURCE here @Target(ElementType.METHOD) @interface Get { String value(); } class ProductController { @Get("/api/products/get-all") public String getAll() { return "[Laptop, Wireless Mouse, Mechanical Keyboard]"; } @Get("/api/products/count") public String count() { return "3"; } public String helper() { return "no note, so never called"; } }

Change RUNTIME to SOURCE and run it again: it prints nothing. The notes were dropped while compiling, so at run time there is nothing to find. That is why every Spring annotation is RUNTIME. Spring's real version is far bigger, but the idea is this one; B1 shows what it does with @GetMapping.

The parameters of @AllArgsConstructor are the fields, in the order you declared them. name and description are both String, so passing them the wrong way round compiles without a murmur — see oops above. @Builder writes a small helper class, ProductResponseBuilder, inside ProductResponse, plus a static method builder() that hands you a new one. Here it is by hand, cut down to three of the six fields:

// PlainBuilder.java — what @Builder writes, for three of ProductResponse's fields import java.math.BigDecimal; public class PlainBuilder { public static void main(String[] args) { ProductResponse r = ProductResponse.builder() .id(3L) .name("Mechanical Keyboard") .price(new BigDecimal("3500.00")) .build(); System.out.println(r.getName() + " " + r.getPrice()); // Mechanical Keyboard 3500.00 ProductResponse partial = ProductResponse.builder().name("Laptop").build(); System.out.println(partial.getId()); // null } } class ProductResponse { private Long id; private String name; private BigDecimal price; public ProductResponse(Long id, String name, BigDecimal price) { // @AllArgsConstructor this.id = id; this.name = name; this.price = price; } public Long getId() { return id; } // @Getter public String getName() { return name; } public BigDecimal getPrice() { return price; } public static ProductResponseBuilder builder() { // @Builder: the way in return new ProductResponseBuilder(); } public static class ProductResponseBuilder { // @Builder: the builder itself private Long id; private String name; private BigDecimal price; public ProductResponseBuilder id(Long id) { this.id = id; return this; } public ProductResponseBuilder name(String name) { this.name = name; return this; } public ProductResponseBuilder price(BigDecimal price) { this.price = price; return this; } public ProductResponse build() { return new ProductResponse(id, name, price); // calls the all-args constructor } } }

Two things make the chain in your toProductResponse work. Each setter-like method ends with return this, so the next .name(…) is called on the same builder. And build() passes everything to the all-args constructor. A field you don't set stays null, like partial.getId().

You'll meet builders that nobody generated, too. JwtClaimsSet.builder() … .build() in JwtService, and User.withUsername(…) … .build() in section 03, are Spring's own builder classes, written by hand. Same shape, same reading.

An interface is a list of methods with no bodies: a promise of what an object can do, without saying how. ProductRepository declares one method of its own, findByCategory. Through extends JpaRepository<Product,Long> it inherits a whole list more — findAll, findById, save, delete — which is why ProductService can call them.

Generics: blanks that you fill in

JpaRepository is declared as JpaRepository<T, ID>. T and ID are type parameters — blanks. Writing JpaRepository<Product, Long> fills them: T is Product, ID is Long. An Instant is a single moment on the timeline, counted in UTC. It prints in a standard form ending in Z (for UTC). It has no time zone to get wrong: two servers in two countries agree on it. Your code uses it for every timestamp — when a user was created, when a token was issued and when it expires, when an error happened (ApiErrorResponse.timestamp). The other kind, LocalDateTime, has no zone at all, so "10:00" could mean any 10:00 on Earth. (A1's Year.now().getValue() came from the same package, java.time.)

Try it — in jshell

import java.time.* Instant start = Instant.ofEpochSecond(0); start // 1970-01-01T00:00:00Z Instant later = start.plusSeconds(3600); later // 1970-01-01T01:00:00Z start // 1970-01-01T00:00:00Z later.isBefore(start) // false later.getEpochSecond() // 3600

Three things to take from this. plusSeconds returns a new Instant and leaves start alone — that's why JwtService has two variables, issuedAt and expiresAt. isBefore compares two moments; your deleteByExpiresAtBefore(Instant) asks the database the same question. And an Instant is, underneath, a count of seconds since the start of 1970 — exactly how a JWT stores iat and exp (B3). Try Instant.now() too: it prints the current moment in UTC.

An enum is a class with a fixed list of objects, one per name, each made once, the first time the enum is used. A Role can only be Role.STUDENT or Role.ADMIN; a typo like Role.ADMN doesn't compile, where the text "ADMN" would. Your code turns a role into text with name() — user.getRole().name() in JwtService (line 40) and CustomUserDetailsService (line 36). How the database stores it (@Enumerated(EnumType.STRING) in User.java) is B1; what Spring does with the text is B3.

You use several of Spring's enums too: HttpStatus, SessionCreationPolicy, GenerationType, MacAlgorithm. An enum constant can carry values of its own — HttpStatus.NOT_FOUND.value() is 404, and .getReasonPhrase() is "Not Found" (GlobalExceptionHandler, lines 28–29). Here is that shape in plain Java:

// Enums.java public class Enums { public static void main(String[] args) { Role role = Role.STUDENT; System.out.println(role.name()); // STUDENT System.out.println(role == Role.STUDENT); // true System.out.println(Role.valueOf("ADMIN")); // ADMIN System.out.println(Status.NOT_FOUND.value() + " " + Status.NOT_FOUND.getReasonPhrase()); // 404 Not Found System.out.println(Role.valueOf("admin")); // Exception in thread "main" java.lang.IllegalArgumentException: No enum constant Role.admin } } enum Role { STUDENT, ADMIN } // the same as yours enum Status { // the shape of Spring's HttpStatus: each constant carries values OK(200, "OK"), NOT_FOUND(404, "Not Found"); private final int value; private final String reasonPhrase; Status(int value, String reasonPhrase) { this.value = value; this.reasonPhrase = reasonPhrase; } public int value() { return value; } public String getReasonPhrase() { return reasonPhrase; } }

In A1 you overrode equals and hashCode on the ISBN, so two Book objects for the same book count as the same — and toString, so a book prints as something readable. Your lab's Product has none of the three, and section 05's table showed why: @Getter, @Setter and the constructor annotations don't write them. Without them, Java uses the versions from Object: equals means "the very same object", and toString prints the class name and a number.

// SameOrNot.java import java.util.*; public class SameOrNot { public static void main(String[] args) { Book a = new Book("9780134685991", "Effective Java"); Book b = new Book("9780134685991", "Effective Java, 3rd edition"); System.out.println(a.equals(b)); // true System.out.println(new HashSet<>(List.of(a, b)).size()); // 1 System.out.println(a); // 9780134685991 Effective Java Product p = new Product(1L); Product q = new Product(1L); System.out.println(p.equals(q)); // false System.out.println(new HashSet<>(List.of(p, q)).size()); // 2 System.out.println(p); // Product@7a81197d } } class Book { // the A1 way: same ISBN, same book private final String isbn; private final String title; Book(String isbn, String title) { this.isbn = isbn; this.title = title; } @Override public boolean equals(Object o) { if (this == o) return true; if (!(o instanceof Book)) return false; Book other = (Book) o; return isbn.equals(other.isbn); } @Override public int hashCode() { return isbn.hashCode(); } @Override public String toString() { return isbn + " " + title; } } class Product { // like yours: no equals, hashCode or toString private final Long id; Product(Long id) { this.id = id; } }

The number after Product@ differs on every run. In your app, the same thing happens if you print a product: System.out.println(product) shows com.esd.ecommerce.entity.Product@ and a number.

Why equals needs hashCode

A HashMap or HashSet finds things in two steps: first it uses hashCode() to pick a bucket, then it uses equals inside that bucket. So two objects that are equals must have the same hashCode, or the set looks in the wrong bucket and never compares them. A1's three maps were keyed by the ISBN String, which already gets both right — that's what made the ISBN a good key.

Try it

In SameOrNot.java, delete Book's hashCode method (both lines) and run it again. a.equals(b) is still true, but the set now holds 2 books: they landed in different buckets.

Should Product have equals?

Your lab code never needed it: it never compares two products or puts them in a set. If you ever add it, the obvious choice — compare id — has a catch. Before a product is saved, its id is null, so every unsaved product would equal every other one. And once saved, its id changes from null to a number, which changes its hashCode while it may already be inside a set. The usual answers: compare id only when it isn't null, or compare a value that never changes and is unique, the way A1 used the ISBN. Lombok's @Data and @EqualsAndHashCode compare every field, which makes this worse — a common reason to put @Getter and @Setter on an entity instead, as your lab does.
