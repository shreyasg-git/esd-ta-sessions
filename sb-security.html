01

Your security code, file by file

Coretwo questions, thirteen files

Every request to your API meets two questions, in this order:

  1. Who are you? That's authentication. When it fails — no token, a forged one, an expired one — the answer is 401 Unauthorized. (The name is old and confusing: 401 means "not authenticated".)
  2. What may you do? That's authorization. When it fails — you're a STUDENT and this route is for ADMINs — the answer is 403 Forbidden.

Each security file in your project answers one of those questions, or helps another file answer it:

config/SecurityConfigThe rules: which routes are open, which need a token, which need ADMIN. Also: no sessions, CSRF off, JSON errors. Sections 02, 03, 10.
config/SecurityBeansConfigTwo beans: the BCrypt password encoder and the AuthenticationManager. Sections 05, 06.
config/JwtConfigThe secret key, the JwtEncoder that signs tokens, the JwtDecoder that checks them. Sections 07, 09.
config/JwtRevocationValidatorOne extra check inside the decoder: has this token been logged out? Section 14.
config/RestSecurityErrorHandlerWrites the 401 and 403 bodies as JSON. Section 12.
controller/AuthController/api/auth/signup, login, me, logout. Sections 05, 06, 13, 14.
service/AuthServiceWhat signup and login actually do. Sections 05, 06.
service/CustomUserDetailsServiceHow Spring loads a user by email during login. Section 06.
service/JwtServicePuts the claims together and asks the encoder to sign them. Section 07.
service/TokenRevocationServiceWith entity/RevokedToken and its repository: the logout table. Section 14.
entity/User, RoleThe users table; every account is STUDENT or ADMIN. Section 05.
dto/SignupRequest …SignupRequest, LoginRequest, AuthResponse, UserResponse: the JSON in and out. Their validation annotations are B2's subject.
application.propertiesLines 9–11: the issuer, the lifetime, the secret. Section 07.

All of it rests on two starters in your pom.xml:

lab2-complete · pom.xml · lines 68–78

<!-- Spring Security: authentication and authorization --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-security</artifactId> </dependency> <!-- Spring Security JWT / Bearer token support --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-security-oauth2-resource-server</artifactId> </dependency>

The first brings Spring Security: the filter chain, password encoders, AuthenticationManager. The second is misleadingly named. You are not doing "OAuth2 login". A resource server, in OAuth2's vocabulary, is simply an API that accepts bearer tokens — and this starter is Spring's ready-made "check a JWT on every request", plus the Nimbus library that signs and reads JWTs. Your app uses it for its own tokens.

Something you won't find

There's no @EnableWebSecurity anywhere. Spring Boot adds it for you when Spring Security is on the classpath. And because you declared your own SecurityFilterChain bean, Boot's default security — a login form and a generated password — steps aside completely. Everything security does in your app is in these files.

02

Stateless: no session, a token every time

CoreSessionCreationPolicy.STATELESS, and CSRF off

lab2-complete · config/SecurityConfig.java · lines 26–31

http .csrf(csrf -> csrf.disable()) .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS) )

Sessions — what you're not doing

A classic website remembers you. At login the server creates a session — "session 8f3a… belongs to Asha" — keeps it in memory, and hands your browser a cookie, JSESSIONID=8f3a…. The browser sends the cookie on every request by itself, and the server looks the session up.

Tokens — what you are doing

Your server remembers nothing about a login. At login it writes down who you are and until when, signs that with a secret only it knows, and hands you the signed text — a JWT. You send it in a header on every request: Authorization: Bearer eyJ…. The server checks the signature and believes what the token says. SessionCreationPolicy.STATELESS (line 30) tells Spring Security never to create an HttpSession and never to look in one.

Try it — nothing remembers you

  1. In Postman, log in (POST /api/auth/login) and look at the response headers. There is no Set-Cookie.
  2. Straight away, call GET /api/auth/me without the Authorization header. 401 — the login a second ago left no trace on the server. Add the header with your token and it's 200.

Why CSRF is off (line 27)

CSRF (cross-site request forgery) is an attack on cookies. A page on evil.example submits a form to your bank; your browser attaches the bank's cookie by itself, so the bank sees a logged-in request you never meant to send. Spring Security's CSRF protection blocks that by demanding a second, secret value that the evil page can't know.

Your API never reads a cookie to decide who you are. The token travels in a header, and a browser never adds an Authorization header on its own. Nothing to forge, so line 27 turns the protection off. (Move the token into a cookie one day and the question comes back.)

Stateless means login state

Your products and users are still in MySQL. "Stateless" only says the server keeps no memory of who logged in. Section 14 shows the one place where your scaffold has to bring a little state back.

Q1A friend copies your token out of Postman and sends it from their laptop. What does your server see?
Show answer

A perfectly valid token. It can't tell who is holding it — that's what bearer means: whoever bears it is you, until it expires. Treat a token like a password.

The filter chain — where security happens

Corebefore your controller runs

Refresher

A request reaches Tomcat, passes through a list of filters, then reaches Spring MVC's DispatcherServlet, which calls your controller. A filter can look at the request, change it, or answer it itself and stop it there. B1 covers the part after the filters.

Spring Security is one filter that runs a list of its own filters, in a fixed order. Your securityFilterChain bean builds that list: every .csrf(…), .sessionManagement(…), .oauth2ResourceServer(…) on http adds, removes or configures a filter.

lab2-complete · config/SecurityConfig.java · lines 84–90

.oauth2ResourceServer(oauth2 -> oauth2 .jwt(Customizer.withDefaults()) .authenticationEntryPoint(authenticationEntryPoint) .accessDeniedHandler(accessDeniedHandler) ); return http.build();

.oauth2ResourceServer(…).jwt(…) is the line that adds the token filter. http.build() turns the whole description into the list. A dozen filters end up in it; five decide what happens to your requests:

Signup — a password you can't read back

CoreBCrypt, and why not encryption

lab2-complete · service/AuthService.java · lines 32–56

public UserResponse signup(SignupRequest request) { String normalizedEmail = request.getEmail() .trim() .toLowerCase(Locale.ROOT); if (userRepository.existsByEmail(normalizedEmail)) { throw new ResponseStatusException( HttpStatus.CONFLICT, "Email is already registered" ); } User user = new User(); user.setEmail(normalizedEmail); user.setPasswordHash( passwordEncoder.encode(request.getPassword()) ); user.setFullName(request.getFullName().trim()); user.setRole(Role.STUDENT); User savedUser = userRepository.save(user); return toUserResponse(savedUser); }
34–36The email is trimmed and lowercased. Login (60–62) and loadUserByUsername do exactly the same, so Asha@Example.com and asha@example.com are one account, not two.
38–43Email taken → ResponseStatusException with 409. Read the warning below before you test it.
47–49The password is hashed before it's stored. Nothing ever stores or logs the original.
51Every account is a STUDENT. SignupRequest has no role field, so a "role": "ADMIN" in the JSON is simply ignored — Jackson skips fields it has nowhere to put.
55The response is a UserResponse, which has no password field and no hash. (Why a DTO: B2.)

The encoder is one bean:

lab2-complete · config/SecurityBeansConfig.java · lines 14–17

@Bean public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

Hashing, not encryption

Encryption can be undone by whoever has the key. If passwords were encrypted, the server — and anyone who stole its key along with the database — could read every one. A hash can't be undone at all. The only thing you can do with it is check a guess: hash the guess the same way and compare. That's all login needs.

BCrypt adds two things a plain hash like SHA-256 lacks. A salt: random bytes, new for every password, mixed in before hashing — so two people with the same password get different hashes, and a precomputed table of common passwords is useless. And a cost: BCrypt is slow on purpose, so an attacker with a stolen database can try far fewer guesses. Both are stored inside the 60-character result:

$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy 2a the BCrypt version 10 the cost: 2^10 rounds N9qo8uLOickgx2ZMRZoMye the salt (22 characters) IjZAgcfl7p92ldGxad68LJZdL17lhWy the hash (31 characters)

The table that holds it:

lab2-complete · entity/User.java · lines 22–43

@Column(nullable = false, unique = true, length = 255) private String email; @Column(name = "password_hash", nullable = false, length = 255) private String passwordHash; @Column(name = "full_name", nullable = false, length = 100) private String fullName; @Enumerated(EnumType.STRING) @Column(nullable = false, length = 20) private Role role; @Column(name = "created_at", nullable = false, updatable = false) private Instant createdAt; @PrePersist protected void onCreate() { if (createdAt == null) { createdAt = Instant.now(); } }
@Column(unique …)The database also refuses a second row with the same email — a backstop behind the existsByEmail check.
@Enumerated(STRING)The role column holds the text STUDENT or ADMIN, not a number. Without it JPA would store the enum's position (0, 1), and adding a role in the middle of Role would silently change everyone's. It's also why you can fix a role with plain SQL in section 11.
@PrePersistonCreate() runs just before Hibernate inserts the row, so created_at is filled in without AuthService having to remember it. updatable = false keeps it from ever changing.

Try it — look at the hashes

  1. Sign up two accounts with the same password.
  2. In MySQL: SELECT email, role, password_hash FROM users; Two different 60-character strings, both starting $2a$10$; the role is the word STUDENT.
  3. Sign up a third account — a new email — with "role": "ADMIN" added to the body. It's still STUDENT.

The 409 that arrives as a 401

Sign up the same email twice on your running app and you won't see 409. You'll see 401, Authentication is required…, with "path": "/error". The service did throw a 409 — but nothing in your @RestControllerAdvice handles ResponseStatusException, so Tomcat forwards the request to Spring Boot's /error page to write the body, and /error isn't on your permitAll() list. The request has no token, so the forward gets your 401. Section 16 has the two ways out.

Q1Two users both choose password123. A leaked dump of users shows both hashes. Can the attacker tell they're the same password?
Show answer

No. Each hash has its own salt, so the two strings share nothing but the $2a$10$ prefix. The attacker has to guess each one separately, slowly.

Q2Why can't your app have a "send me my password" button?
Show answer

It doesn't have the password, only a hash it can't reverse. The best it can offer is a reset: let the user set a new one.

Login — AuthenticationManager and UserDetailsService

Corethe BCrypt check you never wrote

lab2-complete · service/AuthService.java · lines 58–80

public AuthResponse login(LoginRequest request) { String normalizedEmail = request.getEmail() .trim() .toLowerCase(Locale.ROOT); Authentication authentication = authenticationManager.authenticate( new UsernamePasswordAuthenticationToken( normalizedEmail, request.getPassword() ) ); User user = userRepository.findByEmail( authentication.getName() ).orElseThrow(() -> new IllegalStateException( "Authenticated user was not found" ) ); String token = jwtService.generateToken(user);

Line 66's UsernamePasswordAuthenticationToken is not a JWT. It's Spring Security's object for "an unchecked login attempt: this name, this password". authenticate either returns a checked, authenticated version of it or throws.

Who checks the password

lab2-complete · config/SecurityBeansConfig.java · lines 19–25

@Bean public AuthenticationManager authenticationManager( AuthenticationConfiguration configuration) throws Exception { return configuration.getAuthenticationManager(); }

This bean doesn't build anything itself. It asks Spring Security for the manager it already prepared. And because your app has exactly one UserDetailsService bean and one PasswordEncoder bean, Spring prepared it with a DaoAuthenticationProvider wired to both. That provider does the work:

  1. calls your loadUserByUsername(email);
  2. calls passwordEncoder.matches(typedPassword, storedHash) — BCrypt re-hashes the typed password with the salt from the stored string and compares;
  3. returns an authenticated Authentication, or throws BadCredentialsException.

lab2-complete · service/CustomUserDetailsService.java · lines 20–38

@Override public UserDetails loadUserByUsername(String email) throws UsernameNotFoundException { String normalizedEmail = email.trim().toLowerCase(Locale.ROOT); User user = userRepository.findByEmail(normalizedEmail) .orElseThrow(() -> new UsernameNotFoundException( "Invalid email or password" ) ); return org.springframework.security.core.userdetails.User .withUsername(user.getEmail()) .password(user.getPasswordHash()) .roles(user.getRole().name()) .build(); }

Your job in this class is only to translate: from your User entity to Spring's UserDetails — a username, the stored hash, and authorities. .roles("STUDENT") becomes the authority ROLE_STUDENT: Spring adds the ROLE_ prefix. Lines 33–37 use the full name org.springframework.security.core.userdetails.User because your own User entity is imported on line 4.

The same 401 for both mistakes

An unknown email makes line 28 throw UsernameNotFoundException. The provider doesn't let that through: it turns it into the same BadCredentialsException as a wrong password, and it still runs one BCrypt check on a dummy hash, so a missing account isn't even faster to reject. Both exceptions are thrown inside your controller, so they reach your MVC exception handler — not the security filters:

lab2-complete · exception/GlobalExceptionHandler.java · lines 79–93

@ExceptionHandler(AuthenticationException.class) public ResponseEntity<ApiErrorResponse> handleAuthenticationFailure( AuthenticationException exception, HttpServletRequest request) { ApiErrorResponse response = ApiErrorResponse.builder() .timestamp(Instant.now()) .status(HttpStatus.UNAUTHORIZED.value()) .error(HttpStatus.UNAUTHORIZED.getReasonPhrase()) .message("Invalid email or password") .path(request.getRequestURI()) .build(); return ResponseEntity.status(HttpStatus.UNAUTHORIZED).body(response); }

Nobody can use your login to find out which emails have accounts.

What login keeps — nothing

The authenticated Authentication on line 64 holds ROLE_STUDENT. Your code uses it for one thing — authentication.getName() on line 73 — and then drops it. Nothing about this login is remembered on the server. Only the token goes back. Hold on to that for section 11.

Try it — two wrong logins

Log in with a wrong password, then with an email that has no account. Compare the two response bodies: identical, apart from the timestamp.

Q1Where in your code is the line that compares the typed password with the hash?
Show answer

Nowhere. DaoAuthenticationProvider calls passwordEncoder.matches. You supplied the two beans it needs — CustomUserDetailsService and BCryptPasswordEncoder — and Spring connected them.

Q2Why does a wrong password come back from GlobalExceptionHandler, while a missing token comes back from RestSecurityErrorHandler?
Show answer

Where the exception happens. authenticate() runs inside your controller, after the filters, so its exception goes to the MVC exception handlers. A missing token is found by the filters, before any controller — so the security handlers answer it (section 12).

Issuing the token — JwtService and JwtEncoder

Coreclaims in, a signed string out

lab2-complete · service/JwtService.java · lines 21–50

private final JwtEncoder jwtEncoder; @Value("${app.security.jwt.issuer}") private String issuer; @Value("${app.security.jwt.expiration-seconds}") private long expirationSeconds; public String generateToken(User user) { Instant issuedAt = Instant.now(); Instant expiresAt = issuedAt.plusSeconds(expirationSeconds); JwtClaimsSet claims = JwtClaimsSet.builder() .issuer(issuer) .subject(user.getEmail()) .issuedAt(issuedAt) .expiresAt(expiresAt) .id(UUID.randomUUID().toString()) .claim("role", user.getRole().name()) .build(); JwsHeader header = JwsHeader .with(MacAlgorithm.HS256) .build(); return jwtEncoder.encode( JwtEncoderParameters.from(header, claims) ).getTokenValue(); }

A token's contents are claims: short named facts. JwtService writes six:

ClaimLineValueWhat it's for
iss35ecommerce-apiissuer — who made it. The decoder insists on this exact value.
sub36the emailsubject — who it's about. Becomes authentication.getName().
iat37nowissued at.
exp38now + 3600 sexpires — after this the decoder refuses it.
jti39a random UUIDJWT id — this one token's name. Logout needs it (section 14).
role40STUDENT / ADMINYour own claim, not a standard one. Section 11 is about who reads it.

One standard claim is missing: aud, the audience — which app the token is meant for. Section 09 explains why that matters. Lines 43–45 set the header: HS256, HMAC with SHA-256. With HS256 one shared secret both signs and checks a token. That suits a token that only your own app ever makes and checks.

The values come from properties

lab2-complete · application.properties · lines 9–11

app.security.jwt.issuer=ecommerce-api app.security.jwt.expiration-seconds=3600 app.security.jwt.secret=${JWT_SECRET:dev-only-change-this-secret-key-before-deployment-123}

@Value("${app.security.jwt.issuer}") (JwtService 23) tells Spring: fill this field from the property with that name, and refuse to start if there's no such property. Spring converts the text to the field's type, so expiration-seconds arrives as a long. These keys are your own invention — Spring has no idea what app.security.jwt means, it just copies the text.

Line 11 nests one placeholder inside another: ${JWT_SECRET:dev-only-…} means "use the environment variable JWT_SECRET if it is set; otherwise this text after the colon". Your laptop gets the default; a real server sets JWT_SECRET and never has the secret in a file anyone can read.

The key and the encoder

lab2-complete · config/JwtConfig.java · lines 23–41

@Bean public SecretKey jwtSecretKey( @Value("${app.security.jwt.secret}") String secret) { byte[] keyBytes = secret.getBytes(StandardCharsets.UTF_8); if (keyBytes.length < 32) { throw new IllegalStateException( "JWT secret must contain at least 32 bytes"); } return new SecretKeySpec(keyBytes, "HmacSHA256"); } @Bean public JwtEncoder jwtEncoder(SecretKey jwtSecretKey) { return new NimbusJwtEncoder( new ImmutableSecret<>(jwtSecretKey)); }
29–32HS256 needs a key of at least 256 bits — 32 bytes. Too short, and this line stops the app at startup with a clear message, instead of failing at the first login.
34The secret's bytes, wrapped as a Java SecretKey for HMAC-SHA256.
39–40NimbusJwtEncoder is Spring's encoder, built on the Nimbus JOSE library. ImmutableSecret hands it your key as its one and only signing key.

The secret is the whole game

Anyone who knows your secret can make a token for any email with any role, and your app will believe it. The default on line 11 is labelled dev-only for that reason: everyone who cloned ESD_Session has the same one. Never commit a real secret.

Try it — a key that's too short

Change line 11 to app.security.jwt.secret=short and restart. Read the stack trace down to the last Caused by: JWT secret must contain at least 32 bytes. Put the line back.

Q1You change the secret and restart. What happens to every token handed out before the change?
Show answer

All of them fail the signature check — 401 — because the decoder now checks with a different key. Everyone has to log in again. Changing the secret is the bluntest possible "log everyone out".

Coreheader.payload.signature

This is a real token, made exactly the way your JwtService makes them, signed with the default secret from your application.properties:

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhc2hhQGV4YW1wbGUuY29tIiwicm9sZSI6IlNUVURFTlQiLCJpc3MiOiJlY29tbWVyY2UtYXBpIiwiZXhwIjoxNzY4NDczMDAwLCJpYXQiOjE3Njg0Njk0MDAsImp0aSI6IjNmOWMyYTcxLTVkNGUtNGI4YS05ZTYxLTBjN2QyYjhmNGExNSJ9.kzgBTWdlBuyEKzuW30Ch6qHR8Ke72qR_dBAU6ja12-A

Three pieces joined by dots: header.payload.signature. The first two are JSON, written in base64url — ordinary base64 with - and _ instead of + and /, and no = padding, so it's safe in a URL or a header. base64url is an encoding, not encryption: anyone can turn it back. Every token your app makes begins eyJhbGciOiJIUzI1NiJ9, because every one has the same header.

Try it — decode it in the browser console

What the signature proves — and what it doesn't

The signature is HMAC-SHA256 of the text header.payload, computed with your secret. To check it, the decoder computes it again and compares. So a matching signature proves two things:

  1. whoever made this token knew the secret — your app, or someone who stole the secret;
  2. not one character of the header or payload has changed since.

It proves nothing else. It doesn't hide anything — you just read the payload without any key, and so can anyone who sees the token. It doesn't say who is sending it (section 02's friend). And it doesn't say the token is still good: expiry and logout are separate checks, in section 09.

Try it — forge a token, and watch it fail

  1. Paste your own STUDENT token in the box above and press Swap STUDENT ↔ ADMIN. The payload now says ADMIN; the signature is the old one. Press Check: it no longer matches.
  2. Copy the edited token into Postman and call GET /api/auth/me with it. 401. Your server did the same check as the button.

Check a signature with nothing but the console

The box above does this. In the same console as before, after the decode lines:

const bytes = (s) => new TextEncoder().encode(s); const secret = "dev-only-change-this-secret-key-before-deployment-123"; // application.properties line 11 const key = await crypto.subtle.importKey("raw", bytes(secret), { name: "HMAC", hash: "SHA-256" }, false, ["sign"]); const mac = new Uint8Array(await crypto.subtle.sign("HMAC", key, bytes(header + "." + payload))); const b64url = (b) => btoa(String.fromCharCode(...b)).replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, ""); b64url(mac) === signature // true

BearerTokenAuthenticationFilter finds this bean by type — you never call decode yourself. For every token it does two stages:

A NimbusJwtDecoder checks expiry by default. Line 54 throws that default away and installs exactly the list you give it. That's why line 56 passes Spring's standard set back in: write new DelegatingOAuth2TokenValidator<>(jwtRevocationValidator) alone, and expired tokens would be accepted.

Why audience matters

What hasRole("ADMIN") actually asks

An authority is a plain string an Authentication carries, like ROLE_ADMIN. A role is just an authority whose name starts with ROLE_. hasRole("ADMIN") means "is the string ROLE_ADMIN among this request's authorities?" — Spring adds the prefix, which is why hasRole("ROLE_ADMIN") stops the app at startup.

Where a token request gets its authorities

Not from the database, and not from CustomUserDetailsService — that ran once, at login, and its result was dropped (section 06). On every request the authorities come from the token, through a JwtAuthenticationConverter. Line 85, .jwt(Customizer.withDefaults()), configures no converter, and your project defines none, so Spring uses its default. The default follows OAuth2's convention: it reads a claim called scope (or scp), splits it on spaces, and prefixes each word with SCOPE_. A token with "scope": "products:write" would give the authority SCOPE_products:write.

Your token has no scope claim. It has role, and nothing reads role:

PieceWhat it does
JwtService line 40writes "role": "ADMIN"
the default converterreads only scope / scp, makes SCOPE_…
the authorities you getFACTOR_BEARER — Spring Security 7's note that you signed in with a bearer token — and nothing else
hasRole("ADMIN") wantsROLE_ADMIN
result403 for every write — STUDENT and ADMIN alike

As your scaffold stands, no token it can issue passes lines 63–78. If you never tested a write as an ADMIN, you'd never have noticed: the STUDENT's 403 looks exactly right.

Try it — see the 403, then see why

  1. Make yourself an ADMIN in MySQL — signup never will: UPDATE users SET role = 'ADMIN' WHERE email = 'you@example.com';
  2. Log in again (your old token still says STUDENT). Paste the new token in section 08's box: "role": "ADMIN".
  3. POST /api/products/add-product with it and a valid product body. 403.
  4. Ask Spring what it sees. In AuthController.getCurrentUser, add as the first line:
    authentication.getAuthorities().forEach(a -> System.out.println(a.getAuthority()));

The one bean that connects them

Tell the converter which claim holds the roles, and which prefix to give them. A new file next to your other config classes:

package com.esd.ecommerce.config; import org.springframework.context.annotation.Bean; import org.springframework.context.annotation.Configuration; import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationConverter; import org.springframework.security.oauth2.server.resource.authentication.JwtGrantedAuthoritiesConverter; @Configuration public class RoleClaimConfig { @Bean public JwtAuthenticationConverter jwtAuthenticationConverter() { JwtGrantedAuthoritiesConverter roles = new JwtGrantedAuthoritiesConverter(); roles.setAuthoritiesClaimName("role"); // the claim JwtService writes roles.setAuthorityPrefix("ROLE_"); // "ADMIN" -> "ROLE_ADMIN", what hasRole("ADMIN") wants JwtAuthenticationConverter converter = new JwtAuthenticationConverter(); converter.setJwtGrantedAuthoritiesConverter(roles); return converter; } }

You don't touch SecurityConfig. When the resource server sets itself up, it looks for a JwtAuthenticationConverter bean and uses it in place of its default. Restart, log in as your ADMIN, and the same POST is a 201. Your println now prints ROLE_ADMIN as well as FACTOR_BEARER. A STUDENT still gets 403.

The token wins until it expires

With the converter in place, the role comes from the token, not the database. Demote someone in MySQL and their existing token keeps working as ADMIN until its exp — up to an hour. A role change really takes effect at the next login (or after logout, section 14).

Spring can also write the same rule on a method, as @PreAuthorize("hasRole('ADMIN')"); your scaffold keeps every rule in SecurityConfig, which is easier to audit in one place.

Corerevoked_tokens and JwtRevocationValidator

Section 02's table said logout is hard. Here's why: your server keeps nothing about a login, so there is nothing to delete. A token stays valid until its exp, wherever a copy of it is. Deleting it in the browser is not logging out — a copy in Postman, a log file or a friend's laptop still works.

Your scaffold's answer is a denylist: remember the tokens that have been logged out, and refuse them. Logout itself is section 13's second method — revokeToken(jwt.getId(), jwt.getExpiresAt()). How to know you're ready

You understand your Lab 2 security if you can do all of these without looking anything up:

  1. Say what 401 and 403 each mean, and predict which one a given request gets.
  2. Explain why your server keeps no session, and why that makes CSRF protection unnecessary here.
  3. Name the five filters that matter, in order, and say which one answers a bad token.
