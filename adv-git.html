01

What's actually inside .git

demystify it first

Everything in this document becomes easy once you've looked inside the folder. Git is a much simpler system than its interface suggests, and five minutes of poking around removes most of the fear.

Do this now — make a scratch repo and open the box

$ mkdir -p ~/code/git-lab && cd ~/code/git-lab $ git init $ echo "hello" > a.txt $ git add . && git commit -m "First commit" $ ls .git HEAD config description hooks/ index info/ logs/ objects/ refs/
objects/Every version of every file, every directory listing, and every commit you have ever made. This is the actual database.
refs/Branches and tags. Each one is a tiny text file containing a commit hash.
HEADA one-line file saying which branch you're currently on.
indexThe staging area. A binary file listing what's queued for the next commit.
configSettings for this repository — remotes, branch tracking, local overrides.
logs/The reflog: a record of everywhere HEAD has been. Section 09 is entirely about why this saves you.
hooks/Scripts that run at certain moments — before commit, after merge. Sample files only until you enable them.

Four kinds of object, and that's all

blobThe contents of one file. Just bytes — no filename, no permissions.
treeA directory listing: names, permissions, and pointers to blobs and other trees.
commitA pointer to one tree (the whole project at that moment), plus author, message, and pointers to its parent commit(s).
tagAn annotated pointer to a commit, with its own message. Used for releases.

Every object is stored under the SHA-1 hash of its own contents. That's what "content-addressed" means, and it has a neat consequence: two identical files anywhere in your history are stored exactly once. Same content, same hash, same object.

Do this now — read your own commit

$ git log --oneline 3f9a1c4 First commit $ git cat-file -p 3f9a1c4 tree 2b8f0d1a9c... author Shreyas <you@example.com> 1755300000 +0530 committer Shreyas <you@example.com> 1755300000 +0530 First commit $ git cat-file -p 2b8f0d1a9c # the tree it points to 100644 blob e965047ad7... a.txt $ git cat-file -p e965047ad7 # the blob hello

That's the whole storage model. A commit points at a tree, a tree points at blobs and other trees, and every pointer is a hash. Follow them down and you arrive at your text.

Why a commit hash can't be faked

A commit's hash is computed from its content — including its parent's hash. Change anything about an old commit and its hash changes, which changes its child's hash, and so on all the way to the tip.

That's why history rewriting always produces new hashes (section 05), and it's the same idea a blockchain uses. Git got there first, in 2005.

Snapshots, not diffs

Git stores a complete snapshot of the project at each commit, not a list of changes. Unchanged files are simply pointed at again rather than re-stored, so it costs far less than it sounds — and periodically Git compresses loose objects into packfiles, which do use delta compression internally.

The diffs you see in git log -p are computed on demand by comparing two snapshots. They aren't stored.

Q1You commit a 5 MB image, then in the next commit delete it. How much space does the repository use?
Show answer

Still around 5 MB, forever. The blob remains in objects/ because the first commit still references it, and that commit is still in your history.

This is why large files in Git are a genuine problem, why .gitignore matters, and why removing a committed secret requires rewriting history rather than just deleting the file.

02

Branches and HEAD are pointers

41 bytes each

Most people carry the mental model "a branch is a copy of my project". It's wrong, and it's why merging feels dangerous.

The accurate version

A branch is a pointer to one commit. A file containing a 40-character hash and a newline. That's the entire implementation.

Do this now — look at one

$ cat .git/refs/heads/main 3f9a1c4b8d2e05f7a91c3e6b27d4f80a1c5e2b93 $ cat .git/HEAD ref: refs/heads/main $ git switch -c feature $ cat .git/HEAD ref: refs/heads/feature $ ls .git/refs/heads feature main

Creating a branch wrote 41 bytes and changed one line in HEAD. Nothing was copied. This is why teams create and delete branches dozens of times a week without thinking about it.

HEAD"Where I am now." Normally contains ref: refs/heads/<branch> — a pointer to a pointer.
CommittingWrites a new commit object, then rewrites the current branch file to point at it. The branch moves; you don't.
SwitchingChanges HEAD, then makes your working directory match that commit's tree.

Detached HEAD

Check out a commit hash directly rather than a branch and HEAD holds a raw hash instead of a branch reference. Git calls this detached HEAD and warns you loudly.

$ git switch --detach 3f9a1c4 $ cat .git/HEAD 3f9a1c4b8d2e05f7a91c3e6b27d4f80a1c5e2b93 # no "ref:" — that's detached $ git switch - # back to where you were

It isn't broken and it isn't dangerous to be in. It's useful for looking at an old state. The risk is that any commits you make while detached belong to no branch — switch away and there's nothing pointing at them, so they eventually get garbage-collected. If you did work there, give it a branch before you leave: git switch -c rescue.

switch and restore, not checkout

git checkout historically did two unrelated jobs — moving between branches and throwing away file changes — which is why it confused everyone. Modern Git split them: git switch for branches, git restore for files. Use those. checkout still works and you'll see it everywhere in older documentation.

Q2You're on main and run git switch -c feature, then make three commits. Where is main pointing now?
Show answer

Exactly where it was. Committing moves the branch you're on. main hasn't moved, so it still points at the commit you branched from.

That gap between the two pointers is your feature's work — and it's precisely what determines whether the merge later will be a fast-forward.

03

Fast-forward vs merge commit

the one interviewers ask

You branch off, make commits, and merge back. What happens depends entirely on one question: did the base branch move while you were working?

Fast-forwardYour branch already contains every commit on the base. Merging is just moving a pointer forward. No merge commit, and conflicts are impossible.
Three-way mergeBoth sides have new commits. Git compares each against the common ancestor and writes a merge commit with two parents. This is the only situation where conflicts can happen.
$ git merge feature # fast-forward if possible, else merge commit $ git merge --ff-only feature # refuse rather than create a merge commit $ git merge --no-ff feature # always create one, even when avoidable

--no-ff looks pointless but has a real use: it keeps a visible record that a group of commits belonged to one feature, which some teams want in their history.

Where accidental merge commits come from

You have unpushed local commits, the remote has moved, and you run git pull. Git silently merges and creates a commit called "Merge branch 'main' of github.com…". Six of those in a pull request and your reviewer cannot read the diff.

Set this once and the problem disappears permanently:

$ git config --global pull.rebase true
04

Merge conflicts, properly

not as scary as advertised

A conflict happens when the same lines of the same file changed on both sides. That's the whole trigger. Two people editing different files, or different parts of one file, merge silently and automatically.

Do this now — cause one on purpose

$ git switch main $ echo "version one" > conflict.txt $ git add . && git commit -m "Add conflict file" $ git switch -c other $ echo "version two" > conflict.txt $ git commit -am "Change to version two" $ git switch main $ echo "version three" > conflict.txt $ git commit -am "Change to version three" $ git merge other CONFLICT (content): Merge conflict in conflict.txt Automatic merge failed; fix conflicts and then commit the result.

Open the file:

<<<<<<< HEAD version three ======= version two >>>>>>> other
<<<<<<< HEADStart of your version — the branch you're currently on.
=======The divider. Not part of either version.
>>>>>>> otherEnd of the incoming version, labelled with where it came from.

Resolving is just editing

There's no special mode and no magic. Edit the file until it says what you want, delete all three marker lines, save. You can keep one side, keep both, or write something new — Git doesn't care, it just wants the markers gone.

$ git status # lists "both modified" files ... edit the file, remove all markers ... $ git add conflict.txt # "add" here means "I've resolved this" $ git commit # completes the merge
git merge --abortCancels the whole thing and puts you back exactly as you were. Your escape hatch — use it freely.
git diffDuring a conflict, shows a combined diff of the conflicting regions.
git checkout --ours fileTake your side wholesale for that file.
git checkout --theirs fileTake the incoming side wholesale.
git merge --continueSame as committing, once everything is resolved.

"ours" and "theirs" flip during a rebase

In a merge, ours is your branch. In a rebase, Git is replaying your commits onto the other branch, so ours becomes the branch you're rebasing onto and theirs is your own work. This reversal catches almost everybody once.

When in doubt, don't use those flags — read the markers and edit by hand.

VS Code makes this much nicer

Open a conflicted file in VS Code and you get "Accept Current / Accept Incoming / Accept Both / Compare" buttons above each conflict, plus a three-way merge editor. It's editing the same markers, just with a decent interface. Use it — there's no purity points for doing it in vim.

How to have fewer conflicts

Conflicts scale with how long a branch lives and how much it overlaps with others. Short-lived branches merged within a day or two rarely conflict. A branch that sat for three weeks while five people worked on the same files will be painful, and no tool fixes that — it's a process problem, not a Git problem.

05

Rebase

rewriting, not moving

Merge joins two histories. Rebase replays yours on top of a new base, as though you had started from there all along.

$ git switch feature $ git fetch origin $ git rebase origin/main

Git sets your commits aside, moves your branch pointer to origin/main, then replays each of your commits on top, one at a time. If a replay hits a conflict it pauses, you resolve it exactly as in section 04, and continue.

git rebase --continueAfter resolving a conflict, carry on with the next commit.
git rebase --skipDrop the commit currently being replayed. Occasionally what you want when a change is already upstream.
git rebase --abortPut everything back exactly as it was before you started. This is why rebasing is far less frightening than its reputation.

The critical detail

Replayed commits are new commits with new hashes. Same changes, same messages, different identity — because a commit's hash includes its parent's hash, and the parent changed.

The originals still exist in the object database for a while, reachable through the reflog, but they are no longer on your branch. This is history rewriting, and it's the reason for the rule below.

The golden rule

Memorise this sentence

Never rebase commits that other people have based work on. Rebase your own branch, before or during review. Never rebase main. Never rebase a branch someone else has pulled.

The reason is mechanical rather than stylistic. If a colleague has your old commits and you replace them with new hashes, their next pull tries to reconcile two versions of the same work. They get duplicated commits or conflicts they cannot explain, and the fix involves you both on a call.

Merge or rebase — the actual answer

Rebase your feature branchTo pick up the latest main before review. Keeps your pull request diff clean and small, showing only your work.
Merge into mainVia the pull request button, using whatever strategy your team has chosen. Not your decision to make unilaterally.
git pull --rebaseYour everyday pull. Set pull.rebase true globally and stop thinking about it.

Why teams argue about this

Merge-always keeps a perfectly truthful record of what happened, including the messy parts. Rebase-always produces a clean linear history that's far easier to read and to bisect, at the cost of being a tidied-up story rather than a literal one.

Both positions are defensible. What matters is that your team picks one and everyone follows it — mixed strategies produce the worst of both.

06

Interactive rebase & force-pushing

the weekly tool

This is the one you'll actually reach for most often — cleaning up your own commits before anyone reviews them.

$ git rebase -i origin/main # or, to rework just the last five commits: $ git rebase -i HEAD~5

An editor opens with one line per commit, oldest at the top. Change the first word on any line:

pickKeep it as-is. The default for every line.
rewordKeep the change, edit the message.
squashFold into the commit above, and let you combine both messages.
fixupFold into the commit above and discard this message entirely. What you want for "fix typo" commits.
editPause at this commit so you can change the actual files, then git rebase --continue.
dropRemove the commit completely.
reorderNo keyword — just move the lines. They get replayed in the new order.

Do this now — turn four commits into two

$ git switch -c cleanup $ echo 1 > f.txt && git add . && git commit -m "Add feature" $ echo 2 >> f.txt && git commit -am "wip" $ echo 3 >> f.txt && git commit -am "fix typo" $ echo 4 >> f.txt && git commit -am "actually fix it" $ git rebase -i HEAD~4 # change the last three lines from "pick" to "fixup", save, close $ git log --oneline a1b2c3d Add feature # one clean commit

The autosquash workflow

Once you're comfortable, this is faster than editing the list by hand. When you spot a mistake in an earlier commit:

$ git add . $ git commit --fixup a1b2c3d # target the commit it belongs to $ git rebase -i --autosquash HEAD~5 # lines pre-arranged for you

Set git config --global rebase.autosquash true and the flag becomes automatic.

Force-pushing, safely

After any rewrite, your branch has diverged from its copy on the remote, so a normal push is rejected. You have to overwrite it:

$ git push --force-with-lease

Never plain --force

--force overwrites the remote branch no matter what happened there — including a colleague's commits pushed five minutes ago, which are then gone from the branch.

--force-with-lease first checks the remote is still where you last saw it, and refuses if anyone pushed in the meantime. Same command, one word longer, and it is the difference between a normal Tuesday and an apology in the team channel.

Make it the default: git config --global alias.pushf "push --force-with-lease"

Is force-pushing to a PR branch rude?

No — it's normal and expected on a branch that only you work on. GitHub handles it: the pull request updates, and it can still show reviewers what changed between force-pushes.

What's rude is force-pushing to a shared branch, or rewriting after a reviewer has already commented, which can orphan their comments.

07

Stash

a shelf for half-finished work

You're midway through something and need to switch branches urgently. Git won't let you switch with uncommitted changes that would be overwritten. Stash puts them on a shelf.

$ git stash push -m "half-done login form" $ git switch main # clean working directory, free to move ... deal with the urgent thing ... $ git switch feature $ git stash pop # changes come back, stash entry removed
git stash listShow everything on the shelf. Entries are stash@{0}, stash@{1} — newest first.
git stash popApply the newest and delete it from the list.
git stash applyApply but keep it in the list. Safer when you're unsure — you can retry.
git stash push -uInclude untracked files. Without -u new files are left behind, which surprises people constantly.
git stash show -pSee what's actually in a stash before applying it.
git stash dropDelete an entry. git stash clear deletes all of them.
git stash branch new-nameCreate a branch from the commit the stash was made on and apply it there. The clean fix when a stash won't apply.

The stash is where work goes to be forgotten

Stashes have no branch, no message unless you wrote one, and don't show up in any normal command. A stash from three weeks ago is functionally lost — nobody ever scrolls git stash list.

Prefer a scratch commit. git commit -m "wip: half-done login" on your branch is visible, pushable, survives, and can be squashed away later with an interactive rebase. Use stash for the next ten minutes, not the next ten days.

And it becomes actively dangerous with worktrees

Remember this for section 16: the stash is shared across all worktrees of a repository. Stash in one, and you can pop it in another — including by accident. This is one of the strongest practical arguments for the scratch-commit habit.

08

Cherry-pick

one commit, somewhere else

Take a single commit from anywhere in the repository and apply it to your current branch.

$ git switch release-1.2 $ git cherry-pick a1b2c3d # apply that one commit here $ git cherry-pick a1b2c3d^..e4f5g6h # or a range $ git cherry-pick -x a1b2c3d # record where it came from in the message

Like rebase, it creates a new commit with a new hash — same changes, different identity, different parent.

When it's the right tool

Hotfix to a release branchThe classic case. A bug is fixed on main, and the same fix needs to go onto release-1.2 without dragging everything else on main with it.
Rescuing one commitYou built something useful on a branch that's being abandoned. Cherry-pick the good commit out before deleting.
Wrong branchYou committed to main by accident. Cherry-pick it onto a proper branch, then reset main back.

Use -x on release branches

It appends "(cherry picked from commit a1b2c3d)" to the message. Six months later, when someone is working out whether a fix made it into version 1.2, that one line answers the question immediately.

Don't make it a habit

Cherry-picking duplicates work. The same change now exists as two commits with different hashes, and when those branches eventually merge, Git may or may not notice they're the same — often producing a conflict where the change appears twice.

If you find yourself cherry-picking regularly between the same two branches, your branching strategy is wrong. That's a signal, not a workflow.

Q3You cherry-pick a commit from feature onto main. Later you merge feature into main. What happens?
Show answer

Usually it merges cleanly — Git's three-way merge sees that the content already matches and there's nothing to apply. But if the surrounding lines have drifted at all, you get a conflict where the same change looks like it's being added twice.

Which is the point of the warning above: cherry-picking creates duplicate history, and duplicate history has to be reconciled eventually.

09

Reflog — nothing is really lost

the section that saves your job

Git records every movement of HEAD in a local log — every commit, checkout, merge, rebase and reset. Even when a commit is no longer reachable from any branch, it's still in the object database, and the reflog remembers where it was.

$ git reflog a1b2c3d HEAD@{0}: rebase (finish): returning to refs/heads/feature 9f8e7d6 HEAD@{1}: rebase (pick): Add validation 3c4d5e6 HEAD@{2}: checkout: moving from main to feature 7a8b9c0 HEAD@{3}: commit: Add login form 2d3e4f5 HEAD@{4}: reset: moving to HEAD~3

Do this now — destroy some work and get it back

$ git switch -c doomed $ echo "important" > important.txt $ git add . && git commit -m "Very important work" $ git switch main $ git branch -D doomed # deleted, no confirmation $ git reflog # find the commit hash $ git switch -c doomed <that-hash> # and it's back, intact

The three recoveries worth knowing

Deleted a branchFind its last commit in the reflog, then git switch -c <name> <hash>.
Bad git reset --hardgit reset --hard HEAD@{1} puts you back where you were before the reset.
Rebase went wrong and you already finishedThe reflog shows the state before the rebase started. Reset to it.

The limits, stated honestly

The reflog is local only — it isn't pushed or cloned, so it can't help on a different machine. Entries expire (90 days by default for reachable commits, 30 for unreachable), and git gc eventually deletes truly orphaned objects.

And it only covers things that were committed at some point. Uncommitted changes destroyed by git restore or git checkout . are genuinely gone. That's the real argument for committing often — a commit makes work recoverable.

Remember this exists

When you have visibly broken something and your stomach drops, the answer is almost always git reflog. Most "I lost a day's work" stories are actually "I didn't know about the reflog" stories.

10

Remotes, fetch vs pull

what origin/main really is

A remote is a named URL pointing at another copy of the repository. origin is just the conventional name for the one you cloned from.

$ git remote -v $ git remote add upstream https://github.com/original/repo.git $ git remote rename origin fork

The thing most people get wrong

origin/main is a local pointer

origin/main is not on GitHub. It's a file on your disk at .git/refs/remotes/origin/main, recording where GitHub's main was the last time you talked to it.

It can be hours out of date. It only updates when you fetch.

git fetchDownload new commits and update your origin/* pointers. Changes nothing about your branches or files. Completely safe, always.
git pullfetch followed by merge (or rebase). Changes your branch and your files.
git fetch --pruneAlso delete local origin/* pointers for branches that no longer exist on the remote. Worth running weekly, or set fetch.prune true.

Do this now — build the habit

Rather than pulling blindly, look before you leap:

$ git fetch $ git log --oneline HEAD..origin/main # what they have that I don't $ git log --oneline origin/main..HEAD # what I have that they don't $ git diff origin/main # the actual changes $ git rebase origin/main # now decide

Once that's second nature, you'll never again be surprised by what a pull did to your branch.

Tracking branches

A local branch can be linked to a remote one, which is what lets you type bare git push and git pull.

$ git push -u origin feature # -u sets the link, first push only $ git branch -vv # show every branch and what it tracks

-u is short for --set-upstream. Forget it and Git tells you exactly what to type, so this is a self-correcting mistake.

11

Forks and pull requests

how code actually gets in
ForkA complete copy of someone else's repository under your own account. A GitHub concept, not a Git one — to Git it's just another remote.
Pull request"Here is what I changed in my copy — please pull it into yours." A request, not a command. Also a GitHub concept; GitLab calls it a merge request.

Two models, and when each is used

Branch in the same repoWhat most companies do internally. You have write access, you push a branch, you open a PR from it. Simpler.
Fork and PRWhat open source does, and what you'll do at any company where you don't have write access to a repository. You cannot push to theirs, so you push to your fork and ask.
# the fork workflow, in full $ gh repo fork owner/project --clone $ cd project $ git remote -v origin https://github.com/you/project.git (your fork) upstream https://github.com/owner/project.git (the original) $ git switch -c fix/typo-in-readme ... make changes, commit ... $ git push -u origin fix/typo-in-readme $ gh pr create --fill

Keeping a fork current is the part people miss. Your fork does not update itself:

$ git fetch upstream $ git switch main $ git merge upstream/main # or rebase $ git push origin main

GitHub also has a Sync fork button on the web interface that does exactly this in one click.

What makes a pull request good

SmallThe single biggest factor in review quality. A 100-line PR gets real scrutiny; a 2,000-line PR gets "LGTM" and a rubber stamp. If it's big, split it.
One concernDon't fix a bug and reformat the file and rename a variable in one PR. The reviewer can't separate the signal from the noise.
A description that explains whyThe diff shows what. Only you can supply why, what you considered and rejected, and what you're unsure about.
Self-reviewed firstRead your own diff on GitHub before requesting review. You will find something — a leftover console log, a debug flag — every time.
Draft while in progressOpen it as a draft PR early. It's visible, CI runs on it, nobody is asked to review it yet.

Review etiquette, from both sides

As the author: respond to every comment, even just with a thumbs-up or "done". Push a fix rather than arguing in the thread — and if you disagree, say so with a reason. Nobody minds disagreement; silence is what annoys people.

As the reviewer: distinguish blocking issues from suggestions. Prefix optional ones — "nit:" is the near-universal convention. Approve with minor comments rather than blocking on style; a review that sits for two days costs the team more than an imperfect variable name.

The contribution graph detail

Commits sitting on a fork don't count toward your GitHub contribution graph. Opening a PR does, and once it's merged, the commits land in the upstream repository authored by you and count too. Worth knowing if you're building a public profile before placements.

12

The three merge buttons

you'll be asked to pick one

When a PR is approved, GitHub offers three ways to land it. Teams have strong opinions and house rules. Know what each does to history.

Create a merge commitKeeps every one of your commits plus a merge commit joining the lines. Complete history including "wip" and "fix typo". Truthful, noisy.
Squash and mergeCollapses the entire branch into one commit on main. Clean linear history, intermediate steps discarded.
Rebase and mergeReplays your commits onto main individually, no merge commit. Linear and every commit preserved — but only sane if each commit independently builds and passes tests.

Squash is the most common default

Because it makes one PR equal one commit on main, which makes git revert and git bisect trivial. Broke production? Revert one commit, the whole feature is gone.

If you can't say which strategy your team uses, ask in your first week. It changes how you should structure your commits: under squash, your intermediate commits are getting collapsed so don't agonise over them. Under rebase-and-merge, every commit is going on main and must stand alone.

The trap after a squash merge

Squashing creates a brand-new commit on main that your local branch has never seen, while your branch still holds the originals. Pulling now produces a confusing pseudo-conflict — the same changes appear to be arriving twice with different hashes.

The fix is simple and non-obvious: after a squash merge, delete the branch and start the next one fresh from main. Don't try to reuse it. Most teams enable "automatically delete head branches" in repository settings for exactly this reason.

13

Bare repositories

what GitHub physically is

From here on is the core of this document. It starts with a decomposition: a normal repository is exactly two things bolted together.

myproject/ ├── .git/ ← THE REPOSITORY: objects, refs, HEAD, config, index └── src/ ... ← THE WORKING TREE: the files you actually edit

A bare repository is the first half without the second. The contents of .git, promoted to be the directory itself, with core.bare = true in its config. Conventionally named with a .git suffix.

project.git/ ├── objects/ ← every blob, tree, commit, tag ├── refs/ ├── HEAD └── config ← bare = true

Do this now — make one and see

$ cd ~/code $ git init --bare demo.git $ ls demo.git HEAD config description hooks/ info/ objects/ refs/ $ cat demo.git/config | grep bare bare = true

No files to edit. No git status. Nothing to check out. It is a database and nothing else.

Why they exist — one constraint explains everything

The rule

If you push to a branch that is currently checked out somewhere, that working tree would instantly disagree with HEAD — files on disk showing one thing, Git believing another. Git refuses, with an error mentioning receive.denyCurrentBranch.

A bare repository has no working tree, so there is nothing to desync. Every push target is bare.

Which answers a question you may never have thought to ask: what is GitHub, physically? A warehouse of bare repositories, plus a web interface, plus permissions and review tooling on top. When you git push, you are writing objects into a bare repo on their servers.

bare vs mirror

git clone --bare copies branches and tags. git clone --mirror copies all refs including remote-tracking ones, and configures the refspec so git remote update keeps it in lockstep.

Use mirror for migrating a repository between hosts or making a true backup. Use bare for everything else — including the worktree layout in section 15.

Q4Why can't you just push to a colleague's normal working repository over the network?
Show answer

Because their working directory has a branch checked out. If your push moved that branch, their files on disk would no longer match what Git thinks is checked out, and their next git status would show a mass of phantom changes.

Git blocks it by default. The general solution is a shared bare repository that nobody works in directly — which is exactly what GitHub is.

14

Worktrees

the core of this document

A worktree inverts the same decomposition. Bare = a repository with no working tree. A worktree setup = one repository with several working trees.

The mechanism

In a linked worktree, .git is a file, not a folder. It contains one line pointing back into the main repository:

$ cat ../feat-search/.git gitdir: /Users/shreyas/code/project/.git/worktrees/feat-search

And inside the main repo, a small directory per worktree holding that worktree's own HEAD, its own index, and its own ORIG_HEAD:

project/ ├── .git/ │ └── worktrees/ │ ├── feat-search/ ← HEAD, index, ORIG_HEAD for that tree │ └── fix-login/ └── src/ ... ../feat-search/ ← a linked worktree ├── .git ← the pointer file above └── src/ ...

That single design choice explains every property worth knowing.

Commits are instantly visibleCommit in one worktree and every other one can see it immediately. No fetch, no push, no remote — there is only one object database.
Cheap after the firstA second worktree costs a checkout, not a history. On a repository with years of commits, that's a very large difference from a second clone.
One branch, one worktreeGit refuses to check out the same branch in two worktrees. That guard rail prevents an entire class of confusion — two directories silently fighting over one pointer.
Untracked files are NOT sharednode_modules, .env, build caches, target/. Each worktree needs its own. This is the real tax.

The commands

$ git worktree add ../feat-search feat/search # existing branch $ git worktree add -b fix/login ../fix-login # create branch + worktree $ git worktree add --detach ../review HEAD # no branch, just look $ git worktree list /Users/shreyas/code/project a1b2c3d [main] /Users/shreyas/code/feat-search 9f8e7d6 [feat/search] /Users/shreyas/code/fix-login 3c4d5e6 [fix/login] $ git worktree remove ../fix-login $ git worktree prune # tidy up after deleting a folder manually

Do this now — feel the shared-history property

This is the moment worktrees click. Do it rather than reading it.

$ cd ~/code/git-lab $ git worktree add -b experiment ../git-lab-experiment $ cd ../git-lab-experiment $ echo "from the other worktree" > new.txt $ git add . && git commit -m "Commit made in worktree two" $ cd ../git-lab $ git log --oneline experiment 7d8e9f0 Commit made in worktree two # already here. No fetch. $ ls new.txt ls: new.txt: No such file or directory # but not in THIS directory

The commit is visible instantly because the history is shared. The file isn't there because the working trees are separate. That's the entire concept, in two commands.

Why not just git switch?

Because switching branches is a destructive, serialising operation on a directory. Your dev server dies. Your editor reindexes. Your node_modules may now be wrong for this branch. You must stash or commit half-finished work first.

That's perfectly fine when one person does one thing at a time. It stops being fine the moment two things must be in progress at once — a production hotfix while a feature is half-built, reviewing someone's PR without disturbing your uncommitted work, running a long test suite on one branch while you code on another, or three agents working simultaneously.

Q5You have two worktrees. In one you run git branch new-idea. Can the other worktree see that branch?
Show answer

Yes, immediately. Branches are refs, and refs live in the shared repository. Both worktrees read the same refs/heads/.

What each worktree keeps to itself is only which branch it has checked out (its own HEAD), its staging area, and its files.

15

The bare-root layout

when no worktree is special

The setup in section 14 has an asymmetry: the original clone is the "main" worktree and the others hang off it. Delete the main one and things get awkward.

If no worktree should be privileged, combine the two ideas: put a bare repository at the root, and make every branch a sibling directory.

project/ ├── .bare/ ← the bare repository lives here ├── .git ← a FILE containing: gitdir: ./.bare ├── main/ ← a worktree ├── feat-search/ ← a worktree └── fix-login/ ← a worktree

Do this now — set one up

$ mkdir -p ~/code/wt-demo && cd ~/code/wt-demo $ git clone --bare https://github.com/YOUR-USERNAME/git-practice.git .bare $ echo "gitdir: ./.bare" > .git # IMPORTANT: a bare clone doesn't set up remote tracking properly $ git config remote.origin.fetch "+refs/heads/*:refs/remotes/origin/*" $ git fetch origin $ git worktree add main $ git worktree add -b feat/demo feat-demo $ git worktree list

Don't skip the refspec line

git clone --bare deliberately doesn't configure remote-tracking branches — it assumes you want a pristine mirror. Without that remote.origin.fetch line, git fetch updates almost nothing and git worktree add existing-branch can't find remote branches.

This is the single most common reason people try the bare-root layout once, hit something inexplicable, and give up.

The .git file at the root is what makes Git commands work from the project/ directory itself, so you can run git worktree list and git fetch from the top without stepping into any particular tree.

What you get

Branch switching becomes cdcd ../feat-search. Nothing is destroyed, nothing reindexes, your dev server in the other directory keeps running.
Nothing is specialDelete any worktree and the rest are unaffected. main is just another directory.
One history, one fetchFetch once at the root and every worktree sees the new commits.
Editors stay openOne VS Code window per worktree, each with its own terminal, each on a different branch. No context switching cost at all.

Is this overkill for coursework?

Honestly, yes. For a single-file HTML assignment, git switch is fine and this is ceremony.

It earns its keep when a checkout is expensive — large repositories, slow installs, long-running dev servers — or when several things genuinely need to be in flight at once. Which, as the next sections argue, is now the normal case rather than the exception.

16

Worktree gotchas

the honest list

Worktrees are genuinely useful and they have sharp edges. Knowing them in advance is the difference between adopting the pattern and abandoning it after one bad afternoon.

The stash is sharedSurprising and occasionally destructive. git stash in one worktree is visible — and poppable — from all of them. Prefer scratch commits, as section 07 argued.
Config is sharedAll worktrees read the same .git/config. For per-worktree settings you need git config --worktree, which first requires git config extensions.worktreeConfig true. Matters when two trees need different user.email or different hooks.
Dependencies are per-treeThree worktrees on a Node project means three node_modules, three installs, three copies on disk. Write a one-line bootstrap script or you will hate this by day two.
Untracked config doesn't copy.env, local settings, editor config — none of it comes across, because none of it is tracked. Same bootstrap script should handle it.
Ports collideThree dev servers want three ports. Either configure them per-tree or only run one at a time.
Deleting the folder isn't enoughrm -rf on a worktree leaves stale metadata in .git/worktrees/. Run git worktree remove instead, or git worktree prune afterwards.
Submodules are awkwardWorktrees and submodules together are still rough. If your project uses submodules heavily, test carefully before committing to this workflow.
Hooks are sharedAll worktrees run the same hooks from the same directory. Usually what you want; occasionally not.

A bootstrap script pays for itself immediately

#!/usr/bin/env bash # wt — create a worktree and make it usable # usage: wt feat/search set -euo pipefail branch="$1" dir="../$(echo "$branch" | tr '/' '-')" git worktree add -b "$branch" "$dir" origin/main cp .env "$dir/.env" 2>/dev/null || true (cd "$dir" && npm install) echo "ready: $dir"

Worktrees are not isolation

Separate directories are not separate machines. An agent or a script running in one worktree can still cd .., still reach your whole filesystem, still hit the network, and still push to your remote.

If you need genuine isolation — running untrusted code, or letting an agent operate unsupervised — you want a container or a VM. Worktrees solve file collision, not security. Conflating the two is a mistake worth avoiding early.

17

How coding agents actually work

no magic involved

Before arguing that worktrees suit agents, it's worth being precise about what an agent is — because the mechanism is simpler than the marketing suggests, and the properties that matter follow directly from it.

An agent is a loop

A language model wired to a set of tools, running in a cycle: receive context → decide on an action → the harness executes it → feed the result back → repeat until the task is done or it gives up.

The modelProduces text. On its own it cannot touch anything — no files, no network, no commands.
The harnessThe program around it that actually does things: reads files, writes files, runs shell commands, and hands the output back as more text.
ToolsThe specific actions available — read a file, edit a file, run a command, search the codebase, fetch a URL.
ContextEverything the model can see this turn: your instructions, files it has read, previous tool results. It is finite, and it is all the model knows.

Four properties that follow, and they're the ones that matter

It works in a directory, over timeA task means dozens of reads and edits across many minutes. The directory is mutated continuously and is inconsistent halfway through.
It has no memory between runsEverything must be in context. Which is why repositories now carry instruction files — CLAUDE.md, AGENTS.md, .cursorrules — committed alongside the code so the conventions travel with the project.
It can be wrong confidentlyPlausible code that doesn't compile, a fix for the wrong bug, an over-eager refactor of a file you didn't mention. This is not an edge case; it is a routine outcome you must design around.
It reads its own resultsGive it the ability to run tests and it can iterate — write, run, read the failure, fix. This is why agents are far more useful in a repository with a working test suite.

Which makes Git the safety net, not an afterthought

Commit before you start. A clean working tree before an agent runs means git diff shows you exactly what it did, and git restore . undoes all of it instantly.

The diff is the review surface. You are not reading the agent's summary of what it did; you are reading the diff. Those are different things and the second one is authoritative.

Small scoped tasks produce reviewable diffs. "Refactor the auth module" gives you 900 lines you will skim. "Extract the token validation into its own function" gives you 40 you will actually read.

And why running two in one directory fails

Two agents editing the same directory will overwrite each other's changes, and neither can tell which edits are whose. git status shows a mixture with no way to separate them. If one commits, it commits the other's half-finished work too.

There is no clever way around this. They need separate directories — which is precisely the problem the next section solves.

18

Worktrees + agents

why an obscure feature went mainstream

Worktrees shipped in Git 2.5, in 2015, and were a niche curiosity for most of a decade. They became standard tooling in about two years. The reason is worth understanding rather than cargo-culting.

The argument, in three steps

1. An agent works by mutating files in a directory over many minutes (section 17).

2. So two agents need two directories, or they destroy each other's work.

3. But they must share one history — otherwise reviewing and combining their output means pushing and pulling through a remote for every exchange, which is slow, noisy, and fills your remote with junk branches.

One repository, several isolated working directories, shared refs. That is the definition of a worktree. The tool and the problem fit exactly, which is why adoption was so fast once the problem appeared.

What the workflow looks like

$ git worktree add -b feat/search ../search $ git worktree add -b feat/export ../export $ git worktree add -b fix/login-bug ../login-fix # one agent session per directory, running in parallel # each commits to its own branch as it goes # review from anywhere — no fetching, one object database $ git log --oneline feat/search $ git diff main feat/export $ git diff main...fix/login-bug # three dots: only their changes

Three branches, all visible from any of the four directories, because there is only one repository. No fetch. No remote round trip. That immediacy is the whole benefit.

Practices that have settled fairly quickly

One task, one branch, one worktreeThe unit is the task, not the agent. Naming the directory after the branch keeps it obvious which is which when you have four terminals open.
Commit often, in small stepsEvery commit is a checkpoint you can return to. When an agent goes off the rails at step nine, you reset to step eight rather than starting over.
Clean tree before startingSo the diff is unambiguous. Uncommitted work of your own mixed with agent output is genuinely hard to untangle.
Review the diff, not the summaryThe summary is a description. The diff is what happened. Read the diff.
Squash before the PRAgent histories are noisy — "attempt", "fix attempt", "revert attempt". Interactive rebase into a few clean commits before anyone reviews it (section 06).
Instruction files in the repoConventions, architecture notes, commands to run tests. Committed, so they're shared, reviewable, and versioned like everything else.

The costs, stated honestly

Your laptop is the limit long before Git is. Three worktrees means three node_modules, three dev servers, three sets of RAM. Parallelism is bounded by hardware, not by the workflow.

Review does not parallelise. Three agents can produce three features simultaneously; you still read three diffs one after another. If review is your bottleneck — and it usually becomes one — running more agents makes it worse, not better.

Merging three parallel branches that touch the same files gives you three conflict resolutions. Parallelism works best on genuinely independent tasks, and deciding what's independent is a judgement no tool makes for you.

Worth saying in an interview

"I use Git worktrees to run parallel agent sessions" is a fine sentence. Being able to follow it with "because the object database and refs are shared while HEAD, the index and the working files are per-tree — so commits are instantly visible across sessions without a remote round trip" demonstrates that you understand Git's internals and current practice in one breath.

Very few candidates with two years of experience can do that.

Q6Why not just make three separate clones instead of three worktrees?
Show answer

It works, and for some situations it's the right call. Two differences matter.

Disk and time: each clone duplicates the entire history. On a large repository that's significant.

Isolation of refs: separate clones have separate object databases, so a commit made in one is invisible to the others until you push and fetch through a remote. With worktrees it's already there. That immediacy is exactly what you want when reviewing and combining parallel work.

Where separate clones win: when you need genuinely different states of the repository, or when a tool doesn't understand the .git-as-a-file arrangement.

19

How the industry actually uses Git

what to expect on day one

Everything above is mechanics. This is the culture around it, which nobody documents and everybody assumes you've absorbed.

Branching strategy

Trunk-based developmentWhat most product teams do now. One long-lived branch (main), short-lived feature branches off it, merged within a day or two. Main is always deployable.
Git FlowThe 2010 model with develop, release/*, hotfix/* branches. Still used where releases are versioned and shipped on a schedule — desktop software, embedded, enterprise on-premise. Its own author has since said it's overkill for continuously deployed web apps.
Release branchesA middle ground: trunk-based, plus a branch cut per release that fixes are cherry-picked onto.

The single most important habit

Keep branches short-lived. A branch merged within two days rarely conflicts. A branch that lives three weeks while five people touch the same files is a bad afternoon guaranteed.

If a feature is too big for two days, ship it in pieces behind a feature flag. That's what flags are for, and it's why they're everywhere.

What's enforced on you

Protected branchesYou cannot push to main. Full stop. Everything arrives by pull request.
Required reviewsOne or two approvals before merge. Often from a specific team via a CODEOWNERS file that auto-assigns reviewers by file path.
Required status checksAutomated checks must pass before the merge button unlocks — tests, linting, type checking, build. This is the point where Git meets CI, and from your side it's simply "the button is grey until the checks go green."
Linear history requiredSome repositories reject merge commits entirely, forcing squash or rebase merges.
Signed commitsIncreasingly common in finance and security-sensitive work. Commits must be GPG- or SSH-signed to prove authorship.

Conventions you'll be expected to follow

Branch namingfeat/, fix/, chore/, docs/ prefixes, often with a ticket number: feat/PROJ-1234-add-search. Frequently CI-enforced.
Conventional Commitsfeat: add search filter, fix: handle null response, chore: bump deps. Machine-readable, so tools can generate changelogs and version numbers automatically. Widely adopted.
Link the ticketPut the issue number in the PR description. Writing Closes #42 auto-closes the issue on merge.
Delete merged branchesUsually automatic. Otherwise the branch list becomes unusable within months.

Monorepos, briefly

Many large companies keep everything in one enormous repository rather than one per service. It makes cross-cutting changes atomic and dependency management sane, at the cost of tooling complexity and very slow clones.

It's also, incidentally, where worktrees earn their keep hardest: when a checkout takes minutes, you really do not want to switch branches in place.

What actually gets noticed about you

Not clever Git commands. It's whether your PRs are small enough to review, whether your commit messages explain the change, whether you respond to review comments promptly, and whether you break the build. Those four things form most of a team's impression of a new engineer in the first month.

20

What LLMs changed

and what they didn't

A caveat worth reading

This section describes practice that is genuinely unsettled and moving quickly. Treat it as a snapshot and a way of thinking about the change, not as settled doctrine. Some of it will look dated soon; the underlying pressures probably won't.

What didn't change

Git itself. Not one command in this document is new. The model of commits, branches, merges and remotes is the same as it was in 2005, and the fundamentals are — if anything — more valuable now, because more code is passing through them faster.

What did change

Writing code stopped being the bottleneckProducing a plausible first draft of a feature is now fast. Deciding whether it's correct, appropriate and maintainable is not. The constraint moved from generation to review and judgement.
The diff became the primary artifactWhen you didn't type every line, reading the diff carefully is the only way you actually know what changed. Diff literacy — reading a change and reasoning about its consequences — is now the load-bearing skill.
Commit hygiene matters more, not lessThe counterintuitive one. When volume goes up, a history of small well-described commits is what makes a codebase navigable. Ten thousand lines of "update" is now much easier to produce and much worse to live with.
Small PRs went from good practice to necessityA 2,000-line PR was always hard to review. Now they're easy to generate, so the discipline of splitting work has to be deliberate.
Parallelism became normalWhich is the whole worktree story. One person genuinely can have three tasks in flight — and now has to manage the merge and review overhead that creates.
Git became the undo button for automationCommit before running an agent; git diff to see what it did; git restore . to discard it. Version control moved from "how we collaborate" to also being "how we supervise machines".
Repos carry instructions for machinesCLAUDE.md, AGENTS.md, .cursorrules — conventions and architecture notes committed alongside the code. A genuinely new category of file, versioned and reviewed like any other.
Attribution got murkySome teams add trailers like Co-authored-by: to mark generated work. Others don't. There is no settled norm yet, and policies vary — ask rather than assume.

The uncomfortable part

Worth thinking about honestly

If a model can produce the first draft, what is the junior engineer's job? The realistic answer, right now, is: knowing whether the draft is right, understanding the system well enough to say why an approach is wrong, and being the person accountable for what gets merged.

All of which requires understanding the fundamentals better than the previous generation needed to, not worse. You can't review code you don't understand, and you can't debug a framework you only know as an abstraction.

Which is the argument for reading this document properly rather than asking a model to summarise it.

Practical advice for your first job

Use the tools — refusing to is not a principled stand, it's just slower. But commit before you start, read every diff before you stage it, and never open a PR containing code you can't explain line by line.

"The AI wrote it" is not a defence in a review, and it certainly isn't one in an incident postmortem. Your name is on the commit.

Practice run, unaided

the part that makes it stick

Do this on a throwaway repository, without scrolling up. If you get stuck, git status and git log --oneline --graph --all will tell you where you are before any documentation does.

Part one — history surgery

  1. Create a repo with five commits on main.
  2. Branch to feat/one, add three commits, two of which are deliberately messy ("wip", "fix").
  3. Go back to main and add a commit that touches the same file, so the branches diverge.
  4. Rebase feat/one onto main. Resolve the conflict.
  5. Interactive-rebase your three commits into one clean commit with a proper message.
  6. Confirm with git log --oneline --graph --all that the history is linear.

Part two — the recovery drills

  1. Make a commit, then git reset --hard HEAD~1 to destroy it. Recover it using the reflog.
  2. Create a branch, commit to it, delete it with -D, and recover it from the reflog.
  3. Start a rebase, hit the conflict, then --abort. Confirm you're exactly back where you started.
  4. Stash some changes including an untracked file. Prove that plain git stash leaves the untracked file behind and -u doesn't.
  5. Cherry-pick one commit from feat/one onto a new branch off main. Compare the two hashes and explain why they differ.

Part three — worktrees

  1. Add two worktrees on two different branches.
  2. Commit in one. From the other, prove the commit is already visible with no fetch.
  3. Try to check out the same branch in both. Read the error and explain it in your own words.
  4. Stash something in one worktree and list stashes from the other. Confirm the sharing.
  5. rm -rf one worktree directory, then run git worktree list and see the stale entry. Clean it with prune.
  6. Set up the full bare-root layout from section 15, including the refspec line, and add two worktrees to it.

How to judge yourself

You're ready if you got through it needing git status and git log --graph but not this document. Nearly ready if you looked up two or three flags — nobody remembers every option to git worktree.

The real test isn't the commands. It's whether you can explain, out loud, why a rebase produces new hashes and why a worktree can see another worktree's commits without fetching. If you can do that, the commands are just syntax you can look up forever.

Final checkpoint

answer before revealing

Fifteen questions. Answer each in your head — or better, out loud — before opening the answer. Several of these are common interview questions.

1What are the four Git object types, and what does each hold?
Show answer

blob — file contents. tree — a directory listing pointing at blobs and other trees. commit — a pointer to one tree plus author, message and parent(s). tag — an annotated pointer to a commit.

All stored content-addressed by hash, so identical content is stored once.

2Mechanically, what is a branch?
Show answer

A file containing a 40-character commit hash — 41 bytes with the newline. Committing rewrites that file to point at the new commit.

HEAD is a pointer to a branch; detached HEAD means it holds a raw hash instead.

3When is a merge a fast-forward, and when can conflicts happen?
Show answer

Fast-forward when the base branch hasn't moved since you branched — your branch already contains all of its commits, so Git just slides the pointer. Conflicts are impossible in this case.

Conflicts can only occur in a three-way merge, when both sides changed the same lines of the same file.

4Why does rebasing produce new commit hashes?
Show answer

A commit's hash is computed from its content including its parent's hash. Rebasing replays commits onto a different parent, so the parent hash changes, so every replayed hash changes.

That's why it counts as history rewriting, and why the golden rule exists.

5State the golden rule of rebasing and explain the mechanical reason for it.
Show answer

Never rebase commits others have based work on. If a colleague holds your old commits and you replace them with new hashes, their next pull tries to reconcile two versions of the same work — producing duplicates or inexplicable conflicts.

6What's the difference between --force and --force-with-lease?
Show answer

--force overwrites the remote branch unconditionally, including commits someone else pushed since you last looked. --force-with-lease checks the remote is where you last saw it and refuses otherwise.

Always the second one.

7You deleted a branch with unmerged commits. Recover it.
Show answer

git reflog to find the branch tip's hash, then git switch -c <name> <hash>.

Works because the objects are still in the database — only the ref pointing at them was deleted. The reflog is local and entries expire, so this isn't unlimited.

8What exactly is origin/main?
Show answer

A local file recording where the remote's main was the last time you fetched. It's on your disk, not on GitHub, and it can be arbitrarily out of date until you fetch again.

9What is a bare repository, and why is every push target bare?
Show answer

A repository with no working tree — the contents of .git as the directory itself, core.bare = true.

Pushing to a branch that's checked out somewhere would leave that working tree disagreeing with HEAD, so Git refuses. A bare repo has no working tree, so there's nothing to desync. GitHub is a warehouse of bare repos.

10In a worktree setup, what is shared and what is per-tree?
Show answer

Shared: the object database, refs (branches and tags), config, hooks, and the stash.

Per-tree: HEAD, the index, the checked-out files, and all untracked files.

That split explains every property — instant visibility of commits, cheap creation, and the need for a separate node_modules in each.

11Why does Git refuse to check out the same branch in two worktrees?
Show answer

Because both would be moving the same ref while holding different working states. Committing in one would leave the other's files inconsistent with the branch it thinks it's on.

It's the same class of problem that makes push targets bare — a guard rail, not an arbitrary limitation.

12What's the one line people forget in the bare-root worktree layout?
Show answer

git config remote.origin.fetch "+refs/heads/*:refs/remotes/origin/*"

--bare doesn't configure remote-tracking branches, so without it git fetch brings down almost nothing and worktrees can't be created from remote branches.

13Explain in three steps why worktrees suit parallel coding agents.
Show answer

An agent mutates files in a directory over many minutes. Two agents therefore need two directories. But they must share one history, or combining their work means a remote round trip every time.

One repository, several working directories, shared refs — that's a worktree.

14Do worktrees give you isolation for running untrusted code?
Show answer

No. Separate directories are not separate machines. Anything running in a worktree can reach the rest of your filesystem, the network, and your remotes.

Worktrees solve file collision. For actual isolation you want a container or VM.

15What are the three merge buttons, and why is squash the common default?
Show answer

Merge commit (keeps everything plus a join), squash (collapses the branch into one commit), rebase-and-merge (replays commits individually, no merge commit).

Squash is common because one PR becomes one commit on main, which makes git revert and git bisect trivial. Note the trap: delete the branch afterwards rather than reusing it.
