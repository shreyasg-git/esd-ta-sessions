03

No answer at all — NetworkError

Coresrc/api/client.js

Refresher

fetch rejects only when there's no response. A 404 or a 500 is a response: fetch resolves, and you check res.ok (JS Lab 2 · §04). Since Lab 2, apiFetch turns every non-2xx into an ApiError.

Two kinds of failure

What happenedWhat your code gets
The server answered with an error status: 400, 401, 403, 404, 409, 500An ApiError, with status, the server's message and fieldErrors. You know exactly what went wrong.
No answer reached your code: the server is down, the port is wrong, you're offline — or the browser blocked the answer (CORS, section 10)fetch rejects with a TypeError, message "Failed to fetch". No status, no body, no reason. The browser deliberately doesn't tell your code which one it was.

Lab 3's client let that TypeError through, so every page that shows err.message said "Failed to fetch" — true, and no help to anyone. Your job: turn it into an error of its own, with a message a person can act on.

Do this now — see it before you fix it

  1. With npm run dev running and the course list open, set the Network tab's throttling menu (it says No throttling) to Offline.
  2. Click a course. The page says Couldn't load the course: Failed to fetch, and the Network tab shows the request as failed, with no status.
  3. Set it back to No throttling.

Exercise — NetworkError

NetworkError is already declared at the top of client.js, with its fixed message. In apiFetch, wrap the fetch call so that when it rejects, you throw a NetworkError instead, keeping the browser's error as its cause:

export class NetworkError extends Error { // given constructor(cause) { super("Can't reach the server — is your backend running?"); this.name = "NetworkError"; this.cause = cause; } } // in apiFetch — you write this: let res; try { res = await fetch(`${API_BASE}${path}`, init); } catch (err) { throw new NetworkError(err); // fetch rejects only when there's no response at all }

Only the fetch call goes inside the try. A 4xx never lands in that catch — it's an answer, and the code after it turns it into an ApiError as before. Now the two kinds of failure are two classes: err instanceof NetworkError tells them apart, if a page ever needs to (a Retry button only makes sense for one of them). Most pages don't: they show err.message, so the new message appears on the course list, the course page, My courses and the login page without touching any of them.

The message is a guess

"Is your backend running?" is the most likely cause, not the only one. If it is running, look at the Console: a red line starting Access to fetch … has been blocked by CORS policy means the server answered and the browser hid the answer from your code. Section 10 is about exactly that.

$ npx vitest run test/client.test.jsx # the "03 ·" tests pass; the "05 ·" ones wait for section 05

Then Offline again, click a course: the new message.

Q1Why not put the whole of apiFetch — the fetch, the res.ok check, the res.json() — inside one big try, and throw a NetworkError from its catch?
Show answer

Then the ApiError thrown for a 409 would be caught too, and reported as "Can't reach the server" — the one thing it certainly isn't. A try should wrap only the line whose failure it means. Here that's the fetch call.

04

When a token dies in the middle of a session

Coresee the problem — no code yet

Refresher

A 401 means "who are you?" — no token, or one that's invalid, expired or logged out (React Lab 3 · §09). This app keeps the session in sessionStorage, so it survives a reload (Lab 3 · §10).

The app decides you're logged in when it has a token. The server decides when the token works. Those two can disagree, and they will. A token stops working when:

  • it expires — 3600 seconds after login, unless the server is set up otherwise;
  • it's logged out somewhere else — in another tab, on another device: the server revokes it, everywhere;
  • the server can no longer check it — the mock picks a new random signing secret every time it starts, so after you restart npm run dev, every token it issued before fails the signature check;
  • it came from a different server — a token from the mock means nothing to your backend (section 09).

In all four cases the app still holds the token, the header still shows your name — and the next logged-in request gets a 401.

Do this now — two real ways to kill a token

  1. Restart the server. Log in as Sam. In the terminal, stop npm run dev (Ctrl+C) and start it again. The page reloads itself; the header still says Sam. Click My courses: Couldn't load your courses: Authentication required. In the Network tab, the request carried the old token and got 401.
  2. Log out somewhere else. Log in again. In the Console, revoke the app's token behind its back — exactly what a Log out in another tab would do:
const { token } = JSON.parse(sessionStorage.getItem("esd-session")); (await fetch("/api/auth/logout", { method: "POST", headers: { Authorization: `Bearer ${token}` } })).status // 204

Now open CS402 and press Enroll: Authentication required, as a red line under the button, while the header insists you're logged in. Lab 3 shipped this on purpose; the fix is the next two sections.

What should happen instead

One rule, the same everywhere: a 401 on a request that carried a token means the session is over. Forget it, send the person to the login page, tell them why, and after they log in, bring them back to where they were. Everything else — a wrong password, a 403, a 409 — stays the page's business.

Q1The token has an exp claim. Why not decode it in the browser and log the user out a moment before it expires — then there'd be no 401 to handle?
Show answer

Three reasons. The contract makes the token opaque to clients: its inside is the server's business. Expiry isn't the only way a token dies — revocation and a server restart don't change exp at all. And the browser's clock may not agree with the server's. You'd still need 401 handling, so write that, once.

Q2Is a 403 an expired session?
Show answer

No. A 403 means the server knows who you are, and the answer is no — a student creating a course. Logging in again changes nothing, so sending them to the login page would be wrong. Only 401 means "who are you?".

Step 1 — apiFetch notices

In client.js, apiFetch takes one more option, onUnauthorized. In the !res.ok branch, after building the ApiError and before throwing it:

if (res.status === 401 && token && onUnauthorized) onUnauthorized(); throw error; // still thrown: the caller must stop, whatever happens next

Each condition earns its place. 401, not 403 (section 04). token: a 401 on a request without a token is just an answer — a wrong password at login is a 401 with no token, and must not say "your session has expired". onUnauthorized: it's optional, so apiFetch still works for code that doesn't pass one.

Step 2 — AuthProvider reacts

In AuthContext.jsx: an expired state, false to start; your login sets it back to false once it has stored the new session; and sessionExpired. Below, the session is one state value, session, as React Lab 3 §10 had it — if yours is shaped differently, forget it the way your logout() does after its request:

const [expired, setExpired] = useState(false); // why nobody is logged in const navigate = useNavigate(); const location = useLocation(); function sessionExpired() { navigate("/login", { replace: true, state: { from: location } }); // first: leave, remembering where we were setSession(null); // then: forget the session setExpired(true); // and say why }

AuthProvider can use router hooks because it sits inside the router: main.jsx wraps <App /> in <BrowserRouter>, and App puts AuthProvider around the routes. state: { from: location } is Lab 3's redirect-back: the login page already sends you to from after logging in (React Lab 3 · §11).

Navigate first, as Log out does in Lab 3, so you head for the login page before the user disappears. Here both updates happen in the same moment, so on a protected page like /me, RequireAuth may see "no user" first and send you to /login itself — with the same from. Either way you land on the login page, and that's why the reason lives in AuthProvider's state (expired), not in the navigation state: whichever navigation wins, the message is there. replace, like RequireAuth: Back shouldn't lead to a page that needs the session that just ended. (It also means that when two requests get 401 together — in development, StrictMode runs every effect twice — you make one trip to /login, not two.)

expired is not saved to sessionStorage: it describes this moment. A reload tomorrow shouldn't say your session just expired.

Step 3 — api connects them

function api(path, options = {}) { return apiFetch(path, { ...options, token: session?.token, onUnauthorized: sessionExpired }); }

session?.token is the logged-in user's token — whatever your AuthProvider keeps it in. Then put expired and api in your context value, next to user, token, login and logout (section 07 adds signup). Remove the two placeholders the starter left (const expired = false and the api that throws) when you write the real ones.

api is a closure

api remembers session and sessionExpired from the render of AuthProvider that made it (JS Lab 1 · §06). A new render makes a new api with the new session. That's why callers never pass a token: the function already holds the right one.

Which calls stay on plain apiFetch

  • Public reads — the course list, one course. They need no token, so don't send one. There's a second reason: some backends reject a bad token even on a public endpoint (Spring's OAuth2 resource server does), so an expired token sent with GET /api/courses would break the public list.
  • Login — there's no session yet; a 401 there is "Invalid email or password". And the /api/users/me call inside login uses the brand-new token it was just given.
  • Logout — if its token is already dead, the server says 401, and the user, who just clicked Log out, should simply be logged out — not told their session expired. A test checks it.

The dependency array

useMyEnrollments's effect now calls api, and its array stays [token]. Lab 2's rule says everything the effect reads that can change goes in the array (React Lab 2 · §05) — so why not api? api is a new function on every render of AuthProvider, but what it does depends only on the token: the token is the value that decides whether the list must load again. Putting api in the array wouldn't break anything — the list would just reload whenever AuthProvider re-renders, which is more often than needed. The tool that would make api itself stable, useCallback, is on the "not yet" list (React Lab 2 · §09).

CoreAuthContext.signup · SignupPage.jsx · App.jsx

Refresher

Controlled inputs, and one change handler for many fields with a computed key (React Lab 2 · §06). Lab 2's AddCourseForm already shows fieldErrors under its fields — read it again before you start; you'll write the same pattern yourself.

The endpoint

POST /api/auth/signup { "email": …, "password": …, "fullName": … } no token → 201 { "id": 4, "email": "asha@test.com", "fullName": "Asha Rao", "role": "STUDENT", … } → 400 { "message": "Validation failed", "fieldErrors": { "email": "must be a well-formed email address", "password": "size must be between 8 and 64" } } → 409 { "message": "Email already registered", "fieldErrors": null }

Note what the 201 is: the new user, not a token. To be logged in, you still log in. And note the contract's words about fieldErrors: "wording is free". Your backend's messages will be different from the mock's — so the page never compares them; it shows them.

Step 1 — signup() in AuthContext

Plain apiFetch: there's no session yet. No try: if the signup fails, the ApiError goes to the page, which shows it — like login in Lab 3.

Step 2 — SignupPage

In src/pages/SignupPage.jsx: a heading "Create an account"; inputs labelled Full name, Email, Password (the FIELDS list at the top of the file has their names and types); a "Sign up" button. When it throws, keep two things: the error (for its message and status) and its fieldErrors (err.fieldErrors ?? {} — null for a 409 or a network error). Then, for each field:

CORS — what the browser checks

Coreorigins, preflights, and the headers that answer them

Refresher

An origin is scheme + host + port. A page may send a request to another origin, but its JavaScript may only read the answer if that server says so, with Access-Control-Allow-Origin (JS Lab 2 · §10). http://localhost:5173 and http://localhost:8080 are different origins: same machine, different port.

Why the mock never needed it

With npm run dev alone, the page and the API both come from http://localhost:5173: one origin, nothing to check. The moment API_BASE points at port 8080, every request crosses origins, and the browser applies the CORS rules to each one. It's the browser that enforces them. curl, Postman and the conformance suite are not browsers: they never get blocked, which is why "it works in Postman" tells you nothing about CORS.

Two kinds of cross-origin request

KindIn this appWhat the browser does
Simple — a GET (or a form-style POST) with no special headersGET /api/courses, GET /api/courses/4Sends it, with an Origin header. Hands the answer to your code only if the response carries Access-Control-Allow-Origin with your origin (or *).
Preflighted — anything with an Authorization header, a JSON body (Content-Type: application/json), or PUT / DELETElogin, signup, /api/users/me, enroll, drop, every admin writeFirst asks permission with an OPTIONS request — the preflight — carrying no token and no body. Only if the answer allows the origin, the method and the headers does it send the real request. And the real response needs Access-Control-Allow-Origin too.
# 1. the preflight — sent by the browser on its own, before your POST OPTIONS /api/enrollments Origin: http://localhost:5173 Access-Control-Request-Method: POST Access-Control-Request-Headers: authorization,content-type → 204 (or 200) Access-Control-Allow-Origin: http://localhost:5173 Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS Access-Control-Allow-Headers: Authorization, Content-Type Access-Control-Max-Age: 3600 # remember this answer for an hour: no preflight each time # 2. the real request — only now POST /api/enrollments Origin: http://localhost:5173 Authorization: Bearer eyJhbGciOi… → 201 (or 401, 409 …) Access-Control-Allow-Origin: http://localhost:5173 # on errors too, or your code can't read the ApiError

Two consequences matter for your backend. The preflight carries no token — a browser never sends credentials on a preflight — so a server that demands a token on every request answers it 401, and the real request is never sent. And error responses need the header too: a 409 without it reaches your code as a NetworkError, not as the ApiError with the server's message.

CORS doesn't protect your API: anyone can call it with curl, and only your 401s and 403s stop them. It protects people: it stops some other website, open in their browser, from reading your API's answers on their behalf.

CORS in Spring Boot

CoreSecurityConfig · a CorsConfigurationSource bean

The contract's CORS rule (openapi.yaml, last section of the description): for origin http://localhost:5173, allow methods GET, POST, PUT, DELETE, OPTIONS and headers Authorization, Content-Type; a preflight answers 200 or 204 with Access-Control-Allow-Origin; every actual response repeats it. In a Spring Boot app with Spring Security, that's two small changes to your SecurityConfig.

1 — a CorsConfigurationSource bean

import java.util.List; import org.springframework.web.cors.CorsConfiguration; import org.springframework.web.cors.CorsConfigurationSource; import org.springframework.web.cors.UrlBasedCorsConfigurationSource; @Bean public CorsConfigurationSource corsConfigurationSource() { CorsConfiguration config = new CorsConfiguration(); config.setAllowedOrigins(List.of("http://localhost:5173")); // exactly: no trailing slash config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS")); config.setAllowedHeaders(List.of("Authorization", "Content-Type")); config.setMaxAge(3600L); // browsers may cache the preflight UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource(); source.registerCorsConfiguration("/api/**", config); return source; }

2 — turn it on in the security filter chain

import org.springframework.security.config.Customizer; @Bean public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception { http .cors(Customizer.withDefaults()) // ← new: uses the CorsConfigurationSource bean above .csrf(csrf -> csrf.disable()) // … your session policy, authorizeHttpRequests, JWT filter — unchanged … return http.build(); }

.cors(…) puts Spring's CorsFilter at the front of the security filter chain. From there it does two things: it answers every preflight itself, before authentication is even looked at — so a preflight with no token gets its 200, not a 401 — and it adds Access-Control-Allow-Origin to every response that comes back through the chain, the 401s and 403s from the security layer included. Restart your backend and reload the app: the course list loads, login works.

Why @CrossOrigin isn't enough

You may have seen @CrossOrigin(origins = "http://localhost:5173") on a controller, or a WebMvcConfigurer with addCorsMappings. Both belong to Spring MVC, which runs after Spring Security. A preflight has no token; with anyRequest().authenticated(), Security answers it 401 before MVC — and your annotation — ever sees it. Security's own 401 and 403 responses never pass through MVC either, so they'd go out without the header, and the app couldn't read them. Once Security is in the picture, CORS belongs in Security. Keep it in that one place: if you had @CrossOrigin or addCorsMappings before, remove them. With .cors(…) they're dead code — Spring's CORS handling skips a response that already has the header — and dead configuration misleads the next person who reads it. What does send the header twice, which browsers reject, is a hand-written filter or a setHeader("Access-Control-Allow-Origin", …) next to .cors(…).

Don't add allowCredentials

setAllowCredentials(true) is for cookies. This app sends its token in a header, so it doesn't need it. And never combine it with "*" as the origin: Spring refuses that combination with an IllegalArgumentException on every request (you'll see 500s), and browsers would refuse it anyway.

Check it with curl — the same questions a browser asks

$ curl -i -X OPTIONS http://localhost:8080/api/enrollments \ -H "Origin: http://localhost:5173" \ -H "Access-Control-Request-Method: POST" \ -H "Access-Control-Request-Headers: authorization,content-type" HTTP/1.1 200 Access-Control-Allow-Origin: http://localhost:5173 Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS Access-Control-Allow-Headers: authorization, content-type Access-Control-Max-Age: 3600 $ curl -i http://localhost:8080/api/users/me -H "Origin: http://localhost:5173" HTTP/1.1 401 Access-Control-Allow-Origin: http://localhost:5173 # even on the security layer's 401

The exact spelling and order of the values may differ from this; what matters is that each header is there and allows what you asked. If the first command gives a 401, Security is still answering preflights — .cors(…) is missing, or isn't in the chain your requests use. (On Windows PowerShell, type curl.exe instead of curl, and put each command on one line without the \ — or run these in Git Bash.)

Three questions, in order. Which server? The footer. Did the browser hide the answer? The Console: a CORS line means yes, and the fix is on the server. What did the server say? Access-Control-Allow-OriginThe response header that lets a page from that origin read the response. Needed on every cross-origin response — errors included.
Access-Control-Allow-Methods / -HeadersIn a preflight's answer: which methods and request headers the real request may use.

conformance level CThe contract pack's checks for enrollments, admin writes and every 409 rule. With A and B, what this lab needs from your backend.
CORSCross-Origin Resource Sharing: the browser's rule that a page may read another origin's responses only when that server's headers allow it.
CorsFilterThe Spring filter that http.cors(…) adds at the front of the security chain: it answers preflights and adds the CORS headers to responses.
.env.localA file of settings Vite reads when it starts, kept out of Git. Here: VITE_API_URL.
fieldErrorsIn a 400's ApiError: one message per bad field, worded freely by the server. Shown under its field, never compared.
fixed messageA message the contract spells out word for word (like "Course is full"), so clients may compare it.

noValidateA form attribute that turns off the browser's own checks, so the server's messages can be seen.
onUnauthorizedThe function apiFetch calls on a 401 for a request that carried a token. Here, sessionExpired.

preflightThe OPTIONS request a browser sends on its own, without a token, to ask whether a non-simple cross-origin request is allowed.
