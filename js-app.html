The shape of the whole app

Everything in this lab fits one loop. Learn it now; every section fills in one part of it.

// an EVENT happens (a click, a keystroke, a response from the server) // → transition(state, event) returns the NEXT state (section 05) // → setState(next) stores it and calls render() (Lab 1 §15, section 07) // → render() draws the regions whose data changed (sections 06 and 08)

Nothing else is allowed to change the page. A click handler never touches the DOM; a fetch callback never touches the DOM. They describe what happened, and the loop does the rest. That's reactivity, scaled up from one counter to an app.

In React, this becomes…

Exactly the same loop. transition is what React calls a reducer, used with useReducer. "Describe what happened" is dispatch({ type: "ADD", course }). The redraw is React's job. Section 11 lines them up.

Part 2 · Waiting for things
03

Promises, await, and the order things happen in

Coresrc/s03-async.js

Refresher

A promise is a value that isn't ready yet: a placeholder for a result that will arrive later, or a failure. await pauses an async function until the promise settles, then gives you the result — or throws the failure, so try/catch works. Full version: 06 · §17 Promises to §21 Error handling.

JavaScript never waits — it schedules

A browser tab runs your JavaScript on one thread. If it stopped and waited 800 ms for a server, the page would freeze: no clicks, no typing, no scrolling. So nothing waits. A slow job is started, the rest of your code carries on, and when the job finishes, a callback is put in a queue to run once the current code is done. That's the event loop, in one paragraph.

console.log("a"); setTimeout(() => console.log("b"), 0); // a timer, even 0 ms, runs LATER Promise.resolve().then(() => console.log("c")); // promise callbacks run before timers console.log("d"); // a, d, c, b

The current code always finishes first (a, d). Then promise callbacks (c), then timers (b). You don't need the queue names; you need the habit: code after an async call runs before its result arrives.

Stretch — predict, then run

Open predict/async.js. Under each block, write what you expect it to print. Then run node predict/async.js and explain every difference.

await pauses one function, not the program

async function job() { console.log("job starts"); await wait(20); console.log("job ends"); } job(); // starts, runs until the await, returns a promise console.log("main carries on"); // job starts, main carries on, job ends

Every async function returns a promise — always, even async () => 3. Calling it without await just starts it. That's the most common async bug: const data = getJSON(url) gives you Promise {<pending>}, not the data.

Exercise 1 — wait(ms)

Turn setTimeout, which takes a callback, into a promise you can await. This is the pattern for wrapping any callback API in a promise — the hint in the file gives it away; make sure you understand why it works.

await wait(500); // half a second later… // undefined

Exercise 2 — one after another, or all at once?

Three requests that take 100 ms each. Awaited one by one, they take 300 ms. Started together and awaited together, 100 ms.

// in order: each starts when the previous one finished for (const task of tasks) results.push(await task()); // all at once: start them all, then wait for all of them await Promise.all(tasks.map((task) => task()));

Write inOrder(tasks) and allAtOnce(tasks). The tests time them. Use inOrder when each step needs the previous one (log in, then load the profile). Use Promise.all when they're independent — and know that if any of them fails, Promise.all fails, with that error.

Not with forEach

tasks.forEach(async (t) => results.push(await t())) looks like "in order" but isn't: forEach doesn't wait for the async callbacks, so it starts all of them at once and returns immediately — results is still empty. Use for…of with await, or Promise.all with map.

Q1async function f() { return 3; } — what does f() return, and how do you get the 3?
Show answer

A promise that resolves to 3. await f() inside an async function (or the REPL), or f().then((n) => …).

04

fetch, URLs and failures

Coresrc/s04-api.js

Refresher

fetch(url) returns a promise of a Response. The body comes separately: await res.json() is a second promise, because the body may still be downloading when the headers arrive. Full version: 06 · §22 fetch().

Meet the API

Do this now — call it from the address bar

With npm run web running, open these in a browser tab. It's JSON — the same shape as the course API you'll use in the React labs.

GET /api/courses every course, sorted by code GET /api/courses?department=Electronics one department GET /api/courses?q=learn code or title contains "learn" GET /api/courses/4 one course GET /api/courses/999 404, with an error body GET /api/courses?delay=1500 answers after 1.5 seconds GET /api/courses?fail=1 500, with an error body

Open DevTools → Network, reload, and click a request: you'll see its status, headers, timing and response. Keep this tab open for the rest of the lab — when the app misbehaves, it's the first place to look.

Exercise 1 — buildCoursesUrl, and the & problem

One department is called Data Science & AI. Glue it into a URL by hand and you get:

`/api/courses?department=${department}` // "/api/courses?department=Data Science & AI" // the server reads: department = "Data Science ", and a second, empty parameter " AI"

In a query string, & separates parameters. Values have to be encoded. URLSearchParams does it for you:

const params = new URLSearchParams(); params.set("department", "Data Science & AI"); params.toString(); // "department=Data+Science+%26+AI"

Write buildCoursesUrl({ department, q }): "/api/courses" plus only the filters that aren't blank. Never build a query string with + or a template — user input will break it sooner or later.

Exercise 2 — getJSON, and why a 404 isn't an error

This surprises everyone once: fetch only rejects when there's no response at all — no network, the server is down, the request was blocked. A 404 or a 500 is a response, so fetch resolves happily, and res.json() hands you the server's error body as if it were data.

const res = await fetch("/api/courses/999"); res.ok // false res.status // 404 await res.json() // { status: 404, error: "Not Found", message: "No course with id 999", … }

So every fetch needs a check. Write getJSON(url, fetchFn = fetch): fetch, throw new Error(`HTTP ${res.status}`) if !res.ok, otherwise return the parsed body. Then fetchCourses(filters, fetchFn) is one line on top of the two.

Why fetchFn is a parameter

The tests can't depend on a server running, and they need to make the "server" fail on purpose. So getJSON takes the fetch function as an argument, defaulting to the real one, and the tests pass in a fake (support/helpers.js). Passing in what a function depends on, instead of reaching out for it, is called dependency injection — and it's a function-as-value idea straight from Lab 1 · §04. The app uses it too: section 07 passes a fetch that adds the Network switch's options.

Q1The server is down. Which line throws — await fetch(url), res.ok, or await res.json()?
Show answer

await fetch(url) — it rejects with a TypeError ("Failed to fetch" in the browser, "fetch failed" in Node). With no response, there's no res to check.

Q2The URL is wrong and the server answers with an HTML "Not found" page. What does await res.json() do?
Show answer

Throws a SyntaxError: "Unexpected token '<' … is not valid JSON" — the < is the start of <!DOCTYPE html>. Checking res.ok first turns that into a clear HTTP 404.

Part 3 · State as data
05

One state object, one transition function

Coresrc/s05-store.js

Lab 1's counter had one number of state. This app has a list from the server, whether it's loading, an error, two filters, a planner and the grades. Spread those across ten lets and every handler has to remember which ones to change together — the same disease as Lab 1's stage 2, one level up. So all of it goes in one object:

export const initialState = Object.freeze({ status: "idle", // "idle" | "loading" | "ready" | "error" courses: [], // from the last successful load error: null, // the message, when status is "error" departments: [], // every department name, from the first load department: "", // the filter ("" = all) query: "", // the search box planner: [], // [{ id, code, title, credits }, …] grades: {}, // { [courseId]: "A" | "A-" | … } — the SGPA form });

One status, not three booleans

The natural first try is isLoading, hasError, isLoaded. Three booleans have eight combinations, and most are nonsense: loading and errored and loaded? Something will eventually produce one, and the page will show a spinner over an error message over a list. One status field with four allowed values can only ever be in one of them. That's a state machine: a fixed set of states, and events that move you between them.

idle ──LOAD_START──▶ loading ──LOAD_OK───▶ ready │ │ └──LOAD_FAIL──▶ error ──LOAD_START──▶ loading …

transition(state, event) → the next state

Every change to the state is described as an event — a plain object with a type and whatever data it needs — and handled in one function:

EventThe next state
{ type: "LOAD_START" }status "loading", error cleared. Keep the old courses on screen while the new ones load.
{ type: "LOAD_OK", courses }status "ready", these courses. The first time only, also fill departments: unique, sorted.
{ type: "LOAD_FAIL", message }status "error", error = the message. Keep the old courses.
{ type: "SET_DEPARTMENT", department }
{ type: "SET_QUERY", query }		The new filter — or the same state if it didn't change.
{ type: "ADD", course }Append { id, code, title, credits } to the planner — not the whole course, which has fields (like seatsLeft) that go stale. Same state if it's already there.
{ type: "REMOVE", id }Remove it from the planner, and drop its grade. Same state if it wasn't there.
{ type: "SET_GRADE", id, grade }Set that course's grade; "" removes the entry. Same state if unchanged.
anything elseThe same state.

The starter gives you the switch, one case per event. Each case is a Lab 1 immutable update — this section is Lab 1 · §08 and §10 put to work:

case "SET_GRADE": return { ...state, grades: { ...state.grades, [event.id]: event.grade } }; // computed key (08) case "REMOVE": { const { [event.id]: _dropped, ...grades } = state.grades; // rest: every grade except this one return { ...state, planner: state.planner.filter((c) => c.id !== event.id), grades }; }

Neither case is finished: check the table for when each must return the same state, and what "" means for a grade.

Why "the same state" matters so much

When nothing changes, return the very object you were given — not a copy. useState compares with Object.is and skips the redraw when the state is the same object (that's §15's smarter setState — your Lab 1 version, in src/state.js since step 0). Return a fresh copy every time and every no-op click redraws the whole page. Section 08 builds on this: a new object means "something changed", the same object means "nothing did". That only works if you never change an object in place — which is why the tests freeze everything.

In React, this becomes…

const [state, dispatch] = useReducer(transition, initialState). Same function, same events, same rule about returning the same state. React even calls the events actions and the function a reducer — because it has the same shape as the callback you give reduce: (accumulated, next) => accumulated.

Stretch — rules in the transition

A planner over 24 credits, or a full course, shouldn't be possible at all. Make ADD return the same state for a course with seatsLeft === 0, or one that would take the planner past 24 credits. Then the UI can't get into that state, however many buttons you add later. npm run test:stretch.

Q1Why does LOAD_START keep the old courses instead of clearing them?
Show answer

So the list doesn't flash empty on every keystroke. The old results stay visible, with "Loading courses…" above them, until the new ones arrive. Clearing would be a valid choice — but it's a choice, made in one place, rather than something each handler decides.

06

Views — and the SGPA calculator

Coresrc/s06-views.js

Between the state and the DOM sits one more layer: view functions. Each takes state and returns plain data describing what a region shows — the exact text, which button label, what's disabled. No DOM in them at all. That makes them easy to test, and it keeps the DOM code in app.js dumb: it just copies fields onto elements.

cardView(courses[3], planner) // { id: 4, heading: "CS402 · Enterprise Software Development", // meta: "4 credits · Computer Science", seats: "3 seats left", // inPlanner: false, buttonLabel: "Add", disabled: false } summaryView(planner) // { count: 3, credits: 10, overLimit: false, text: "3 courses · 10 credits" } statusView(state) // { message: "Loading courses…", showRetry: false }

The comments above each function in the file give every case, including the singular "1 seat left" / "1 course". The tests check the exact strings.

Derived data is computed, never stored

Notice what's not in the state: the total credits, the button labels, the SGPA. They can all be worked out from what is there. If you stored the total too, every event that touches the planner would have to update it as well — and the first one that forgets makes the screen lie. Store the minimum; compute the rest on every render. (The same rule as Lab 1's stage 2: one source of truth.)

The SGPA calculator

The planner has a grade dropdown per course. That's the form; state.grades holds what's picked, and sgpaView works out the result:

GRADE_POINTS // { A: 10, "A-": 9, B: 8, "B-": 7, C: 6, D: 5, F: 0 } // SGPA = Σ (credits × grade points) / Σ credits — over the courses that HAVE a grade // CS402 (4 cr) A, MA101 (4 cr) B, HS101 (2 cr) not picked yet: // (4×10 + 4×8) / (4 + 4) = 72 / 8 = 9.00 sgpaView(planner, { 4: "A", 10: "B" }) // { graded: 2, total: 3, credits: 8, sgpa: 9, text: "SGPA 9.00 · 2 of 3 courses graded" }

A filter for the graded courses, two reduces, one division — Lab 1 · §11. Two details the tests check: sgpa is rounded to 2 decimals as a number (Math.round(x * 100) / 100), and the text always shows 2 decimals (toFixed(2): 9 → "9.00"). Make sure an ungraded course counts neither in the top nor in the bottom of the fraction.

Q1Why does cardView take the planner, not just the course?
Show answer

Because what a card shows depends on both: "Add" or "Remove", and whether a full course's button is disabled, depend on whether it's in the planner. A view takes everything its output depends on — and nothing it doesn't.

const [getState, setState] = useState(initialState, render); const dispatch = (event) => setState((state) => transition(state, event));

Two lines, and they're the whole architecture. dispatch is the one door into the state: give it an event, it runs the transition on the current state (an updater function — Lab 1 · §15), and useState redraws if the result is a new object. 08

Redraw only what changed

Corerender() with reference checks

Your render() redraws all five regions on every event. It works — but watch what it costs.

Do this now — find the problem

  1. Add console.count("renderCourses") as the first line of renderCourses. Type a word in the search box and pick a few grades. Every keystroke and every grade rebuilds all the cards — and neither changes a single card.
  2. Add two courses. Now use only the keyboard: Tab to the first grade dropdown and pick a grade (arrow keys; on a Mac Space, arrows, Enter). Then try to pick a different grade the same way, without touching the mouse. Then type document.activeElement in the console.

The second one is the real bug. Picking a grade dispatches SET_GRADE, render rebuilds the planner, and the dropdown you were using is thrown away and replaced by an identical new one. Focus was on the old one, so it's gone: document.activeElement is <body>, your keys now scroll the page instead of changing the grade, and a screen reader loses its place. For anyone not using a mouse, the form is close to unusable. The same thing would wipe a half-typed input, a text selection, or a scroll position inside a region.

The fix: compare references

Each region depends on a few fields of the state. Redraw it only if one of those fields is a different object from last time:

RegionDepends on
renderDepartmentsdepartments, department
renderStatusstatus, error, courses
renderCoursescourses, planner
renderPlannerplanner
renderSgpaplanner, grades

Keep the previous state in a variable outside render. On each render, a region whose fields are all === to last time is skipped. On the very first render there is no previous state, so everything draws. One region, to show the idea:

let previous = null; function render() { const state = getState(); if (previous === null || previous.planner !== state.planner) renderPlanner(state); // … the other four, with their own fields previous = state; }

Write it for all five — a small helper like changed("courses", "planner") keeps it readable. Then repeat both experiments: the counter stays still while you type, and the focus stays on the dropdown.

Why a !== check is enough

Comparing contents would mean walking every course in two arrays on every render. You don't need to, because of the rule you've followed since Lab 1 · §10: data is never changed in place. If planner is the same object as last time, it cannot have different contents. If anything in it changed, the transition made a new array. A cheap reference check is a complete answer — but only because every transition is immutable.

The bug this exposes

Write state.planner.push(course); return { ...state }; in ADD (the tests would catch it, but imagine they didn't). The state is a new object, so useState redraws — but planner is the same array, so renderPlanner is skipped. The course is in the data and not on the screen. That's the most common React bug there is, reproduced in your own code: React makes exactly the same reference check.

In React, this becomes…

React re-runs your component function on every state change, and then compares what it returned with last time, element by element, touching only the real DOM nodes that differ — so a <select> whose props didn't change is the same element and keeps its focus. That comparison is called reconciliation. And React.memo, useMemo and the dependency arrays of useEffect all decide "did this change?" the way you just did: with Object.is on references.

Q1The search box is never redrawn by any region. Why does that matter?
Show answer

If a region rebuilt the input on every keystroke, you'd lose the focus and the cursor after each letter, and typing would be impossible. The search box's value lives in the input itself and is copied into the state, not drawn from it. React calls that an uncontrolled input; when React does draw it from state (a controlled input), reconciliation is what keeps it from being replaced.

09

Responses that arrive out of order

Coresrc/s09-latest.js

Do this now — break it

  1. Network → Random. The server now takes anywhere from 0.1 to 1.5 seconds per request.
  2. Click Electronics, Humanities, Mathematics — quickly, one after another.
  3. Wait. Mathematics is highlighted. Which department's courses are listed? Try it a few times.

Often the list ends up showing Electronics or Humanities under a highlighted Mathematics button. Open the Network tab and you'll see why: three requests went out, and they came back in whatever order the server finished them. Each one, when it arrived, dispatched LOAD_OK — so whichever arrived last won, not whichever was asked for last. Typing "learn" in the search box sends five requests and has the same problem.

This is a race condition: the result depends on timing you don't control. It doesn't show up on your fast local machine with Network on Normal — which is exactly why it ships, and shows up for the user on a slow phone connection.

Exercise — only the latest call counts

Each load() should ask: by the time my response arrived, was I still the latest request? If not, throw the result away. createLatestOnly() returns a function track(promise) that answers that question:

const track = createLatestOnly(); const result = await track(fetchCourses(filters, fetchWithNetwork)); if (!result.stale) dispatch({ type: "LOAD_OK", courses: result.value }); // result is { stale: false, value } — or { stale: true } if a newer track() started meanwhile

Inside, it's a closure with a counter (Lab 1 · §06): every call to track takes the next number, and when its promise settles, it compares its number with the latest one. If the promise rejects, rethrow only if it's the latest — nobody cares that an old, abandoned request failed. Make the s09 tests pass, use track in load(), and repeat the experiment: the list now always matches the button.

Ignoring isn't cancelling

The stale requests still run to the end; you just ignore their answers. The browser can also cancel a request: AbortController gives you a signal to pass as fetch(url, { signal }), and controller.abort() stops it. That saves bandwidth but needs more code, and you still need the "is this the latest?" check for anything that isn't a fetch. Look it up if you're curious; it isn't part of this lab.

In React, this becomes…

Loading data in React happens in useEffect, and the classic way to avoid exactly this race is a flag in the effect's cleanup: let ignore = false; … if (!ignore) setCourses(data); … return () => { ignore = true; };. React runs the cleanup of the old effect before starting the new one. Same idea as track: a closure that knows whether it's still current.

Stretch — debounce the search

Even with track, typing "learning" sends eight requests to use one. Write debounce(fn, ms): it returns a function that waits until it hasn't been called for ms milliseconds, then calls fn once, with the last arguments. Use it for the search box only (a click should load at once):

const loadSoon = debounce(load, 250); // in the search handler: dispatch SET_QUERY, then loadSoon()

Another closure: it remembers the pending setTimeout and cancels it with clearTimeout each time it's called again. Watch the Network tab while you type — one request. npm run test:stretch.

Q1With track in place, you click Electronics then Mathematics, and the Mathematics request fails while the Electronics one succeeds. What does the page show?
Show answer

The error, with Try again. Electronics' response is stale and is ignored; the Mathematics failure is the latest call's, so it's rethrown and becomes LOAD_FAIL. Showing Electronics' courses under a Mathematics button would be the old bug again.

10

Other servers — public APIs and CORS

Stretchwhy some fetches fail before they start

Your app only talks to the server it came from. Real apps call other servers too — and the first time you try, you may meet this in the console:

Access to fetch at 'https://example.com/' from origin 'http://localhost:5500' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Origins

An origin is scheme + host + port: http://localhost:5500 and http://localhost:5501 are different origins. By default, a page's JavaScript may send a request to another origin, but it's not allowed to read the response — unless that server says so, with an Access-Control-Allow-Origin header. That's CORS, Cross-Origin Resource Sharing. It protects you: without it, any website you visit could quietly read your mail or your bank page using your logged-in cookies.

Do this now — see both sides

  1. With the app open, in its console: await fetch("https://dummyjson.com/quotes/random").then((r) => r.json()). It works: DummyJSON is a public API that sends the header, allowing every origin.
  2. Now await fetch("https://example.com/"). "Failed to fetch", and the CORS message above. The request was sent; example.com answered; the browser refused to hand the answer to your code. Find the request in the Network tab.
  3. Start a second copy of the server on another port: in a second terminal, PORT=5501 npm run web (Windows Command Prompt: set PORT=5501 && npm run web). Open localhost:5501/web/, and in its console fetch http://localhost:5500/api/courses. Blocked — same machine, same code, different port.

The lesson: a CORS error is fixed on the server, never in your fetch. The server has to send the header for your origin. You'll do exactly that in the Spring Boot backend when the React app (on port 5173) starts calling the API (on 8080).

Try it — a quote under the header

Use your own getJSON to show a random quote at the top of the page: fetch https://dummyjson.com/quotes/random once on start, and put quote and author in a new element. Should the quote go in the app state, with its own events? Think about what happens if the request fails, and what the user should see.

Public APIs have limits

A whole lab of students behind one college network looks like one very busy user to an API, and many free APIs limit requests per address per hour. Don't call one in a loop, or on every keystroke.
