Sending a request

curl sends one HTTP request from the terminal and prints the answer. It comes with macOS, Linux and current Windows.

$ curl http://localhost:8080/api/products/get-all [{"category":"Electronics","description":"15-inch laptop for everyday use","id":1, …}, …] $ curl -i http://localhost:8080/api/products/get/1 # -i also prints the status line and the headers $ curl -v http://localhost:8080/api/products/get/1 # -v also prints what curl sent

On Windows

In PowerShell, type curl.exe, not curl: plain curl there is a different command. For requests with a JSON body (section 11), Postman or Swagger (section 13) is less fiddly than quoting JSON in PowerShell.

Postman does the same with a form: method, URL, and for POST and PUT a body (Body → raw → JSON). A browser can only send GET requests from the address bar, which is why the lab used it for the GET endpoints only.

02

How one request travels

CoreGET /api/products/get/1, to MySQL and back

The lab's central slide, How One Request Travels, followed GET /api/products/get-all through the layers. Here is its sibling, GET /api/products/get/1, on the same trip, with every box named after code you wrote. Every later section zooms into one box of this picture.

The nine steps, against your code

Line numbers are in controller/ProductController.java and service/ProductService.java at tag lab1-complete.

StepWhat happensYour code
1curl connects to port 8080 and sends a few lines of text: the request. Tomcat, the web server Spring Boot started inside your app, reads them and hands the request to Spring's DispatcherServlet. It finds the method whose annotations match GET and /api/products/get/{id}, turns the text "1" into the Long 1, and calls it.Controller, lines 25–26
2Your controller asks the service.Controller, line 28
3The service asks the repository.Service, line 21
4The object behind your repository interface asks Hibernate to load Product 1. Hibernate writes the SQL, borrows a database connection, and sends it.none (section 07)
5MySQL finds the row with id 1.your table
6One row comes back. Hibernate creates an empty Product and fills each field from a column.Product.java
7findById returns an Optional<Product>; .orElse(null) unwraps it.Service, line 21
8The product isn't null, so the controller returns ResponseEntity.ok(product).Controller, lines 30–35
9Spring reads the ResponseEntity: status 200, body a Product. Jackson turns the Product into JSON by calling its getters. Tomcat sends it back.none (section 09)

What actually travels: text

HTTP is plain text. curl -v prints both halves: lines starting > are what curl sent, lines starting < are what came back. Without the arrows, the request is:

GET /api/products/get/1 HTTP/1.1 Host: localhost:8080 User-Agent: curl/… Accept: */*
first lineThe method (GET), the path, and the protocol version.
headersOne per line, Name: value. Accept: */* means "any format will do". A GET has no body, so the request ends here.

And the response:

HTTP/1.1 200 Content-Type: application/json {"category":"Electronics","description":"15-inch laptop for everyday use","id":1,"name":"Laptop","price":65000.00,"stock":10}
status lineThe status code: 200 means it worked. Tomcat leaves out the word "OK"; the number is what counts. Section 10 has the codes you'll meet.
Content-TypeHow to read the body: here, as JSON. curl shows a few more headers (a date, how the body is sent); your code didn't set those.
blank line, then bodyThe JSON Jackson wrote from the Product. The keys come out in alphabetical order; section 09 says why.

The SQL in your console

Because your application.properties turns on show-sql and format_sql, Hibernate prints each statement it sends:

Hibernate: select p1_0.id, p1_0.category, p1_0.description, p1_0.name, p1_0.price, p1_0.stock from products p1_0 where p1_0.id=?

You didn't write it; Hibernate did, from your entity: the table name from @Table, one column per field. p1_0 is a short alias Hibernate makes up for the table. The ? is a placeholder: the value 1 travels separately from the SQL text, so a value can never be mistaken for SQL. (A stretch box in section 07 shows how to see the values.) One request, one SELECT.

Try it — follow the request yourself

  1. curl -v http://localhost:8080/api/products/get/1. Find the request lines (>), the status line, the Content-Type and the JSON.
  2. Look at the console: one select … where p1_0.id=?. Send the same request again: another select. Each request goes all the way to MySQL.
  3. curl -i http://localhost:8080/api/products/get/999: a 404 and your own sentence. The console still shows one select. The lookup ran, and found nothing.
  4. curl -i http://localhost:8080/api/products/get/abc: a 400, and no select at all. Spring couldn't turn abc into a Long at step 1, so your method never ran.
Q1Which of your classes decides that GET /api/products/get/1 should run getProductById?
Show answer

None of them. Spring's DispatcherServlet decides, at step 1, using the annotations you put on the controller: @RequestMapping("/api/products") on the class and @GetMapping("/get/{id}") on the method. Section 09 shows how it matches.

Q2At which step does a Product object first exist? At which step does JSON first exist?
Show answer

The Product appears at step 6, when Hibernate builds it from the row. JSON appears only at step 9, when Jackson writes it. Between them, your classes pass ordinary Java objects; none of your code ever touches JSON or SQL text.

What Initializr gave you

Corepom.xml, mvnw, the application class, auto-configuration

At tag lab1-start the project had two Java files, and neither was yours. This section is about what those files and Spring Boot do every time you press Run, before any line of yours is involved.

pom.xml: the libraries you asked for

On Spring Initializr you ticked Spring Web, Spring Data JPA, MySQL Driver, Lombok and Springdoc OpenAPI. They became this (pom.xml at lab1-start, lines 5–10 and 32–66, trimmed):

<parent> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-parent</artifactId> <version>4.1.1</version> </parent> … <dependencies> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-data-jpa</artifactId> </dependency> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-webmvc</artifactId> </dependency> <dependency> <groupId>org.springdoc</groupId> <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId> <version>3.1.0</version> </dependency> <dependency> <groupId>com.mysql</groupId> <artifactId>mysql-connector-j</artifactId> <scope>runtime</scope> </dependency> <dependency> <groupId>org.projectlombok</groupId> <artifactId>lombok</artifactId> <optional>true</optional> </dependency> <!-- plus spring-boot-starter-data-jpa-test and spring-boot-starter-webmvc-test, scope test --> </dependencies>

A starter is a dependency with no code of its own: it pulls in a set of libraries that are known to work together. One line in your pom, a dozen libraries on the classpath.

spring-boot-starter-parentPicks a version for every library Spring Boot knows about. That's why the starters have no <version>. springdoc isn't one of them, so it carries its own.
…-starter-webmvc"Spring Web" on Initializr. Brings Spring MVC (DispatcherServlet, @RestController, @GetMapping…), an embedded Tomcat, and Jackson for JSON. On Boot 3 this starter was called spring-boot-starter-web.
…-starter-data-jpaBrings Hibernate (it writes the SQL), Spring Data JPA (JpaRepository) and HikariCP (a pool of open database connections).
mysql-connector-j, runtimeThe JDBC driver: the code that speaks MySQL's network protocol. runtime means "needed to run, never imported by your code" — you never write a MySQL class name.
lombok, optionalWrites getters, setters and constructors while compiling (B0). Not needed once the code is compiled.
springdoc-…-uiThe Swagger page (section 13). Boot 4 needs springdoc 3.x; Boot 3 used 2.x.
the two -test startersJUnit, MockMvc and friends, for tests (B4). On Boot 3 there was one spring-boot-starter-test.

mvnw: Maven without installing Maven

mvnw (macOS, Linux) and mvnw.cmd (Windows) are the Maven wrapper. The first time you run one, it downloads the exact Maven version named in .mvn/wrapper/maven-wrapper.properties, then uses it. IntelliJ has its own Maven, so you didn't need the wrapper in the lab; it's for the terminal, and for anyone who clones the project.

$ ./mvnw spring-boot:run # Windows: mvnw.cmd spring-boot:run — the same app, the same log, no IntelliJ. Ctrl+C stops it.

The one class Initializr wrote

EcommerceApplication.java, unchanged since lab1-start:

package com.esd.ecommerce; import org.springframework.boot.SpringApplication; import org.springframework.boot.autoconfigure.SpringBootApplication; @SpringBootApplication public class EcommerceApplication { public static void main(String[] args) { SpringApplication.run(EcommerceApplication.class, args); } }

@SpringBootApplication is three annotations in one:

@SpringBootConfigurationThis class is configuration: it may define beans (section 04).
@EnableAutoConfigurationSwitch on auto-configuration, below.
@ComponentScanLook for your classes, starting from this class's package. More on that at the end of this section.

SpringApplication.run(…) creates Spring's container, runs the scan and the auto-configuration, starts Tomcat, and returns. main then ends, but Tomcat's threads keep the program alive, waiting for requests.

Auto-configuration: what you didn't write

You never wrote code that opens MySQL connections, or turns objects into JSON, or listens on a port. Spring Boot set all of that up at startup, by looking at two things: which libraries are on the classpath (your pom), and what's in application.properties. Each auto-configuration is a rule of the form "if this library is present, and you haven't defined your own, create one of these".

You haveSpring Boot creates
MySQL driver + spring.datasource.urla DataSource: a HikariCP pool of connections to that database
Hibernate + that DataSourcean EntityManagerFactory: Hibernate, set up from the spring.jpa.* properties
Spring Data JPAan object for each interface that extends JpaRepository (section 07)
Spring MVC + Tomcatan embedded Tomcat on port 8080, and the DispatcherServlet
Jacksonthe JSON mapper used for every @RequestBody and every object you return
springdoc/v3/api-docs and the Swagger UI page

The TA called Spring Boot "convention over configuration": the conventions are these defaults, and application.properties is where you change them. For example, server.port=8081 moves Tomcat to another port.

Read your startup log

Every one of those rules leaves a trace when you press Run. Here are the lines that matter. Each real line also starts with a timestamp, a level (INFO, WARN), a thread and a logger name, and there are more lines between these:

Starting EcommerceApplication using Java 17… Tomcat initialized with port 8080 (http) HikariPool-1 - Starting... HikariPool-1 - Start completed. Initialized JPA EntityManagerFactory for persistence unit 'default' spring.jpa.open-in-view is enabled by default. Therefore, database queries may be performed during view rendering. … Tomcat started on port 8080 (http) … Started EcommerceApplication in … seconds …

Tomcat comes up, the connection pool connects to MySQL, Hibernate starts, and the app reports it's ready. The one WARN you see every time, about open-in-view, is about how long Hibernate keeps its session open during a request. It's harmless in this app; leave it.

Your first request adds one more line: Initializing Spring DispatcherServlet 'dispatcherServlet'. Spring sets the DispatcherServlet up lazily, on the first request, not at startup.

Try it — see what auto-configuration did

  1. Restart your app and find each line above in the console. Send one request and find the DispatcherServlet line.
  2. Add debug=true to application.properties and restart. Search the console for CONDITIONS EVALUATION REPORT. Under Positive matches is every auto-configuration that switched on, and why. Find DataSourceAutoConfiguration.
  3. Remove debug=true again. The report is long.

Component scan: why the main class sits in the top package

@ComponentScan starts at the package of EcommerceApplication, com.esd.ecommerce, and looks in it and in every package below it: com.esd.ecommerce.controller, .service, .repository, .entity. Any class there marked @RestController, @Service, @Repository or @Component becomes a bean (section 04). The same starting package is used to find your entities and your repositories.

That's why Initializr puts the application class at the top of your packages, and why all your classes go below it. A class anywhere else is invisible to Spring.

The silent 404

A controller in the wrong package doesn't fail loudly. The app starts with no error, and every URL of that controller answers 404. It's easy to do by accident in IntelliJ: create a package called com.esd.controller instead of com.esd.ecommerce.controller, and you've done it.

Q1Your pom has no <version> for spring-boot-starter-data-jpa. Which version do you get?
Show answer

The one spring-boot-starter-parent 4.1.1 picks. The parent manages versions for every library Spring Boot knows about, so they all match each other.

Q2You add com.esd.shop.CartController with @RestController and @GetMapping("/cart"). The app starts without errors, and GET /cart is a 404. Why?
Show answer

com.esd.shop isn't com.esd.ecommerce or below it, so the component scan never sees the class. It never becomes a bean, and its mapping is never registered. Move it to com.esd.ecommerce.controller.

04

Beans, and who fills in @Autowired

Corethe container, field injection, constructor injection

From service/ProductService.java, tag lab1-get, lines 10–14:

@Service public class ProductService { @Autowired private ProductRepository productRepository;

And the same pattern in controller/ProductController.java (lab1-complete, lines 12–17):

@RestController @RequestMapping("/api/products") public class ProductController { @Autowired private ProductService productService;

Nobody in your code writes new ProductService(). Nobody writes new ProductRepository() either; you couldn't, it's an interface. Yet productRepository isn't null when getAllProducts runs. Who made these objects, and who put one inside the other?

The container and its beans

At startup Spring creates an application context, usually called the container: a collection of objects that Spring creates, wires together and keeps for the life of the app. Each of those objects is a bean. Your app's beans come from three places:

  • the classes the component scan finds with a stereotype annotation: your controller and your service;
  • the objects auto-configuration makes (section 03): the DataSource, Hibernate, Jackson's mapper, Tomcat…;
  • one object per repository interface, made by Spring Data (section 07).
AnnotationMeans
@Component"Make one of these and keep it." The other three are @Component with a more specific name.
@ServiceA component that holds application logic. Yours: ProductService.
@RepositoryA component that talks to the database. Yours: ProductRepository.
@RestControllerA component that handles HTTP requests (section 09). Yours: ProductController.

By default there is one of each bean. One ProductService is made at startup and shared by every request, on every Tomcat thread, until the app stops.

One object, many requests at once

Because the service is shared, a field like private Product lastProduct; in it would be shared by every request in flight. Keep per-request data in local variables and parameters. Fields in a bean are for its dependencies, like productRepository.

Dependency injection

ProductService needs a ProductRepository to do its job: that's a dependency. The class doesn't create it; it only declares that it needs one, and the container supplies it. That's dependency injection. The container works out the order: repository first, then the service with the repository put in, then the controller with the service put in.

How @Autowired on a private field works

  1. The container calls ProductService's no-argument constructor. Java gives a class one when you write none. At this moment, productRepository is null.
  2. It looks for fields marked @Autowired, finds a bean of the field's type (there is exactly one ProductRepository), and sets the private field using reflection: Java's way for a library to reach into an object's private members while the program runs.
  3. Only then does anyone else get the bean.

So it works, but only when Spring builds the object. Build it yourself and nobody fills the field:

ProductService service = new ProductService(); // the lab's class service.getAllProducts(); // NullPointerException: productRepository is null

Constructor injection: what Lab 2 switched to

Lab 2 wrote the same service like this (service/ProductService.java at lab2-complete, lines 14–18):

@Service @RequiredArgsConstructor public class ProductService { private final ProductRepository productRepository;

@RequiredArgsConstructor is Lombok: it writes a constructor that takes one argument for every final field (B0 shows the generated code). Without Lombok, the class would be:

@Service public class ProductService { private final ProductRepository productRepository; public ProductService(ProductRepository productRepository) { this.productRepository = productRepository; } public List<Product> getAllProducts() { return productRepository.findAll(); } // … the other methods, unchanged }

When a class has exactly one constructor, Spring uses it to create the bean and passes in a bean for each parameter. No @Autowired is needed; it's allowed, just unnecessary. The controller works the same way:

@RestController @RequestMapping("/api/products") public class ProductController { private final ProductService productService; public ProductController(ProductService productService) { this.productService = productService; } // … the same methods as before }

Why constructor injection is the usual choice

finalThe field is set once, in the constructor, and can never be null or replaced afterwards. The compiler checks it.
visibleThe constructor lists everything the class needs. A constructor with eight parameters tells you the class is doing too much; eight @Autowired fields hide it.
testable without Springnew ProductService(fakeRepository) works in a plain unit test. The lab's version, made with new, has a null repository (above).
no half-built objectsIf a dependency is missing, the object can't be created at all, so there's never a moment when it exists with a null field.

Both styles work, and Spring supports both. Field injection is the shortest thing to type, which suits a live session. Lab 2, the contract backend, and most Spring code you'll read use constructors, and the Spring reference documentation recommends constructor injection for dependencies a class can't work without.

Try it — take a bean away

  1. Remove @Service from ProductService and restart. The app stops, and the console shows:
*************************** APPLICATION FAILED TO START *************************** Description: Field productService in com.esd.ecommerce.controller.ProductController required a bean of type 'com.esd.ecommerce.service.ProductService' that could not be found. … Action: Consider defining a bean of type 'com.esd.ecommerce.service.ProductService' in your configuration.
  1. Read it as a sentence: the field productService in ProductController needs a ProductService bean, and there isn't one. Without @Service, the scan skipped the class.
  2. Put @Service back and restart.

One. Each request runs on its own Tomcat thread, but both threads call methods on the same single ProductService bean. That's fine here because the service keeps nothing per request in its fields.

The database, and what ddl-auto did

Coreapplication.properties, your hand-made table

src/main/resources/application.properties, tag lab1-db-config, all seven lines:

spring.datasource.url=jdbc:mysql://localhost:3306/ecommerceDB spring.datasource.username=root spring.datasource.password=YOUR_PASSWORD spring.jpa.hibernate.ddl-auto=update spring.jpa.show-sql=true spring.jpa.properties.hibernate.format_sql=true
datasource.urlA JDBC URL. jdbc:mysql:// picks the driver, localhost:3306 is where MySQL listens (3306 is its usual port), /ecommerceDB is the database.
username, passwordMySQL's own login, the one you use with mysql -u root -p.
hibernate.ddl-autoWhat Hibernate may do to your tables at startup. Below.
show-sqlPrint every SQL statement Hibernate sends, after Hibernate:.
…format_sqlSpread each statement over several indented lines. Anything after spring.jpa.properties. is handed straight to Hibernate.

Passwords in files

This file usually ends up in git. A local lab password there is fine; a real one never is. That's why the reference repository says YOUR_PASSWORD.

The table you made by hand

Before any Java, you ran the lab's script in the MySQL client (database/lab1_setup.sql, tag lab1-db-config):

CREATE DATABASE IF NOT EXISTS ecommerceDB; USE ecommerceDB; CREATE TABLE IF NOT EXISTS products ( id BIGINT PRIMARY KEY AUTO_INCREMENT, name VARCHAR(100) NOT NULL, description VARCHAR(500), price DECIMAL(10, 2) NOT NULL, category VARCHAR(50), stock INT NOT NULL ); DELETE FROM products; INSERT INTO products (name, description, price, category, stock) VALUES ('Laptop', '15-inch laptop for everyday use', 65000.00, 'Electronics', 10), ('Wireless Mouse', 'Ergonomic wireless mouse', 1200.00, 'Accessories', 25), ('Mechanical Keyboard', 'RGB mechanical keyboard', 3500.00, 'Accessories', 15);

The TA did this on purpose, so you'd see the real table and rows before JPA hid them behind Java objects.

What ddl-auto=update did to it

DDL (data definition language) is the part of SQL that changes structure: CREATE, ALTER, DROP. ddl-auto says how much DDL Hibernate may run at startup, comparing your entities with the tables it finds:

ValueAt startup, Hibernate…
nonedoes nothing to the schema.
validatechecks that every entity's table and columns exist, and refuses to start if one is missing.
updateadds missing tables and missing columns. Never drops or changes anything that's there.
createdrops the tables and creates them again from the entities. Your rows are gone.
create-droplike create, and drops the tables again when the app stops.

Your table already had a column for every field of Product, so update found nothing to add and ran no DDL at all; look for an alter table in your startup log and you won't find one. And since update never changes an existing column, the table kept exactly what your script gave it: VARCHAR(100), DECIMAL(10,2), and NOT NULL on name, price and stock.

Two things follow, and you can see both:

  1. Add a field, and update adds a column. Give Product a new field, restart, and the log shows an alter table products add column …; the existing rows get NULL in it. Delete the field again and the column stays. update never drops.
  2. The NOT NULLs belong to the database, not the entity. Your entity has no rule that name must be present. The table does. POST a product without a name and MySQL refuses the INSERT: you get a 500, and the log says Column 'name' cannot be null. A PUT that leaves out stock fails the same way. Checking input before it reaches the database is B2's subject.

If the table hadn't existed, update would have created it from the entity, with Hibernate's defaults: varchar(255) for every String, decimal(38,2) for the price, and no NOT NULL except on the id.

What update can't do is create the database. If ecommerceDB doesn't exist, or the URL misspells it, the app stops at startup.

Where this goes

update is a development convenience, and the TA chose it for that. Teams with real data usually hand the schema to a migration tool such as Flyway, one versioned SQL file per change, and set ddl-auto to validate or none.

Try it — break the connection, read the error

  1. In application.properties, misspell the database: …/ecommerceDBB. Restart.
  2. The app stops. The last lines may talk about a Dialect or JDBC metadata: that's Hibernate failing later, because it never got a connection. Scroll up to the first WARN or Caused by:. It says Unknown database and the name you typed.
  3. Fix the name. Now change the password to something wrong and restart: Access denied for user 'root'@'localhost'. Fix it.
  4. Stop MySQL (or don't start it) and run the app: Communications link failure. MySQL isn't listening.
Q1Your Product entity has no "not null" rule anywhere. Why does a POST without price give a 500?
Show answer

The table came from your SQL script, which says price DECIMAL(10, 2) NOT NULL. ddl-auto=update never changes an existing column, so the constraint is still there, and MySQL rejects the INSERT. The 500 is the database saying no, not your code.

Q2A teammate sets ddl-auto=create to "make sure the table is right". What happens to the three seed rows on the next start?
Show answer

They're gone. create drops the table and creates an empty one from the entity, on every start. (And the new table has Hibernate's defaults, so the NOT NULLs from your script are gone too.)

06

The entity: Product

Coreone class, one table; one object, one row

entity/Product.java, tag lab1-entity, lines 8–29 (the imports are jakarta.persistence.* and lombok.*):

@Entity @Table(name = "products") @Getter @Setter @NoArgsConstructor @AllArgsConstructor public class Product { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; private String name; private String description; private BigDecimal price; private String category; private Integer stock; }

An entity is a class whose objects are rows. JPA (Jakarta Persistence) is the standard that defines these annotations; Hibernate is the library that implements it, reads the annotations, and writes the SQL.

@EntityHibernate manages this class: one object ↔ one row. Without it, Product is an ordinary class, and the app won't start (Try it, below).
@Table(name = "products")The table's name. Leave it out and Spring Boot uses the class name in snake_case: product, which your script never created.
@IdThis field is the primary key. Every entity has exactly one.
@GeneratedValue(IDENTITY)The database assigns the id, with MySQL's AUTO_INCREMENT. So a new product's id is null until its row is inserted, and saving it has to run the INSERT straight away to learn the id.
Lombok's fourGetters, setters, a no-argument constructor and an all-arguments constructor, written for you (B0).

The no-argument constructor: who needs it

Two libraries build Product objects without knowing anything about your fields in advance, and both start the same way: create an empty object with the no-argument constructor, then fill it in.

  • Hibernate, at step 6 of section 02: an empty Product, then each field set from a column. JPA requires every entity to have a no-argument constructor for this reason.
  • Jackson, for @RequestBody (section 11): an empty Product, then one setter call per key in the JSON.

That's what @NoArgsConstructor is for. @AllArgsConstructor is for you, when you want a complete product in one line.

Fields and columns

Each field maps to the column with the same name, in snake_case: a field minStock would map to a column min_stock, and a class StockAlert to a table stock_alert. Your names are single words, so they match the script exactly.

Each field, its Java type, the column your script made, and what Hibernate would have made on its own (section 05):

id · Longscript: BIGINT AUTO_INCREMENT · Hibernate: bigint, auto-increment
name · Stringscript: VARCHAR(100) NOT NULL · Hibernate: varchar(255)
description · Stringscript: VARCHAR(500) · Hibernate: varchar(255)
price · BigDecimalscript: DECIMAL(10,2) NOT NULL · Hibernate: decimal(38,2)

stock · Integerscript: INT NOT NULL · Hibernate: integer

Why Long and Integer, not long and int? A wrapper type can be null. A new product's id is null until the database assigns one, and Spring Data uses exactly that to decide between INSERT and UPDATE (section 07). Why BigDecimal for the price? It stores decimals exactly; double can't even hold 0.10 exactly (B0).

The repository: an interface with no class

CoreJpaRepository, the proxy, save, derived queries

repository/ProductRepository.java, tag lab1-repository, lines 7–9:

@Repository public interface ProductRepository extends JpaRepository<Product,Long> { }

Three lines, no method bodies, and no class anywhere that implements the interface. Yet productRepository.findAll() returned your three rows.

What JpaRepository<Product, Long> gives you

The two type arguments say: this repository stores Product objects, and their @Id is a Long (B0 explains generics). In return, your interface inherits a set of ready methods. These are the ones the lab used, and the SQL each one prints:

findAll()Returns a List<Product>. SQL: one select … from products. Used by getAllProducts.
findById(id)Returns an Optional<Product>. SQL: one select … where id=?. Used by getProductById and updateProduct.
save(product)Returns the saved Product. SQL: an insert (no id) or an update (id set). Used by addProduct and updateProduct.
deleteById(id)Returns nothing. SQL: a select, then a delete. Used by deleteProduct (lab1-complete).
count()Returns a long. SQL: a select count(…).

findById returns an Optional because the row might not exist; your service turns "empty" into null with .orElse(null) (section 08). B0 covers Optional.

Who implements it

At startup, Spring Data JPA finds every interface in your packages that extends one of its repository types, and builds an object for each: a proxy, a class generated while the app runs, which implements your interface and passes each call on to SimpleJpaRepository, Spring Data's ready-made class with the real findAll, findById, save… That proxy is the bean the container injects into ProductService.

@Repository on the interface is optional: Spring Data finds the interface without it. It does no harm.

  1. Make this the first line of getAllProducts() in your service: System.out.println(productRepository.getClass());
  2. Restart and call get-all. The console prints something like class jdk.proxy2.$Proxy115: a class generated at startup, which exists in no source file.
  3. Remove the line.

save(): insert or update?

save looks at the id. null: a new product, so an INSERT, and the new id is put into the object. Not null: an existing product, so Hibernate makes sure it has that row loaded, copies your values onto it, and runs an UPDATE. That's how addProduct and updateProduct can both end in save().

Derived queries: a method name is a query

Lab 2 added one line to this interface (repository/ProductRepository.java at lab2-complete, line 12):

public List<Product> findByCategory(String category);

No body, and no SQL. At startup Spring Data reads the method's name: findBy, then Category, which is a field of Product. From that it builds select … from products where category=?. These are derived queries. The name is made of pieces:

PieceMeans
findBy · countBy · existsByWhat to return: the rows, how many, or whether any
Category · Name · PriceA field of Product, with a capital letter
And · OrCombine two conditions
LessThan · GreaterThan · Between · Containing · StartingWithThe comparison (plain = equals)
IgnoreCaseCompare text without caring about case
OrderBy…Asc · OrderBy…DescSort the result

A few more you could add to ProductRepository:

List<Product> findByCategoryIgnoreCase(String category); List<Product> findByPriceLessThan(BigDecimal price); List<Product> findByNameContainingIgnoreCase(String text); List<Product> findByCategoryOrderByPriceAsc(String category); long countByCategory(String category); boolean existsByName(String name);

With the three seed rows: findByPriceLessThan(new BigDecimal("5000")) gives the mouse and the keyboard; findByNameContainingIgnoreCase("key") gives the keyboard; findByCategoryOrderByPriceAsc("Accessories") gives the mouse, then the keyboard; countByCategory("Accessories") is 2.

Case, and which database you're on

MySQL compares text without caring about case by default, so on your MySQL findByCategory("accessories") also finds the two Accessories products. Many other databases (H2, which tests often use, and PostgreSQL) find nothing. If you mean "ignore case", say so in the name: IgnoreCase.

The service: load, change, save

CoreProductService, method by method

service/ProductService.java at lab1-put, lines 16–43 (the class and its field are in section 04):

public List<Product> getAllProducts() { return productRepository.findAll(); } public Product getProductById(Long id) { return productRepository.findById(id).orElse(null); } public Product addProduct(Product product) { return productRepository.save(product); } public Product updateProduct(Long id, Product product) { Product existingProduct = productRepository.findById(id).orElse(null); if (existingProduct == null) { return null; } existingProduct.setName(product.getName()); existingProduct.setDescription(product.getDescription()); existingProduct.setPrice(product.getPrice()); existingProduct.setCategory(product.getCategory()); existingProduct.setStock(product.getStock()); return productRepository.save(existingProduct); }
getAllProductsStraight through to findAll().
getProductByIdUnwraps the Optional: the product, or null for "not found". The controller checks for that null (section 10). Lab 2 replaced the null with an exception, ProductNotFoundException (B2).
addProductA product that came from a request has no id, so save runs an INSERT and returns it with its new id.
updateProductLoad, change, save. Below.

Most of these methods are a single repository call, which is normal for a first version. The service is where an application's rules go as it grows (Lab 2 added "not found" handling and trimming of names here). Keeping it apart from the controller means those rules don't care whether a call came over HTTP, from a test, or from another service.

"Why not call the repository from the controller?"

A fair question: it would work today. The split keeps HTTP (paths, status codes, JSON) in the controller and the application's logic in the service, so each can change without the other. When the logic grows, it grows in one place.

PUT is load, change, save

  1. Load. findById(id) gets the product as it is now, or null, and then the method returns null (the controller turns that into a 404).
  2. Change. Copy five fields from the request's Product onto the loaded one. Not the id: the id comes from the URL. If the JSON body also has an "id", it's ignored here.
  3. Save. save(existingProduct): it has an id, so Hibernate runs an UPDATE.

In the console, a PUT prints a select (the load) and then an update (the save).

Copying every field has a consequence: it's a full replacement. A key missing from the JSON is null in the request's Product, and that null is copied over the real value. Send a PUT without description and the description is gone. Send one without stock and your MySQL table's NOT NULL rejects the UPDATE with a 500 (section 05). That's what PUT means: "here is the whole new version". The HTTP method for "change only these fields" is PATCH; the lab doesn't have one.

Q1PUT /api/products/update/1 with the body {"id": 3, "name": "Gaming Laptop", …}. Which row changes, 1 or 3?
Show answer

Row 1. The service loads product 1 (the id from the URL) and copies only name, description, price, category and stock. The "id": 3 was set on the request's Product by Jackson, and then never used.

Show answer

Two statements: a select … where p1_0.id=? from findById, then an update products set … where id=? from save.

{id} in the pattern is a path variable. @PathVariable Long id says: take that part of the path, convert it to a Long, pass it in. They're matched by name: {id} goes to the parameter called id.

How Spring picks the method

At startup, Spring collects every mapping from every controller. For each request, the DispatcherServlet compares the request's method and path with that list:

RequestWhat happens
GET /api/products/get-allgetAllProducts() runs.
GET /api/products/get/1getProductById(1) runs.
GET /api/products/get/abcThe path matches, but abc isn't a Long. 400, and your method never runs. Same for get/1.5.
POST /api/products/get-allThe path exists, but not for POST. 405 Method Not Allowed, with an Allow header naming GET.
GET /api/products/get-alNothing matches. 404, with Spring Boot's own error JSON (section 10).

Paths aren't the only way to pass values. A query parameter, as in /api/products?category=Accessories, reaches a method through @RequestParam. The lab didn't use any (Lab 2's category search put the category in the path, /get-category/{category}); the contract's catalogue filters do (contract §09).

JSON out: Jackson

getAllProducts returns a List<Product> inside the ResponseEntity. Spring hands it to Jackson, which:

  • calls each getter (getId(), getName()…, the ones Lombok's @Getter wrote) and uses the name after get, first letter lowercased, as the key. Jackson reads getters, not your private fields;
  • writes a List as a JSON array […], one object per product;
  • writes a BigDecimal as a number that keeps its two decimals: 65000.00;
  • writes a null field as null; the key is still there.
[ {"category":"Electronics","description":"15-inch laptop for everyday use","id":1,"name":"Laptop","price":65000.00,"stock":10}, {"category":"Accessories","description":"Ergonomic wireless mouse","id":2,"name":"Wireless Mouse","price":1200.00,"stock":25}, {"category":"Accessories","description":"RGB mechanical keyboard","id":3,"name":"Mechanical Keyboard","price":3500.00,"stock":15} ]

curl prints that on one line; it's spread out here. The array's order is whatever order MySQL returned: findAll() has no ORDER BY, so no order is promised, even if it's usually by id.

Why are the keys in alphabetical order?

Spring Boot 4 uses Jackson 3, which sorts an object's keys alphabetically by default. On Boot 3, with Jackson 2, they came out in field order. It doesn't matter to any client: a JSON object's keys have no order, and a client reads them by name. (Jackson 3 lives in packages starting tools.jackson, Jackson 2 in com.fasterxml.jackson. Your code never imports either, so nothing else changes for you.)

CoreResponseEntity, and what a String body means

ResponseEntity: the whole response

A ResponseEntity carries a status, headers and a body. You built three kinds in the lab, and Lab 2 added a fourth:

ResponseEntity.ok(x)Status 200, body x.
.status(HttpStatus.CREATED).body(x)Status 201, body x (section 11).
.status(HttpStatus.NOT_FOUND).body(…)Status 404, with whatever body you give it.
.noContent().build()Status 204, no body at all (Lab 2's delete).

If a method returns a plain Product instead of a ResponseEntity, Spring always sends 200. ResponseEntity is how you choose.

The status codes you've met

CodeMeansWhere you saw it
200 OKIt worked; here's the body.get-all, get/1, update, Lab 1's delete
201 CreatedA new resource exists; here it is.add-product
204 No ContentIt worked; there's no body.Lab 2's delete
400 Bad RequestThe request itself is wrong.get/abc; broken JSON in a POST
404 Not FoundNothing there.get/999 (yours); a mistyped path (Spring's)
405 Method Not AllowedThe path exists, not with this method.POST to get-all
415 Unsupported Media TypeThe body isn't in a format this endpoint reads.a POST body sent as Text instead of JSON
500 Internal Server ErrorThe server failed.a POST without name (section 05)

The first digit is the family: 2xx success, 4xx the client got something wrong, 5xx the server did.

Why ResponseEntity<?>

The method returns a Product on one branch and a String on the other. One return type has to cover both, so it's ResponseEntity<?>: a ResponseEntity of anything (B0 explains the ? wildcard). The price is that the compiler no longer checks what goes inside.

What the String body means for a client

Compare what curl -i shows for the two branches:

HTTP/1.1 200 Content-Type: application/json {"category":"Electronics","description":"15-inch laptop for everyday use","id":1,"name":"Laptop","price":65000.00,"stock":10}
HTTP/1.1 404 Content-Type: text/plain;charset=UTF-8 Product with ID 999 not found

Spring picks the body's format from its Java type. An object goes through Jackson and becomes JSON. A String is sent as it is, as plain text. So:

  • A client that reads every response as JSON, as most front-end code does with response.json(), fails on this 404: Product with ID 999 not found isn't JSON.
  • Your 404 (no such product) and Spring's 404 (no such URL) look different: Spring's is JSON with "status", "error" and "path" keys; yours is a sentence. A client has to handle both.

That's why Lab 2 changed it: getProductById throws a ProductNotFoundException, and one handler turns every error into the same JSON shape, ApiErrorResponse. B2 explains how. The contract asks for exactly that: one JSON error shape for every non-2xx response (contract §10).

For comparison, here is Spring Boot's own error, for get/abc (you didn't write this one; the timestamp is cut short):

{"timestamp":"…","status":400,"error":"Bad Request","path":"/api/products/get/abc"}

  2. curl -i http://localhost:8080/api/products/get-al (mistyped). A 404 too, but JSON, from Spring Boot. No SQL appears in your console: none of your code ran.

Core@RequestBody, 201, idempotence, DELETE

controller/ProductController.java, tags lab1-post and lab1-put, lines 38–59:

@PostMapping("/add-product") public ResponseEntity<Product> addProduct(@RequestBody Product product) { Product savedProduct = productService.addProduct(product); return ResponseEntity.status(HttpStatus.CREATED).body(savedProduct); } @PutMapping("/update/{id}") public ResponseEntity<?> updateProduct( @PathVariable Long id, @RequestBody Product product) { Product updatedProduct = productService.updateProduct(id, product); if (updatedProduct == null) { return ResponseEntity.status(HttpStatus.NOT_FOUND) .body("Product with ID " + id + " not found"); } return ResponseEntity.ok(updatedProduct); }

@RequestBody: from JSON to a Product

A GET carries everything in its URL. A POST or a PUT also carries a body, and here that body is the product, as JSON:

POST /api/products/add-product HTTP/1.1 Host: localhost:8080 Content-Type: application/json { "name": "USB-C Hub", "description": "7-in-1 USB-C Hub", "price": 2499.00, "category": "Accessories", "stock": 20 }

@RequestBody Product product tells Spring: read the body, and turn it into this parameter. Spring first checks the Content-Type header, which must say application/json. Then Jackson creates an empty Product with the no-argument constructor and calls one setter for each key in the JSON: setName("USB-C Hub"), setPrice(2499.00)… Your method receives a ready object. The answer:

HTTP/1.1 201 Content-Type: application/json {"category":"Accessories","description":"7-in-1 USB-C Hub","id":4,"name":"USB-C Hub","price":2499.00,"stock":20}

What Jackson does with the keys it finds, and doesn't find:

a key with a setterSet on the Product.
a key you leave outNever set, so the field stays null. Leave out description in a POST and the new product has none.
a key Product doesn't haveIgnored, no error: "colour": "red" just disappears. (That's Jackson 3's default, and the contract's rule too.)
an "id" keySet as well. Then save() sees an id and runs an UPDATE instead of an INSERT: POST with "id": 1 overwrites the laptop, and still answers 201. Lab 2's request class, ProductRequest, has no id field at all, which closes this door (B2).
not JSON at allA trailing comma, single quotes, a missing value: 400 before your method runs, and the log has a WARN naming HttpMessageNotReadableException.
not application/jsonIn Postman, a body left on Text is sent as text/plain. 415 Unsupported Media Type.

201 Created

201 says: this request created something new. Your code sends the saved product back, new id included, so the client learns the id without asking again. Many APIs also send a Location header with the new product's URL. Yours doesn't, and the contract allows either.

Methods, and which ones are safe to repeat

GETRead. Safe and idempotent. Yours: get-all, get/{id}.
POSTCreate. Neither safe nor idempotent. Yours: add-product.
PUTReplace the thing at this URL. Idempotent, not safe. Yours: update/{id}.
DELETERemove. Idempotent, not safe. Yours: delete/{id}.

Safe: changes nothing on the server. Idempotent: sending it twice leaves the server in the same state as sending it once. POST the USB-C Hub twice and you have two hubs, ids 4 and 5. PUT the same body to update/1 twice and product 1 ends up exactly the same; the second PUT changes nothing. DELETE product 1 twice and it's gone after the first; the second finds nothing to remove.

This matters when a request times out and nobody knows whether it arrived. A client can simply send a GET, PUT or DELETE again. Sending a POST again may create a duplicate.

Coretwo ways to name the same endpoints
The lab's URLsResource style

The lab's URLs name the action twice: in the method (GET) and in the path (get-all). That made each endpoint easy to tell apart while typing them live, and it works perfectly well.

Resource-style URLs name the action once. The path names a thing: the collection /api/products, or one item /api/products/1. The HTTP method says what to do with it. Filters go in query parameters: GET /api/products?category=Accessories. Most public HTTP APIs use this style, and so does the course's contract (contract §04).

Moving from one to the other changes only the strings in the mapping annotations, such as @GetMapping("/{id}") instead of @GetMapping("/get/{id}"). The methods, the service and everything below stay the same. Lab 2 kept the lab's style and renamed one endpoint, get/{id} to get-id/{id}, so a client written for Lab 1 needs that one URL changed.

Access denied for user 'root'@'localhost'Wrong MySQL password in application.properties (05).
Communications link failureMySQL isn't running, or isn't on port 3306 (05).
… Dialect … / … JDBC metadata …Hibernate couldn't connect to the database. The real reason is further up: one of the three rows above (05).
404, JSON with "error":"Not Found"No mapping matched: a typo in the path, or the controller is outside the package (03, 09).
404, Product with ID 5 not foundYour own 404: there's no product 5. Check get-all for the ids that exist.
405 Method Not AllowedThe wrong method for that path, e.g. POST to get-all (09).
415 Unsupported Media TypeThe body was sent as Text. In Postman: Body → raw → JSON (11).
400 on a POST or PUT, log WARN with HttpMessageNotReadableExceptionThe JSON is broken: a trailing comma, single quotes, a missing value, or no body at all (11).
500, log says Column 'name' cannot be nullA NOT NULL column from your SQL script, and the JSON left that field out (05).
Whitelabel Error PageAny error, seen in a browser. The status code is on the page (09).
cannot find symbol: method getName()Lombok isn't generating code. In IntelliJ: Settings → Build, Execution, Deployment → Compiler → Annotation Processors → Enable annotation processing.
release version 17 not supportedIntelliJ is compiling with a JDK older than 17: File → Project Structure → Project → SDK.

Reading a failed start

If the console shows an APPLICATION FAILED TO START box, read its Description first; it's written for you. If there's no box, find the last Caused by: in the stack trace: that's the root cause, and everything above it failed because of it. B4 teaches reading stack traces properly.
