01

What a webpage actually is

the whole secret

One sentence

A webpage is a text file. The browser reads it and draws it. That's it. There is nothing else going on.

That sounds too simple, and it genuinely isn't. Every website you've ever used — your bank, YouTube, GitHub — arrives at your machine as text. The browser reads that text, works out what it means, and paints pixels accordingly.

Three languages divide the work between them:

HTMLWhat things are. This is a heading, that's a paragraph, this is a text box for an email address. Structure and meaning. This document.
CSSWhat things look like. Colours, spacing, fonts, layout. A separate language with separate files.
JavaScriptWhat things do. Reacting to clicks, fetching data, changing the page after it has loaded.

Keeping those three jobs separate is the oldest good idea in web development. When people mix them up — using headings because they look big, using tables to position things — everything downstream gets harder.

What HTML stands for

HyperText Markup Language. "Markup" is the useful word: you take plain text and mark parts of it up to say what they are. Like a proofreader annotating a manuscript — this bit is a title, this bit is a quotation.

Note that it is a markup language, not a programming language. There are no variables, no loops, no logic. This isn't a criticism; it's a different job. HTML describes, JavaScript decides.

Q1Someone tells you they "wrote a program in HTML". What's wrong with that sentence?
Show answer

HTML isn't a programming language — it has no logic, no conditionals, no loops. It's a markup language that describes structure.

Pedantic-sounding, but it matters: it tells you where to look when something is wrong. If the page is showing the wrong thing, that's HTML. If it's showing the right thing in the wrong way, that's CSS. If it's not doing the right thing, that's JavaScript.

02

Your first page

hands on keyboard from here

You need almost nothing: a text editor and a browser. Use VS Code and Chrome so that what you see matches what's described here.

Do this now — make a folder and a file

$ mkdir -p ~/code/html-practice $ cd ~/code/html-practice $ code .

In VS Code, create a new file called index.html. Type this in — don't paste it:

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>My first page</title> </head> <body> <h1>Hello</h1> <p>This is my first webpage.</p> </body> </html>

Save it. Then double-click the file in your file manager, or drag it onto a browser window. There it is — a real webpage, made by you, running on your machine.

Windows: turn on file extensions first

Windows hides the .html part of filenames by default. That means you can save something as index.html, Windows quietly makes it index.html.txt, and the browser shows you raw text with no explanation.

File Explorer → View → Show → tick File name extensions. Do it now. On Mac: Finder → Settings → Advanced → Show all filename extensions.

Live Server — stop refreshing by hand

In VS Code, open the Extensions panel (the four-squares icon), search Live Server by Ritwick Dey, install it. Then right-click index.html → Open with Live Server.

Your page opens in the browser at an address like http://127.0.0.1:5500. Now change the <h1> text and press save. The browser updates by itself. From here on, save is your refresh.

Why an address instead of a file path

Live Server runs a tiny web server on your own machine. 127.0.0.1 means "this computer". You're now loading the page over HTTP, the same way a real site works — which matters later, because some browser features refuse to work on plain file:// paths.

Two settings worth turning on now

Format on SavePress Ctrl+,, search format on save, tick it. Then search default formatter and choose Prettier (install the extension if prompted). Your HTML will indent itself.
EmmetAlready built in. Type ! then Tab in an empty HTML file and VS Code writes the whole skeleton for you. Useful — but read section 03 before you rely on it.

Indentation is not decoration

Badly indented HTML is the single reason people can't find their own unclosed tag. When every element lines up with its parent, a missing </div> is visible at a glance. When it doesn't, you're hunting through 200 lines. Turn on Format on Save and never think about it again.

03

The skeleton, line by line

don't copy it blindly

Every HTML file starts the same way. Most people copy it forever without knowing what any of it does. Six lines, six explanations.

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <meta name="viewport" content="width=device-width, initial-scale=1.0"> <title>Course Registration</title> </head> <body> <!-- everything a human sees goes here --> </body> </html>
<!DOCTYPE html>"Use modern rules." It isn't a tag and it isn't part of the page. Historical baggage from the 1990s — leave it there and move on. Without it, browsers fall into "quirks mode" and lay things out the way they did in 1998.
<html lang="en">The root element — everything lives inside it. The lang attribute tells screen readers which language to pronounce, and browsers whether to offer translation. One attribute, real accessibility.
<head>Information about the page. Nothing in here is drawn on screen. It's where the title, character encoding, stylesheets and scripts get declared.
<meta charset="UTF-8">Says which alphabet the file uses. Without it, ₹ and Marathi and emoji all come out as garbage. Put it first in the head.
<meta name="viewport">Tells phones not to pretend they're a desktop screen. Without it your page renders zoomed-out and tiny on mobile. Matters the moment you touch CSS.
<title>The text in the browser tab, and the name used when someone bookmarks you. Also what Google shows as the clickable headline in search results.
<body>Everything a human actually sees.

Do this now — prove the head is invisible

Change your <title> to your own name and save. Nothing changes on the page — but look at the browser tab. That's what "the head isn't drawn" means.

Then break the charset, deliberately

Add a line with a rupee symbol and some non-English text, save, and look. Now delete the <meta charset> line and save again. Depending on your browser you'll see mangled characters — that's what that one line prevents.

<p>Fee: ₹500 · नमस्कार · 🎓</p>
Q2Which of these will appear on the screen when the page loads?
  1. The contents of <title>
  2. The contents of <body>
  3. Both
Show answer

(b) only. The <title> shows in the browser tab, not in the page. Everything inside <head> is information about the page rather than content of it.

04

Tags, elements, attributes, nesting

four words, used precisely

These four words get used interchangeably by people who don't know the difference. Learn them properly now — every error message and every piece of documentation you read assumes them.

TagThe marker itself. <p> is an opening tag, </p> is a closing tag.
ElementThe whole thing: opening tag + content + closing tag. <p>Hello</p> is one paragraph element.
AttributeExtra information, written inside the opening tag only, as name="value". lang="en", href="...", id="email".
NestingElements inside other elements. The inner one must close before the outer one does.
<p id="intro">A <strong>bold</strong> word.</p> │ │ │ │ │ └─ attribute └─ nested element └─ closing tag └─ opening tag

Nesting has to be strict

✓ correct — inner closes first <p><strong>Hello</strong></p> ✗ wrong — they cross over <p><strong>Hello</p></strong>

Think of them as boxes inside boxes. You can't close the outer box while the inner one is still sticking out of it. Browsers will try to guess what you meant and usually get it wrong in interesting ways — which is exactly the kind of bug that takes an hour to find.

Elements with nothing inside

Some elements have no content, so they have no closing tag. They're called void or self-closing elements:

<img src="logo.png" alt="Logo"> <br> <hr> <input type="text"> <meta charset="UTF-8">

You'll sometimes see them written <br /> with a slash. That's a leftover from XHTML; both work, and modern HTML doesn't need the slash.

Comments

<!-- This is a note for humans. The browser ignores it. -->

Useful for leaving yourself notes and for temporarily switching off a chunk of HTML while you debug. Be aware: comments are still sent to the browser and anyone can read them with View Source. Never put anything private in one.

Q3In <a href="page.html" target="_blank">Click</a> — name the element, the attributes, and the content.
Show answer

Element: the anchor (a) element — the whole thing from <a to </a>.

Attributes: two of them — href="page.html" and target="_blank", both inside the opening tag.

Content: the text Click.

05

Text, headings and lists

the everyday elements

Do this now — build up your body

Replace the contents of your <body> with this, saving as you go so you watch it grow.

<h1>Course Registration</h1> <p>Register for the coming semester. The deadline is <strong>31 August</strong>.</p> <h2>Available courses</h2> <ul> <li>Advanced Databases</li> <li>Distributed Systems</li> <li>Embedded Systems Design</li> </ul> <h2>How to register</h2> <ol> <li>Fill in the form below</li> <li>Check your details</li> <li>Submit before the deadline</li> </ol>

Headings are hierarchy, not size

There are six: h1 through h6. The number is the level in an outline, not how big the text looks.

The rule people break constantly

Never pick a heading level because of how big it renders. That's CSS's job — you can make an h4 enormous and an h1 tiny with two lines of CSS.

Pick the level that describes the document's structure: one h1 per page (the page's subject), h2 for its main sections, h3 for subsections of those. Don't skip levels — an h4 directly inside an h2 section is a broken outline.

This matters more than it sounds. Screen reader users navigate an unfamiliar page by jumping heading to heading, exactly the way you'd skim a textbook's contents page. A page with random heading levels is, to them, a contents page with the chapters shuffled.

Lists

<ul>Unordered list — bullets. Use when the order doesn't matter.
<ol>Ordered list — numbers. Use when it does: steps, rankings.
<li>One item. Only ever goes directly inside a ul or ol.

Lists nest — put a whole <ul> inside an <li>, not between two of them. Getting that wrong is one of the most common structural mistakes beginners make.

Emphasis, and why there are two of each

<strong>This content is important. Renders bold by default, but the meaning is importance — a screen reader may change tone for it.
<em>This content is emphasised. Renders italic. Again, the meaning is the point.
<b> and <i>Bold and italic with no meaning attached — for things like keywords or a ship's name. If you're unsure, you want strong or em.

This split — a meaningful element and a purely visual one that look identical — is a theme you'll keep meeting in HTML. The browser renders them the same. Everything else that reads your page does not.

Whitespace is collapsed

Press Enter fifty times between two paragraphs and the browser shows one space. HTML collapses runs of spaces, tabs and newlines into a single space. This is why you can indent your code however you like without affecting the output — and why you can't create gaps by hitting Enter. Spacing is CSS's job.

06

Links and images

the two that need paths

Links

<a href="https://developer.mozilla.org">MDN docs</a> <a href="about.html">About this course</a> <a href="#forms">Jump to the form below</a> <a href="mailto:someone@example.com">Email us</a>

href means "hypertext reference" — where the link goes. Four kinds worth knowing: a full URL to another site, a relative path to another file of yours, a # fragment that scrolls to an element on this page, and special schemes like mailto:.

Write link text that means something on its own

<a href="...">click here</a> is bad, and not only stylistically. Screen reader users can pull up a list of every link on a page — a list of nine "click here" entries is useless. Say where it goes: "MDN's forms guide", "the syllabus PDF".

Images

<img src="logo.png" alt="College logo"> <img src="images/campus.jpg" alt="The main campus building" width="400">
srcWhere the image file is. Same path rules as href.
altA text description. Shown if the image fails to load, and read aloud by screen readers. Not optional.
width / heightWorth setting — it lets the browser reserve the right amount of space before the image arrives, so your page doesn't jump around while loading.

Do this now — break an image on purpose

Add an <img> pointing at a file that doesn't exist, with a sensible alt. Save and look. You'll see your alt text where the image should be. That's exactly what a blind user gets — every time, not just when it's broken.

When alt should be empty

If an image is purely decorative and carries no information, write alt="" — empty, but present. That tells a screen reader to skip it silently. Leaving alt off entirely is different: some screen readers then read out the filename, which is worse than nothing.

Paths — the thing that actually breaks

logo.pngSame folder as this HTML file.
images/logo.pngIn a sub-folder called images.
../logo.pngOne folder up. Two dots means "the parent folder".
/images/logo.pngStarts from the site root. Behaves differently depending on how the page is served — avoid until you understand why.
https://...A full URL to somewhere else entirely.

Case sensitivity will catch you

Logo.PNG and logo.png are the same file on Windows and Mac, and different files on Linux — which is what almost every web server runs on.

So a page that works perfectly on your laptop can show broken images the moment it's deployed. Save yourself the debugging session: use lowercase filenames with hyphens, always. campus-building.jpg, not Campus Building.JPG.

07

The DOM — what the browser builds

the important one

Here's the part most tutorials skip, and it's the part that turns HTML from a set of memorised tags into something you understand.

When the browser receives your HTML text, it does not keep it as text. It reads it once, and builds a tree of objects in memory. That tree is called the DOM — the Document Object Model.

The definition to remember

The DOM is the browser's live, in-memory model of your page, shaped as a tree. Your HTML file is the recipe. The DOM is the cake.

Take this HTML:

<html> <head> <title>My Page</title> </head> <body> <h1>Hello</h1> <p>Welcome</p> </body> </html>

The browser turns it into this:

The vocabulary of a tree

nodeAny single item in the tree. Elements are nodes; so is text; so are comments.
element nodeA node made from a tag — h1, p, body.
text nodeThe actual characters inside an element. "Hello" is a separate node inside the h1, not a property of it.
parentThe node directly above. body is the parent of h1.
childA node directly below. h1 and p are both children of body.
siblingNodes sharing a parent. h1 and p are siblings.
descendant / ancestorAny node further down / further up, at any depth. The "Hello" text is a descendant of body, and html is an ancestor of everything.
rootdocument sits above everything. <html> is the root element.

Why this is worth your attention

JavaScript talks to the DOMNot to your HTML file. Every line of JS you will ever write that changes a page is reaching into this tree and modifying nodes.
CSS selects through the treenav a means "every anchor that is a descendant of a nav". Selectors are tree queries. They make no sense without the tree.
React and every other frameworkAll of them exist to manage this tree for you. A "virtual DOM" is a lightweight copy of it, kept so the library can work out the smallest set of real changes to apply.
Bugs live here"Why is my click handler not firing?" is almost always a question about which node you actually attached it to.

The interview question

"What is the DOM?" is asked constantly, and a surprising number of candidates with React on their CV cannot answer it. The answer is one sentence: a tree of objects that the browser builds from your HTML, which JavaScript can read and modify to change what's on screen.

If you can say that and then point at a tree, you're ahead of a lot of people with two years of experience.

Q4In the tree above, what is the relationship between title and h1?
Show answer

Neither parent nor sibling — they're cousins. title's parent is head; h1's parent is body. They share a grandparent (html) but not a parent, so they aren't siblings.

This matters for CSS: a selector like head + body h1 works on relationships, so being precise about them is practical, not pedantic.

Q5Is the text "Hello" part of the h1 node, or a separate node?
Show answer

A separate node — a text node, which is a child of the h1 element node.

This seems like a technicality until you meet JavaScript's childNodes and wonder why an apparently empty <div> reports children. Whitespace between tags becomes text nodes too.

08

Reading the DOM in DevTools

go slowly here

The DOM isn't abstract. Your browser will show it to you, live, right now. This section is the one that makes you self-sufficient for the rest of your career — every bug you ever chase in a browser starts here.

Do this now — open it

With your page open in Chrome, right-click any text on it and choose Inspect. Or press F12. A panel opens; make sure the Elements tab is selected.

The name is misleading

The panel is called "Elements", but what it shows you is the DOM tree, not your file. Keep that distinction in your head — section 09 is entirely about why it matters.

Five things to try, in order

1 — Expand and collapse

Click the little triangles next to <html>, <body>, and your elements. You are folding and unfolding branches of the tree. Notice how the indentation matches your file's nesting exactly — this is the visual proof that nesting creates the tree.

2 — Hover a node, watch the page

Move your mouse over <h1> in the panel. The heading highlights on the page, with a coloured overlay showing exactly how much space it occupies. Hover <body> — the whole page highlights.

This is the single fastest way to answer "which element is that thing on screen?"

3 — Go the other way

Click the arrow-in-a-box icon at the top-left of DevTools (or press Ctrl+Shift+C), then click anything on the page. DevTools jumps straight to that node in the tree.

Page → tree, and tree → page. Once both directions are automatic, you can navigate any website in the world.

4 — Edit the live DOM

Double-click the text inside your <h1> in the panel. Type something else. Press Enter.

The page changes instantly. Now press F5 to reload — your change is gone.

What that just demonstrated

You edited the DOM, not the file. The DOM is a live model held in memory; reloading rebuilds it from your HTML file, which you never touched.

This also means you cannot break anything by experimenting in DevTools. Change other people's websites. Delete nodes on a news site. Refresh and it's all back. This is the safest sandbox you will ever have, and beginners under-use it enormously.

5 — Read the breadcrumb

Click a deeply nested element and look at the bar along the bottom of the Elements panel. It shows something like html › body › main › form › label — the full path of ancestors from the root to your selection.

That breadcrumb is the tree, written on one line. When you can't work out why a CSS rule isn't applying, read it.

The Console, and a first look at the DOM as objects

Click the Console tab. This is a place to type JavaScript and see what happens. You're not learning JavaScript here — you're using it as a torch to look at the tree.

Do this now — type these one at a time and press Enter

> document.title "Course Registration" > document.querySelector("h1") <h1>Course Registration</h1> > document.querySelector("h1").textContent "Course Registration" > document.querySelectorAll("li").length 6 > document.querySelector("h1").textContent = "Changed!"

That last one changes the heading on the page as you press Enter. You have just modified the DOM with code — which is, in essence, everything JavaScript does on a webpage.

documentThe root object. The whole tree hangs off it.
querySelector("h1")"Find me the first node matching this." The thing in quotes is a CSS selector — the same syntax you'll use for styling.
querySelectorAll("li")Find all matching nodes, as a list.
.textContentA property of the node — the text inside it. Read it, or assign to it and the page updates.

Notice what "object model" means

Each node is an object with properties you can read and change. document.querySelector("h1") hands you the actual object; .textContent is one of its properties. That's the "Object Model" half of the name, and it's why the tree is useful rather than merely descriptive.

Q6You edit some text in the Elements panel and it changes on screen. Your teammate reloads the same page on their laptop. Do they see your change?
Show answer

No. You changed the DOM in your own browser's memory. The HTML file is untouched, the server has no idea, and even you lose the change on reload.

Worth internalising early: DevTools edits are for experimenting and diagnosing. To make a change real, you edit the file.

09

Source is not the DOM

the distinction that explains modern web

Two different things, and browsers give you a separate view of each:

View SourceCtrl+U. The original HTML text the server sent. A frozen snapshot of the file.
Elements panelThe DOM right now, including everything JavaScript has added, removed or changed since the page loaded.

On the simple page you just built these look identical, because nothing has modified the tree. On most real websites they look nothing alike.

Do this now — see them diverge

Open any large site you use. Press Ctrl+U for the source, then F12 for the Elements panel, and compare.

The source is often short, with a mostly empty body. The DOM is enormous. Everything in the gap was built by JavaScript after the page arrived.

The tag that explains it

Here is the entire <body> of a brand-new React project, as Create React App generated it for years:

<body> <noscript>You need to enable JavaScript to run this app.</noscript> <div id="root"></div> </body>

Before reading on: what does <noscript> do, and why does a React app need it? Sit with that for a moment.

<noscript>Its contents are shown only when the browser has JavaScript turned off or blocked. If JS is running, the browser skips it entirely.
<div id="root"></div>Empty. Completely empty. That is the entire visible content of the file.
So why the noscript?Because the whole interface is built into that empty div by JavaScript after loading. No JavaScript means an empty white page with no error and no explanation. The <noscript> line is the apology.

This is the point of the section

For a React app, the source is nearly empty and the DOM is the entire application. The gap between View Source and the Elements panel is the framework.

Most people who have shipped a React project have never read that line and could not explain it. Now you can.

Do this now — switch JavaScript off

  1. Open DevTools on your own page. Press Ctrl+Shift+P, type javascript, choose Disable JavaScript.
  2. Reload. Your page works perfectly. Every heading, every list, and later every form field and its validation.
  3. Now visit a JavaScript-heavy site with JS still disabled. Blank page, or a single apologetic sentence.
  4. Turn JavaScript back on before you forget — Live Server's auto-reload stops working otherwise and you'll waste ten minutes wondering why.

The takeaway

Your page has no JavaScript at all and it fully works. That's not because it's simple — it's because HTML is the floor. It's what works before the bundle downloads, before the framework boots, on a bad connection, on an old phone, for a search engine crawler.

React sits on top of that floor. If you don't understand the floor, you don't understand what your framework is doing for you or what it's costing you.

One detail, if you're curious

Vite's React template doesn't include <noscript> — it was a Create React App convention that got copied around. So if a project has it, that tells you something about where its author started.

Q7You View Source on a site and see almost nothing, but the Elements panel shows thousands of nodes. What happened?
Show answer

JavaScript built the page after it loaded. The server sent a near-empty shell plus a script; the script constructed the DOM in the browser.

This is called client-side rendering, and it's how most single-page applications work. The trade-offs — slower first paint, harder for crawlers to read, breaks entirely without JS — are exactly why server-side rendering keeps coming back into fashion.

10

div, span and semantic elements

boxes with and without meaning

Now that you can see the tree, this section is about giving its branches names that mean something.

<div>A generic block-level box. Means nothing at all. Takes up a full line by default.
<span>A generic inline box. Also means nothing. Sits within a line of text.

Both exist purely to group things so you can style or script them. They're the plain cardboard boxes of HTML.

The same boxes, with labels on

<header>Introductory content for the page or a section — a title block, a logo.
<nav>A block of navigation links.
<main>The main content. Only one per page, and it shouldn't contain repeated things like the site header.
<section>A thematic grouping, normally with a heading.
<article>Something that would still make sense on its own — a blog post, a news item, a comment.
<aside>Tangential content — a sidebar, a pull quote.
<footer>Closing content for a page or section — credits, contact details.

Here's the thing worth knowing: these render exactly like a div. Visually, in a plain browser with no CSS, there is no difference whatsoever.

Do this now — wrap your page properly

<body> <header> <h1>Course Registration</h1> <p>Deadline: 31 August</p> </header> <main> <section> <h2>Available courses</h2> <ul> <li>Advanced Databases</li> </ul> </section> </main> <footer> <p>M.Tech CSE · ESD</p> </footer> </body>

Save and look. The page looks identical. Now open the Elements panel — the tree is completely different. It has meaningful branch names instead of anonymous boxes.

So why bother?

Screen readers navigate by themA blind user can jump straight to <main> and skip your navigation entirely. That works with <main>. It does not work with <div class="main"> — the class name is meaningless to the browser.
Search engines read themGoogle uses structure to work out what's actually the content of a page versus boilerplate.
Your future self reads themScrolling through forty nested </div> tags trying to work out which one you're closing is a real and common experience. </main> tells you.
Reader modes and browser featuresReader view, "jump to content", and various assistive tools all key off semantic structure.

A simple rule

Reach for the semantic element first. Fall back to <div> only when you genuinely just need a box to hang styling on and no existing element describes it.

You will still write plenty of divs. That's fine. The goal isn't zero divs, it's zero divs where a meaningful element existed.

Q8Someone says "semantic HTML doesn't matter, it looks the same either way." What's the strongest single counter?
Show answer

It looks the same to people who can see it. To a screen reader, <main> is a landmark that can be jumped to and <div class="main"> is nothing at all.

The counter that lands in a workplace: it costs nothing. Typing <main> instead of <div> is the same number of keystrokes, and it's often a legal requirement for public-sector and enterprise work.

11

id and class — the DOM's handles

how you grab a node

You have a tree. Now you need a way to point at one specific branch of it. That's what id and class are for — they're the handles that CSS and JavaScript grab.

idA name for one specific element. Must be unique in the whole document. Written id="submit-button".
classA label that any number of elements can share. One element can have several, space-separated: class="card featured".
<p id="intro" class="lead highlighted">Welcome.</p> <p class="lead">Another paragraph.</p>

The rule of thumb: id for one thing, class for a kind of thing. If you find yourself wanting two elements with the same id, you wanted a class.

Do this now — use them from the Console

Add the two paragraphs above to your page, save, then in the Console:

> document.querySelector("#intro") <p id="intro" class="lead highlighted">Welcome.</p> > document.querySelectorAll(".lead").length 2 > document.getElementById("intro").textContent "Welcome."
#nameIn a selector, # means "the element with this id".
.name. means "every element with this class".
tagnameA bare word means "every element of this type" — p, li, input.

That syntax is shared between CSS and JavaScript, which is not a coincidence — both are querying the same tree. Learn it once and it works in both.

ids have a second job

An id also becomes a link target. Give a section an id, and you can link straight to it:

<h2 id="registration">Register</h2> ... <a href="#registration">Jump to registration</a>

And yoursite.com/page.html#registration opens the page already scrolled there. That's exactly how the contents list at the top of this document works.

Naming rules worth following

Lowercase, hyphens between words, describe what it is rather than what it looks like. class="error-message", not class="red-text" — because in six months the design changes and your red text is blue.

No spaces inside a single id or class name; a space starts a new class. And ids must be unique — duplicating one is invalid HTML, and getElementById will silently return only the first, which is a genuinely nasty bug to track down.

Q9You give five buttons id="btn" and then run document.getElementById("btn"). What comes back?
Show answer

Only the first one. No error, no warning — it just quietly ignores the other four.

ids are required to be unique. When several elements are the same kind of thing, they want a shared class, and you select them with querySelectorAll(".btn") to get all of them.

12

Tables, briefly

for data, and only data

Tables are for tabular data — things with rows and columns that genuinely belong in a grid. Marks, timetables, price comparisons.

<table> <thead> <tr> <th>Course</th> <th>Credits</th> </tr> </thead> <tbody> <tr> <td>Advanced Databases</td> <td>4</td> </tr> </tbody> </table>
<tr>Table row. Everything lives inside rows.
<th>Header cell. Bold and centred by default, and announced as a header by screen readers.
<td>Data cell.
<thead> <tbody>Group the header rows and the body rows. Optional, but they make long tables far easier to read and style.

Never use a table for page layout

Before CSS was any good, people built entire page layouts out of invisible tables. That era ended around 2005, and using a table to position things today is the fastest way to signal that you learned from a very old tutorial. It's also genuinely bad for screen readers, which announce it as a data table and try to read it cell by cell.

Layout is CSS's job. Tables are for data.

13

Forms — the container

how the web takes input

Everything you've done so far shows information. Forms are how a page collects it — and they are the single most common thing you'll build.

<form action="/register" method="post"> <!-- fields go here --> </form>
actionThe URL the data gets sent to when the form is submitted.
methodHow to send it. post puts the data in the body of the request. get puts it in the URL as ?name=value&other=value.

get or post?

get for things that only read — a search box. The data ends up in the URL, so the results are bookmarkable and shareable.

post for things that change something or are private — registering, logging in, uploading. Data in the URL gets stored in browser history and server logs, so never send a password with get.

Nothing will happen when you submit, and that's correct

You have no server. There's nothing listening at /register. When you click submit you'll get a 404 or a blank page — this is expected, not a bug in your HTML.

The form itself is complete and correct; the other half of the conversation just doesn't exist yet. Backends come later in the course.

In the DOM

A <form> becomes a node like any other — but a special one. It keeps a live list of every input inside it, which is what makes form.elements work in JavaScript. Section 19 comes back to this.

14

Labels and inputs

get this pairing right

An input on its own is a mystery box. A label tells the user — and the browser, and assistive technology — what it's for.

<label for="fullname">Full name</label> <input type="text" id="fullname" name="fullname">

Three attributes are doing three different jobs here, and confusing them is the most common forms mistake there is.

for (on the label)Points at an input's id. This is what connects the two.
id (on the input)The input's unique handle — for the label, for CSS, for JavaScript.
name (on the input)What gets sent to the server. Nothing to do with the label. This is the key that the data arrives under.

Do this now — watch the connection work

Add the pair above to your form and save. Now click on the words "Full name" — not the box, the label text.

The cursor jumps into the input. That's for and id matching.

Now change the label to for="fullnam" — one letter off — and save. Click the label again. Nothing happens. Fix it.

The one that will bite you: name

No name, no data. An input without a name is simply not included when the form is submitted. The field looks perfect, the user fills it in, and the value silently vanishes.

There's no error and no warning. Every developer loses an hour to this at least once.

Why labels are not optional

Bigger click targetClicking the label focuses the field. On a phone, that turns a tiny checkbox into something you can actually hit.
Screen readersReaching an unlabelled input, a screen reader can only announce "edit text, blank". The user has no idea what to type.
It's in the DOMThe connection becomes a real relationship between two nodes — input.labels exists as a property. It isn't just visual proximity.

The wrapping alternative

<label> Full name <input type="text" name="fullname"> </label>

Putting the input inside the label works too, and needs no for/id pair. It's tidier, but you often still want an id for CSS or scripting — so the explicit version is more common in real codebases. Either is correct; be consistent.

A placeholder is not a label

placeholder="Full name" looks like a tidy space-saving trick and it is a genuinely bad idea on its own. It disappears the moment someone types, so they can no longer check what the field was. It fails colour-contrast requirements in most designs. And screen reader support for it is inconsistent.

Use a label. Add a placeholder as well if it helps — for a format hint like DD/MM/YYYY. Never a placeholder alone.

Q10An input has id="email" but no name. The user fills it in and submits. What does the server receive?
Show answer

Nothing from that field. The id is for the label, CSS and JavaScript — it plays no part in submission. Only fields with a name are sent.

Convention is to give both the same value (id="email" name="email"), which is why the two get confused so often. They're doing entirely separate jobs.

15

Input types

let the browser do the work

One element, <input>, changes behaviour completely depending on its type. Choosing the right one gives you keyboard optimisation, validation and specialised pickers for free.

type="text"The default. A single line of anything.
type="email"Checks the format on submit, and phones show a keyboard with @ on it.
type="password"Masks what's typed. Note: this hides it from someone looking over a shoulder. It is not encryption — the value travels as plain text unless the site uses HTTPS.
type="number"Numbers only, with up/down arrows. Pairs with min, max, step.
type="tel"Numeric keypad on mobile. Deliberately does not validate — phone number formats vary too much worldwide.
type="url"Expects a full URL including the scheme.
type="date"A real date picker, built into the browser, with zero JavaScript.
type="time" / "datetime-local"Same idea for times.
type="file"A file chooser. Needs enctype="multipart/form-data" on the form to actually upload.
type="color"Opens the OS colour picker. Rarely needed, pleasant when it is.
type="range"A slider. Use when the precise number doesn't matter.
type="hidden"Not shown, but submitted with the form. Used for things like record ids.

Do this now — build the top of the registration form

<label for="fullname">Full name</label> <input type="text" id="fullname" name="fullname"> <label for="roll">Roll number</label> <input type="text" id="roll" name="roll"> <label for="email">Email</label> <input type="email" id="email" name="email"> <label for="start">Preferred start date</label> <input type="date" id="start" name="start">

Save and click the date field. You get a full calendar picker that you did not build, that works with a keyboard, that's translated into the user's language, and that matches their operating system. That's what "let the browser do the work" means.

Never trust the browser as your only check

All of this validation runs on the user's machine, and anyone can bypass it by opening DevTools and deleting the attribute, or by sending the request directly without a browser at all.

Client-side validation is a convenience — it tells honest users about mistakes instantly. The server must check everything again. This is one of the most common security holes in student projects and junior code.

16

Radios, checkboxes, select, textarea

the choosing controls

Radio buttons — pick exactly one

<fieldset> <legend>Mode of study</legend> <input type="radio" id="fulltime" name="mode" value="full"> <label for="fulltime">Full time</label> <input type="radio" id="parttime" name="mode" value="part"> <label for="parttime">Part time</label> </fieldset>

The rule that makes radios work

Same name = one group. That shared name is the only thing telling the browser these options belong together and are mutually exclusive.

Each needs a different id (so its label can point at it), the same name (to group them), and its own value (what gets sent when it's the one selected).

Do this now — break it deliberately

Change the second radio's name to "mode2" and save. Now try to select both. You can — the form is nonsense. Change it back and watch them become exclusive again.

Ninety seconds, and you'll never debug this one slowly.

fieldset and legend

<fieldset> groups related controls; <legend> is its caption. For a radio group this isn't cosmetic — without it, a screen reader reads "Full time, radio button" with no indication of what question it answers. The legend supplies the question.

Checkboxes — zero or more

<input type="checkbox" id="terms" name="terms"> <label for="terms">I confirm these details are correct</label>

Independent by default. Give several the same name and they submit as a list of the checked values — useful for "select all that apply".

A quirk worth knowing

An unchecked checkbox sends nothing at all — not "false", not an empty string. The key simply isn't in the submitted data. Server code that expects it to always be present will break, which surprises people the first time.

Dropdowns

<label for="course">Course</label> <select id="course" name="course"> <option value="">-- Select a course --</option> <option value="adb">Advanced Databases</option> <option value="ds">Distributed Systems</option> <option value="esd">Embedded Systems Design</option> </select>
value vs textThe value is what gets submitted; the text between the tags is what the user reads. They're usually different — a short code versus a full name.
The empty first optionNot decoration. It's what makes required work on a dropdown — without it, the first real option is pre-selected and the field can never be empty.
selectedPre-selects an option: <option value="adb" selected>.
<optgroup>Groups options under a heading inside the dropdown. Useful once you have more than about ten.

Multi-line text

<label for="why">Why this course?</label> <textarea id="why" name="why" rows="4" maxlength="300"></textarea>

textarea is not self-closing

Unlike <input>, a textarea has an opening and closing tag — and anything between them becomes its starting content. Put a newline or spaces in there and the box starts with that text in it.

Write <textarea></textarea> with nothing at all between the tags. This catches people constantly.

Q11You have three radio buttons that should be one question, but the user can select all three. What's wrong?
Show answer

They have different name attributes. The shared name is what makes radios mutually exclusive — give all three the same name and different values.

The mirror-image mistake: giving them the same id. That's invalid, and it breaks the labels because every one will point at the first radio.

17

Buttons and what submit does

an invisible default
<button type="submit">Register</button> <button type="reset">Clear form</button> <button type="button">Do something with JavaScript</button>
type="submit"Validates the form, then sends it to the action URL. This is the default for a button inside a form.
type="reset"Clears every field back to its initial value. Rarely a good idea — users hit it by accident and lose everything.
type="button"Does nothing on its own. For buttons you'll wire up with JavaScript.

The bug this causes, every time

A <button> inside a form with no type is a submit button. So you add a button that's meant to add a row or toggle something, click it, and the whole page reloads and your data is gone.

That's not a mysterious JavaScript problem — it's the form submitting exactly as specified. Always write type explicitly on every button. It costs nothing and prevents an afternoon of confusion.

What actually happens on submit

  1. The browser runs its built-in validation on every field. If anything fails, it stops and shows a message.
  2. It collects the name/value pair from each successful control. Fields with no name are skipped. Unchecked boxes are skipped. Disabled fields are skipped.
  3. It packages them up and sends them to action using method.
  4. The browser navigates to the response. The page reloads.

That last step is worth sitting with. A plain HTML form submission is a full page navigation — the same as clicking a link. The smooth, no-reload form submissions you're used to on modern sites are JavaScript intercepting step 4 and doing it in the background instead.

Do this now — watch the data go

Temporarily change your form to <form action="" method="get">, fill in a few fields and submit.

The page reloads, and look at the address bar. You'll see something like ?fullname=Shreyas&email=me%40example.com&mode=full.

That is your form data, encoded into a URL. Every name you set is a key in it. Any field you forgot to name is missing — this is the fastest way to check your form is wired correctly.

You just learned a debugging trick

Whenever a form isn't sending what you expect, switch it to method="get" and read the URL. It shows you precisely what the browser collected — no server needed. Switch it back afterwards.

18

Validation you get for free

no JavaScript required

Do this now — add required and try to submit

<input type="text" id="fullname" name="fullname" required>

Leave it blank, click Register. The browser stops the submission, scrolls to the field, focuses it and shows its own error bubble — translated into the user's language, styled by their operating system. You wrote one word.

requiredCannot be left empty. Works on text, email, select, checkbox and radio groups.
minlength / maxlengthCharacter limits for text. maxlength physically stops typing past the limit.
min / maxFor numbers and dates. min="2026-08-01" on a date field works exactly as you'd hope.
stepFor numbers — step="0.5" allows halves only.
patternA regular expression the value must match. Powerful; pair it with a title explaining the expected format, because the default error message is unhelpful.
type itselftype="email" validates format on its own. Choosing the right type is validation.

A worked example — a roll number that must be two letters followed by four digits:

<input type="text" id="roll" name="roll" pattern="[A-Za-z]{2}[0-9]{4}" title="Two letters followed by four digits, e.g. CS2024" required>

Attributes with no value

required has no ="something". It's a boolean attribute — its presence means true, its absence means false. There is no required="false"; to switch it off you delete it. Same for disabled, checked, readonly, selected.

Say it once more, because it matters

Every one of these checks runs in the user's browser and can be removed by anyone in about four seconds using DevTools. The server must validate everything again.

Browser validation is for helping honest users. Server validation is for security. They are not alternatives.

Q12You put required on a <select> but the form submits happily with nothing chosen. Why?
Show answer

Your first <option> has a non-empty value, so it counts as a valid selection — and it's selected by default, so the field is never empty.

Fix it with an empty-valued placeholder option first: <option value="">-- Select --</option>. Now "nothing chosen" is genuinely empty and required has something to catch.

Forms in the DOM

where it all connects

Back to the tree, now that there's a form in it. This section is where the first half of the document and the second half meet.

Do this now — inspect a form field

Right-click one of your inputs → Inspect. Look at where it sits: form › label, form › input, siblings under the form node. Your nesting made that shape.

Now open the Console and explore the same nodes as objects:

> document.querySelector("#fullname") <input type="text" id="fullname" name="fullname" required> // type something into the field on the page first, then: > document.querySelector("#fullname").value "Shreyas" > document.querySelector("#terms").checked false > document.querySelector("form").elements.length 9 > document.querySelector("#fullname").value = "Set from the console"
.valueWhat's currently in the field. Read it or write it. This is the property you'll use most in JavaScript.
.checkedTrue or false, for checkboxes and radios. Their .value is the value attribute, which isn't what you want here.
form.elementsA live collection of every control in the form. You can also reach one by name: form.elements.email.
.labelsThe label elements pointing at this input — real proof that for/id creates a genuine DOM relationship.

The distinction that trips people up

Type something into the field, then in the Console:

> document.querySelector("#fullname").value "Shreyas" // the live value, right now > document.querySelector("#fullname").getAttribute("value") null // the attribute in the HTML — never set

Look at the Elements panel while you type. The HTML shown there doesn't change, but .value does. The attribute is the initial value from your source. The property is the current value in the live DOM.

This is section 09 again, in miniature

Source versus DOM, at the level of a single field. The HTML file says what a thing starts as; the DOM holds what it is now. Understanding that one distinction resolves an enormous number of "but the HTML says…" bugs.

Why name matters here too

id is how your code finds the field. name is how the data is keyed when it leaves the browser. Same field, two identities, two different consumers. Missing the id means your JavaScript can't find it; missing the name means the server never sees it.

What this sets up

Every form library you'll ever use — React Hook Form, Formik, whatever comes next — is a layer over exactly these properties. When you write a controlled component in React and wire up value and onChange, you are managing .value on a DOM node by hand.

People who learned React first find this baffling. You'll find it obvious, because you saw the node before you saw the abstraction.

Q13You type "hello" into a text input. In the Elements panel, the HTML still shows <input type="text" id="q"> with no value. Is something broken?
Show answer

No, that's correct behaviour. Typing changes the element's value property in the DOM. It does not rewrite the value attribute, which represents the initial state.

Check with document.querySelector("#q").value in the Console — it returns "hello". The attribute and the property are related but separate, and this is the classic example.

Accessibility, almost for free

you've already done most of it

Accessibility sounds like an extra chore bolted on at the end. For HTML it mostly isn't — it's what you get automatically by writing the markup correctly, which you've been doing all along.

Every input has a labelSection 14. This is the single biggest one for forms.
Headings describe structureSection 05. Screen reader users navigate by heading, like a contents page.
Images have alt textSection 06. Empty alt="" for decorative ones.
Semantic elementsSection 10. <main> and <nav> are landmarks that can be jumped to.
Radio groups in a fieldsetSection 16. The legend supplies the question the options answer.
Link text that means somethingSection 06. Not "click here".
lang on the html elementSection 03. Tells a screen reader which pronunciation rules to use.

That's most of it, and every item was already the correct way to write the markup.

Do this now — use your page with no mouse

Click on the page, then press Tab repeatedly. Focus moves through your links and form fields in order. Shift+Tab goes back. Space toggles a checkbox, arrow keys move within a radio group, Enter submits.

All of that works and you did not write a line of it. It comes from using real form elements.

Which is why "div soup" is a real problem

The moment someone builds a button out of <div onclick="...">, all of it vanishes. It isn't focusable, Tab skips it, Enter and Space do nothing, and a screen reader announces it as meaningless text.

You can rebuild all that by hand with tabindex, ARIA roles and keyboard handlers — dozens of lines to reproduce what <button> gave you for free. This is the practical argument for using the right element: it's less work.

Check it yourself

In Chrome DevTools, open the Lighthouse tab, tick Accessibility, and run it on your page. You get a score and a specific list of problems. Also worth knowing: the Accessibility pane inside the Elements panel shows you the accessibility tree — a parallel structure the browser builds alongside the DOM, which is what assistive software actually reads.

When it goes wrong

the usual suspects

HTML has no error messages. A mistake doesn't crash anything — the browser guesses what you meant and carries on, which is helpful right up until it isn't. These are the ones you'll hit.

The browser shows my raw codeThe file isn't saved as .html. On Windows it's probably index.html.txt — turn on file extensions (section 02).
My change doesn't appearYou didn't save, or you're looking at a different file than the one you're editing. Check the path in the address bar.
Everything after a point is bold/italic/brokenAn unclosed tag. Open the Elements panel — the DOM tree shows you what the browser actually built, and the mis-nesting will be visible as wrong indentation.
My image doesn't loadWrong path, or wrong case in the filename. Check the Console tab — a failed load logs a 404 with the exact URL it tried.
Clicking the label does nothingfor doesn't match any id. Usually a typo, sometimes a capital letter.
A field's value never reaches the serverNo name attribute. Switch to method="get" and read the URL to see exactly what is being sent.
My radios aren't exclusiveDifferent name values. They must share one.
The page reloads when I click a buttonThe button has no type, so it defaults to submit. Add type="button".
required does nothing on my dropdownYou need a first option with value="".
My textarea starts with blank linesThere's whitespace between the opening and closing tags. Close it immediately: <textarea></textarea>.
Special characters look wrongMissing <meta charset="UTF-8">, or the file was saved in another encoding.

How to debug HTML, generally

  1. Open the Elements panel. Compare the tree the browser built with the tree you intended. The difference is your bug.
  2. Check the Console for failed file loads.
  3. Run it through a validator — validator.w3.org/nu takes pasted HTML and lists every structural error with line numbers. Unclosed tags, bad nesting, duplicate ids. Two minutes, and it finds things you'd stare past for an hour.
  4. Comment out half. If the page is broken and you can't see why, comment out half the body. Still broken? The problem is in the other half. Repeat. Five rounds narrows 500 lines down to about fifteen.

Asking for help is a skill, not a failure

When you're properly stuck, ask someone — and have a screenshot of both your code and the Elements panel ready when you do. The gap between the two usually makes the answer obvious in seconds.

answer before revealing

Fifteen questions. Answer each in your head — or better, write it down — before opening the answer. Getting one wrong is information, not failure; go back to the section it came from.

1What are the three languages of the web, and what is each one's job?
Show answer

HTML — what things are (structure and meaning). CSS — what they look like. JavaScript — what they do.

2Define the DOM in one sentence.
Show answer

A tree of objects that the browser builds in memory from your HTML, which JavaScript can read and modify to change what's on screen.

Your HTML file is the recipe; the DOM is the cake.

3What's the difference between View Source and the Elements panel?
Show answer

View Source shows the original HTML text the server sent — a frozen snapshot. The Elements panel shows the live DOM right now, including everything JavaScript has changed since load.

On a React app the first is nearly empty and the second is the whole application.

4In <body><h1>Hi</h1><p>There</p></body> — what is h1 to p, and what is "Hi" to h1?
Show answer

h1 and p are siblings — both children of body.

"Hi" is a text node, and a child of h1 — not a property of it.

5Why is choosing h3 because "it's the right size" a mistake?
Show answer

Heading level is document structure, not size — size is CSS's job. Screen reader users navigate by heading level, so wrong levels give them a shuffled contents page. Search engines read the outline too.

6What does <noscript> do, and why did Create React App put one in every project?
Show answer

Its content shows only when JavaScript is off or blocked. React apps ship an empty <div id="root"> and build the entire interface with JavaScript — so with JS disabled the user gets a blank white page and no explanation. The <noscript> line is the apology.

7Give three reasons to use <main> rather than <div class="main">.
Show answer

Screen readers can jump straight to it as a landmark; search engines use it to identify real content; and your own code is far easier to read than a wall of closing divs. It also costs nothing — same number of keystrokes.

8When do you use id and when do you use class?
Show answer

id for one specific element — must be unique in the document. class for a kind of element that several can share.

If you want two elements with the same id, you wanted a class.

9Name the three attributes on a labelled input and say what each is for.
Show answer

for on the label points at the input's id. id is the input's unique handle for the label, CSS and JavaScript. name is the key the data is sent under — no name, no data.

10Three radio buttons; the user can select all three. What's wrong?
Show answer

They don't share a name. Same name makes them one mutually exclusive group; each still needs a different id and its own value.

11Why does a button inside a form sometimes reload the page unexpectedly?
Show answer

A <button> with no type defaults to type="submit", so clicking it submits the form and navigates. Always write type explicitly.

12You have required on a dropdown but it submits empty. Fix?

13Is browser validation enough to keep your app safe?
Show answer

No. It runs on the user's machine and can be removed in seconds with DevTools, or bypassed entirely by sending a request without a browser.

Client-side validation is a convenience for honest users. The server must re-check everything. They aren't alternatives.

DevTools console, for poking at the tree

> document.querySelector("#id") // first match > document.querySelectorAll(".class") // all matches > el.textContent // text inside a node > el.value // current value of a field > el.checked // checkbox / radio state > el.parentElement // walk up the tree > el.children // walk down > form.elements // every control in a form
