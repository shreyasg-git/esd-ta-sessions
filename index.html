01

Git is not GitHub

clear this up first

These are two different things made by two different companies, and confusing them causes more beginner pain than anything else in this document. Sort it out now and a lot of later confusion simply never happens.

GitA program on your laptop. Written in 2005 by Linus Torvalds, the same person who wrote Linux. It records versions of a folder. It works with no internet connection, forever, and it is free.
GitHubA website, owned by Microsoft, that stores copies of Git projects online so you can share them and work with other people. It's one of several — GitLab and Bitbucket do the same job.

An analogy that holds up: Git is like a camera. GitHub is like Instagram. The camera takes and stores the photos. The website is where you put them so other people can see. You can own a camera and never post anything. You cannot post without taking a photo first.

What problem is Git solving?

You have almost certainly done this:

project_final.docx project_final_v2.docx project_final_FINAL.docx project_final_FINAL_use_this_one.docx

That is a version control system. A bad one. It can't tell you what changed between two files. It can't combine two people's edits. It breaks completely the moment two people work at once. And after a week you genuinely cannot remember which one is real.

Git fixes exactly this. You keep one folder. Git remembers every saved state of it, along with a note about what changed and who changed it. You can look at any past version, compare any two, and combine work from several people without anyone overwriting anyone.

Why you personally should care

Every job uses itNot most — every software job, without exception. It is assumed the way typing is assumed.
It's your public recordYour GitHub profile is often the first thing an interviewer opens, sometimes before your resume. A profile with real commits on real dates says more than a bullet point does.
It removes fearBeing able to say "I broke it, let me go back to yesterday" is what lets you experiment. People without version control code timidly, because every change is a risk.
It's how you submitIn this course, your assignments are graded from your repository. Git isn't a side topic here; it's the delivery mechanism.

Vocabulary you'll meet shortly

Skim these now. They'll each get a proper section — this is just so the words aren't strangers.

repository (repo)A folder that Git is tracking. It has a hidden .git sub-folder inside it where Git keeps its records.
commitOne saved snapshot of the whole project, with a message describing it. Used as a noun ("look at that commit") and a verb ("commit your work").
cloneDownload a repository from GitHub onto your laptop.
pushSend your commits up to GitHub.
pullBring down commits from GitHub that you don't have yet.
remoteThe nickname for the copy living on GitHub. Almost always called origin.
branchA separate line of work. Section 18 introduces it; the session covers it properly.
Q1Your laptop has no internet for a whole day. Which of these can you still do?
  1. Make commits
  2. Push to GitHub
  3. Clone a new repository
  4. All of them
Show answer

(a) Make commits. Git runs entirely on your laptop, so committing works offline all day long. Pushing and cloning both have to reach GitHub's servers, so they need a connection.

This is the practical test of whether the distinction has landed. Commit whenever you like; push when you have internet.

Q2True or false: if GitHub shut down tomorrow, every Git repository in the world would be lost.
Show answer

False. Every clone is a complete copy, including the entire history. If GitHub vanished, every developer with a clone would still have the full project and could push it somewhere else the same afternoon.

That's what "distributed" means in "distributed version control" — there is no single master copy that everything depends on.

02

A terminal survival kit

skip if you're comfortable

Git is used by typing commands. If the black window with text makes you uneasy, this section fixes that. It's a small number of commands and they're all simple — the discomfort is unfamiliarity, not difficulty.

Opening one

WindowsSearch Git Bash in the Start menu. Use this, not Command Prompt or PowerShell — Git Bash gives you the same commands Mac and Linux users have, so every instruction here works identically for you.
MacSearch Terminal in Spotlight (Cmd+Space).
LinuxWhatever terminal your distribution gives you.
Inside VS CodePress Ctrl+` (the backtick key, above Tab). This opens a terminal already sitting in your project folder, which is usually what you want.

Reading the prompt

shreyas@laptop MINGW64 ~/code/git-practice (main) $

Left to right: your username, your machine, where you currently are, and — once you're inside a Git repository — the branch you're on in brackets. The $ is where your typing goes. In this document, $ marks the start of a command; you never type the $ itself.

The six commands you actually need

pwd"Print working directory" — where am I? When something goes wrong, this is the first thing to check.
lsList the files here. ls -a also shows hidden files, which you'll need for .git.
cd foldernameGo into a folder. cd .. goes up one level. cd ~ goes to your home folder. cd with nothing does the same.
mkdir nameMake a folder. mkdir -p a/b makes nested folders and doesn't complain if they already exist.
cat filePrint a file's contents to the screen. Handy for a quick look without opening an editor.
clearWipe the screen. Nothing is deleted; it just tidies up.

Do this now — get your bearings

$ pwd /Users/shreyas # or /home/you, or /c/Users/You $ ls Desktop Documents Downloads $ mkdir -p ~/code $ cd ~/code $ pwd /Users/shreyas/code

You've just made the folder where all your course work will live, and moved into it. That's the whole skill.

What ~ means

The tilde is shorthand for your home folder — /Users/yourname on Mac, /home/yourname on Linux, C:\Users\YourName on Windows. So ~/code means "the code folder inside my home folder", and it works the same on everyone's machine, which is why this document uses it.

Four things that will make you much faster

Tab completionType the first few letters of a filename and press Tab. The terminal finishes it. This prevents typos and is the single biggest speed-up available to you. Use it constantly.
Up arrowRecalls your previous commands. Press it repeatedly to go further back. You will retype the same four Git commands hundreds of times — don't actually retype them.
Ctrl+CStops whatever is running, or clears a line you've made a mess of. Your escape key for the terminal.
qExits the scrolling view that git log and git diff open. Just the letter q. Everyone gets stuck in this exactly once.

Avoid spaces in folder names

A folder called my project has to be typed as cd "my project" or cd my\ project, and it will trip you up repeatedly. Use my-project or my_project. This is a genuine convention in software, not a personal preference.

You do not need to memorise the terminal

Six commands cover almost everything you'll do for months. Nobody is testing you on it, and looking things up is completely normal — professional developers search for shell syntax constantly.

Q3You're in ~/code/git-practice and you want to get to ~/code. What do you type?
Show answer

cd .. — two dots means "the folder above this one".

cd ~/code also works and is sometimes clearer, because it says exactly where you're going rather than relying on where you started.

03

Three checks before you start

do not skip these

Check 1 — is Git installed?

$ git --version git version 2.45.2 # your number will differ, that's fine

If it says "command not found", install it first:

WindowsDownload Git for Windows from git-scm.com/download/win. During install, when asked about the default editor, choose Visual Studio Code — anything else drops you into an editor you can't get out of.
MacJust type git --version. macOS pops up a dialog offering to install developer tools. Click Install and wait.
Linuxsudo apt install git on Ubuntu/Debian, sudo dnf install git on Fedora. It's often already there.

Check 2 — does Git know who you are?

Every commit is signed with a name and email. If you skip this, your commits are anonymous and won't link to your GitHub account — meaning all your work is invisible on your profile.

$ git config --global user.name "Your Full Name" $ git config --global user.email "the-email-on-your-github@example.com" $ git config --global user.name # read it back to check Your Full Name

The email must match your GitHub account exactly

Not "similar to" — the same address. If it doesn't match, GitHub cannot tell the commits are yours, and your contribution graph stays empty no matter how much you push.

Two more one-time settings that will save you real pain:

$ git config --global init.defaultBranch main $ git config --global core.editor "code --wait"

The second one tells Git to use VS Code whenever it needs you to type something longer. Without it you may land in Vim, an editor that does not respond to normal keys and traps people for ten minutes. Set this now and it can't happen.

Windows users, one more:

$ git config --global core.autocrlf true

Windows and everyone else disagree about how lines end in a text file. Without this setting, you'll eventually see Git claim that every single line of a file changed when you only touched one. This makes the problem go away. On Mac and Linux use input instead of true.

Check 3 — do you have a GitHub account?

If not, sign up at github.com/signup. Two things matter:

  • Pick a username you'd put on a CV. Your name, or your name plus a number. Recruiters look at this. Not coolcoder_007.
  • Verify your email by clicking the link they send. An unverified account cannot push code.

Then log your laptop into GitHub. This is by far the easiest way:

$ gh auth login

Answer the prompts: GitHub.com → HTTPS → Yes → Login with a web browser. Copy the one-time code it shows, press Enter, paste it into the browser, click Authorize. You never do this again.

$ gh auth status ✓ Logged in to github.com account your-username

If gh isn't installed

Get the GitHub CLI from cli.github.com. It's genuinely worth it — the alternative involves generating access tokens by hand, and it's the single most miserable part of getting started.

04

The four places a file can live

the model everything hangs off

This is the most important section in the document. If you hold this picture, every command below becomes obvious. If you skip it, you'll be memorising magic spells for the next two years — which is exactly what happened to the people who find Git frightening.

At any moment, a file in a Git project is in one of four places. Every command you're about to learn moves it one step to the right.

1. Working directoryThe actual files on your laptop that you open in VS Code and edit. Git can see them but is not recording them yet.
2. Staging areaA holding pen. It means "these are the changes I want in my next snapshot." You put things here with git add. Sometimes called the "index" in documentation.
3. Commit historyPermanent snapshots, stored inside the hidden .git folder on your laptop. git commit takes whatever is in staging and makes one.
4. GitHubA copy on the internet. git push sends your commits there. Until you push, your work exists on exactly one laptop.

"Why does the staging area exist? It feels pointless."

Fair question, and here's the honest answer: it lets you change five files but save only three of them together as one meaningful snapshot. Say you fixed a bug and also renamed a variable somewhere unrelated — staging lets you commit those separately, so your history tells a clean story instead of a jumbled one.

For now, just treat git add as "get ready" and git commit as "save". The usefulness becomes obvious within a month of real work.

Q4You edit index.html and save it in VS Code. You have not run any Git commands. Where does that change live?
Show answer

The working directory only. Saving in your editor and saving in Git are completely separate actions. Git has noticed the file changed, but it has recorded nothing.

This trips up almost everyone at first: pressing Ctrl+S does not create a commit.

Q5You run git add index.html then git commit -m "Fix header". Your teammate on another laptop pulls. Do they get your change?
Show answer

No. You committed, which saved it to your laptop's history. You never pushed, so GitHub doesn't have it, so there's nothing for them to pull.

Commit saves locally. Push shares. Forgetting the second step is the most common reason people say their work "disappeared" — it's usually sitting safely on their laptop, uncommunicated.

05

Make a repo and clone it

hands on keyboard from here

We start on GitHub and come down to the laptop, rather than the other way round. Fewer steps, and it means your work is backed up online from the very first minute.

Do this now — create the repository

  1. Go to repo.new in your browser. That's the whole URL — it redirects to GitHub's new-repository page.
  2. Repository name: git-practice
  3. Description: Learning Git basics
  4. Choose Public
  5. Tick "Add a README file" — this matters, it gives the repo a first commit so there's something to download
  6. Click Create repository

Look at what you've made. One file, README.md, and GitHub has already made one commit containing it. A repository with zero commits is an awkward edge case, and ticking that box avoided it entirely.

Do this now — clone it to your laptop

Replace YOUR-USERNAME with your actual GitHub username. Type it out; don't paste the placeholder.

$ cd ~/code $ git clone https://github.com/YOUR-USERNAME/git-practice.git Cloning into 'git-practice'... remote: Enumerating objects: 3, done. Receiving objects: 100% (3/3), done. $ cd git-practice

What just happened: Git downloaded the entire repository — every file plus its complete history — into a new folder called git-practice. It also remembered where it came from, so future pushes and pulls already know where to go.

Look inside

$ ls README.md $ ls -a . .. .git README.md
README.mdYour one actual file. GitHub displays this as the front page of any repository.
.gitThe hidden folder where Git keeps everything — all history, all settings. This folder is what makes the folder a repository. Delete it and you have an ordinary folder again. Never edit anything inside it by hand.
The leading dotFiles starting with . are hidden by default, which is why you needed ls -a rather than plain ls.

Do this now — confirm the connection

$ git remote -v origin https://github.com/YOUR-USERNAME/git-practice.git (fetch) origin https://github.com/YOUR-USERNAME/git-practice.git (push)

origin is just a nickname for "the copy on GitHub". It's a convention rather than a keyword, but everyone uses it, so treat it as fixed. When you later type git push, that's where it goes.

Check your own username is in that URL

If you ever clone someone else's repository by mistake, everything works fine until you try to push — then you get a permissions error, usually at the worst possible moment. git remote -v is the check that prevents it, and it's worth doing every time you clone.

Optional — open the folder in VS Code

$ code .

The dot means "this folder". If code isn't recognised, just open VS Code normally and use File → Open Folder.

Q6What is the difference between an ordinary folder and a Git repository?
Show answer

A hidden .git sub-folder. That's the entire difference. Git commands work inside a folder that has one and fail with "fatal: not a git repository" in a folder that doesn't.

If you ever see that error, the usual cause is simply standing in the wrong directory. Run pwd to see where you are.

06

git status — your one diagnostic

run it constantly

If you learn one command properly, make it this one. It tells you where every file is, what Git is about to do, and usually what you should type next. It changes nothing, so you can run it as often as you like — there is no such thing as running it too much.

$ git status On branch main Your branch is up to date with 'origin/main'. nothing to commit, working tree clean

Line by line: you're on the branch called main; your laptop and GitHub agree with each other; you have no unsaved changes. This is the calm state.

Do this now — make a mess and look at it

Create one new file and edit the existing one.

$ echo "My name is [your name]" >> README.md $ echo "practice notes" > notes.txt $ git status

(>> adds a line to the end of a file. A single > replaces the whole file. Worth knowing the difference before you use the wrong one.)

On branch main Changes not staged for commit: (use "git add <file>..." to update what will be committed) modified: README.md Untracked files: (use "git add <file>..." to include in what will be committed) notes.txt no changes added to commit

The four states, and their colours

Untracked (red)A brand-new file Git has never seen. It is being completely ignored until you git add it once.
Modified (red)A file Git knows about, which you've changed. The change will not be in your next commit unless you add it.
Staged (green)Added and ready. Will be in your next commit.
Clean"nothing to commit, working tree clean" — everything is saved. Nothing to do.

Learn this one sentence

Red means it is not going in. Green means it is. That single rule explains ninety per cent of "why didn't my change get saved?" — the answer is nearly always that it was red and nobody looked.

The other line to watch for

After you commit but before you push, status says:

Your branch is ahead of 'origin/main' by 2 commits. (use "git push" to publish your local commits)

"Ahead by 2" means you've saved twice on your laptop and sent neither to GitHub. Notice that Git is telling you the exact command to run. It usually is — those hints in brackets are worth reading rather than skipping past.

A shorter version, once you're comfortable

git status -s gives a compact two-column output: ?? for untracked, M for modified, A for added. Faster to scan once you know what you're looking at. Stick with the full version while you're learning — the hints are the useful part.

Q7You run git status and see modified: style.css in red. You then run git commit -m "Update styles". What ends up in the commit?
Show answer

Nothing. Git refuses with "no changes added to commit". The file was modified but never staged, so there was nothing for the commit to capture.

You need git add style.css first. Red → add → green → commit.

07

git add — the staging area

turning red into green

git add takes a change from your working directory and puts it in the staging area. It saves nothing permanently — it only marks it as "include this in my next snapshot".

Do this now — stage one file and watch it change colour

$ git add README.md $ git status
Changes to be committed: modified: README.md Untracked files: notes.txt

There it is. README.md moved into a new section and turned green. notes.txt is still red because you didn't add it. That's the staging area doing its job — you are choosing what goes in.

Do this now — stage the rest

$ git add . $ git status Changes to be committed: modified: README.md new file: notes.txt

The ways to add

git add filenameOne specific file. Precise, and what to use when you're being careful.
git add .Everything changed in the current folder and below. Convenient, and what most people use most of the time.
git add *.htmlEverything matching a pattern — all HTML files here, in this case.
git add -pInteractive. Walks you through each chunk of change and asks yes or no. Powerful; you don't need it yet, but remember it exists.

The habit that separates careful people from careless ones

git add . is a loaded gun. It stages everything — including the 2 GB video you dropped in the folder, the file of API keys you meant to delete, and half-finished work you weren't ready to save.

Always run git status before git add ., and actually read the list. Two seconds of attention. It's the difference between a clean history and an embarrassing one that's now permanent and public.

Changing your mind

Staged something by mistake? git restore --staged filename takes it back out. Your edits are completely untouched — it just turns the file red again. Nothing is lost.

Q8You run git add report.txt. Then, before committing, you edit report.txt again. You commit. Is the second edit included?
Show answer

No. This is the subtle one, and it's worth understanding properly rather than filing away.

git add stages a snapshot of the file as it was at that moment, not a permanent link to the file. Your later edit exists only in the working directory. Run git status and you'll see report.txt listed twice — green under "to be committed" and red under "not staged".

The fix is simply to run git add report.txt again before committing.

08

git commit — save points

the actual save

A commit takes everything currently staged and freezes it into a permanent snapshot, with a message explaining why.

Do this now — your first commit

$ git commit -m "Add my name to README and create notes file" [main 4f2a91b] Add my name to README and create notes file 2 files changed, 2 insertions(+) create mode 100644 notes.txt $ git status On branch main Your branch is ahead of 'origin/main' by 1 commit. nothing to commit, working tree clean

Clean again — and "ahead by 1 commit", telling you the work is saved locally but not yet on GitHub.

What's inside a commit

A snapshotThe state of every tracked file at that moment, not just the ones you changed. A commit is a project version, not a file version.
A messageYour explanation of why the change was made.
Author and timestampTaken from the user.name and user.email you set in section 03.
A hashThat 4f2a91b is a unique fingerprint, shortened from 40 characters. It's how you refer to this exact commit forever, and no two commits ever share one.
A parentA link to the commit that came before it. Chain those links together and you have your project's history — that chain is, quite literally, what a Git repository is.

A useful thing to know

Git stores full snapshots, not lists of changes. That sounds wasteful, but if a file didn't change between two commits, Git stores it once and points at it twice. So a hundred commits on a large project costs far less space than you'd expect — this is why cloning a repo with ten years of history is usually quick.

Always use -m

If you type git commit with no -m, Git opens a text editor to ask for a message. If you set core.editor back in section 03, that's VS Code and you're fine — type the message, save, close the tab.

If you skipped that step, it may be Vim, which does not respond to normal keys. Escape route: press Esc, type :q!, press Enter. Write that down somewhere; you'll need it eventually.

Do this now — a second commit, from memory

Don't scroll up. Open notes.txt in VS Code, add a line about what you've learned so far, save it, then get it committed. If you get stuck, run git status and read what it tells you to do. That's the actual skill being practised here — not memorising commands, but knowing how to ask Git what to do next.

How often should you commit?

More often than feels natural. A good commit is one complete small thing — "add the email field", "fix the broken link". Not "everything I did today".

Small commits mean that when something breaks, you can find exactly which change caused it. Big commits mean staring at 400 changed lines wondering which one did it. Nobody has ever regretted committing too often.

09

Writing messages people respect

low effort, high signal

This feels cosmetic. It isn't. Commit messages are the most visible writing you do as a developer — reviewers, teammates and interviewers all read them, and a history full of "update" tells them something about you that you'd rather it didn't.

The rule

Finish this sentence

"If applied, this commit will…"

So: "Add email validation to the signup form". Present tense, describes the change, no full stop needed, under about 50 characters.

Badupdate · fix · asdf · final · final v2 · changes · done · .
GoodAdd roll number field to registration form
GoodFix broken syllabus link in footer
GoodRemove unused CSS from header
GoodRename student folder to match username

A useful test: if you looked at this list of messages in three months, could you find the one commit you're looking for without opening any of them? That's the entire purpose.

Why present tense?

It reads as an instruction the commit carries out, which is how Git's own generated messages are written ("Merge branch…", "Revert…"). Consistency with the tool is the reason; it's a convention, not a law, but it's near-universal and following it costs nothing.

Fixing the last message

Typo in the message you just wrote? git commit --amend -m "Better message" replaces it. Only do this before you push. After pushing, leave it alone — making a new commit is normal and nobody minds.

Q9Which of these is the best commit message?
  1. fixed stuff
  2. Fixed the thing where the button didn't work properly when you clicked it on mobile devices sometimes
  3. Fix submit button not responding on mobile
  4. update index.html
Show answer

(c). It says what changed, it's specific, it's present tense, and it fits on one line.

(a) and (d) say nothing useful — (d) is especially empty because Git already records which file changed. (b) has the right information but is far too long for a summary line; that level of detail belongs in the commit's extended description, if anywhere.

10

git log and git diff

reading what happened

git log — your history

$ git log --oneline a91c3e2 Add learning notes 4f2a91b Add my name to README and create notes file 8c1d0f4 Initial commit

Newest at the top. Three commits: GitHub made the first when you ticked "Add a README", and the other two are yours.

git log --onelineCompact, one line each. What you'll use nearly all of the time.
git logFull detail — author, date, complete message. Press q to exit.
git log -3Only the last three commits.
git log --statAdds which files changed and how many lines in each.
git log --oneline --graphDraws the history as a diagram. Looks like a straight line now; it'll be more interesting once you use branches.

Stuck in a screen you can't exit?

Long output opens in a pager. Press q to quit. Arrow keys or Space scroll. This catches everyone exactly once — q for quit.

git diff — exactly what changed

Do this now

Edit notes.txt, add any line, save, then run:

$ git diff diff --git a/notes.txt b/notes.txt --- a/notes.txt +++ b/notes.txt @@ -1,2 +1,3 @@ practice notes learned about staging +learned about diff

Lines starting with + (green) were added. Lines with - (red) were removed. Unmarked lines are context, shown so you can see where the change sits. The @@ -1,2 +1,3 @@ line says which line numbers you're looking at — you can ignore it.

git diffChanges you have not staged yet.
git diff --stagedChanges you have staged. A good last check before committing.
git diff filenameJust that one file.

Build this habit now

Run git diff before every git add. It takes seconds and it catches the debugging line you forgot to delete, the password you accidentally hardcoded, and the file you changed by mistake. Professional developers do this reflexively, and it's the cheapest quality habit you can build.

11

git push and git pull

talking to GitHub

Do this now — send your work up

$ git push Enumerating objects: 8, done. Writing objects: 100% (6/6), 512 bytes, done. To https://github.com/YOUR-USERNAME/git-practice.git 8c1d0f4..a91c3e2 main -> main $ git status Your branch is up to date with 'origin/main'.

Now refresh your repository page on GitHub. Your files are there, your commits are listed, your name is on them. That is the loop. Everything else in this course is a variation on it.

Take a moment to look around

Click the commit count above the file list. You'll see your commits with their messages. Click one — GitHub shows you the exact diff, the same information git diff gave you in the terminal. This is what your TA reads when marking your work, and what an interviewer sees when they open your profile.

git pull — the other direction

Pull brings down commits that exist on GitHub but not on your laptop. You need it when you work on two machines, when you're on a team, or when you edit a file directly on the GitHub website.

Do this now — create a change on GitHub and pull it

  1. On GitHub, open README.md and click the pencil icon.
  2. Add a line. Scroll down, click Commit changes.
  3. Back in your terminal:
$ git pull Updating a91c3e2..d3f8b02 Fast-forward README.md | 1 + $ cat README.md # your web edit is now on your laptop

You'll see the words "Fast-forward". That means your laptop had nothing new of its own, so Git could simply catch up. You'll meet that term properly in the session — for now, it just means the update was clean.

The rule that avoids most pain

Pull before you start working. Push when you finish.

If you and GitHub both have new commits, Git has to combine them, which is where beginners get confused and frightened. Pulling first means that situation almost never arises.

Working on two computers

Common in a hostel — a laptop and a lab machine. The pattern is simple and worth internalising now:

$ git pull # when you sit down ... do work, commit as you go ... $ git push # before you get up

Break that habit and you'll eventually have different work on two machines with no easy way to tell which is which. Keep it and Git handles the syncing invisibly.

If push is rejected

"Updates were rejected because the remote contains work that you do not have locally" means GitHub has something you don't. Run git pull, then git push. If the pull opens a text editor asking for a merge message, press Esc then type :wq then Enter to accept the default.

Q10You work on your laptop all evening and make six commits. You never push. Your laptop's drive fails overnight. What have you lost?
Show answer

All six commits. Committing saves to the .git folder on that laptop and nowhere else. The version on GitHub is still whatever you last pushed.

This is the practical argument for pushing often — not at the end of the week, but whenever you finish something. Push is your backup.

12

Renaming, moving and deleting

the bit tutorials skip

You will rename and delete files constantly, and it confuses beginners because Git needs to be told — dragging something to the Bin doesn't remove it from your repository.

Deleting

Do this now — delete a file and watch what Git says

$ echo "temporary" > scratch.txt $ git add . && git commit -m "Add scratch file" $ rm scratch.txt # or delete it in your file manager $ git status Changes not staged for commit: deleted: scratch.txt

Red again — the deletion is a change like any other, and it isn't recorded until you stage and commit it.

$ git add . $ git commit -m "Remove scratch file" $ git push

This is why "I deleted it but it's still on GitHub"

Deleting the file locally is only step one. Until you commit the deletion and push, GitHub still has it. There's nothing strange happening — deletion just follows the same add-commit-push loop as everything else.

git rm scratch.txt does the delete and the staging in one step, if you prefer. Both are fine.

Renaming and moving

$ git mv notes.txt learning-notes.txt $ git status Changes to be committed: renamed: notes.txt -> learning-notes.txt

You can also just rename it in VS Code or your file manager. Git then sees a deleted file and a new one, but when you git add . it's usually smart enough to notice the contents are identical and report it as a rename anyway. Both routes work; git mv is simply more explicit.

A trap on Windows and Mac

Those systems treat Index.html and index.html as the same file, but Git and Linux servers don't. So renaming a file to change only its capitalisation may appear to do nothing at all in Git.

If you need to, do it in two steps: git mv index.html temp.html then git mv temp.html Index.html. This matters more than it sounds — it's a classic cause of "it works on my laptop but the deployed site shows a broken image".

Getting a deleted file back

Deleted something by accident and haven't committed yet?

$ git restore scratch.txt

It comes straight back, exactly as it was at the last commit. This is one of those moments where the value of committing often becomes very concrete.

13

.gitignore

what not to track

Some files should never go into a repository. A .gitignore file lists them, and Git then pretends they don't exist — they won't show as untracked, and git add . will skip them.

Dependenciesnode_modules/ — tens of thousands of files that anyone can regenerate with one command. Never commit this.
Secrets.env, API keys, passwords, credentials. Committing these to a public repo is a real security incident that happens to real people every week.
Build outputdist/, build/, target/, *.class — generated from your source, so storing it is duplication that goes stale.
OS and editor junk.DS_Store on Mac, Thumbs.db on Windows, .vscode/. Nobody else needs your editor settings.
Large binariesVideos, big datasets, installers. Git stores every version forever, so a 200 MB file committed five times is a 1 GB repository nobody can clone quickly.

Do this now — add one

$ touch .gitignore $ code .gitignore

Put this in it:

# dependencies node_modules/ # secrets — never commit these .env *.key # build output dist/ build/ # OS junk .DS_Store Thumbs.db
node_modules/Trailing slash means "this folder and everything in it".
*.keyThe asterisk matches anything, so this ignores every file ending in .key.
# commentLines starting with # are notes for humans. Use them — a bare list of patterns is unreadable in six months.

Then test that it actually works

$ echo "SECRET_KEY=hunter2" > .env $ git status # .env does NOT appear. That's the point. $ git add .gitignore $ git commit -m "Add gitignore" $ git push

Note that .gitignore itself is committed. It's a shared rule for the project, so everyone who clones it gets the same protection.

The important limitation

.gitignore only affects files Git isn't already tracking. If you commit a file first and add it to .gitignore afterwards, Git keeps tracking it — and worse, it stays in your history permanently, visible to anyone who looks, even if you delete it later.

So: write your .gitignore before your first commit. If secrets do get committed to a public repo, the only safe response is to treat them as compromised and change them.

You don't have to write these from scratch

When creating a repository, GitHub offers a .gitignore template — pick Node, Java, Python, whatever fits. They're far more thorough than anything you'd write from memory. github.com/github/gitignore has one for every language.

Writing a README

the front page of your work

The README.md is what GitHub displays when anyone opens your repository. It is the first thing a TA sees when grading and the first thing a recruiter reads when they click through from your profile. An empty one makes a project look abandoned.

Markdown, in about two minutes

The .md means Markdown — plain text with a few symbols that turn into formatting. This is basically the whole language:

# Big heading ## Smaller heading ### Smaller still Normal text. **Bold text.** *Italic text.* - A bullet point - Another one 1. A numbered item 2. Another one `inline code` [Link text](https://example.com)

For a block of code, wrap it in three backticks with the language name:

```html <h1>Hello</h1> ```

You'll use Markdown constantly — GitHub issues, pull request descriptions, documentation, and this course's submissions all use it.

Do this now — write a real README

Open README.md, delete what's in it, and write something like this with your own details:

# Git Practice My first Git repository, created while learning the basics for ESD, M.Tech CSE. ## What I learned - The difference between Git and GitHub - Staging changes with `git add` before committing - Reading `git status` to work out what state things are in - Pushing to GitHub so work is backed up ## Author Your Name — [@your-username](https://github.com/your-username)

Then commit and push it, and look at the repository page. GitHub renders it properly — headings, bullets, a working link.

$ git add README.md $ git commit -m "Write a proper README" $ git push

What a good README answers

What is this? How do I run it? What's it built with? Who wrote it? Four questions, four short sections. That's enough for coursework and, honestly, for most professional projects too.

Preview it while you write

In VS Code, press Ctrl+Shift+V with a .md file open to see it rendered. Much easier than pushing and refreshing to check your formatting.

15

Undoing things without panic

five escape hatches

Fear of breaking things is what makes beginners commit rarely and push never. So here's the reassurance, and it's true: once you have committed, it is very hard to permanently lose work in Git. Almost everything is recoverable.

You don't need to memorise these. Bookmark the page and come back when you need one.

Unstage a filegit restore --staged file.txt
Takes it out of staging. Your edits are completely untouched — it just turns green back to red.
Throw away your editsgit restore file.txt
Reverts the file to how it was at the last commit. This one does destroy work. Uncommitted changes cannot be recovered. Be certain.
Fix the last commit messagegit commit --amend -m "Better message"
Only before you've pushed.
Add a forgotten file to the last commitgit add forgotten.txt then git commit --amend --no-edit
Folds it in and keeps the existing message. Again, only before pushing.
Undo a pushed commitgit revert a91c3e2
Creates a new commit that undoes that one. Safe for shared work because it adds to history rather than erasing it.

The one rule about --amend

It rewrites your last commit. Safe before you push, messy after. If you've already pushed, don't amend — just make a new commit that fixes the problem. That's completely normal and nobody will comment on it.

Looking at an old version

Want to see what a file looked like three commits ago? Get the hash from git log --oneline, then:

$ git show 4f2a91b:notes.txt

That prints the old version to the screen without changing anything in your folder. This is the payoff for all the committing — every past state is still there and still reachable.

Your real safety net

Your repository on GitHub is a complete backup. If your local folder ever gets into a state you can't untangle, you can delete the whole folder and clone it again fresh. You lose only work you hadn't pushed.

That isn't a failure — it's a legitimate move, and experienced developers do it too rather than spend an hour untangling something. Push often and the cost of doing it stays near zero.

When it goes wrong

every error you're likely to hit

Read the error message first. Git's messages are unusually good — they normally tell you exactly what to type next. These are the ones that catch people anyway.

fatal: not a git repositoryYou're standing in the wrong folder. Run pwd, then cd into your project. Git commands only work inside a folder containing .git.
I'm trapped in a weird editorYou forgot -m. Press Esc, type :q!, Enter. Then redo the commit with -m "your message". Prevent it for good: git config --global core.editor "code --wait"
Password rejected on pushYour password isn't wrong — GitHub removed password-over-Git in 2021, so that method no longer exists. Run gh auth login once and it's solved permanently.
Permission denied / 403You're pushing to a repository you don't own. Run git remote -v and check your own username is in the URL.
Updates were rejectedGitHub has commits you don't have. git pull, then git push.
nothing to commitYou didn't git add. Red means it isn't going in.
I committed but GitHub is emptyYou didn't push. Check git status — if it says "ahead by N commits", that's exactly what's happening.
Stuck in a scrolling screenPress q. That's the pager, used by git log and git diff.
Every line shows as changedThe Windows line-endings problem. Run git config --global core.autocrlf true and re-clone. See section 03.
Please tell me who you areYou skipped the user.name and user.email config. Section 03 has the two commands.
error: pathspec did not matchYou typed a filename that doesn't exist — nearly always a typo. Run ls to see the real names, and use Tab completion next time.

Helping yourself

$ git help commit # full manual, press q to exit $ git commit -h # short summary of the options

And searching is completely legitimate. Paste the exact error message into a search engine — Git has been around for twenty years, and whatever you've hit, several thousand people have hit it before you and written it up.

Asking for help is a skill, not a failure

When you're properly stuck, ask someone — and have a screenshot of your terminal showing git status and the error message ready when you do. That single screenshot usually makes the answer obvious in seconds.

Asking early with good information is a professional skill that people get promoted for. Silently struggling for two days is not.

A first look at branches

so you arrive warm, not cold

This is where the session starts, so you don't need to master it. You just need the word to be familiar rather than frightening when it appears on the screen.

You've been on a branch this entire time. git status has been saying "On branch main" since section 06.

What a branch is

Most tutorials say "a parallel copy of your project". That's misleading, and it's why merging feels scary to people. Here's the accurate version:

A branch is a pointer to one commit

That's it. It's a tiny file containing the ID of a commit. When you make a new commit, the pointer moves forward to it.

Because it's just a pointer, creating a branch copies nothing, takes no time, and uses no meaningful space.

Do this now — see it for yourself

$ cat .git/refs/heads/main a91c3e2f4b8d1c05e7a92f3b6d840c1e5a7b2f93 $ git log --oneline -1 a91c3e2 Add learning notes

The same ID. The branch "main" is literally that one line of text pointing at your latest commit. No magic anywhere.

Why they exist

You want to try something risky without disturbing the working version. So you make a branch, experiment there, and if it works you combine it back in. If it doesn't, you delete the branch and nothing was harmed. On a team, everyone works on their own branch and combines at the end, so nobody overwrites anybody.

Optional — try one

Entirely safe. You can undo all of it.

$ git switch -c experiment # create a branch and move to it $ echo "trying something" >> notes.txt $ git add . && git commit -m "Try an experiment" $ git switch main # go back $ cat notes.txt # your experiment line is GONE $ git switch experiment $ cat notes.txt # and it's back $ git branch # list branches, * marks where you are

Your files changed on disk when you switched. Nothing was lost — the two branches simply point at different commits, and Git makes the folder match whichever one you're on.

What the session will cover

Switching and checking out · merging branches together · fast-forward vs merge commits · stashing half-finished work · rebasing · worktrees · and pull requests, which is how you'll submit every assignment this term.

None of that is needed now. Arriving knowing that a branch is a pointer puts you comfortably ahead of where most people start.

Q11You create a branch on a project with ten years of history and 50,000 files. Roughly how much disk space does the new branch use?
Show answer

About 41 bytes. A branch is one small file containing a commit ID. Nothing is copied.

This is why teams create and delete branches casually, dozens per week. If branches were copies that would be absurd — because they're pointers, it's free.

Final checkpoint

Fifteen questions. Answer each one in your head — or better, write it down — before opening the answer. Getting one wrong is information, not failure; go back to the section it came from and reread that bit.

1In one sentence each: what is Git, and what is GitHub?
Show answer

Git is a program on your laptop that records versions of a folder. GitHub is a website that stores copies of Git projects online so you can share them and collaborate.

2Name the four places a file can be, in order, and the command that moves it between each.
Show answer

Working directory →(git add)→ staging area →(git commit)→ commit history →(git push)→ GitHub.

3What does a red filename in git status mean?
Show answer

It's changed (or brand new) but not staged, so it will not be in your next commit. Run git add to turn it green.

4What's the difference between git add . and git add filename, and why should you be careful with the first?
Show answer

The dot stages every change in the current folder and below; naming a file stages only that one. The dot can sweep up secrets, huge files and half-finished work — so run git status and read it first.

5You commit but don't push. Where does your work exist?
Show answer

Only in the .git folder on that one laptop. GitHub has nothing. If the laptop dies, the work is gone.

6Write a good commit message for: you added a phone number field to a signup form.
Show answer

Something like Add phone number field to signup form. Present tense, specific, completes "if applied, this commit will…", under about 50 characters.

7What does origin refer to?
Show answer

The default nickname for the remote copy of your repository — in practice, the GitHub URL you cloned from. A convention rather than a keyword, but effectively universal.

8Name three kinds of file that belong in .gitignore, and say why for one of them.
Show answer

Dependencies (node_modules/) — regenerable, tens of thousands of files. Secrets (.env) — committing them to a public repo is a security incident. Build output (dist/) — generated from source, so it's duplication. Large binaries and OS junk also count.

9You add a file to .gitignore but it was already committed last week. Is it now ignored?
Show answer

No. .gitignore only affects files Git isn't already tracking. It also stays in your history permanently. This is why the .gitignore should come before the first commit — and why a leaked secret must be changed, not just deleted.

10You delete a file in your file manager. Is it gone from the repository?
Show answer

Not yet. git status shows it in red as deleted:. You still have to git add, commit and push for the deletion to be recorded. Deletion follows the same loop as every other change.

11You're trapped in a strange editor after running git commit. What do you press?
Show answer

Esc, then :q!, then Enter. Then redo the commit with -m "your message".

12Your push is rejected saying the remote has work you don't have. What do you do?
Show answer

git pull to bring their commits down, then git push. Better still, build the habit of pulling before you start work.

13What is a branch, mechanically?
Show answer

A pointer to a single commit — a small file holding a commit ID. Not a copy of the project. Committing moves the pointer forward.

14You staged a file by mistake. How do you unstage it without losing your edits?
Show answer

git restore --staged filename. It turns green back to red; your edits are untouched. Note that git restore filename — without --staged — is the dangerous one that throws the edits away.

Show answer

git status → git add . → git commit -m "message" → git push
