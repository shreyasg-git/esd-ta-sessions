01

What the Bug Lab gave you

Corethe app, the suite, the loop

In the Bug Lab you didn't write tests. You were given an API with eight things wrong with it, a list of those eight, and a test class that already checked each one. Your job was to change the app until the tests passed. This section names the pieces, so the rest of the page can talk about them.

The appA Campus Event Registration API. Events have a capacity; students register for an event with their email; a registration is ACTIVE or CANCELLED. Spring Boot 3.3.5, Spring Data JPA, an in-memory H2 database and Swagger UI. No security.
The bug listESD-Lab3-Bugs-to-Fix.md: eight bugs, each written as "it does this; it should do that", most with the status code it should return.
The testsLab3BugTests.java: one test per bug, named B1_… to B8_…, plus smoke_eventListWorks. At the start, the eight failed and the smoke test passed.
The loopThe README's step 6: one bug at a time — find a failing test, reproduce it, investigate, fix, rerun that test, rerun them all.
The reportFor each bug: observed behaviour, expected behaviour, root cause, correction, verification — with screenshots.
Two feature tasksRegistration transfer and check-in. Not covered here: this page is about proving code works, not building it.

The loop is a method

The README's six steps are one idea, repeated eight times. Written as a method:

StepWhat you do
PredictBefore you run anything, say what you expect and why. "The test wants 409. I think the app returns 201, because nothing checks the capacity." Sections 03 and 06.
TriggerMake the wrong behaviour happen on demand: the failing test, or the same request in Swagger or curl. Sections 03 and 09.
Find the causeFollow the evidence to one line of code: the failure message, the stack trace, the log, the SQL. Sections 07 and 08.
FixChange the app — never the test — at the cause, not where the symptom showed up. Section 06.
Re-triggerRun the same test again: green. Then run all of them, to check you broke nothing else. Section 06.

The report's headings are the same method written down. Observed and expected are the trigger and the prediction. Root cause is what you found. Correction is the fix. Verification is the re-trigger. If you could fill all five boxes for a bug, you understood it. If you couldn't fill root cause, the test went green but you don't yet know why.

Why the tests were off-limits

A test is the specification, written as code. Change it to match the app and it now specifies the bug. The README said "Do not change or weaken the tests", and the same holds for tests you write yourself: if a test really is wrong, change it on purpose, as a decision about what the app should do — never just to get a green tick.

Six kinds of bug

The eight bugs weren't eight different problems. Each was one of six kinds, and each kind looks the same from the outside in any app, yours included:

Validation missingBad input is accepted.
A rule not enforcedA request that breaks a business rule succeeds.
A status mapped wrongThe right failure comes back with the wrong number.
A state not savedThe response says it worked; the database didn't change.
A filter missingA list holds rows it shouldn't.
A wrong lookupYou get a real object, just not the one you asked for.

Section 10 takes each kind and shows what you see, which assertion catches it, and where in the code to look.

Your Product app is not the Bug Lab

The Bug Lab ran on Spring Boot 3.3.5 with no security. Your Product project runs on Boot 4.1.1, with Spring Security and JWTs from Lab 2. The tests work the same way in both. Where a name or an import is different, there's an "On Boot 3" note, and where security changes what you see, the page says so.

Q1The report asks for both a root cause and a correction. Why isn't the correction enough?
Show answer

The correction says what you changed. The root cause says why the old code behaved wrongly. You can make a test pass with a change you don't understand — at the wrong place, or by luck. Writing the cause in one sentence is how you check that your fix is at the cause and not at the symptom.

Q2At the start of the lab, the smoke test passed. Why have it at all?
Show answer

It shows that the app starts and that one simple request works. If the smoke test fails too, the problem isn't one of the eight bugs: the whole app is broken (section 03, "Every test red at once").

02

How its tests are built

Corefive ideas in 150 lines

Look past the bug names and Lab3BugTests.java uses only five ideas: start the app, get a fake HTTP client, empty the tables, and then arrange, act, assert in every test. Here is the top of the class (lines 28–45 of the file):

@SpringBootTest @AutoConfigureMockMvc class Lab3BugTests { @Autowired MockMvc mvc; @Autowired EventRepository events; @Autowired RegistrationRepository registrations; @BeforeEach void clean() { registrations.deleteAll(); events.deleteAll(); }
@SpringBootTestStarts your whole application inside the test run: every bean, the H2 database, Hibernate creating the tables. It starts once and is kept for every test that asks for the same setup.
@AutoConfigureMockMvcAlso builds a MockMvc connected to that application.
@Autowired fieldsThe test asks Spring for beans, the way your services do (From request to row). With the repositories, a test can write and read rows directly.
@BeforeEach clean()Runs before every test, so each test starts with empty tables and none depends on what another left behind. Registrations go first because each one points at an event: deleting an event that still has registrations would break the foreign key.
throws ExceptionOn every test that calls perform(…), because it can throw. If it does, the test errors instead of failing (section 03).

What MockMvc runs, and what it skips

MockMvc is a fake HTTP client. It builds a request object in memory and hands it straight to Spring's DispatcherServlet, in the same Java process, on the same thread. No server starts, no port opens, and nothing crosses the network. Everything after that point is real: your filters (in the Product app, Spring Security), the controller, @Valid, your exception handler, Jackson, the service, the repository, and real SQL on H2. That's why a MockMvc test can catch a wrong status: the status comes from your real code. The one thing it skips is what a real server does with an error your code didn't handle. Section 09 shows when that matters.

One test, three parts

Every test in the file has the same shape. Here is B3 (lines 65–76):

@Test void B3_rejectsRegistrationAtCapacity() throws Exception { Event e = events.save(new Event("Full", 1)); registrations.save( new Registration(e, "first@example.com", RegistrationStatus.ACTIVE) ); mvc.perform(post("/api/events/" + e.getId() + "/registrations") .contentType(MediaType.APPLICATION_JSON) .content("{\"studentEmail\":\"second@example.com\"}")) .andExpect(status().isConflict()); }
LineWhat it does
events.save(…), registrations.save(…)Arrange. Writes rows straight to the database through the repositories, skipping the API, so the test controls exactly what exists: one event with one seat, already taken.
mvc.perform(post(url))Act. Builds a request: the HTTP method and the URL. get, post, put and delete come from MockMvcRequestBuilders.
.contentType(MediaType.APPLICATION_JSON)The Content-Type header. Leave it out and @RequestBody refuses the body with 415 Unsupported Media Type.
.content("{…}")The body, as a string of JSON. The \" are Java escapes for quotes. On Product below, a text block ("""…""", Java 15+) reads more easily.
.andExpect(status().isConflict())Assert. Reads the status of the response. If it isn't 409, the test fails.

The other shapes in the file

jsonPath (B6)jsonPath("$", hasSize(1)) says the body is a list of one item; jsonPath("$[0].studentEmail").value(…) checks a field of the first item. In a JSON path, $ is the whole body, .name a field, [0] the first element and [*] every element. hasSize is a Hamcrest matcher.
Read the row back (B5)After the request, registrations.findById(…) reads the database, and assertEquals checks the status column. A 204 only says the code returned 204. Only the row says whether anything changed.
No Spring at all (B7)new ApiExceptionHandler(), a MockHttpServletRequest, a direct call to the handler method, and a check on the ResponseEntity. That's a plain unit test: no app starts, so it's very fast, and it tests one method alone.
Give the bug room (B8)It saves one event before asking for id 99999. With no events at all, a lookup that falls back to "some event" would find nothing and pass by accident.
The smoke testOne cheap request that should always work.

B7's shape works on your Product app too. Your Lab 2 GlobalExceptionHandler can be tested the same way:

package com.esd.ecommerce; import com.esd.ecommerce.dto.ApiErrorResponse; import com.esd.ecommerce.exception.GlobalExceptionHandler; import com.esd.ecommerce.exception.ProductNotFoundException; import org.junit.jupiter.api.Test; import org.springframework.http.HttpStatus; import org.springframework.http.ResponseEntity; import org.springframework.mock.web.MockHttpServletRequest; import static org.junit.jupiter.api.Assertions.assertEquals; class GlobalExceptionHandlerTests { @Test void productNotFoundBecomes404() { GlobalExceptionHandler handler = new GlobalExceptionHandler(); MockHttpServletRequest request = new MockHttpServletRequest("GET", "/api/products/get-id/7"); ResponseEntity<ApiErrorResponse> response = handler.handleProductNotFound(new ProductNotFoundException(7L), request); assertEquals(HttpStatus.NOT_FOUND, response.getStatusCode()); assertEquals("Product with ID 7 not found", response.getBody().getMessage()); assertEquals("/api/products/get-id/7", response.getBody().getPath()); } }

On Boot 3 (the Bug Lab)

@AutoConfigureMockMvc was imported from org.springframework.boot.test.autoconfigure.web.servlet. On Boot 4 (your Product app) it is org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc, from the spring-boot-starter-webmvc-test dependency your pom already has. @SpringBootTest, MockMvc, the request builders and the matchers didn't move.

Try it — label one test

In Lab3BugTests.java, pick B4 and B6. For each, find the arrange lines, the act line and the assert lines. Then answer Q1 below without looking.

Q1In B4, what does the arrange step create, and why is the email in the request written in capitals?
Show answer

An event with three seats and one ACTIVE registration for student@example.com. The request registers STUDENT@example.com: the same person in different letters. The bug list says email comparison should ignore case, so the capitals are the whole point of the test — a check that compares exactly would let the duplicate through.

Q2B5 already expects 204 No Content. Why does it also read the row?
Show answer

Because the status is just a number the controller returns. A cancel method can return 204 and change nothing. The row is the only proof that the state changed. (Section 10, "a state not saved".)

Q3Why does clean() run before each test, rather than once before all of them?
Show answer

JUnit doesn't promise an order for the tests, and the application — with its database — is shared between them. Emptying the tables before each test means every test starts from the same place, and a test can't pass or fail because of rows another test left behind.

03

Reading a test that fails

Coretwo numbers, then the response

A red test has already done half the work. It tells you what it wanted and what it got. Read that before you open any of the app's code.

Failure or error

JUnit has two kinds of red. A failure is an assertion saying no: an AssertionError with "expected … but was …". An error is the test throwing something else before it could assert — an exception out of perform(…), or an app that wouldn't start. Maven counts them separately at the end of mvn test:

[ERROR] Tests run: 9, Failures: 8, Errors: 0, Skipped: 0 … [INFO] BUILD FAILURE

A failure means the code ran and answered wrongly. An error means it didn't get as far as answering. They send you to different places.

The status message

Status expected:&lt;400&gt; but was:&lt;201&gt;

Expected is the test; was is the app. The pair narrows the search before you've opened a file — this is the predict step:

You seeIt suggests
400 wanted, 201 or 200 cameThe app accepted input it should have rejected: validation didn't run, or isn't there.
409 wanted, 201 cameA business rule wasn't checked: the service saved without asking.
409 wanted, 400 cameThe rule was checked and its exception thrown — but the exception is mapped to the wrong status.
404 wanted, 200 cameThe app found something when there was nothing to find: a wrong lookup.
2xx wanted, 401 / 403 cameSecurity stopped the request before your controller. In a test, usually a missing user (section 05).
2xx wanted, 400 / 415 cameThe body was refused before your method ran: invalid, unreadable, or sent without a content type.

The other messages

Each assertion has its own wording. You'll meet all four on the Product app later in this page:

JSON path "$.message" expected:&lt;Product with ID 99999 not found&gt; but was:&lt;…&gt; JSON path "$" Expected: a collection with size &lt;1&gt; but: collection size was &lt;0&gt; No value at JSON path "$.validationErrors.name" expected: &lt;Notebook A4&gt; but was: &lt;Notebook&gt;
JSON path … expected … but wasThe field is there but holds something else.
Expected: a collection with sizeHamcrest's wording for hasSize: the list is longer or shorter than it should be. Section 08.
No value at JSON pathThe field isn't in the body at all. Usually a different body came back from the one you expected: an error body instead of data, or the other way round.
expected: <…> but was: <…>JUnit's own assertEquals, with spaces in its wording. Section 10.

Scroll up: the request and the response

When a MockMvc test fails, Spring Boot prints the whole exchange in the test's output, just above the failure: the request, the controller method that handled it, any exception your advice resolved, and the response. Here is a shortened example, from the bug you'll plant in section 06:

MockHttpServletRequest: HTTP Method = POST Request URI = /api/products/add-product … Handler: Type = com.esd.ecommerce.controller.ProductController Method = com.esd.ecommerce.controller.ProductController#addProduct(ProductRequest) … Resolved Exception: Type = null … MockHttpServletResponse: Status = 201 … Body = {"category":"Books", … ,"name":"", … }

Read it from the bottom up. Status and Body are what the app answered. Resolved Exception names the exception your advice turned into the response; here it's null, because as far as the app knew, nothing went wrong. Handler says which method ran, so you know which file to open first. Tests that pass print nothing: Boot prints the exchange only on failure.

Every test red at once

If every test fails, the smoke test too, and each one says Failed to load ApplicationContext, no single bug is to blame: the application didn't start inside the test. Only the first test shows the real reason. The rest say ApplicationContext failure threshold (1) exceeded: skipping repeated attempt to load context, which means "same problem as above; not trying again". Find the first failing test and read its last Caused by. Section 07 shows how.

Try it — make one test fail on purpose

  1. In Lab3BugTests.java, change the smoke test's status().isOk() to status().isCreated(). Run only that test (the green arrow beside it).
  2. Read the message: both numbers are in it. Then scroll up in the output and find Status in the printed response.
  3. Change it back and run it again: green.

Q1A test says Status expected:<201> but was:<403>. Before you open any code, where do you look?
Show answer

At security. 403 means the request was refused because of who sent it, before the controller ran. In a test that usually means the user in the request doesn't have the role the route needs. Nothing in the service is involved yet.

Q2A test expects jsonPath("$.name").value("Pen") and fails with No value at JSON path "$.name". The status assertion above it was isOk() and passed. What came back?
Show answer

A 200 whose body has no top-level name: most likely a list ([{…}]), so the path would be $[0].name. Scroll up to the printed Body and look at its first character.

04

Setting up tests in the Product project

Corea test database, a test user

The Bug Lab came with its tests set up. Your Product project has only the one test Spring Initializr wrote, EcommerceApplicationTests, which checks that the app starts. Before you add more, three things differ from the Bug Lab — and one of them can cost you your data.

Your tests would run on your MySQL

The Bug Lab used H2 for everything. Your Product app's application.properties points at MySQL, ecommerceDB. A @SpringBootTest starts the real app with that file — so a test that empties a table the way the Bug Lab's clean() did would empty your real products table. Add the test database below before you write a single test.

1 · What your pom already has

Spring Initializr added two test starters (lab2-complete pom.xml, lines 57–66): spring-boot-starter-data-jpa-test and spring-boot-starter-webmvc-test. Between them you have JUnit, MockMvc, JsonPath, Hamcrest, AssertJ and Mockito. Nothing to add for those.

2 · Add two test dependencies

Inside <dependencies> in your pom.xml:

<!-- tests run on an in-memory database, never on your MySQL --> <dependency> <groupId>com.h2database</groupId> <artifactId>h2</artifactId> <scope>test</scope> </dependency> <!-- a logged-in user inside a test --> <dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-security-test</artifactId> <scope>test</scope> </dependency>
h2, scope testOn the classpath only while tests run. Your app itself still runs on MySQL. No version: Spring Boot chooses it.
spring-boot-starter-security-testLets a test act as a logged-in user — your add, update and delete routes are ADMIN-only. On Boot 4 this starter also connects Spring Security's test support to MockMvc; plain spring-security-test on its own doesn't make @WithMockUser reach the request.

After editing the pom, reload Maven in IntelliJ (the reload button in the Maven tool window, or the small "Load Maven Changes" icon that appears in the editor).

On Boot 3

The dependency was org.springframework.security:spring-security-test, and Boot 3 connected it to MockMvc by itself.

3 · A properties file just for tests

Create src/test/resources/application.properties (make the resources folder if it isn't there):

# Used instead of src/main/resources/application.properties when tests run. # An in-memory H2 database: made for the test run, gone afterwards. MySQL is never touched. spring.datasource.url=jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1 spring.datasource.username=sa spring.datasource.password= spring.jpa.hibernate.ddl-auto=create-drop # This file replaces the main one, so repeat every app.* property your code reads. app.security.jwt.issuer=ecommerce-api app.security.jwt.expiration-seconds=3600 app.security.jwt.secret=test-only-secret-key-that-is-at-least-32-bytes-long

When tests run, this file is used instead of your main application.properties, not on top of it: both files have the same name, and the test copy comes first on the classpath. That's why it repeats the three app.security.jwt.* properties. Leave the secret out and every test fails with Could not resolve placeholder 'app.security.jwt.secret' — section 07 reads that trace. ddl-auto=create-drop makes Hibernate create the tables from your entities when the tests start. H2 starts empty, so each test saves the rows it needs.

4 · Where test classes go

In src/test/java/com/esd/ecommerce/, next to EcommerceApplicationTests. @SpringBootTest finds your app by looking for @SpringBootApplication in the test's package and then in its parent packages, so a test must sit in com.esd.ecommerce or in a package below it.

Try it — prove the tests don't need MySQL

  1. Add the two dependencies and the file, then reload Maven.
  2. If you can, stop your MySQL server.
  3. Run EcommerceApplicationTests (right-click → Run). Green means the app started on H2 with your test properties. With MySQL stopped, that's proof the tests never touch it.
Q1You put logging.level.org.hibernate.SQL=DEBUG in your main application.properties. Do your tests print SQL?
Show answer

No. When tests run, the test file replaces the main one, so nothing from the main file applies. Put settings you want in tests into src/test/resources/application.properties.

05

Your first tests: a status, JSON, a 404, a 400

Corethe Bug Lab's style, on Product

Here is a test class for the Product API in the Bug Lab's style. Every part of it is something section 02 explained. The new parts are text blocks for the JSON and a logged-in admin. Save it as src/test/java/com/esd/ecommerce/ProductApiTests.java:

package com.esd.ecommerce; import com.esd.ecommerce.entity.Product; import com.esd.ecommerce.repository.ProductRepository; import org.junit.jupiter.api.BeforeEach; import org.junit.jupiter.api.Test; import org.springframework.beans.factory.annotation.Autowired; import org.springframework.boot.test.context.SpringBootTest; import org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc; import org.springframework.http.MediaType; import org.springframework.test.web.servlet.MockMvc; import java.math.BigDecimal; import static org.hamcrest.Matchers.containsInAnyOrder; import static org.hamcrest.Matchers.hasSize; import static org.junit.jupiter.api.Assertions.assertEquals; import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.user; import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get; import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post; import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath; import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status; @SpringBootTest @AutoConfigureMockMvc class ProductApiTests { @Autowired MockMvc mvc; @Autowired ProductRepository products; @BeforeEach void clean() { products.deleteAll(); } private Product saved(String name, String category) { return products.save(new Product( null, name, "for tests", new BigDecimal("49.00"), category, 10)); } @Test void getAllListsEveryProduct() throws Exception { saved("Notebook", "Books"); saved("Pen", "Stationery"); mvc.perform(get("/api/products/get-all")) .andExpect(status().isOk()) .andExpect(jsonPath("$", hasSize(2))) .andExpect(jsonPath("$[*].name", containsInAnyOrder("Notebook", "Pen"))); } @Test void getByIdReturnsThatProduct() throws Exception { saved("Notebook", "Books"); Product pen = saved("Pen", "Stationery"); mvc.perform(get("/api/products/get-id/" + pen.getId())) .andExpect(status().isOk()) .andExpect(jsonPath("$.name").value("Pen")) .andExpect(jsonPath("$.category").value("Stationery")); } @Test void unknownIdIs404WithTheErrorBody() throws Exception { saved("Notebook", "Books"); // another product exists, so a wrong lookup has room to show mvc.perform(get("/api/products/get-id/99999")) .andExpect(status().isNotFound()) .andExpect(jsonPath("$.status").value(404)) .andExpect(jsonPath("$.message").value("Product with ID 99999 not found")) .andExpect(jsonPath("$.path").value("/api/products/get-id/99999")); } @Test void adminCanAddAProduct() throws Exception { mvc.perform(post("/api/products/add-product") .with(user("admin").roles("ADMIN")) .contentType(MediaType.APPLICATION_JSON) .content(""" {"name": "Notebook", "price": 49.00, "category": "Books", "stock": 10} """)) .andExpect(status().isCreated()) .andExpect(jsonPath("$.id").isNumber()) .andExpect(jsonPath("$.name").value("Notebook")); assertEquals(1, products.count()); // read the database, not just the response } @Test void blankNameIsRejectedWith400() throws Exception { mvc.perform(post("/api/products/add-product") .with(user("admin").roles("ADMIN")) .contentType(MediaType.APPLICATION_JSON) .content(""" {"name": " ", "price": 49.00, "category": "Books", "stock": 10} """)) .andExpect(status().isBadRequest()) .andExpect(jsonPath("$.message").value("Request validation failed")) .andExpect(jsonPath("$.validationErrors.name").value("Product name is required")); assertEquals(0, products.count()); } @Test void addingWithoutALoginIs401() throws Exception { mvc.perform(post("/api/products/add-product") .contentType(MediaType.APPLICATION_JSON) .content(""" {"name": "Notebook", "price": 49.00, "category": "Books", "stock": 10} """)) .andExpect(status().isUnauthorized()); } }
saved(…)A small helper for the arrange step. Product has an all-arguments constructor from Lombok; the null id lets the database choose one.
getAllListsEveryProductTwo rows, then the status, the length, and the names in any order. findAll() promises no order, so the test doesn't assume one.
getByIdReturnsThatProductSaves two and asks for the second, so a lookup that returns "the first product" would fail.
unknownIdIs404WithTheErrorBodyB8's idea: another product exists. Then the error body your GlobalExceptionHandler builds — its status, message and path.
adminCanAddAProduct.with(user("admin").roles("ADMIN")) puts a logged-in ADMIN into this one request. Then the test reads the database: one row.
blankNameIsRejectedWith400The validation failure: 400, your handler's message, the field error under validationErrors.name — and nothing saved.
addingWithoutALoginIs401The same request with no user. Spring Security runs before your controller, so without a user every add is 401, whatever the body.

A user, not a token

In the running app you log in and send a JWT. The test needs none of that: user(…) sets the logged-in user directly, so the test checks your product code and not your login code. Putting @WithMockUser(roles = "ADMIN") on a test method does the same for the whole method. Testing login and tokens themselves is a different job: Who are you, and what may you do.

Running them

$ ./mvnw test -Dtest=ProductApiTests … [INFO] Tests run: 6, Failures: 0, Errors: 0, Skipped: 0 … $ ./mvnw test -Dtest=ProductApiTests#blankNameIsRejectedWith400 # just that one test $ ./mvnw test # every test in the project

On Windows, use mvnw.cmd in Command Prompt, or .\mvnw in PowerShell with the -D argument in quotes: .\mvnw test "-Dtest=ProductApiTests". In IntelliJ, click the green arrow beside the class or beside one test.

Try it — run them, then break one

  1. Add the class and run it: six green.
  2. In unknownIdIs404WithTheErrorBody, change the expected message to "Product 99999 not found". Predict the failure message, run it, and compare. Change it back.

Other kinds of test you'll meet

Everything above starts the whole app. Two other kinds start only part of it, and one tool isn't a Java test at all. The Bug Lab used none of them; learn the full-app test first.

@DataJpaTestStarts only the JPA part — entities, repositories, a database — and runs each test in a transaction that is rolled back at the end. For testing a repository method on its own. Boot 4: org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest (Boot 3: org.springframework.boot.test.autoconfigure.orm.jpa), from spring-boot-starter-data-jpa-test, already in your pom.
@WebMvcTest + @MockitoBeanStarts only the web layer for one controller; the service is replaced by a Mockito stand-in that you tell what to return. For testing a controller and your advice alone. Boot 4: org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest; @MockitoBean is org.springframework.test.context.bean.override.mockito.MockitoBean. Boot 3's @MockBean no longer exists in Boot 4.
SchemathesisReads an OpenAPI file and sends hundreds of generated requests to a running backend, checking every response against it. The contract doc shows it for your contract backend: api-contract §17.
06

The method, on a planted bug

Corepredict, trigger, fix, re-trigger

Now the Bug Lab's loop, on code you know. You'll plant one bug in the Product app, watch a test catch it, and take it out again. Commit first (git commit -am "before planting") so that undoing it is one command.

Plant it

In ProductController.addProduct, delete @Valid (lab2-complete, line 48):

@PostMapping("/add-product") public ResponseEntity<ProductResponse> addProduct( @RequestBody ProductRequest request) { // planted: @Valid deleted ProductResponse savedProduct = productService.addProduct(request); return ResponseEntity.status(HttpStatus.CREATED).body(savedProduct); }

1 · Predict

Before running anything, write down what you expect and why. The rules are still on ProductRequest — @NotBlank on name — but nothing checks them any more: @Valid is the switch that tells Spring to validate the body before calling your method (A slice you can defend). So a body with "name": " " reaches the service, trim() turns the name into "", and the product is saved. Prediction: blankNameIsRejectedWith400 goes red, with 201 where it wanted 400. The other five stay green.

2 · Trigger

Run ProductApiTests. The red test is your trigger: one click, the same result every time.

Status expected:&lt;400&gt; but was:&lt;201&gt;

The prediction was right, number for number. That matters. If a test goes red for a reason you didn't predict, you don't understand the bug yet, however obvious the fix looks. Scroll up to the printed exchange (section 03): Status = 201, and "name":"" in the body. The row was saved.

When there's no test yet

Write one now — before the fix. Write the test for the right behaviour, run it, and watch it fail with the numbers you predicted. A test you have never seen fail might not be testing anything: a test with a wrong URL, or one that asserts nothing, is just as green.

By hand, this route needs an ADMIN token in the running app (Who are you, and what may you do). The test makes itself the admin in one line — one more reason to trigger with a test.

3 · Fix

Put @Valid back. That fix is at the cause. A fix at the symptom — say, if (request.getName().isBlank()) in the service — would also turn this test green. But the rule would then live in two places, the other fields still wouldn't be validated, and this 400 would look different from every other 400 your app sends.

4 · Re-trigger

Run blankNameIsRejectedWith400 again: green. Then run the whole class, then the whole project: still green. That second run is the README's last step: the check that your fix didn't break something else. Here it couldn't have, but on a fix to shared code — a handler, a repository method — that is the run that catches it.

07

Reading a stack trace

CoreCaused by, and your own frame

Keep @Valid deleted from addProduct for a moment, and add one more test to ProductApiTests — a body with no name at all:

@Test void missingNameIsRejectedWith400() throws Exception { mvc.perform(post("/api/products/add-product") .with(user("admin").roles("ADMIN")) .contentType(MediaType.APPLICATION_JSON) .content(""" {"price": 49.00, "category": "Books", "stock": 10} """)) .andExpect(status().isBadRequest()) .andExpect(jsonPath("$.validationErrors.name").value("Product name is required")); }

With @Valid in place it passes: @NotBlank rejects a missing name too. Without @Valid, it doesn't fail — it errors. There's no "expected … but was …". There's this (shortened: framework line numbers and counts will differ on your machine):

jakarta.servlet.ServletException: Request processing failed: java.lang.NullPointerException: Cannot invoke "String.trim()" because the return value of "com.esd.ecommerce.dto.ProductRequest.getName()" is null at org.springframework.web.servlet.FrameworkServlet.processRequest(FrameworkServlet.java:1008) at org.springframework.web.servlet.FrameworkServlet.doPost(FrameworkServlet.java:…) … at org.springframework.security.web.FilterChainProxy.doFilter(FilterChainProxy.java:…) … at org.springframework.test.web.servlet.MockMvc.perform(MockMvc.java:…) at com.esd.ecommerce.ProductApiTests.missingNameIsRejectedWith400(ProductApiTests.java:…) … Caused by: java.lang.NullPointerException: Cannot invoke "String.trim()" because the return value of "com.esd.ecommerce.dto.ProductRequest.getName()" is null at com.esd.ecommerce.service.ProductService.addProduct(ProductService.java:36) at com.esd.ecommerce.controller.ProductController.addProduct(ProductController.java:50) at java.base/java.lang.reflect.Method.invoke(Method.java:…) at org.springframework.web.method.support.InvocableHandlerMethod.doInvoke(InvocableHandlerMethod.java:…) … ... 90 more

How to read it

  1. The first line is the outer exception and its message. ServletException: Request processing failed is a wrapper: the DispatcherServlet wraps whatever your code threw. Its message already quotes the inner exception, but read on.
  2. Skip the frames under it. Each at … line is a method that was running, newest first. This block is the wrapper's own route: the servlet, the security filters, MockMvc, your test method. That's framework code doing its job.
  3. Find Caused by. It's the exception inside the wrapper. If there are several Caused by lines, the last one is the root cause: the thing that went wrong first.
  4. Find your first frame. Under the last Caused by, the first line in your package, com.esd.ecommerce, is where it happened: ProductService.addProduct, line 36. The line under it is its caller: ProductController.addProduct, line 50. Frames from java.base/, jdk.internal and org.springframework are the framework calling you.
  5. Read the message as a sentence. Java's NullPointerException says exactly which value was null: the return value of getName(). Line 36 is product.setName(request.getName().trim());.
  6. ... 90 more means the rest of this chain is the same as the block above it, so Java doesn't print it twice.

Now the cause. Line 36 assumes the name is there, because validation should have rejected the body before the service ran. The null is a symptom; the missing @Valid is the cause — the same bug as section 06, with a different input. Same fix. A null check on line 36 would stop the crash and hide the bug.

The same crash in the running app

In a running app's console, Tomcat logs the same crash as one ERROR line followed by the root cause's frames (shortened):

… ERROR … o.a.c.c.C.[.[.[/].[dispatcherServlet] : Servlet.service() for servlet [dispatcherServlet] in context with path [] threw exception [Request processing failed: java.lang.NullPointerException: Cannot invoke "String.trim()" because the return value of "com.esd.ecommerce.dto.ProductRequest.getName()" is null] with root cause java.lang.NullPointerException: Cannot invoke "String.trim()" because the return value of "com.esd.ecommerce.dto.ProductRequest.getName()" is null at com.esd.ecommerce.service.ProductService.addProduct(ProductService.java:36) at com.esd.ecommerce.controller.ProductController.addProduct(ProductController.java:50) …

"with root cause" means the trace printed under it is already the innermost exception, so there's no Caused by to hunt for. What the client sees is another matter: section 09.

When the app doesn't start

The other trace you'll meet in tests is the one behind "every test red at once" (section 03). Here is what you get if the test properties leave out the JWT secret. Shortened — the beans in the middle depend on which one Spring was building when it failed:

java.lang.IllegalStateException: Failed to load ApplicationContext for [WebMergedContextConfiguration@… testClass = com.esd.ecommerce.ProductApiTests, …] … Caused by: org.springframework.beans.factory.UnsatisfiedDependencyException: Error creating bean with name '…' … … Caused by: org.springframework.util.PlaceholderResolutionException: Could not resolve placeholder 'app.security.jwt.secret' in value "${app.security.jwt.secret}" …

Same rule: go to the last Caused by. It names the missing property, and the fix is to add it to src/test/resources/application.properties (section 04). The Caused by lines above it are only the chain of beans that needed the one that couldn't be made. Startup errors in the running app have the same shape; the common ones are in From request to row.

When reading isn't enough: the debugger

A trace shows where code crashed. When nothing crashes and a value is simply wrong, stop the code and look at it. In IntelliJ:

  1. Set a breakpoint. Click in the gutter beside line 28 of ProductService, the findById line in getProductById. A red dot appears.
  2. Debug, don't Run. Right-click unknownIdIs404WithTheErrorBody → Debug. (Or start the app with Debug and send the request from Swagger.) Execution stops on the red line, and the Variables pane shows id = 99999.
  3. Step. Step Over (F8) runs the line. Step Into (F7) goes into the method being called — on a repository call that means Spring's generated code, not yours, so Step Out (Shift+F8) to come back. Resume with F9 (macOS: Cmd+Opt+R).
  4. Evaluate. Evaluate Expression (Alt+F8; macOS Opt+F8) runs any Java while stopped: try productRepository.count() or productRepository.findById(id).isPresent().
  5. Only when it matters. Right-click the red dot and give it a condition, such as id == 99999, so it stops only for that request.

08

Logs, levels and the SQL

Corewhen nothing crashes

A trace tells you where something crashed. Most bugs don't crash; they quietly return the wrong thing. For those, you want the app to tell you what it's doing: which method a request reached, what SQL it sent, and which values went into that SQL.

Levels

Every log line has a level: ERROR, WARN, INFO, DEBUG, TRACE, from most to least serious. Spring Boot shows INFO and above by default. You can choose a level for each package in application.properties; a package then shows that level and everything more serious:

# the SQL Hibernate sends to the database logging.level.org.hibernate.SQL=DEBUG # the values bound to each ? in that SQL (TRACE, not DEBUG) logging.level.org.hibernate.orm.jdbc.bind=TRACE # which controller method each request reached, and the status it left with logging.level.org.springframework.web=DEBUG # your own log lines logging.level.com.esd.ecommerce=DEBUG

Each line works on its own. Turn on the one you need, and turn it off again afterwards. For tests, put them in src/test/resources/application.properties; for the running app, in the main file.

show-sql versus the logger

Your Lab 2 application.properties has spring.jpa.show-sql=true and format_sql=true. They print every statement as Hibernate: select …, but straight to the console, around the logging system: no time, no level, and no bound values. logging.level.org.hibernate.SQL=DEBUG logs the same SQL as a proper log line, and the bind category adds the values. Use one or the other: with both on, you see every statement twice. These category names are the same on Boot 3 (Hibernate 6). Older tutorials for Hibernate 5 name a different bind category.

A bug you can only see in the SQL

Suppose the rule is: category search ignores case — get-category/books finds the products in "Books". Lab 2's service calls findByCategory(category). Does it keep the rule? Predict, then add this test to ProductApiTests:

@Test void categoryFilterIgnoresCase() throws Exception { saved("Notebook", "Books"); saved("Pen", "Stationery"); mvc.perform(get("/api/products/get-category/books")) .andExpect(status().isOk()) .andExpect(jsonPath("$", hasSize(1))) .andExpect(jsonPath("$[0].name").value("Notebook")); }

On H2 it's red:

JSON path "$" Expected: a collection with size &lt;1&gt; but: collection size was &lt;0&gt;

An empty list isn't an error, so there's no trace to read. Add the SQL and bind lines to src/test/resources/application.properties and run it again. In the test output (shortened):

… DEBUG … org.hibernate.SQL : select p1_0.id,p1_0.category, … from products p1_0 where p1_0.category=? … TRACE … org.hibernate.orm.jdbc.bind : binding parameter (1:VARCHAR) &lt;- [books]

There's the cause, in two lines. Spring Data turned findByCategory into category=?, and the value bound to ? is books, exactly as typed. The row says Books. On H2, those aren't equal.

Now try it on MySQL

Run your app and open http://localhost:8080/api/products/get-category/electronics. It finds the Laptop. MySQL's default collation — its rule for comparing text — ignores case; H2 compares exactly. So on MySQL the rule was kept, but by the database, by accident. Move to another database, or change the column's collation, and it silently breaks. The test on H2 found a rule your code never stated.

State it in the code. Spring Data reads IgnoreCase in a method name (From request to row explains derived queries):

// ProductRepository List<Product> findByCategoryIgnoreCase(String category);
// ProductService public List<ProductResponse> getProductsByCategory(String category) { log.debug("Filtering products by category '{}'", category); return productRepository.findByCategoryIgnoreCase(category) .stream() .map(this::toProductResponse) .toList(); }

Now the SQL compares upper(p1_0.category)=upper(?), and the test is green — on H2 and on MySQL.

Your own log lines

The log.debug line in that method is yours. Declare a logger once at the top of the class:

import org.slf4j.Logger; import org.slf4j.LoggerFactory; @Service @RequiredArgsConstructor public class ProductService { private static final Logger log = LoggerFactory.getLogger(ProductService.class); private final ProductRepository productRepository; // … the methods, as before }

With logging.level.com.esd.ecommerce=DEBUG, each call prints a DEBUG line ending in Filtering products by category 'books'. Why not System.out.println? A log line has a level, a time and the class name; you can switch it off with one property instead of hunting it down to delete it; and the {} placeholder only builds the message when that level is on.

Did the request reach my code?

logging.level.org.springframework.web=DEBUG prints each request's way through Spring MVC (shortened):

… DEBUG … : GET "/api/products/get-category/books", parameters={} … DEBUG … : Mapped to com.esd.ecommerce.controller.ProductController#getProductByCategory(String) … DEBUG … : Completed 200 OK

If the Mapped to line doesn't name your controller method, the request never reached it: check the URL and the HTTP method. If it does and the answer is still wrong, the cause is in your code, after that line.

Try it — read the SQL of your running app

  1. In your main application.properties, comment out the two show-sql lines and add the SQL and bind lines. Restart the app.
  2. Open get-category/electronics, then get-category/Electronics. In the console, find the SQL and the bound value for each.
  3. Put your file back the way you like it.

Corethe client's view

A test is the trigger you can repeat. Doing it by hand is how you explore: change the body, try the next id, look at the headers. In the Bug Lab you did this in Swagger; the same tools work on Product.

Swagger UI

Wherehttp://localhost:8080/swagger-ui/index.html, in both apps. The JSON description behind it is at /v3/api-docs; springdoc builds it from your controllers.
Try it outOpen an operation, click Try it out, edit the parameters or the body, then Execute. Underneath you get the curl command it ran, the response code, the body and the headers.
Admin routesIn the Product app, click Authorize and paste a token from /api/auth/login. How roles reach Spring Security — and why an admin token can still get 403 — is in Who are you, and what may you do. The public GET routes need nothing.

curl

$ curl -i http://localhost:8080/api/products/get-id/99999 HTTP/1.1 404 … Content-Type: application/json … {"error":"Not Found","message":"Product with ID 99999 not found","path":"/api/products/get-id/99999","status":404,"timestamp":"…Z","validationErrors":null}

-i prints the status line and the headers too, which is often where the answer is. The body is your GlobalExceptionHandler's ApiErrorResponse. Its fields come out in alphabetical order: Boot 4's JSON library, Jackson 3, sorts them by default (on Boot 3 they came in the order they're declared). Postman shows the same thing — use whichever you like.

The database

Bug Lab (H2)The H2 console at http://localhost:8080/h2-console. On its login form, replace the JDBC URL with the app's — jdbc:h2:mem:esdlab3 — user sa, empty password. The tables were campus_events and event_registrations. An in-memory database exists only while the app runs.
Product (MySQL)MySQL Workbench or the mysql command line: SELECT * FROM products; in ecommerceDB.
Why lookAfter a request that should change a row, look at the row. A 200 or a 204 says what the code returned, not what's in the table.

On Boot 4

The H2 console moved into its own module, org.springframework.boot:spring-boot-h2console. Without that dependency, spring.h2.console.enabled=true does nothing.

When the test and curl disagree

Try this on your running Product app, with no token:

$ curl -i http://localhost:8080/api/products/get-id/abc HTTP/1.1 401 … {"error":"Unauthorized","message":"Authentication is required. Please provide a valid JWT token.","path":"/error","status":401,"timestamp":"…Z","validationErrors":null}

The same request in a MockMvc test gives 400. Here's why. abc isn't a Long, so Spring answers 400 — but a real server doesn't send that 400 straight back. It hands the error to Spring Boot's error page, /error, as a second, internal request. That second request goes through Spring Security too, and your SecurityConfig doesn't permit /error. So a caller without a token gets your 401 instead.

Two clues give it away: "path":"/error" in the body, and the console, which still says what really happened (shortened):

… WARN … : Resolved [org.springframework.web.method.annotation.MethodArgumentTypeMismatchException: …]

MockMvc has no server, so it never makes the /error request — that's the gap in the section 02 diagram. The same happens to any exception your code doesn't handle: an anonymous caller sees 401, not 500 (section 10). Closing the gap belongs to your error handling and your security rules: handle the exception in your advice (A slice you can defend), or permit /error (Who are you, and what may you do). The contract wants the first: every error as your own error body.

Try it — the client's view

  1. Run both curl commands above against your running app. Compare the path in the two bodies.
  2. Find the WARN … Resolved [ line in the console for the second one.
  3. Open Swagger UI, run get-id with 99999, and compare its curl command with yours.
Q1A classmate says: "My test says 400 but Postman says 401 — the test must be wrong." What do you tell them?
Show answer

Both are right about different things. The test shows what Spring decided (400). Postman shows what a real server sent after forwarding that error to /error, which security blocked for a caller without a token (401). Look for "path":"/error" and the WARN line. The fix is in error handling or security, not in the test.

Part 4 · Bugs by kind, and what's next
10

Six kinds of bug, and the test that catches each

Corewhat you see, what to assert, where to look

Every bug in the Bug Lab was one of these six. They're worth knowing as kinds, because each one looks the same from the outside in any app — yours included — and each has a test shape that catches it.

KindWhat you see · the test that catches it · where to look
Validation missingBad input is accepted: 201 or 200 where 400 belongs.
Catch it: assert status().isBadRequest(), then jsonPath on the field error.
Look in: the request DTO's constraints, or @Valid on the controller parameter (section 06).
A rule not enforcedA request that breaks a business rule succeeds.
Catch it: arrange the data exactly at the limit — full, duplicate, the last one left — then assert status().isConflict().
Look in: the service, before it saves: the check is missing, or it's wrong exactly at the limit.
A status mapped wrongThe right failure with the wrong number, or a crash where a 4xx belongs.
Catch it: assert the exact status.
Look in: the exception handler's mapping, or an exception that no handler maps.
A state not savedA success status, an unchanged row.
Catch it: read the row back with the repository after the request.
Look in: the service: the change is never saved, or the condition around it is wrong.
A filter missingA list holds rows it shouldn't.
Catch it: assert jsonPath("$", hasSize(n)) and a field that identifies each row.
Look in: the repository query (its method name or @Query); the SQL log shows it (section 08).
A wrong lookupA real object, but not the one you asked for — or one when there should be none.
Catch it: arrange another row first, then assert 404 or an identifying field.
Look in: the service's find… call, and what it does when nothing matches.

Here are two of them, planted on Product.

A crash where a 404 belongs

Plant it: in ProductService.getProductById, replace Lab 2's orElseThrow with .get():

public ProductResponse getProductById(Long id) { Product product = productRepository.findById(id).get(); // planted return toProductResponse(product); }

Predict. findById(99999) returns an empty Optional, and .get() on an empty Optional throws NoSuchElementException with the message "No value present". Nothing in GlobalExceptionHandler maps that exception, so there is no 404. Trigger: unknownIdIs404WithTheErrorBody errors (shortened):

jakarta.servlet.ServletException: Request processing failed: java.util.NoSuchElementException: No value present … Caused by: java.util.NoSuchElementException: No value present at java.base/java.util.Optional.get(Optional.java:…) at com.esd.ecommerce.service.ProductService.getProductById(ProductService.java:28) …

From curl, without a token, it isn't even a 500: the crash goes to /error, and you get section 09's 401 with "path":"/error". Fix: Lab 2's own line, .orElseThrow(() -> new ProductNotFoundException(id)) — an exception that your handler maps to 404. That's this kind's fix in general: make the failure an exception that something maps to the right status.

A response that lies

Plant it: in ProductService.updateProduct, delete the save line and build the response from the object you changed:

public ProductResponse updateProduct(Long id, ProductRequest request) { Product existingProduct = productRepository.findById(id) .orElseThrow(() -> new ProductNotFoundException(id)); existingProduct.setName(request.getName().trim()); existingProduct.setDescription(request.getDescription()); existingProduct.setPrice(request.getPrice()); existingProduct.setCategory(request.getCategory().trim()); existingProduct.setStock(request.getStock()); return toProductResponse(existingProduct); // planted: save(...) deleted }

Predict. The PUT returns 200 with the new name, because the response is built from the Java object, and the object did change. The row didn't: nothing wrote it. The status can't tell the difference. Only reading the row can, the way B5 did. Add this test (and import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.put;):

@Test void updateChangesTheRow() throws Exception { Product notebook = saved("Notebook", "Books"); mvc.perform(put("/api/products/update/" + notebook.getId()) .with(user("admin").roles("ADMIN")) .contentType(MediaType.APPLICATION_JSON) .content(""" {"name": "Notebook A4", "price": 49.00, "category": "Books", "stock": 3} """)) .andExpect(status().isOk()) .andExpect(jsonPath("$.name").value("Notebook A4")); assertEquals("Notebook A4", products.findById(notebook.getId()).orElseThrow().getName()); }

With the bug planted, both andExpect lines pass and the last line fails:

expected: &lt;Notebook A4&gt; but was: &lt;Notebook&gt;

Fix: Lab 2's own productRepository.save(existingProduct). (Inside a @Transactional method, changes to an entity you loaded are written when the transaction commits, even without save: A slice you can defend.)

Try it — plant, predict, catch

Plant one of the two bugs. Write down which test goes red and the exact message you expect. Run, compare, put Lab 2's line back, and run everything.

Using this in your contract backend

Corea suite you didn't write

The contract's conformance suite is the Bug Lab's idea at the scale of a whole backend: checks you didn't write, against code you did. The method is the same.

$ cd esd-labs/api-contract $ npm run conformance -- --level A

Your backend must be running on port 8080. Each failed check prints the request it sent, what the contract expected, what came back, and often a hint: read it the way you read "expected … but was …" (section 03). The contract doc explains the output and a way to work through it: api-contract §15, Reading the suite's output.

  • One level at a time, lowest first. The first failure often causes the ones after it.
  • Reproduce the failed check with curl -i, and watch your backend's log while you do (sections 08 and 09).
  • Before you fix it, write it as a MockMvc test in your own project (section 05). It goes red for the reason you predicted, then green — and it keeps checking after you've moved on.
  • Change one thing, rerun that check, then rerun the level.

Schemathesis, the optional second opinion that generates requests from openapi.yaml, is in api-contract §17.

A test passes alone but fails in the full runIt depends on rows another test left behind. Empty the tables in @BeforeEach, as the Bug Lab did (02).
Every SQL statement appears twiceshow-sql and logging.level.org.hibernate.SQL are both on. Keep one (08).
SQL in the log, but no valuesThe bind category must be TRACE, not DEBUG (08).
H2 console: Database … not foundThe login form still has its own default JDBC URL. Use the app's: jdbc:h2:mem:esdlab3 (09).
mvn: command not found / 'mvn' is not recognizedMaven isn't installed on its own. Use the wrapper in the project: ./mvnw, or mvnw.cmd on Windows (05).
PowerShell runs the wrong tests with -Dtest=…Put the argument in quotes: "-Dtest=ProductApiTests" (05).

How to debug, generally

Read the failure message first and predict from its two numbers. Then the last Caused by and your first frame, if there's a trace. If there isn't, turn on the log that shows what you can't see — the SQL, the bound values, the mapping — and reproduce the request by hand. Change one thing at a time, and rerun the same test after each change.
