Two DTOs, and what each one earns

CoreProductRequest, ProductResponse

In Lab 1, the entity went in and the entity came out:

Your code · lab1-complete · controller/ProductController.java · lines 38–44

@PostMapping("/add-product") public ResponseEntity<Product> addProduct(@RequestBody Product product) { Product savedProduct = productService.addProduct(product); return ResponseEntity.status(HttpStatus.CREATED).body(savedProduct); }

In Lab 2, a request DTO comes in and a response DTO goes out. DTO means data transfer object: a plain class whose only job is to be the shape of some JSON.

Your code · lab2-complete · controller/ProductController.java · lines 46–53

@PostMapping("/add-product") public ResponseEntity<ProductResponse> addProduct( @Valid @RequestBody ProductRequest request) { ProductResponse savedProduct = productService.addProduct(request); return ResponseEntity.status(HttpStatus.CREATED).body(savedProduct); }

Your code · lab2-complete · dto/ProductResponse.java · lines 12–25

@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder public class ProductResponse { private Long id; private String name; private String description; private BigDecimal price; private String category; private Integer stock; }

So why three classes? Each DTO has to earn its place. Here's what each one earns, shown on your own code.

The request DTO: the client doesn't choose the id

Lab 1's add-product accepted a whole Product — id included. Spring Data's save() looks at the id: null means a new row, so it inserts; an id means "this one already exists", so it updates that row instead. With Lab 1's code, this request didn't add anything. It replaced the laptop:

$ curl -i -X POST localhost:8080/api/products/add-product \ > -H "Content-Type: application/json" \ > -d '{"id":1,"name":"Overwritten","description":"x","price":1.00,"category":"Junk","stock":0}' HTTP/1.1 201 Content-Type: application/json {"category":"Junk","description":"x","id":1,"name":"Overwritten","price":1.00,"stock":0}

A 201 Created — for a product that was not created. Product 1 is now "Overwritten" and the table still has three rows. This is called over-posting (or mass assignment): the client sets a field you never meant it to set.

ProductRequest has no id field. Jackson, the library that turns JSON into objects, ignores JSON fields that have nowhere to go — so in Lab 2 the same request is a new product with a new id, and the laptop is untouched. For updates, the id comes from the URL (/update/{id}), never from the body.

Try it — send an id

With the temporary rule in, send the request above to your Lab 2 app. You get 201 with a new id. Then read /api/products/get-id/1: still the laptop. (If you still have your Lab 1 project, or a clone at lab1-complete, you can see the overwrite there — Lab 1 has no security, so no rule is needed.)

The response DTO: a promise that doesn't follow the table

ProductResponse looks like a copy of Product. It earns its place the day the two differ — and your project already has that day, on the login side. The User entity holds the password hash:

Your code · lab2-complete · entity/User.java · lines 18–26

@Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; @Column(nullable = false, unique = true, length = 255) private String email; @Column(name = "password_hash", nullable = false, length = 255) private String passwordHash;

Signup doesn't answer with the User. It copies five fields into a UserResponse, and passwordHash isn't one of them:

Your code · lab2-complete · service/AuthService.java · lines 92–100

private UserResponse toUserResponse(User user) { return UserResponse.builder() .id(user.getId()) .email(user.getEmail()) .fullName(user.getFullName()) .role(user.getRole()) .createdAt(user.getCreatedAt()) .build(); }

Jackson writes every property it can read from the object you return. Return the User itself and the hash is in the JSON, for anyone who signs up. Return a UserResponse and it can't be: the field doesn't exist. (What the hash is, and why it must stay private, is sb-security.)

For products nothing is secret yet. But the day Product gains a field for the shop's own use — a supplier's price, an internal note — Lab 1's code would send it to every client the moment you added it. Lab 2 sends exactly what toProductResponse copies, no more.

Try it — a field the client never sees

  1. Sign up a user (POST /api/auth/signup with email, password, fullName). The answer has createdAt, email, fullName, id, role — no hash.
  2. Add private String supplierNote; to Product and restart. ddl-auto=update adds a column for it. Read /api/products/get-id/1: still the same six fields.
  3. Remove the field again. The new column stays in MySQL until you drop it; it does no harm.

The keys come out in alphabetical order

Spring Boot 4's JSON library, Jackson 3, sorts properties by name unless told otherwise; Spring Boot 3 kept the order of the fields. A JSON object has no order, so nothing should depend on it. Every output on this page is what Boot 4 prints.

What it costs

Two more classes and a mapping method. Where the request, the response and the entity really are identical and nothing will ever be private, a DTO is a choice, not a must. Here the request already differs (no id), and the response is a promise you'd rather not tie to the table — so both earn their keep.

Q1A classmate's ProductRequest has a private Long id; "in case it's needed". With Lab 2's service, what can a client do with it?
Show answer

Nothing yet: addProduct builds a fresh Product and copies five fields, never the id. But no requirement asks for that field, so cut it. The day someone copies it across — or swaps the hand-written mapping for a library that copies every matching name — you're back to Lab 1's overwrite.

Q2The shop decides clients shouldn't see stock. Which classes change, and which must not?
Show answer

ProductResponse loses the field and toProductResponse loses the line. Product keeps it (the shop still stores stock) and so does ProductRequest (an admin still sets it). One API change, one place — that's the response DTO earning its place.

Mapping by hand

Coreentity ↔ DTO in the service

Something has to copy fields between the DTOs and the entity. In your project that's the service, by hand. One method goes entity → response:

Your code · lab2-complete · service/ProductService.java · lines 76–85

private ProductResponse toProductResponse(Product product) { return ProductResponse.builder() .id(product.getId()) .name(product.getName()) .description(product.getDescription()) .price(product.getPrice()) .category(product.getCategory()) .stock(product.getStock()) .build(); }

builder() exists because of Lombok's @Builder on ProductResponse (sb-java shows what it generates). Every method that returns products goes through this one, so it's the single place that decides what a client sees. For a list, each entity goes through it in turn:

Your code · lab2-complete · service/ProductService.java · lines 20–25

public List<ProductResponse> getAllProducts() { return productRepository.findAll() .stream() .map(this::toProductResponse) .toList(); }

(.stream().map(this::toProductResponse).toList() is plain Java — streams and method references are in sb-java.)

Request → entity, in addProduct

Your code · lab2-complete · service/ProductService.java · lines 34–45

public ProductResponse addProduct(ProductRequest request) { Product product = new Product(); product.setName(request.getName().trim()); product.setDescription(request.getDescription()); product.setPrice(request.getPrice()); product.setCategory(request.getCategory().trim()); product.setStock(request.getStock()); Product savedProduct = productRepository.save(product); return toProductResponse(savedProduct); }
  • A new Product, five setters, no id. The database assigns the id when save inserts the row, and save hands back the entity with it filled in — which is what goes into the response.
  • .trim() on name and category, not on description. " Desk Lamp " is stored as "Desk Lamp"; a description keeps its spaces. A name can't trim down to "", because a blank name was already refused (section 04).
  • The line numbers matter later. Line 36 is the first line that touches the request. Section 05 breaks it on purpose.

updateProduct replaces every field

Your code · lab2-complete · service/ProductService.java · lines 47–60

public ProductResponse updateProduct(Long id, ProductRequest request) { Product existingProduct = productRepository.findById(id) .orElseThrow(() -> new ProductNotFoundException(id)); existingProduct.setName(request.getName().trim()); existingProduct.setDescription(request.getDescription()); existingProduct.setPrice(request.getPrice()); existingProduct.setCategory(request.getCategory().trim()); existingProduct.setStock(request.getStock()); Product updatedProduct = productRepository.save(existingProduct); return toProductResponse(updatedProduct); }

All five fields are copied, every time. Leave description out of a PUT and the product's description becomes null. That's what PUT means: send the whole thing, and it replaces the whole thing. (orElseThrow is section 06.)

Why by hand?

Six fields, all visible, and the compiler checks every name. Libraries such as MapStruct generate this code for you; they pay off with dozens of DTOs, and they hide the one decision you most want to see — which fields cross the line. For one entity and two DTOs, hand-written is the clearer choice.

Try it — trim, and a full replacement

  1. With the temporary rule in, add a product with padded text. The answer has "name":"Desk Lamp" and "category":"Lighting", while the description keeps its spaces.
  2. Update product 1 without a description. The answer has "description":null. Send it again with the description to put it back.
$ curl -i -X POST localhost:8080/api/products/add-product \ > -H "Content-Type: application/json" \ > -d '{"name":" Desk Lamp ","description":" LED ","price":1499.00,"category":" Lighting ","stock":12}' HTTP/1.1 201 Content-Type: application/json {"category":"Lighting","description":" LED ","id":4,"name":"Desk Lamp","price":1499.00,"stock":12} $ curl -i -X PUT localhost:8080/api/products/update/1 \ > -H "Content-Type: application/json" \ > -d '{"name":"Laptop","price":65000.00,"category":"Electronics","stock":10}' HTTP/1.1 200 Content-Type: application/json {"category":"Electronics","description":null,"id":1,"name":"Laptop","price":65000.00,"stock":10}

Your new product's id may not be 4 — MySQL keeps counting from the highest id it has ever handed out.

CoreBean Validation

(It shares a name with Hibernate, the database library, and nothing else — it never touches the database.) The annotations themselves are the standard Bean Validation ones, in jakarta.validation.constraints. Lab 1 had no rules at all: whatever arrived went straight to the database.

Null passes almost everything

Every rule except @NotNull, @NotBlank and @NotEmpty counts null as valid. "Is it there?" and "is it good?" are separate questions, asked by separate annotations. That's why price has two: @NotNull asks whether it's there, @DecimalMin whether it's more than zero. With only @DecimalMin, leaving the price out would pass. And description has only @Size, so leaving it out is fine — it's the one optional field.

Others you'll meet

@PositiveMore than zero. For money, @DecimalMin("0.01") is stricter: @Positive accepts 0.001.
@Min / @MaxWhole-number bounds, such as @Min(1) @Max(6) for credits.
@EmailLooks like an email address. Your SignupRequest uses it.
@Pattern(regexp = …)Matches a regular expression — a product code, a course code.

The message = "…" on each rule is the text the client gets back (section 07). Leave it out and Hibernate Validator uses its own default sentence, in your computer's language.

The rules are a promise about the table, too

The rules say what the API accepts. The columns say what MySQL will store. They should agree. With the table from the lab's SQL script (database/lab1_setup.sql), they don't:

05

@Valid — checked before your method runs

Corewho reads the annotations, and when

The annotations on ProductRequest are labels. Nothing reads them until something asks. In your controller, @Valid is the ask — on both methods that take a body:

Your code · lab2-complete · controller/ProductController.java · lines 46–64

@PostMapping("/add-product") public ResponseEntity<ProductResponse> addProduct( @Valid @RequestBody ProductRequest request) { ProductResponse savedProduct = productService.addProduct(request); return ResponseEntity.status(HttpStatus.CREATED).body(savedProduct); } @PutMapping("/update/{id}") public ResponseEntity<ProductResponse> updateProduct( @PathVariable Long id, @Valid @RequestBody ProductRequest request) { ProductResponse updatedProduct = productService.updateProduct(id, request); return ResponseEntity.ok(updatedProduct); }

@Valid tells Spring: after you've built this object from the JSON, check it against its rules before you call me. For a POST to add-product, this is the order things happen in:

  1. The security filters check the token and the role. Refused → 401 or 403, and nothing below runs.
  2. Spring finds the method from the path and the HTTP method.
  3. Jackson reads the JSON into a new ProductRequest. Names must match exactly; a JSON field with nowhere to go is ignored, and a missing field stays null. If the body isn't JSON, has a value of the wrong type ("price": "abc") or isn't there at all, Spring throws HttpMessageNotReadableException.
  4. @Valid: the validator checks every rule on that object and collects every failure. If there are any, Spring throws MethodArgumentNotValidException, carrying all of them.
  5. Only now does addProduct run — with a request that's known to be complete.

Two things follow that you can see from outside. Your method never has to check for nulls. And the body is checked before the method looks anything up: PUT /update/999 with {} is a 400 (bad body), not a 404 (no product 999), because the lookup is inside the method that never ran. Section 08 draws the whole sequence.

Without @Valid

Try it — take @Valid off, once

  1. Remove @Valid from addProduct only. Restart, and send {} (temporary rule in).
  2. You get a 500. Read the app's log — the first line of the exception and the first line that is in your code:
java.lang.NullPointerException: Cannot invoke "String.trim()" because the return value of "com.esd.ecommerce.dto.ProductRequest.getName()" is null at com.esd.ecommerce.service.ProductService.addProduct(ProductService.java:36)
  1. Put @Valid back and restart.

The rules were still on the class; nobody checked them. The request went straight into the service, and the first line that touched a missing field — line 36, request.getName().trim() — crashed. Java's message even names the method that returned null. (Reading stack traces properly is in sb-testing.)

Lab 1 had no rules at all. With the lab's table, {} reached the INSERT and MySQL refused it, because name is NOT NULL — also a 500. Either way, the client's bad input became the server's error. That is the most common bug in generated slices: "missing validation" — a 500 where a 400 belongs.

@Valid goes on every body

Check PUT as well as POST in your own project. Generated controllers often have it on one and not the other, and nothing warns you: the missing one just lets anything through. Your reference has both.

Q1You send PUT /api/products/update/999 with {}. Product 999 doesn't exist. 400 or 404?
Show answer

400. Validation happens before updateProduct is called, and the "does 999 exist?" check is inside it. Send a valid body to the same URL and you get the 404.

Q2You send a valid product but spell the field "Price". What comes back?
Show answer

A 400 with "price": "Product price is required". Jackson matches names exactly, so "Price" has nowhere to go and is ignored; price stays null, and @NotNull catches it. The message is right — the field you meant really is missing.

Part 4 · One shape for every failure
06

ProductNotFoundException

Corea failure with its own name

Lab 1 said "not found" with a null. The service returned it:

Your code · lab1-complete · service/ProductService.java · lines 20–22

public Product getProductById(Long id) { return productRepository.findById(id).orElse(null); }

…and the controller had to check for it, and answer with a bare string:

Your code · lab1-complete · controller/ProductController.java · lines 25–36

@GetMapping("/get/{id}") public ResponseEntity<?> getProductById(@PathVariable Long id) { Product product = productService.getProductById(id); if (product == null) { return ResponseEntity.status(HttpStatus.NOT_FOUND) .body("Product with ID " + id + " not found"); } return ResponseEntity.ok(product); }

Lab 2 gives the failure a name of its own:

Your code · lab2-complete · exception/ProductNotFoundException.java · lines 4–9

public class ProductNotFoundException extends RuntimeException { public ProductNotFoundException(Long id) { super("Product with ID " + id + " not found"); } }

The service throws it, and the controller is left with only the happy path:

Your code · lab2-complete · service/ProductService.java · lines 27–32 · controller/ProductController.java · lines 28–34

public ProductResponse getProductById(Long id) { Product product = productRepository.findById(id) .orElseThrow(() -> new ProductNotFoundException(id)); return toProductResponse(product); } @GetMapping("/get-id/{id}") public ResponseEntity<ProductResponse> getProductById( @PathVariable Long id) { ProductResponse product = productService.getProductById(id); return ResponseEntity.ok(product); }

Three things changed, and each one earns something:

  • The decision moved to where the lookup is. getProductById, updateProduct and deleteProduct all need "product id must exist"; each says it in one line, with the same exception and the same message. Nobody can forget a null check, because there is no null.
  • The controller method only returns success. When the product is missing, the method doesn't return at all — the exception leaves it. That's why ResponseEntity<?> could become ResponseEntity<ProductResponse>: there's no second kind of body any more.
  • The client gets JSON in the error shape, not a bare string. Section 07 is where the exception becomes that JSON.

extends RuntimeException makes it unchecked, so it passes up through the service and the controller without a throws clause on every method. Checked and unchecked exceptions are in sb-java. orElseThrow takes a function that makes the exception — it's only called when the Optional is empty; Optional is in sb-java too.

How it's wired

  • @RestControllerAdvice makes the class a component that Spring finds at startup, like your controllers. From then on, whenever a controller method — or anything it calls — throws, Spring looks in this class for a method whose @ExceptionHandler type matches the exception, calls it, and sends what it returns as the response.
  • "Rest" means the same as in @RestController: the returned object is the response body, written as JSON.
  • The parameters are whatever the method asks for: here the exception itself, and the HttpServletRequest so the body can say which path failed.
  • The status is set on the ResponseEntity. The status field inside the body is just a copy for the client to read; the HTTP status line comes from ResponseEntity.status(…).

Which status for which failure

Core400, 404, 409, 500 — and what falls through

Your GlobalExceptionHandler knows three exceptions: ProductNotFoundException → 404, MethodArgumentNotValidException → 400, HttpMessageNotReadableException → 400. Every other failure falls through to Spring. First, what each status is for:

StatusMeansIn your Product app
400 Bad RequestThe request itself is wrong, and the client can fix it.a rule broken; not JSON; a wrong type; no body; an id that isn't a number
401 UnauthorizedWho are you? No token, or a bad one.a write with no token (sb-security)
403 ForbiddenI know who you are; you may not.a write without the ADMIN role (sb-security)
404 Not FoundThere's no such thing.no product with that id
405 Method Not AllowedThat path exists, but not with that method.GET /api/products/add-product
409 ConflictThe request is fine, but it clashes with what's already stored — a duplicate of something that must be unique, a seat that's already taken.none yet: no product field has to be unique
415 Unsupported Media TypeThe body isn't in a format this endpoint reads.a body sent without Content-Type: application/json
500 Internal Server ErrorThe server failed. The client can't fix it by changing the request.anything nobody planned for

The rule of thumb

4xx: the client should change the request. 5xx: someone should change the server. So a 500 for bad input is always a bug on the server — like the 150-character name in section 04. And a 409 is not a 400: the request was well-formed, the data said no.

Falling through: Spring Boot's default body

When an exception isn't handled by your advice, Spring either knows a status for it (400 for an id that isn't a number, 415, 405) or doesn't (500). Either way it makes the answer the same way: it forwards the request to /error, a built-in endpoint that writes Spring Boot's default body:

{ "timestamp": "2026-01-15T09:30:00.481+00:00", "status": 400, "error": "Bad Request", "path": "/api/products/get-id/abc" }

Not your shape: no message, no validationErrors. Spring Boot leaves the message out on purpose — for a 500 it would be the exception's text, which can carry SQL, class names, file paths. The details go to the app's log instead, and that's where you look.

The 401 that isn't about your token

Now take the temporary rule out and send /api/products/get-id/abc with no token. get-id is public, yet you get a 401:

$ curl -i localhost:8080/api/products/get-id/abc HTTP/1.1 401 Content-Type: application/json {"error":"Unauthorized","message":"Authentication is required. Please provide a valid JWT token.","path":"/error","status":401,"timestamp":"2026-01-15T09:30:00.481203Z","validationErrors":null}

Look at the path: /error. The request was public, Spring raised its 400 and forwarded to /error — and the forward went through the security filters again. /error isn't in your rules, so it fell to "any other request needs a token", and with no token the forward was refused. The 401 hides the real 400. With a valid token of any role, the same request shows the 400; that's why the temporary rule opens /error as well. A failure your handler answers — /get-id/99 — never forwards, so it's a clean 404 with or without a token.

The same happens to an exception that carries its own status but that your handler doesn't know. Signing up twice with the same email throws a ResponseStatusException with 409 CONFLICT in AuthService; nothing in GlobalExceptionHandler handles it, so Spring forwards to /error, and a real server answers 401 with "path":"/error" instead of the 409. (sb-security walks through that one.)

Two ways to make these answers yours: handle more exceptions in GlobalExceptionHandler, so fewer fall through; and permit /error in SecurityConfig, so the ones that still do aren't masked. Section 11 points to the list the contract expects.

  2. Take the rule out, restart, and send /get-id/abc again: 401, with "path":"/error". Then /get-id/99: still a clean 404.
Q1A client sends a 150-character name and gets a 500. Whose mistake is the request, whose bug is the 500, and what should the answer be?
Show answer

The request is the client's mistake; the 500 is the server's bug, because the server knew its limit and didn't say so. The answer should be a 400 with "name": "…must not exceed 100 characters" — a rule that matches the column (section 04).

Q2With no token, why is /get-id/99 a 404 but /get-id/abc a 401?
Show answer

/get-id/99 throws ProductNotFoundException, your handler answers inside the request, and the request was public. /get-id/abc fails on a conversion your handler doesn't know, so Spring forwards to /error, which your rules don't permit — and a request without a token is refused there.

Find by category

Your code · lab2-complete · repository/ProductRepository.java · line 12 · service/ProductService.java · lines 69–74 · controller/ProductController.java · lines 36–44

There's no query written anywhere. Spring Data reads the method's name when the app starts: findBy means "a query that returns rows", and Category is a field of Product, so the condition is "category equals the argument". The return type, List<Product>, says "every match". With spring.jpa.show-sql=true and format_sql=true in your application.properties, the log shows the one SELECT each call sends:

-- printed once per GET /api/products/get-category/Accessories select p1_0.id, p1_0.category, p1_0.description, p1_0.name, p1_0.price, p1_0.stock from products p1_0 where p1_0.category=?

p1_0 is Hibernate's short name for the products table in this query, and ? is where your argument goes — sent separately from the SQL, never pasted into it. A name Spring Data can't turn into a query — a typo such as findByCategry — fails when the repository is created, so the app stops at startup with an error that names the method, instead of failing at the first request. The general rules for these names are in From request to row. Three things about this endpoint:

  • No match is 200 [], not 404. 404 means "no such resource", and this one exists — it's a list, and the list is empty. A filter that matches nothing has still answered the question. (The contract does the same: an unknown department is 200 [].)
  • A category with a space goes into the URL encoded: /get-category/Home%20Office. Spring decodes it before your method sees it, so category is "Home Office". Postman and browsers encode for you; with curl, type the %20.
  • Whether case matters is the database's decision, not Spring's. Spring sends p1_0.category=?. MySQL's default comparison ignores case, so /get-category/electronics usually finds Electronics there; H2, the database tests often run on, doesn't. If case shouldn't matter, say so in the name — findByCategoryIgnoreCase — instead of relying on the database.
$ curl -i localhost:8080/api/products/get-category/Accessories HTTP/1.1 200 Content-Type: application/json [{"category":"Accessories","description":"Ergonomic wireless mouse","id":2,"name":"Wireless Mouse","price":1200.00,"stock":25},{"category":"Accessories","description":"RGB mechanical keyboard","id":3,"name":"Mechanical Keyboard","price":3500.00,"stock":15}] $ curl -i localhost:8080/api/products/get-category/Toys HTTP/1.1 200 Content-Type: application/json []

Smells to look for in a generated slice

  • An entity returned from any endpoint — search the controllers for ResponseEntity<Product> or List<Product>.
  • @Valid on POST but not on PUT.
  • Rules that don't match the columns, or rules nobody asked for ("name must be at least 3 characters" — says who?).
  • A handler that answers 200 with an error message in the body.
  • An @ExceptionHandler(Exception.class) that copies ex.getMessage() into the response — it can send SQL and class names to the client. A catch-all should send a fixed message and log the details.
  • ResponseEntity<?> or ResponseEntity<Object> where one body type would do.
  • A try/catch in the controller that swallows an exception your advice should answer.
  • DTO fields that nothing sends or reads; mapper classes for conversions that never happen.
  • Annotations nobody on the team can explain — the box below names a few that generated code likes to add.

Try it — cut one thing

On a new branch (git switch -c audit), remove one element you think isn't earned. Restart and poke the endpoints it touches. If nothing changes anywhere, it wasn't earned — keep it cut. If something breaks, you've just found what it was for. Switch back to your main branch afterwards.

What this slice doesn't need yet

Generated code often adds these. In the Product slice none of them is earned — you'll meet each when its reason arrives:

  • @ManyToOne and lazy loading — when one entity points at another (a review of a product, an enrollment in a course), and with them the "N+1 queries" problem when a list touches the relation row by row.
  • @Version — when two people may change the same row at the same moment: two buyers, one item left in stock.
  • Pageable — when a list grows too long to send at once. The contract says "no pagination", so not there either.

Using this in your contract backend

Corea pointer, not a build

Your ApiErrorResponse is most of the contract's ApiError already. What changes when you grow your Lab 2 project into the contract backend:

  • The names and one message. The map is called fieldErrors (present in every error, null when it isn't a validation failure), and a validation failure's message is exactly Validation failed. The contract fixes a few other messages word for word too.
  • Nothing falls through. Every failure in section 08's table — including the id that isn't a number, the 405, an unknown path and the 500 — answers in the contract's shape, and so do the 401 and 403.
  • 409s arrive. Enrolling checks a fixed list of rules in a fixed order: 404, then three different 409s, each with its own message. The pattern is the one you've just read: one exception per meaning, one handler per exception.

The rules, the exact messages and the order are in the contract doc: §10 One error shape for everything and §13 Level C — enrollments, admin and the 409 rules. The error-shape checks are part of conformance level A, so npm run conformance -- http://localhost:8080 --level A in esd-labs/api-contract tells you how close your shape is.
