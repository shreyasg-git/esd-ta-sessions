03

Values, truthiness and expressions

Corethe smallest pieces

Refresher

JavaScript has eight types: number, string, boolean, null, undefined, bigint, symbol and object (arrays and functions are objects). Exactly eight values are falsy — false 0 -0 0n "" null undefined NaN — and everything else is truthy. Always compare with ===.

Full version → 05 · §02 The fast recap — values & flow

Expressions and statements

An expression is any piece of code that produces a value: 3 + 4, course.title, courses.length > 0, seatLabel(course). A statement does something but has no value: if (…) { … }, for (…) { … }, const x = …;.

The difference matters wherever JavaScript expects a value. Inside ${ } in a template literal, as an argument to a function, on the right of = — only an expression fits there. You can't put an if inside ${ }. So JavaScript gives you expression-shaped versions of choice:

const seats = 0; // statement — does something, has no value if (seats === 0) { console.log("Full"); } // expression — the same choice, as a value you can use anywhere const label = seats === 0 ? "Full" : `${seats} left`; console.log(`Status: ${seats === 0 ? "Full" : "Open"}`); // Status: Full

&&, || and ?? return one of their operands

This surprises almost everyone. && and || don't return true or false — they return one of the two values you gave them.

a && bIf a is falsy, returns a. Otherwise returns b.
a || bIf a is truthy, returns a. Otherwise returns b.
a ?? bIf a is null or undefined, returns b. Otherwise returns a — even if a is 0 or "".

Predict each line, then type it.

The trap you will hit in React

A badge that should only show when the planner has something in it: count && `${count} in planner`. When count is 3, you get the text. When it is 0, you don't get "nothing" — you get 0, and React prints a stray 0 on the page. Make the left side a real boolean: count > 0 && …, or use a ternary. (Your plannerBadge must return null for zero, not false — so use the ternary there.)

Optional chaining

course?.title reads title if course exists, and gives undefined instead of crashing if it is null or undefined. You'll need it whenever data might not have arrived yet — and in React, on the first render, it usually hasn't.

const found = courses.find((c) => c.code === "XX999"); // undefined found.title // TypeError: Cannot read properties of undefined (reading 'title') found?.title // undefined — no crash found?.title ?? "No such course" // "No such course"

In React, this becomes…

The curly braces in JSX — <h1>{…}</h1> — accept exactly one expression. That one rule is why React code never has an if inside the markup, and instead uses ? : for either/or, && for "only if", and .map() for lists. You're learning the only three tools there are.

04

Functions are values

Corethe idea React is built on

Refresher

Three ways to write a function: a declaration function add(a, b) { return a + b; }, an expression const add = function (a, b) { … }, and an arrow const add = (a, b) => a + b. Parameters can have defaults: (credits = 3) => ….

Full version → 05 · §03 Functions — three ways · 06 · §01 Functions are values

A function is just another value

In JavaScript, a function is a value in exactly the way 42 and "CS101" are values. Anything you can do with a number, you can do with a function: store it in a variable, put it in an array or an object, pass it to another function, return it from a function.

const shout = (text) => text.toUpperCase(); typeof shout // "function" const alsoShout = shout; // store it in another variable alsoShout("full") // "FULL" const formatters = { // put functions in an object short: (c) => c.code, long: (c) => `${c.code} · ${c.title}`, }; formatters.long(courses[0]) // "CS101 · Programming Fundamentals" [shout, (t) => t + "!"].map((f) => f("hi")) // ["HI", "hi!"]

The name is the function; the parentheses run it

This distinction is the whole section. seatLabel is the function. seatLabel(course) runs it, and is whatever it returned.

seatLabel // [Function: seatLabel] — the function itself seatLabel(courses[1]) // "Full" — the result of running it

Pass it, don't call it

button.addEventListener("click", save()) looks right and is wrong. The parentheses run save immediately, while the page loads, and hand addEventListener whatever save returned — usually undefined. The click then does nothing. Pass the function itself: addEventListener("click", save). If it needs an argument, wrap it in a new function that will call it later: addEventListener("click", () => save(course.id)).

The three arrow-function return rules

Most "my map returns undefined" bugs are one of these.

// 1. No braces → the expression is returned automatically const credits = courses.map((c) => c.credits); // [4, 4, 4, …] // 2. Braces → it's a block; nothing is returned unless you say return const broken = courses.map((c) => { c.credits }); // [undefined, undefined, …] const fixed = courses.map((c) => { return c.credits; }); // 3. Returning an object literal → wrap it in parentheses, // or the braces are read as a block const wrong = courses.map((c) => { code: c.code }); // [undefined, …] const right = courses.map((c) => ({ code: c.code })); // [{ code: "CS101" }, …]

In React, this becomes…

A React component is a function that returns what to show. Event handlers are functions you pass: <button onClick={handleAdd}>. Writing onClick={handleAdd()} calls it during every render — and if handleAdd changes state, React re-renders, which calls it again, forever. React stops it with the error "Too many re-renders". Now you know what it means.

05

Callbacks and higher-order functions

Core"don't call us, we'll call you"

Refresher

A higher-order function takes a function as an argument, returns a function, or both. setTimeout, addEventListener and every array method you know (map, filter, reduce) are higher-order. The function you pass in is a callback.

Full version → 06 · §02–05 Higher-order functions · 05 · §12 Higher-order functions

The receiver decides when to call it

When you pass a callback, you hand over control. You don't call it — the function you gave it to calls it, when it decides, with the arguments it chooses. setTimeout calls yours after a delay. addEventListener calls yours on each click, with an event object. map calls yours once per item, with that item.

Writing one yourself makes this concrete. Here's a function that returns the first item that passes a test — the test is a callback:

function firstWhere(list, predicate) { for (const item of list) { if (predicate(item)) return item; // WE call the callback, once per item, until one passes } return undefined; } firstWhere(courses, (c) => c.seatsLeft === 0).code // "CS201" (the first full course)

firstWhere knows how to search. It has no idea what you're searching for — the callback supplies that. One general function, any number of questions. (It's what the built-in find does — section 11.)

Your countWhere(list, predicate) walks the list the same way, but counts the items that pass instead of stopping at the first:

countWhere(courses, (c) => c.seatsLeft === 0) // 5 countWhere(courses, (c) => c.credits === 2) // 3

Functions that make functions

A function can also build a function and hand it back, with a setting baked in:

function atLeastCredits(n) { return (course) => course.credits >= n; // a new test, made to order } courses.filter(atLeastCredits(4)).length // 12 countWhere(courses, atLeastCredits(4)) // 12 — the same test, handed to your countWhere

sort takes a comparator: a function of two items that returns a negative number if a comes first, positive if b does, and 0 if they're equal. For one number field you can write it by hand:

[...courses].sort((a, b) => a.seatsLeft - b.seatsLeft)[0].code // "CS201" (a full course)

Writing one per field gets repetitive, so byField(field) builds the comparator for any field — the same move as atLeastCredits. Subtraction won't do for it: it must work for strings too, and "a" - "b" is NaN. Compare with < and > instead, which work on both.

const byTitle = byField("title"); byTitle(courses[0], courses[1]) // 1 — "Programming Fundamentals" comes after "Data Structures" byTitle(courses[1], courses[0]) // -1 byTitle(courses[0], courses[0]) // 0

Why [...courses] and not courses

sort changes the array you call it on. The [...courses] makes a copy first so the original keeps its order. Section 09 explains why this matters; for now, always sort a copy.

Handing over a function to compute later

Here is the idea from this section you'll use most in React. Imagine a setter that accepts either a new value or a function that works the new value out from the current one. That's your applyUpdate(current, update):

applyUpdate(3, 5) // 5 — a value: just use it applyUpdate(3, (n) => n + 1) // 4 — a function: call it with the current value

To tell the two apart, ask what you were handed: typeof x === "function" is true only for functions.

Now apply three updates in a row, each to the result of the one before. Compare these two:

const count = 0; applyAll(count, [count + 1, count + 1, count + 1]); // 1 — count + 1 was worked out NOW, three times, from the same 0 applyAll(count, [(n) => n + 1, (n) => n + 1, (n) => n + 1]); // 3 — each function runs LATER, on the latest value

A value is computed the moment you write it. A function is a recipe, run later, with whatever is current then. That is the entire difference.

In React, this becomes…

setCount(count + 1) called three times in one click adds 1. setCount((c) => c + 1) three times adds 3. Your applyAll is a simplified version of exactly how React processes a queue of updates. And when a child component needs to tell its parent something, the parent passes a callback down — onAdd — and the child calls it. Events flow up through callbacks.

06

Scope and closures

Corethe engine under every hook

Refresher

Scope looks outward: code inside a function can see the variables of every function around it, never the other way. A closure is a function together with the variables it could see where it was created — and it keeps them alive after the outer function has finished.

Full version → 05 · §04 Scope · 05 · §05 Closures · 06 · §06–10 Closures, step by step

function makeCounter() { let n = 0; // lives in this call's scope return () => ++n; // the returned function still refers to it } const a = makeCounter(); a(); a(); a() // 3 — makeCounter finished long ago, but n survived

Function factories

A function that builds and returns another function, with some settings baked in. Each call makes a new function with its own variables:

function createGreeter(greeting) { let calls = 0; return (name) => `${greeting}, ${name} (call ${++calls})`; } const hello = createGreeter("Hello"); const hi = createGreeter("Hi"); hello("Asha"); hello("Ravi") // "Hello, Ravi (call 2)" hi("Asha") // "Hi, Asha (call 1)" — its own calls, untouched by the other

Your createIdGenerator(prefix) is a factory like this one: const next = createIdGenerator("ORD"), then next() gives "ORD-1", then "ORD-2" — and a second generator starts again from 1.

A closure sees the variable, not a copy

A closure doesn't take a snapshot of a value. It keeps a link to the variable. If the variable changes, the closure sees the change:

let total = 0; const report = () => console.log(total); total = 24; report() // 24

One call, one set of variables

So why does React talk about "stale" values? Because of this: every call to a function creates fresh variables. A closure made during one call is linked to that call's variables — and a later call has different ones.

function render(count) { // pretend this is a React component const handleClick = () => console.log("clicked, count was", count); return handleClick; } const fromFirstRender = render(0); const fromSecondRender = render(1); fromFirstRender() // clicked, count was 0 fromSecondRender() // clicked, count was 1

A value only a function can change

Put these ideas together. createBox(initial) locks a value inside a closure — a variable inside the call, like calls above, starting at initial — and hands back two arrow functions in an array: one that returns the variable, and one that replaces it with whatever it's given. Nothing else in the program can reach the value.

const [getPlanner, setPlanner] = createBox([]); getPlanner() // [] setPlanner([4, 10]); getPlanner() // [4, 10]

Look at the last two lines and then back at section 02: const [planner, setPlanner] = useState([]). Same shape. A value you can't touch directly, and a function that is the only way to change it. Why would React want to force every change through a function? Because a function can do something extra every time it's called. Hold that question — section 15 answers it, and you'll build the answer yourself.

In React, this becomes…

Every event handler you write in a component is a closure over that render's state and props. Usually that's exactly what you want. When a timer or a subscription outlives the render that created it, you get a stale closure — the most-asked React bug of all. The fix you already know: the updater function from section 05, setCount((c) => c + 1), which never reads a captured count at all.

07

this — and why React stopped needing it

Coreon the syllabus for good reason

The rule

this is decided by how a function is called, not where it is written. The same function can see a different this on every call.

Full version → 06 · §11–13 this · 05 · §15 Methods and this · 05 · §17 Classes

The four ways a function gets called

obj.method()this is obj — the thing before the dot.
method()A plain call. this is undefined (in modules and classes, which are always strict mode).
new Thing()this is the brand-new object being built.
m.call(x) · m.apply(x) · m.bind(x)this is x. call/apply for one call; bind returns a new function with this fixed for good.

And one exception: an arrow function has no this of its own. It uses the this of the code around it, like any other outer variable.

The callback trap

Here's a class that keeps a playlist. It works when you call the method on the object — and breaks the moment you pass the method somewhere as a callback:

class Playlist { constructor(name) { this.name = name; this.songs = []; } addSong(title) { this.songs.push(title); } } const mix = new Playlist("Road trip"); mix.addSong("Song A"); // fine — called as obj.method(), this = mix ["Song B", "Song C"].forEach(mix.addSong); // TypeError: Cannot read properties of undefined (reading 'songs')

Why? mix.addSong without parentheses is just the function — it isn't attached to mix any more. forEach later calls it as a plain addSong("Song B"): pattern two, this is undefined, and this.songs crashes.

Three fixes

// 1. Bind once, in the constructor — this is fixed for good constructor(name) { this.name = name; this.songs = []; this.addSong = this.addSong.bind(this); } // 2. Make the method an arrow-function class field — it takes this from the class addSong = (title) => { this.songs.push(title); }; // 3. Don't detach it — wrap the call in an arrow at the call site ["Song B", "Song C"].forEach((title) => mix.addSong(title));

A short history of this in React

Before hooks arrived, most React components were classes, and every event handler had to be bound by hand:

class Counter extends React.Component { constructor(props) { super(props); this.state = { count: 0 }; this.handleClick = this.handleClick.bind(this); // forget this line → crash on click } handleClick() { this.setState({ count: this.state.count + 1 }); } render() { return <button onClick={this.handleClick}>{this.state.count}</button>; } }

Forgetting that bind was one of the most common React bugs there was. Then React added hooks, and components became plain functions:

function Counter() { const [count, setCount] = useState(0); const handleClick = () => setCount(count + 1); // a closure — no this anywhere return <button onClick={handleClick}>{count}</button>; }

Same behaviour, no this, nothing to bind. The handler gets count and setCount through a closure (section 06) instead of through this. That trade — this out, closures in — is the main reason modern React looks the way it does.

In React, this becomes…

Mostly, nothing: you will rarely write this in React code. But you'll read class components in older codebases and tutorials, and the callback trap is still how this works everywhere else in JavaScript. Knowing why it disappeared is what makes the function-component style make sense.

Destructuring, spread, rest and computed keys

Corethe syntax every component uses

Refresher

Destructuring unpacks values out of an object or array into variables. Spread (...x) unpacks them into a new array or object. Rest (also ...x, on the left of = or in parameters) collects whatever is left over.

Full version → 05 · §10 Destructuring, spread, rest

Object destructuring — by name

Array destructuring — by position

const [first, second] = ["CS101", "CS201", "CS305"]; first // "CS101" const [, , third] = ["CS101", "CS201", "CS305"]; // skip with empty slots third // "CS305" // a function returning a pair — the caller chooses both names const [getPlanner, setPlanner] = createBox([]);

Object destructuring matches by name; array destructuring matches by position. That's why a pair like [value, setValue] comes back as an array: you can call the two things whatever suits each use.

Spread — copy and merge

const planner = [4, 10]; const bigger = [...planner, 18]; // [4, 10, 18] — planner is unchanged const updated = { ...course, seatsLeft: 2 }; // copy every field, then override one updated.seatsLeft // 2 course.seatsLeft // 3 — the original is untouched

In an object spread, later wins. { ...course, seatsLeft: 2 } overrides; { seatsLeft: 2, ...course } would be overridden right back.

Rest — collect what's left

const [head, ...tail] = [4, 10, 18]; tail // [10, 18] // remove a field without changing the original object const { description, ...summary } = course; summary // { id: 4, code: "CS402", title: …, department: …, credits: 4, … } — no description

Default parameters — a value for an argument that's left out

The = you used inside { room = "TBA" } works on plain parameters too. If the caller leaves the argument out, the default is used instead:

function creditsLabel(credits, unit = "cr") { return `${credits} ${unit}`; } creditsLabel(4) // "4 cr" creditsLabel(4, "credits") // "4 credits" creditsLabel(4, undefined) // "4 cr" — undefined counts as "left out" creditsLabel(4, null) // "4 null" — null doesn't

The default is worked out on every call that needs it, so items = [] gives each call its own new array. You'll lean on this in JS Lab 2: getJSON(url, fetchFn = fetch) uses the real fetch when the app calls it with one argument, and the tests pass a fake one as the second (JS Lab 2 · §04).

Shorthand properties and computed keys

const id = 21, code2 = "CS610"; const short = { id, code: code2 }; // { id: id } can be written { id } // a key that lives in a variable: square brackets const key = "department"; const filters = { department: "", search: "" }; const next = { ...filters, [key]: "Electronics" }; next // { department: "Electronics", search: "" }

That last line is the one to remember. With a computed key, one function can update any field of a form — the field name arrives as data.

References, equality and copies

Stretchwhere most React bugs start

Refresher

Numbers, strings and booleans are copied when you assign them. Objects and arrays are not. A variable holds a reference to the object — an arrow pointing at it — and assigning copies the arrow, not the object.

Full version → 05 · §09 References and mutation

Two names, one array

const planner = [4, 10]; const alias = planner; // copies the reference, not the array alias.push(18); planner // [4, 10, 18] — "planner" changed too planner === alias // true — they are the same array

=== on objects asks "same object?", not "same contents?"

Object.is is === with two edge cases fixed (NaN equals itself; 0 and -0 differ). It matters here only because it's the exact check React uses to decide whether your state changed.

const stops reassignment, not change

const ids = [1]; ids.push(2); // allowed: the array changed, the binding didn't ids = [3]; // TypeError: Assignment to constant variable.

Spread copies one level

structuredClone(plan) copies every level. It exists, and you should know it does — but you'll rarely need it, because the immutable updates in the next section copy only the path you change, which is cheaper and keeps everything else shared.

In React, this becomes…

When you call a setter, React compares the new state with the old one using Object.is. Same reference → "nothing changed" → no re-render. Immutable updates

Corechange by making something new

An immutable update never changes the value it's given. It builds and returns a new one with the change in it. You already have the pieces: spread from section 08, and map and filter, which always return new arrays.

The one thing to know about references

A variable holding an object or array holds a reference to it, not a copy: after const alias = planner, both names point at the same array, and alias.push(18) changes "both". And === on objects asks "the same object?", not "the same contents?" — [4] === [4] is false. React decides whether your state changed with exactly this check, so a changed-in-place array looks unchanged to it. Section 09 (stretch) has the details.

Pure functions and side effects

A function is pure when it returns the same output for the same input and changes nothing outside itself. Anything else it does is a side effect: changing its arguments, writing to the page, logging, starting a timer, calling the network, reading Math.random() or the clock. Every function in src/ is pure, which is exactly why a test can check it with one line.

The patterns

To…Write
add to an array[...list, item] (end) or [item, ...list] (start)
remove from an arraylist.filter((x) => x.id !== id)
update one itemlist.map((x) => x.id === id ? { ...x, seatsLeft: 0 } : x)
sort or reverselist.toSorted(cmp), list.toReversed() — or [...list].sort(cmp)
update an object field{ ...obj, field: value }
remove an object fieldconst { field, ...rest } = obj → use rest

Never on data you were given

push, pop, shift, unshift, splice, sort, reverse, and obj.field = …. They all change the original. Use them freely on arrays you just created yourself — never on the ones passed in.

Updating one item inside a list

function renameCourse(courses, courseId, title) { return courses.map((c) => (c.id === courseId ? { ...c, title } : c)); } const next = renameCourse(courses, 5, "Distributed Systems II"); next === courses // false — a new list next[4] === courses[4] // false — a new object for the course that changed next[0] === courses[0] // true — every other course is the SAME object

Only the path to the change is new: the list, and the one course. Everything else is shared. That's what makes it cheap, and it's what lets React skip re-drawing the 19 cards that didn't change. Your takeSeat is this pattern with a different change inside.

When nothing changes, return the same thing

function setTitle(course, title) { return course.title === title ? course : { ...course, title }; } const c = courses[0]; setTitle(c, c.title) === c // true — same title, so nothing new setTitle(c, "Intro") === c // false — a real change, a new object

Returning the same reference is how you say "no change". Given the same reference, React skips the re-render entirely. addToPlanner and removeFromPlanner do this: addToPlanner([4, 10], 10) hands back the very same array.

In React, this becomes…

Every state update in React is one of the patterns in that table. Adding to a list: setPlanner([...planner, id]). Removing: setPlanner(planner.filter((x) => x !== id)). Updating one item: a map with a spread inside. Components must also be pure — given the same props and state, render the same thing — and all side effects go in event handlers or effects. In development, React (in Strict Mode) even runs your components twice to catch impure ones.

An event doesn't stay where it happened. After running listeners on the target, it travels up through every ancestor — the li, the ul, the main, all the way to document — running their listeners too.

Bubbling is also useful. Instead of one listener per item, put one listener on the parent and work out which item was hit. This is event delegation, and it also works for items added later:

When the data changes, everything on screen that depends on it updates by itself. You only ever change the data — the state. The view reacts. React is named for exactly this, and almost everything it does exists to make it true.

Much better. There's now exactly one place that knows how the number becomes the page, so the Reset bug can't happen. But two problems are left. Every change still needs a render() after it — forget one and that button silently stops updating the page. And count is an ordinary variable: any code anywhere can change it without redrawing.

Stage 4 — make changing and redrawing one action

You already have the tool, from section 06: lock the value inside a closure so the only way to change it is through a function. Then put the redraw inside that function. Now it's impossible to change the value without redrawing.

So useState(initial, onChange) in src/s15-state.js is your createBox from section 06 with one addition: it takes a second argument, onChange — the redraw — and the setter calls it every time it stores a new value. It returns the pair [getState, setState], so the caller chooses the names (section 08). In web/counter.js it's used like this:

// web/counter.js import { useState } from "../src/s15-state.js"; const [getCount, setCount] = useState(0, render); // render is your stage 3 function

Now render() reads getCount() instead of a variable, and each handler becomes one line that only says what the new count is — setCount(…) — and never touches the page; the setter does the rest. Call render() once at the start to draw the first screen. A second piece of state — the step input — is one more useState line, and +, − and the disabled check then use the step instead of 1.

That's reactivity. Your handlers change state and nothing else; the screen follows. One way to say it that you'll hear again: the view is a function of the state — render() reads the state and produces the page, and setState makes sure it runs whenever the state changes.

Seen in the JavaScript concepts lecture

The shop demo's setState(next) — replace the state, then call render — is this stage 4, with the state in a top-level variable instead of a closure. Its Object.is check and the updater-function fix for stale closures are the two upgrades in "A smarter setState" below.

So why does useState return two things?

Because the value on its own can't do anything when it changes — that was stage 1's lesson. The setter is the only door to the value, and the door has code bolted to it: store the new value, then redraw. That's the answer to the question from section 06. A plain variable can't notify anyone. A function can.

A smarter setState

Two upgrades to your setter make your useState behave like React's. Both use ideas from earlier sections.

  1. Accept an updater function, exactly like applyUpdate in section 05: if the setter is handed a function, it calls it with the current value and uses what comes back. Handlers become setCount((c) => c + 1), which always works from the latest value.
  2. Skip the redraw when nothing changed: if Object.is(newValue, currentValue) is true, store nothing and don't call onChange. Notice what follows: if you push onto the array in state and pass the same array back, Object.is says "same" and nothing redraws. That's why every update must make a new value (section 10) — and React behaves exactly the same way.
const [getCount, setCount] = useState(5, render); setCount((c) => c + 1); // render runs; getCount() is now 6 setCount(6); // same value: render does NOT run

Make both changes and pass node --test test/s15-smarter.test.js.

How React's version differs

No render argumentReact already knows which component called useState, so it knows what to redraw. You never pass it a render.
A value, not a getterReact gives you const [count, setCount] — a plain value. It can, because it calls your component function again on every render, and each call gets a fresh count (the stretch part of section 06). Our script runs only once, so it needs getCount() to read the latest value.
Only what changedOur render() rewrites all four places every time. React compares the new page description with the previous one and touches only the parts that differ. The next lab shows why that matters.

In React, this becomes…

The whole counter page, as a React component — with no querySelector, no textContent, and no render() call, because the JSX is the render function:

  2. {seatsLeft === 0 ? "Full" : `${seatsLeft} left`} — JSX braces hold one expression (03), so the either/or is a ternary, with a template literal inside.
  3. onClick={onAdd} — passing the function, not calling it (04). The card doesn't know what "add" means; its parent does. The card just calls the callback it was handed: events flow up (05).
  4. const [planner, setPlanner] = useState([]) — array destructuring of a pair (08): a value you don't change directly, and the one function that changes it. Your useState from section 15, almost exactly.
  5. plannerCredits(planner, courses) — ids to courses, then a total: your stretch function from section 11. Computed fresh on every render, never stored, so it can't drift.
  6. planner.length > 0 && <span>… — "only if", written safely so a 0 never shows (03).
  7. courses.map((course) => <CourseCard key={course.id} … />) — a list on screen is map (11), with a stable id as the key, never the index.

It changes its input, and it returns the same state object. React compares old and new state with Object.is, sees the same reference, and concludes nothing changed. Copy the path to the change instead:

const addCourse = (state, course) => ({ ...state, courses: [...state.courses, course] });
