Part 2 · Screens and URLs
03

One page, many screens — the URL is state

Corewhy a router exists

Refresher

In JS Lab 2 you kept everything the page shows in one state object and drew the screen from it (JS Lab 2 · §05). There's one more piece of state you didn't put in it, because the browser already keeps it for you: the URL.

What the URL does for a user

Think about what people do with a link to a course page. They press Back to return to the list. They bookmark it. They paste it to a friend. They reload it. They open it in a new tab. Every one of those only works if the screen can be rebuilt from the URL alone. So the URL has to say which screen, and which course — and the app has to draw the screen from it, the same way it draws from any other state.

Websites did this with files; single-page apps can't

On an old-style website, each URL is a different HTML file on the server. Click a link, the browser asks the server for the next page, and the whole page is thrown away and replaced — including every JavaScript variable. A React app is one HTML page, index.html, with JavaScript that swaps what's on it. If it did nothing about the URL, the address bar would say localhost:5173/ forever: no Back, no bookmarks, no sharing.

Client-side routing fixes that. JavaScript changes the URL without asking the server for a new page, and draws the screen that belongs to it. The browser gives you the tool:

Do this now — change the URL without leaving the page

With the app open (npm run dev), in the DevTools console:

location.pathname // "/" history.pushState(null, "", "/courses/4") location.pathname // "/courses/4" — and nothing reloaded history.back() // the address bar goes back to "/"

The address bar changed, a new entry went on the Back stack, and the page didn't reload — the Network tab shows no new request. But the screen didn't change either: nothing in the app was listening. A router is the code that listens. It reads the URL, draws the matching screen, and redraws when the URL changes. React Router does exactly that, on top of history.pushState.

Why a reload still works

Type localhost:5173/courses/4 in the address bar and press Enter. That is a request to the server, for a file called /courses/4 — which doesn't exist. Vite's dev server knows it's serving a single-page app: for any path that isn't a real file or /api/…, it answers with index.html. The app starts, the router reads /courses/4 from the address bar, and draws that screen.

$ curl -s -o /dev/null -w "%{http_code} %{content_type}\n" http://localhost:5173/me 200 text/html # index.html — the app, not a file called "me"

On Windows PowerShell, type curl.exe instead of curl, and -o NUL instead of -o /dev/null.

Whatever hosts the built app later has to do the same, or every reload on an inner page is a 404. Keep the distinction in your head: clicking a link inside the app never asks the server for a page; typing a URL or reloading always does — and a reload starts the JavaScript from scratch, which will matter a lot in section 09.

Q1Which of these belong in the URL: the course being viewed; the password typed into the login form; who's logged in; the department filter on the list?
Show answer

The course, yes — it's what a link to the page has to say. The filter usually yes, so a filtered list can be shared (this lab doesn't need one). The password, never: URLs end up in history, logs and screenshots. Who's logged in, no: two people opening the same link should see the same page, each as themselves. That's per-browser state, and it gets its own home in section 08.

04

Routes, Route and Link

Coresrc/App.jsx

Refresher

A component is a function from props to JSX, and you build screens by putting components inside each other (React Lab 1 · §05–06). A router is just more components.

The router: BrowserRouter

Open src/main.jsx (given). The app is wrapped in a <BrowserRouter>:

import { BrowserRouter } from "react-router"; createRoot(document.getElementById("root")).render( <StrictMode> <BrowserRouter> <App /> </BrowserRouter> </StrictMode> );

BrowserRouter holds the current location in React state. It reads it from the address bar at start, listens for Back and Forward, and gives every component inside it a way to move to a new URL (with history.pushState, as you just did by hand). When the location changes, everything that depends on it re-renders. Every router component and hook in this lab only works inside it — section 16 has the error you get otherwise.

The tests use a <MemoryRouter initialEntries={["/courses/4"]}> instead (see test/support/app.jsx). Same thing, but the "address bar" is an array in memory, starting wherever the test wants. That's why the router is in main.jsx, not in App: the tests can wrap App in a different one.

The route table: Routes and Route

<Routes> looks at the current URL and renders the <Route> that matches it — only that one:

import { Routes, Route } from "react-router"; <Routes> <Route path="/" element={<CoursesPage />} /> <Route path="/login" element={<LoginPage />} /> </Routes>

Three things to notice. element takes an element — <CoursesPage />, with the angle brackets — so if a page needed props, you'd write them right there in the table. The routes are ranked, not tried in order: the most specific match wins, wherever it is in the list. And a URL that matches nothing renders nothing — section 05 adds a catch-all for that.

Link, not <a>

To move between screens, use <Link to="/login">Log in</Link>. It renders a real <a href="/login"> — so hovering shows the URL, a screen reader announces a link, and right-click → Open in new tab works. But when it's clicked, it cancels the browser's normal page load and calls pushState instead. The difference is the whole point:

You writeWhat happens on click
<Link to="/me">The URL changes, the router draws the new screen. No request for a page. All React state — including who's logged in — is still there.
<a href="/me">A full page load: the browser asks the server for /me, gets index.html, and starts the app from scratch. Every piece of React state is gone. Your login survives only because section 10 keeps a copy of it in sessionStorage.

Do this now — see the difference in the Network tab

When your routes work (end of section 05): Network tab, filter Doc. Click links in the header — no new rows. Then press Enter in the address bar — one row, a whole new page. A <Link> click should never add a Doc row.

Exercise — the route table

In src/App.jsx, replace the starter's lone <CoursesPage /> with <Routes>. Keep <AuthProvider> around the outside (it's a stub until section 10; every page will need it). These are the routes — all of them go inside a layout route, which is the first thing in section 05, so read that before you type:

path="courses/:id"<CourseDetail /> — section 06

Q1You put <Route path="*" element={<NotFound />} /> first in the list. Does /login still show the login page?
Show answer

Yes. React Router ranks the routes by how specific they are — a fixed segment like login beats a :param, which beats * — and the order you wrote them in doesn't matter. (Older routers matched the first route that fitted, which is why you may see advice about ordering.)

05

Layouts, Outlet and the 404 route

Coresrc/pages/Layout.jsx · NotFound.jsx

Every screen has the same header. You could put <Header /> at the top of every page component — and then change six files whenever the header changes. Instead, routes nest: a layout route draws the frame once, and the matched child route's page appears inside it.

<Routes> <Route element={<Layout />}> {/* no path: it wraps its children */} <Route index element={<CoursesPage />} /> {/* "/" */} <Route path="login" element={<LoginPage />} /> {/* "/login" — relative, no leading slash */} {/* … the rest of the table from section 04 … */} </Route> </Routes>

The outer <Route> has no path: it matches whenever one of its children does, and renders <Layout />. Child paths are relative to the parent, so they have no leading slash. index means "the parent's own URL" — here, /.

Outlet — where the child goes

The layout decides where in itself the page appears, with <Outlet />:

import { Link, Outlet } from "react-router"; export function Layout() { return ( <> <header className="topbar"> <nav aria-label="Main"> <Link to="/">Courses</Link> <Link to="/me">My courses</Link> </nav> <div className="who">{/* TODO: a "Log in" link to /login */}</div> </header> <main> <Outlet /> {/* the matched child route's element renders here */} </main> </> ); }

That's nearly all of the exercise — finish the Log in link and it's done. Use a real <header> and <main>: the tests find them by role (a top-level <header> is a banner), and so does a screen reader. There's a bonus you can't see: moving from / to /login, the Layout element stays mounted and only the Outlet's content changes. Any state in the layout survives navigation — useful in section 10, where the header shows who's logged in.

The 404 route

path="*" matches any URL, and ranks below everything else, so it only wins when nothing else does. Put it inside the layout route, so a wrong URL still gets the header and a way out. Write NotFound: a heading "Page not found", the path that wasn't found, and a link "Back to the courses" to /. For the path, useLocation() gives you the current location — { pathname, search, state, … }.

Then in the browser: the header on every screen, Log in goes to the (still empty) login page, /nope shows Page not found, and the Network tab's Doc filter stays empty as you click.

Swap the header's Links for NavLinks. A NavLink is a Link that knows whether it points at the current page: when it does, it gets class="active" and aria-current="page". styles.css already underlines .topbar nav a.active. One detail: a NavLink is also active on the pages under it (/me/anything) unless you add end; the root link to="/" is the exception, active only on / itself. npx vitest run --mode stretch test/stretch/navlink.test.jsx.

URL parameters — a page per course

CoreCoursesView · useCourse · CourseDetail

Twenty courses, one page component. The route courses/:id has a parameter: :id matches any single segment — /courses/4, /courses/9999, even /courses/abc — and the page reads it with useParams():

import { useParams } from "react-router"; // on /courses/4 const { id } = useParams(); id // "4" — always a string: it came out of a URL id === 4 // false — compare with Number(id) if you need to

Here the id goes straight back into another URL, /api/courses/${id}, so the string is fine as it is.

Step 1 — link every course to its page

In src/courses/CoursesView.jsx — your Lab 2 View, from step 0 — make each course's name a <Link> to /courses/<the course's id>, with the same text, CS402 · Enterprise Software Development (import Link from react-router). A template literal builds the path. Change nothing else in the file.

Step 2 — useCourse(id): fetch one course

Same seam as Lab 2 (React Lab 2 · §07): the fetching lives in a hook, the page only renders. src/courses/useCourse.js has the state; write the effect that loads GET /api/courses/{id} — the Lab 2 pattern, ignore flag and all (§05). Two differences from useCourses:

  • Keep the whole error, not just its message: setError(err). The page needs err.status to tell "no such course" (404) from everything else. (useCourses keeps only the message, because its page only shows it. Keep what the screen needs.)
  • The dependency array is [id], and the effect starts with setStatus("loading"). Why both? Read on.

The same component, a different id

Going from /courses/4 to /courses/5, the same route matches, so React keeps the same CourseDetail — it re-renders it with a new id, it doesn't remount it. An effect with [] ran once, for course 4, and never runs again: the URL says 5, the page shows 4. With [id], React re-runs the effect whenever id changes (and runs the old one's cleanup first, so a slow answer for 4 can't land on the page for 5). setStatus("loading") stops the old course showing while the new one loads.

  2. Change [id] to [] in useCourse. Click Next → a few times. The URL counts up; the heading doesn't.
  3. Put [id] back; watch it work; delete the Next link.

In src/courses/CourseDetail.jsx, replace the starter's const id = "1" with useParams(), then fill in the TODO above the return: "Loading course…" while loading; on an error, a heading "Course not found" and a link "Back to the courses" if error.status === 404, and the error's message (with role="alert") for anything else. Two kinds of "not found", at two different layers: Page not found is the router finding no route for the URL. Course not found is a route that matched, a request that went out, and an API that answered 404. Same words for the user; different code, different place.

07

Navigating from code

CoreuseNavigate · <Navigate> · location.state

A <Link> is for a person clicking. Sometimes your code decides where to go: after logging in, go back where you came from; after creating a course, go to its page; when someone who isn't logged in opens /me, send them to log in. React Router has two tools, and which one you use depends on when you decide.

useNavigate — in an event handler

import { useNavigate } from "react-router"; const navigate = useNavigate(); // at the top of the component, like any hook navigate("/me"); // push: a new entry on the Back stack navigate("/", { replace: true }); // replace: swap the current entry instead navigate(-1); // the same as pressing Back navigate("/login", { state: { from: location } }); // carry data along (below)

Push or replace? Push when the user should be able to come back. Replace when the page you're leaving shouldn't be in the history at all — after logging in, pressing Back shouldn't show the login form again.

<Navigate> — while rendering

Calling navigate() while a component is rendering is a side effect in the middle of a render; React Router warns about it, and it misbehaves. When it's the render that discovers "this user shouldn't be here", return a <Navigate> element instead. It navigates as soon as it's on the screen:

if (!user) return <Navigate to="/login" replace />; // section 11 is built on this line

The rule: in a handler, call navigate(); in render, return <Navigate />.

location.state — data that travels with a navigation

Both tools take a state: any value, stored with that history entry, and read on the other side with useLocation().state. It isn't in the URL, so it doesn't show, can't be bookmarked, and is gone if the link is opened in a new tab — which is exactly right for "where was this person trying to go before we sent them to log in?". Sections 11 and 13 use it for that, and nothing else.

const location = useLocation(); location // { pathname: "/login", search: "", hash: "", state: { from: { pathname: "/me", … } }, key: "…" }
Q1After a successful login, the login page calls navigate(from). Push or replace — and what goes wrong with the other one?
Show answer

Replace. With push, the history is … /me → /login → /me, so Back from /me shows the login form to someone who's already logged in. With replace, /login is swapped out and Back goes to wherever they were before.

Context — sharing without passing down

CorecreateContext · useContext · off the "not yet" list

Refresher

State lives in the closest common parent of everything that needs it, and goes down as props; events come up as callback props (React Lab 1 · §08–09). In React Lab 2 · §09, context was on the not yet list: "props are enough at this size". This section is about the size at which they stop being enough.

The problem: one value, needed everywhere

Once there's a login, many parts of the app need to know who's logged in, or need their token to call the API:

App ← the session would have to live here: the common parent ├─ Layout needs user (name in the header), logout │ └─ Outlet → whichever page the URL picks: │ ├─ CoursesPage → useCourses needs token (addCourse is ADMIN-only) │ ├─ CourseDetail → useCourse needs user (Enroll), token │ ├─ LoginPage needs login │ └─ RequireAuth needs user │ └─ MyCoursesPage → useMyEnrollments needs token

With props only, the session lives in App, and the route table turns into this:

<Route element={<Layout user={user} onLogout={logout} />}> <Route index element={<CoursesPage token={token} />} /> <Route path="courses/:id" element={<CourseDetail user={user} token={token} />} /> <Route path="login" element={<LoginPage onLogin={login} />} /> <Route path="me" element={<RequireAuth user={user}><MyCoursesPage token={token} /></RequireAuth>} /> </Route>

…and inside each page, the token is handed on again to its hook: useCourse(id, token), useMyEnrollments(token), useCourses(token). Most of these components don't use the token; they just pass it along. That's prop drilling. It works, but every new page has to remember to thread it through, and adding one more app-wide value (a language setting, say) means editing every one of them.

Context: provide once, read anywhere below

A context lets a component high up provide a value, and any component below it — at any depth, through any routes — read it directly, without the ones in between knowing:

import { createContext, useContext } from "react"; const AuthContext = createContext(null); // 1. a channel, with a default value <AuthContext.Provider value={{ user, token, login, logout }}> // 2. provide a value, high up <Routes>…every page…</Routes> </AuthContext.Provider> const { user, token } = useContext(AuthContext); // 3. read it, in any component inside

Reactivity carries over: when the provider's value changes — someone logs in or out — every component that read it re-renders. The header switches from Log in to the user's name without anybody passing it a prop. And a component outside every provider gets the default you gave createContext — here null — which is why the lab's useAuth() checks for it and throws a clear error.

The lab wraps all of this in a tiny file, src/auth/AuthContext.jsx, that exports two things: AuthProvider (a component that holds the session state and renders the provider) and useAuth() (a custom hook: useContext(AuthContext) plus the check). Components never touch AuthContext itself. You write it in section 10.

children — what goes between the tags

AuthProvider is used as a wrapper, <AuthProvider><Routes>…</Routes></AuthProvider>, and that needs one more fact about props. Whatever you put between a component's opening and closing tags arrives as a prop called children. It's an ordinary prop — JSX puts it in the props object for you, as in React Lab 1 · §04's jsx("h1", { …, children: […] }) — and the component decides where it goes:

function Card({ title, children }) { // props, as in React Lab 1 §05 return ( <section className="card"> <h2>{title}</h2> {children} </section> ); } <Card title="CS201"><p>Data Structures</p></Card> // children is the <p>

Authentication in a single-page app

Corethe token, the header, 401 vs 403

Refresher

You read a JWT filter in the Spring Boot auth lab. This is the same mechanism from the other side: the browser holding the token and sending it. The rules are in the contract, openapi.yaml → Authentication.

Three requests

POST /api/auth/login { "email": …, "password": … } → 200 { "accessToken": "eyJhbGciOi…", "tokenType": "Bearer", "expiresIn": 3600 } → 401 { "message": "Invalid email or password", … } (same message for both cases) GET /api/users/me Authorization: Bearer eyJhbGciOi… → 200 { "id": 2, "email": "student@esd.local", "fullName": "Sam Student", "role": "STUDENT", … } POST /api/auth/logout Authorization: Bearer eyJhbGciOi… → 204 — the server revokes this token; from now on it gets 401 everywhere

The token is a JWT, signed by the server. Your app treats it as opaque: it doesn't decode it, doesn't check its expiry, doesn't read the role out of it. Who the user is and what role they have comes from GET /api/users/me. The server is the only judge: on every request it checks the signature, the expiry, whether the token was logged out, and the role.

401 and 403 are different questions

StatusWhat the server is saying
401 Unauthorized
"Authentication required"		Who are you? No token, a malformed Authorization header, or a token that's invalid, expired or logged out. Fix: log in (again).
403 Forbidden
"Access denied"		I know who you are, and no. A valid token, but the wrong role (a student creating a course) or not yours (dropping someone else's enrollment). Logging in again changes nothing.

Do this now — be the client, by hand

With npm run dev running, in the app's DevTools console, one line at a time:

Where the token lives

The app keeps the token in React state, inside AuthProvider. On its own, that has a consequence you'll see at once: a reload, a typed-in URL, a new tab or an <a href> click restarts the JavaScript, and the token is gone — you're logged out. So section 10 also keeps a copy in sessionStorage, which survives a reload in the same tab, and spells out what that costs.

The two changes to Lab 2's code

1. src/api/client.js takes a token. In Lab 2, apiFetch logged in as the admin behind your back, so the add form worked before there was a login screen. That stand-in is gone. Now apiFetch takes a token option, and sends it as the header when it's given:

export async function apiFetch(path, { method = "GET", body, token } = {}) { const headers = {}; if (body !== undefined) headers["Content-Type"] = "application/json"; if (token) headers.Authorization = `Bearer ${token}`; // ← the change // … fetch, then 204 → null, !res.ok → throw ApiError, else the JSON — as in Lab 2 } apiFetch("/api/users/me/enrollments", { token }) // a logged-in call apiFetch("/api/courses") // public: no token, no header

Why pass it in, rather than have apiFetch find the token itself? For the same reason getJSON took fetchFn in JS Lab 2 · §04: a function that gets what it needs from its arguments is easy to read, test and trust. The token lives in React state; the components that have it hand it over.

2. Your src/courses/useCourses.js reads the token from context. This one is yours to do, in the file step 0 brought over: import useAuth from ../auth/AuthContext.jsx, add one line at the top of the hook — const { token } = useAuth(); — and pass token along in addCourse's apiFetch options. (Until section 10, token is always null; the in-lab task in section 15 is what needs it.) Nothing else in Lab 2's files changes, except that the list's course names become links (section 06) and the form moves to the admin page (section 15).

Q1Logging out could just forget the token in the browser. Why does the contract make you call POST /api/auth/logout?
Show answer

Because forgetting it here doesn't stop it working anywhere else. Anyone who copied it — from a shared computer, a log, an extension — could keep using it until it expires. The server writes the token's id on a deny-list, so after logout it's rejected everywhere. The contract says it plainly: "Discarding the token on the client alone is not logout."

Q2Why fetch /api/users/me after logging in, instead of decoding the JWT to get the role?
Show answer

The contract says clients treat the token as opaque: its inside is the server's business, and may change. /api/users/me is the documented answer to "who is this?", and it has things the token doesn't, like fullName. It also proves the token works before the app says "logged in".

Step 4 — survive a reload, and know what it costs

Keep the session in sessionStorage as well, so a reload doesn't log you out. Two pieces, both in AuthProvider — the first replaces step 1's useState(null):

const [session, setSession] = useState(loadSession); // a function: React calls it once, at the start useEffect(() => { // copy every change out of React if (session) sessionStorage.setItem("esd-session", JSON.stringify(session)); else sessionStorage.removeItem("esd-session"); }, [session]);

Write loadSession() to read it back (and return null if there's nothing, or it isn't valid JSON). The effect is effects doing their real job: keeping something outside React in step with state inside it.

The trade-off is real. Memory: a reload or a new tab logs you out. sessionStorage: a reload keeps you logged in (in that tab, until it closes) — and any script running on the page can read the token with one line and send it somewhere. If an attacker ever gets their JavaScript onto your page (that's XSS, cross-site scripting), the storage is the first place they look. localStorage: every tab, even after the browser closes; the most convenient, and the longest-lived target. Many real apps use a cookie the server sets as httpOnly, which JavaScript can't read at all — with its own rules to learn. This contract uses Bearer tokens, so here it's memory or storage — and this app, React Lab 4 and the OAuth lab keep the session in sessionStorage. npx vitest run test/session.test.jsx, then in the browser: log in, reload — still logged in; log out, reload — logged out.

Protected routes

Coresrc/auth/RequireAuth.jsx

/me means nothing without a logged-in user. Open it logged out and the page would send a request with no token and show "Authentication required". Better: send the person to log in, and bring them back afterwards. That's a protected route — a component that wraps a page and decides, while rendering, whether it may show:

export function RequireAuth({ children }) { const { user } = useAuth(); const location = useLocation(); if (!user) return <Navigate to="/login" replace state={{ from: location }} />; return children ?? <Outlet />; } // in App.jsx (you wrote this in section 04): <Route path="me" element={<RequireAuth><MyCoursesPage /></RequireAuth>} />

Every piece is from section 07. It's a decision made during render, so it's <Navigate>, not navigate(). It's replace, so the history doesn't keep a /me that bounces you to the login page every time you press Back. And it carries the current location as from. children ?? <Outlet /> lets it work both ways: wrapped round one page, as above, or as a layout route with the protected pages as its children.

Redirect-back, step by step

  1. Logged out, you open /me. RequireAuth renders <Navigate to="/login" replace state={{ from: location }} /> — location.pathname is "/me".
  2. The URL is now /login, and that history entry carries { from: { pathname: "/me", … } }.
  3. You log in. LoginPage reads location.state?.from?.pathname → "/me", and calls navigate("/me", { replace: true }).
  4. RequireAuth renders again; now there's a user, so it renders MyCoursesPage.

Write RequireAuth, and npx vitest run test/protected.test.jsx.

A protected route is for the user, not for security

Everything in src/ is sent to the browser. Anyone can open DevTools, change it, or skip the app entirely and call the API — you did, in section 09. Hiding a page protects nothing. What protects the data is the server, answering 401 or 403 on every request. RequireAuth is there so a person isn't shown a broken page.

  3. Put RequireAuth back.

Why Log out navigates first

Section 10 had you write navigate("/") before await logout(). Swap them and log out while you're on /me: you land on the login page, not the course list. Here's why. React Router applies every navigation as a transition — a low-priority update that waits behind ordinary ones. logout()'s setSession(null) is ordinary, so React draws it first, while the URL is still /me. RequireAuth sees no user and renders <Navigate to="/login" replace>, which replaces the / you asked for. Navigating first means the guarded page is already gone when the user disappears. A test checks it.

You should call navigate() in a React.useEffect(), not when your component is first renderednavigate() was called during render. In render, return <Navigate to=… />; call navigate() in event handlers (07).
After logging in you land on /, not where you were goingThe login page ignores location.state?.from?.pathname, or the guard didn't pass state={{ from: location }}, or you navigated to from (an object) instead of from.pathname (11).
Back after logging in shows the login form againnavigate(from) without { replace: true } (07).
Logging out on My courses lands on the login pageawait logout() before navigate("/"). Navigate first — the reason is in section 11.
Couldn't load your courses: Authentication required — while logged inThe request went without a token: a missing { token } in an apiFetch call. Check the request's headers in the Network tab (09, 12).
401 Authentication required, with a token, after logging out or a while after logging inThe server no longer accepts that token: it was logged out (revoked), or it expired (3600 seconds). Something kept an old copy, or the session simply ran out. Log in again; handling this everywhere at once is React Lab 4.
403 Access deniedLogged in, but not allowed: the wrong role, or not your enrollment. Often an enrollment's id mixed up with a course's id (12).

Test: Unable to find role="banner"The header isn't a <header> element, or it's inside <main> (05).

How to debug a routing or auth problem

Two questions, in this order. Where am I? Put console.log(useLocation()) at the top of Layout: every render prints the path and the state, so redirects show up as a sequence. Who am I? Add console.log(useAuth().user) next to it. Then the Network tab answers the third: what did the server get? — the request, its Authorization header, and the status.

401 Unauthorized"Who are you?" No token, or one that's invalid, expired or logged out. Log in (again).
403 Forbidden"I know who you are, and no." A valid token without the right role or ownership.
Authorization headerAuthorization: Bearer <token> — how each request says who it's from.
BrowserRouterThe router for the real browser: keeps the location in state, in step with the address bar and Back/Forward.
catch-all routepath="*": matches anything, ranks last. Your 404 page.
client-side routingChanging the URL and the screen with JavaScript, without asking the server for a new page.
contextA value provided high in the tree that any component below can read with useContext, without props in between.
index routeA child route with no path of its own: it shows at the parent's URL.
JWTJSON Web Token: a signed string the server issues at login. Opaque to the client; only the server judges it.
layout routeA route without a path that renders a frame (header, nav) and an <Outlet /> for its children.
LinkA real <a href> whose click changes the URL with pushState instead of loading a page.
location.stateData stored with one history entry, not in the URL. Read with useLocation().state.
MemoryRouterA router whose "address bar" is an array in memory. For tests.
NavigateAn element that navigates when rendered. For decisions made during render, like a guard's.
NavLinkA Link that marks itself active / aria-current="page" when it points at the current page.
OutletWhere a layout route draws the matched child route's element.
prop drillingPassing a value through components that don't use it, just so one deeper down can.
protected routeA wrapper that shows a page only to logged-in users and sends everyone else to log in. A convenience, not security.

redirect-backRemembering where someone was going (from), sending them to log in, then on to from.
sessionStoragePer-tab browser storage that survives a reload, cleared when the tab closes. Readable by any script on the page.
transitionA low-priority React update that waits behind ordinary ones. React Router applies navigations as transitions.
URL parameterA :name segment in a route path, read with useParams(). Always a string.
