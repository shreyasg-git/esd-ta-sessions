Reading a failing test

Vitest prints the test's name, what it expected, what it got, and the line in the test file. When a test can't find something on the page, Testing Library prints the whole page your component drew, as HTML:

TestingLibraryElementError: Unable to find an accessible element with the role "button" and name "Row 1, column 2: 5" ... <body> <div> <button class="cell" aria-label="Row 0, column 1: 5">5</button> </div> </body>

Read that HTML: it's what your code actually produced. Here the label counts from 0 where the test wanted 1.

Why the tests ask for "the button named…"

The tests find things the way a person does: the button named "Row 1, column 2: 5", the heading "Stats" — not "the third div" or "the element with class x". That's why your markup must use real elements (<button>, <h2>, <table>) and give each cell a name. A page these tests can use is a page a screen reader can use.

02

What you're building

Corethree components, one state

A grid of numbers. Click a cell, and its number goes up by one. Next to the grid — outside it — a small panel shows the sum, the average, the biggest number and how many cells aren't zero, and they change as you click. That's the whole app. It's small on purpose: the mental model is the point, and every later React lab builds on it.

At the end (section 11), the numbers stop being written in your code and come from a server instead — and you'll see how little has to change.

The component tree

What each part teaches

Matrix made of CellsComposition: small components inside bigger ones, each with one job (05, 06).
a number reaches a CellProps flow down: the parent decides, the child shows (05).
a click changes the numbersEvents flow up: the Cell calls a function its parent gave it (08).
stats outside the matrixLifted state: two siblings need the same numbers, so they live in the parent (09).
one click, two places changeRe-render: you change the state; React redraws the screen (10).

Why the numbers can't live in a Cell

The obvious first idea is that each Cell keeps its own number. It would even work — click, number goes up — until you build the stats panel. Stats needs all nine numbers, and in React, data only flows down: a component can't reach into a sibling, or up into its parent. So the numbers have to live in the closest component that is above both the cells and the stats: App. That's called lifting state up, and this problem was chosen because it forces it. Keep the picture above in mind; section 09 comes back to it.

By hand (JS Lab 2) → React

JS Lab 2's loop was: an event → transition makes the next state → setState stores it and calls render(), which redraws the regions that changed (JS Lab 2 · §02). React's loop is the same, with two steps taken off your hands: an event → you call setMatrix(next) → React runs your components again → React changes only the parts of the page that differ.

03

Vite — the dev server, and the path to your component

Corenpm run dev, index.html, main.jsx

A browser can't run your React code as written. It doesn't understand JSX (the HTML-looking parts), and it doesn't know where import … from "react" lives — that's a package name, not a file path. Vite is a dev server that fixes both: when the browser asks for src/App.jsx, Vite translates it into plain JavaScript on the spot and sends that. JS Lab 2's tools/serve.js just handed files over; Vite translates them first. It also watches your files: save, and the page updates.

Do this now — start it, and leave it running

  1. In the react-lab1 terminal: npm run dev.
  2. Open localhost:5173. It says TODO: section 04 — that's the placeholder in src/Header.jsx, your first exercise.
  3. Open src/Header.jsx, change the text inside the <h1>, and save. The page changes without a reload. Change it back.
  4. Leave npm run dev running for the whole lab, and use a second terminal (the + in VS Code's terminal panel) for npm test. Ctrl+C stops the server.
$ npm run dev VITE v7.3.7 ready in 220 ms ➜ Local: http://localhost:5173/

From index.html to your component

Follow the chain once, so nothing about it is mysterious. index.html is almost empty: one <div id="root">, and one script tag that loads src/main.jsx. That file is given:

import { StrictMode } from "react"; import { createRoot } from "react-dom/client"; import App from "./App.jsx"; import "./styles.css"; createRoot(document.getElementById("root")).render( <StrictMode> <App /> </StrictMode> );

That's the only line in the whole app that touches the DOM. It finds the empty div, hands it to React, and says: draw <App /> in here. App draws everything else. From now on you never call querySelector, createElement or textContent — you describe what the page should look like, and React makes it so.

By hand (JS Lab 2) → React

JS Lab 2's app.js started by grabbing every region with querySelector and kept those elements in an els object, so the render functions could write into them (JS Lab 2 · §07). Here, one createRoot call takes one empty element, and React owns everything inside it.

StrictMode, in one paragraph

<StrictMode> is a development-only checker. To catch components that aren't pure (same input, same output, no side effects — JS Lab 1 · §10), React calls your component functions twice in development, and on start-up runs your effects twice too. A pure function doesn't care; an impure one shows its bug. So if you put a console.log in a component and see it twice, that's StrictMode, not a bug. Section 10 uses it on purpose. A production build doesn't do it.

Building for real

npm run build writes a dist/ folder: plain HTML, JavaScript and CSS, with no JSX left, that any web server can host. npm run preview serves it on port 4173. You don't need either for this lab; it's good to have seen it once.

Error: Port 5173 is already in use

Another npm run dev is still running — in another terminal, or in another lab's folder. Each lab folder has its own server, and only one can have port 5173. Find it and stop it with Ctrl+C, then start yours again.

04

JSX is JavaScript

Coresrc/Header.jsx

Refresher

An expression is code that produces a value; a statement does something and has none. JSX braces { } take exactly one expression — which is why React code uses ? :, && and map, never if or for, inside the markup.

Full version → JS Lab 1 · §03 Values, truthiness and expressions · §16 Reading React

It's a function call, not HTML

JSX looks like HTML, but Vite turns every tag into an ordinary function call. This:

const name = "Asha"; const heading = <h1 className="title">Hello, {name}</h1>;

becomes, roughly:

const heading = jsx("h1", { className: "title", children: ["Hello, ", name] }); heading // { type: "h1", props: { className: "title", children: ["Hello, ", "Asha"] }, … }

So a JSX tag is an expression that produces a plain object — a description of an element, not the element itself. You can store it in a variable, return it from a function, put it in an array. React reads these descriptions and creates the real DOM elements. That's the createElement work from JS Lab 1 · §12, done for you.

The rules that follow from that

WriteBecause
className="cell"class is a JavaScript keyword. (for on a label is htmlFor, for the same reason.) React warns: Invalid DOM property `class`. Did you mean `className`?
{value} {row + 1} {ok ? "yes" : "no"}Braces hold one expression: a variable, arithmetic, a call, a ternary, &&, a map. Never an if or a for.
<br /> <input /> <Cell … />Every tag must be closed. A tag with no children closes itself with />.
return ( <> … </> );A function returns one value, so a component returns one element. Two side by side need a wrapper. A fragment, <> … </>, wraps them without adding an element to the page.
return ( … );The parentheses let JSX span several lines after return — the arrow-function rules from JS Lab 1 · §04.
onClick onContextMenuEvent props are camelCase, and take a function (section 05).
style={{ color: "red" }}Not a string: an object. The outer braces say "expression"; the inner ones are the object literal.
{/* a comment */}Inside JSX, a comment is an expression slot holding only a comment. // doesn't work between tags.

What braces can show

<p>{"text"}</p> // text <p>{42}</p> // 42 <p>{[1, 2, 3]}</p> // 123 — an array shows each item <p>{true}</p> // nothing — so do false, null and undefined <p>{0 && "items"}</p> // 0 — the trap from JS Lab 1 §03: && returns the 0 <p>{{ sum: 45 }}</p> // Error: Objects are not valid as a React child

That last one is worth remembering: in section 09 you'll compute stats(matrix), an object, and putting it straight in braces gives exactly that error. Show its fields — {sum} — not the object.

05

Components and props — the Cell

Coresrc/Cell.jsx

Refresher

A function is a value: you can pass it, store it, and call it later. save is the function; save() runs it now. And an object parameter can be destructured right in the parameter list: function f({ code, title }) { … }.

Full version → JS Lab 1 · §04 Functions are values · §08 Destructuring

A component is a function

A component is a function that takes one object — its props — and returns JSX. Its name starts with a capital letter: <cell> is an HTML tag React doesn't know; <Cell> is your function. When you write

<Cell row={0} col={1} value={5} onClick={handleClick} />

React calls your function with the attributes collected into one object:

Cell({ row: 0, col: 1, value: 5, onClick: handleClick })

so you destructure them in the parameter list, exactly like any other object parameter:

function Cell({ row, col, value, onClick }) { return <button …>{value}</button>; }

Props flow down, and are read-only

The parent decides what a child shows; the child shows it. A Cell never changes its own value — it doesn't own it, and assigning to a prop changes nothing anyone else can see. When the value needs to change, the Cell asks, by calling a function the parent gave it (section 08).

"5" or {5}?

value="5" passes the string "5". value={5} passes the number 5. Quotes only for plain strings; braces for everything else — numbers, booleans, arrays, objects and functions. With the string, value + 1 is "51".

A real button, with a name

A Cell is a <button>, not a <div> with a click handler. A button can be reached with Tab, pressed with Enter or Space, and announced by a screen reader — for free. A div gets none of that.

Nine buttons that say "1", "2", "3"… aren't enough for someone who can't see the grid, so each one gets an accessible name with aria-label: where it is, and what it holds. People count from 1, so row 0, column 1 is "Row 1, column 2":

aria-label={`Row ${row + 1}, column ${col + 1}: ${value}`} // "Row 1, column 2: 5"

A template literal in braces — an expression, like everything in JSX. The tests find each cell by this name.

Events are props too

onClick takes a function, and React calls it on each click. Pass the function; don't call it:

<button onClick={onClick}> // React calls onClick later, on each click <button onClick={onClick()}> // YOU call it now, during the render — every render

That's JS Lab 1 · §04's addEventListener("click", save()) bug, in JSX. In this app it's worse than "the click does nothing": once the Cell's onClick changes the numbers (section 08), calling it while rendering changes the numbers, which renders again, which calls it again — the numbers count up on their own. The last test in s05 checks that rendering doesn't call onClick.

By hand (JS Labs 1–2) → React

In JS Lab 2 a course card was two things: a view function that turned data into plain values (cardView, §06), and a render function that turned those values into DOM nodes. A component is both, in one function: data in, a description of the elements out. And there's no addEventListener — the handler is a prop on the element it belongs to (JS Lab 1 · §13).

06

Composition, lists and keys — the Matrix

Coresrc/Matrix.jsx

Refresher

map turns every item of an array into something else and returns a new array of the same length. On screen, that's "one card per course". And a thing is found by its id, never by its position — positions change when a list is sorted or filtered.

Full version → JS Lab 1 · §11 The array toolkit for UIs · JS Lab 2 · §08 Redraw only what changed

Components inside components

Composition is building a component out of other components. Matrix renders Cells; App renders Matrix. Each one is small and has one job: a Cell knows how to show one number, and nothing about grids. The Matrix knows about rows and columns, and nothing about how a cell looks.

A list is a map

A matrix is an array of rows, and a row is an array of numbers. So drawing it is two maps, one inside the other: rows become <tr>s, numbers become <td>s with a <Cell> inside. The outer one:

<table className="matrix"> <tbody> {matrix.map((values, r) => ( <tr key={r}> {/* one <td> per number in values, each with a <Cell> inside */} </tr> ))} </tbody> </table>

The inner one has the same shape, with (value, c). map returns an array of JSX objects, and an array in braces shows each item — that's all a list is. Note the parentheses after =>: the arrow returns the JSX without a return (rule 1 in JS Lab 1 §04). With braces instead, you'd need return, and forgetting it gives an empty table.

Write the <tbody>. Browsers insert one between a <table> and its rows anyway, so React warns if you leave it out: In HTML, <tr> cannot be a child of <table>.

Why lists need keys

When the matrix changes, React gets a new list of rows and has to match each new one with an old one: which stayed, which moved, which are new, which are gone. Only then can it touch just what changed. A key is how you tell it which is which. Without keys, React falls back to matching by position and warns:

Each child in a list should have a unique "key" prop. Check the render method of `Matrix`.

The rule: a key says which thing this is, and stays the same for the same thing on every render. For a list of courses, that's course.id — never the position, because sorting or filtering moves a course to a different position (JS Lab 1 · §11).

In this grid, though, nothing is ever added, removed or moved. The cell at row 1, column 2 is always that cell — its position is its identity. So here the index is the right key: key={r} on each row, key={c} on each cell. "Never use the index" isn't the rule; "the key must name the thing" is. The index is wrong as soon as items can be inserted, deleted or reordered — the React Bug Lab shows you exactly what breaks.

Keys that look clever and aren't

key={value}: two cells can hold the same number, and the number changes on every click — so after a click, React thinks the cell is a different cell, throws the button away and builds a new one. The button you clicked is gone, and so is the keyboard focus. That's the focus bug from JS Lab 2 · §08, which you fixed by hand with reference checks. key={Math.random()} does the same on every render. A test in section 08 catches both.

The key goes on the element you return from map — the <tr>, the <td> — not on something inside it. And a key isn't a prop: React uses it and doesn't pass it on, so a component can't read props.key.

By hand (JS Lab 2) → React

In JS Lab 2 you kept the previous state and asked, per region, previous.planner !== state.planner to decide what to redraw. React asks the same question per element, and keys are how it knows which old element a new one corresponds to. You decided by reference; React decides by type and key.

Q1Why is key={r} fine for these rows, but key={index} wrong for a list of courses you can sort?
Show answer

A key must name the thing. Grid rows never move, so a row's index always names the same row. Sort the courses and the course at index 0 is a different course, so index 0 no longer names the same thing — React would reuse the wrong element for it. Use course.id.

Q2Where does the key go in values.map((value, c) => <td><Cell key={c} … /></td>)?
Show answer

On the <td> — the element map returns. A key inside it is on the wrong level: the tds are the list items, and they have none, so React still warns.

State lives in App — React's useState

Coresrc/App.jsx

Refresher

In JS Lab 1 you wrote useState(initial, onChange). It locks the value in a closure and returns [getState, setState]; setState stores the new value and calls render(), so changing the data and redrawing the page become one action. The view is a function of the state.

Full version → JS Lab 1 · §15 Reactivity — build your own useState · §06 Closures

React's useState

Here is React's. Put it at the top of App:

import { useState } from "react"; import { START } from "./matrix.js"; export default function App() { const [matrix, setMatrix] = useState(START); return ( <main className="app"> <Header /> <Matrix matrix={matrix} /> </main> ); }

Same shape as yours: a pair, destructured, a value and the only function that changes it. Three differences, and each one is worth understanding:

Yours (JS Lab 1 §15)React's
useState(initial, render)useState(initial). No render argument: React knows which component called it, so it knows what to redraw.
[getState, setState] — read with getState()[matrix, setMatrix] — the value itself, in a plain const.
Your script ran once; getState() fetched the latest valueReact calls App() again after every change. Each call gets the latest value in a fresh const, so a getter isn't needed.
setState(next): store, then render()setMatrix(next): store, then React schedules a new render of App and everything below it.
Stretch: accept an updater; skip if Object.is(next, value)Built in. setMatrix((prev) => …) works, and setting the same object skips the re-render.

App runs again — and START isn't put back

The third row is the one to sit with. App is an ordinary function, and React calls it on the first render and again after every change. So the line useState(START) runs every time. But START is only used the first time; on every later call, useState hands back whatever you last set:

// first render: App() → useState(START) → [START, setMatrix] // a click: setMatrix(next) // next render: App() → useState(START) → [next, setMatrix] START ignored now

React remembers the value for you, outside your function, and gives it back on each call. Each call's matrix is a fresh constant belonging to that render — one call, one set of variables, exactly as in the stretch part of JS Lab 1 · §06.

Hooks go at the top, every time

useState is a hook — a function, starting with use, that only works while React is rendering a component. React matches hooks by the order they're called in, so call them at the top level of the component: not inside an if, a loop, or an event handler. Called from a handler, you get Invalid hook call. Hooks can only be called inside of the body of a function component.

Q1Why not just let matrix = START; in App, and assign a new matrix on a click?
Show answer

Two reasons. Changing a variable tells nobody anything — the screen doesn't move (stage 1 of JS Lab 1 §15). And even if React did re-run App, the let would start from START again: a function's local variables don't survive between calls. useState keeps the value outside your function, and its setter is the door that also triggers the redraw.

08

Events up, and an immutable 2-D update

Coresrc/matrix.js · Matrix.jsx · App.jsx

Refresher

When you pass a callback, the receiver decides when to call it, and with what. And an immutable update never changes what it was given: it builds something new, with only the path to the change being new — takeSeat returned a new list in which one course was new and the other nineteen were the same objects.

Full version → JS Lab 1 · §05 Callbacks · §10 Immutable updates

The click is in the Cell; the numbers are in App

A Cell can't change the matrix: it doesn't have setMatrix, and it shouldn't — it only knows its own number. So App hands a function down, and the Cell calls it. The function runs in App, where the state is. That's what "events flow up" means: not an event bubbling through the DOM, but a call to a function that was passed down as a prop.

Three hops, one per component:

// App — owns the state, so it owns the change function increment(row, col) { setMatrix((prev) => incrementAt(prev, row, col)); } <Matrix matrix={matrix} onIncrement={increment} /> // Matrix — knows each cell's position, so it fills it in <Cell row={r} col={c} value={value} onClick={() => onIncrement(r, c)} /> // Cell — knows only that it was clicked <button onClick={onClick}>{value}</button>

Look at the middle line. Matrix makes a new arrow function for each cell, and each one closes over that cell's r and c — buildButtons from JS Lab 1 · §04, and a closure from §06. The Cell doesn't need to know about rows and columns to report a click; Matrix answers "which one?" for it.

By hand (JS Labs 1–2) → React

By hand, you put one listener on the whole list and worked out what was hit: event.target.closest("button[data-id]"), then Number(button.dataset.id) because dataset values are strings (JS Lab 1 · §13, JS Lab 2 · §07). In React, each element gets its own handler, written right where the data is in scope — no data- attributes, no string-to-number, no closest. React still does delegation, internally: one listener at the root, for the whole app.

The update: a new matrix, sharing what didn't change

incrementAt(matrix, row, col) returns a new matrix with one cell one higher. It's takeSeat from JS Lab 1 §10 — a map with a ternary — applied at two levels: the outer map picks the row, and only the row that changes gets an inner map.

matrix.map((values, r) => r === row ? /* a new array: values, with one number changed */ : values )

You'll often see it written as prev.map((row, i) => row.map((val, j) => …)). That works on screen, but it copies every row, including the ones that didn't change. The test wants the rule you've followed since JS Lab 1: untouched things stay the same objects. It's what lets a cheap === answer "did this change?" — for your reference checks in JS Lab 2 §08, and for React.

Why the setter gets a function

setMatrix((prev) => incrementAt(prev, row, col)) hands React an updater: "whatever the matrix is when you get to this, here's how to make the next one". That's applyUpdate from JS Lab 1 · §05. setMatrix(incrementAt(matrix, row, col)) also works for a single click, but it uses this render's matrix; two updates before the next render would both start from the same old value, and one would be lost. The updater never is.

Why not matrix[row][col] += 1?

Because then you hand React the same array it already has. React compares old and new with Object.is — the check you wrote in JS Lab 1 §15's stretch — sees the same object, and concludes nothing changed: no re-render, nothing on screen moves. The data is changed and the page doesn't know. Section 10 has you do it on purpose and watch.

  2. In Matrix.jsx, give each Cell onClick={() => onIncrement(r, c)}.
  3. In App.jsx, write increment(row, col) and pass it as onIncrement.

Derived values — the stats, and why the state lives in App

Coresrc/matrix.js · Stats.jsx · App.jsx

Refresher

Anything you can work out from the state is derived, and derived data is computed on every render, never stored. Store the total too, and every change has to update both — and the first one that forgets makes the screen lie.

Full version → JS Lab 2 · §06 Views — derived data is computed, never stored · JS Lab 1 · §11 reduce

stats(matrix)

One pure function, four numbers:

stats([[1, 0], [3, 4]]) // { sum: 8, average: 2, max: 4, nonZero: 3 }

Make the rows one list first: [[1, 0], [3, 4]].flat() is [1, 0, 3, 4]. Then it's JS Lab 1 §11: a reduce for the sum, Math.max(...values) for the biggest, a filter and a length for the non-zero count. The average is the sum divided by the number of cells, zeros included.

The empty matrix

For [], Math.max() of nothing is -Infinity, and 0 / 0 is NaN. Neither should ever reach the screen. The test wants all four to be 0 — check for an empty list first.

The Stats component computes; it doesn't store

export default function Stats({ matrix }) { const { sum, average, max, nonZero } = stats(matrix); // every render, from the props return ( <section className="stats"> <h2>Stats</h2> <dl> <dt>Sum</dt> <dd>{sum}</dd> {/* Average (2 decimals: average.toFixed(2)), Max, Non-zero */} </dl> </section> ); }

No useState anywhere in it. The numbers are worked out from the matrix every time Stats renders — for nine numbers that takes microseconds. A <dl> is a description list: pairs of a term (<dt>) and its value (<dd>), which a screen reader announces as pairs.

const [sum, setSum] = useState(45)

Don't. Now there are two copies of the truth — the matrix, and a sum that is supposed to match it — and increment must remember to update both. Every new feature (a Reset, a decrement) must remember too. It's stage 2 of JS Lab 1 · §15 again: the same value in two places, kept in step by hand. Only the matrix is state; everything about it is computed.

Now you can see why the state is in App

Stats is a sibling of Matrix — both are children of App. Both need the numbers. Props only go down, from a parent to its children, so the numbers have to live in a component above both of them: App. If the numbers lived in the Cells, Stats couldn't reach them; if they lived in Matrix, Stats still couldn't. That's lifting state up: put state in the closest common parent of everything that needs it, and pass it down.

So App renders the two side by side, with the same matrix:

<div className="board"> <Matrix matrix={matrix} onIncrement={increment} /> <Stats matrix={matrix} /> </div>

Do this now — mutate, and watch nothing happen

Same app, data from the server

Coresrc/App.jsx — useEffect + fetch

Refresher

fetch(url) returns a promise of a Response; the body is a second promise, res.json(). And fetch only rejects when there's no response at all — a 404 still resolves, so real code checks res.ok.

Full version → JS Lab 2 · §04 fetch, URLs and failures · §03 Promises

The last step: the numbers stop being written in your code and come from a server instead. Same app — only where the data comes from changes. And because the data already lives in exactly one place, App, the change touches exactly one place. Matrix, Cell and Stats don't change at all.

The "server"

Vite serves anything in the public/ folder as it is. Open localhost:5173/matrix.json: it's a 4×4, as JSON. A real server would compute that answer; for this lab a file is enough, and later labs fetch from a real API.

Where can the fetch go?

Not in the body of App. App runs on every render; a fetch there would start a request on every render, its answer would call setMatrix, which renders again, which fetches again — forever. And not in an event handler: there is no event. You want it to happen once, when App first appears on the screen. That's what an effect is for: code React runs after it has put a render on the screen.

import { useEffect, useState } from "react"; export default function App() { const [matrix, setMatrix] = useState(START); useEffect(() => { fetch("/matrix.json") .then((res) => res.json()) .then((data) => setMatrix(data)); }, []); // … increment, and the return, unchanged }

The [] at the end is the dependency array. Empty means: run this once, after the first render, and never again. Leave it out and the effect runs after every render — and since this one sets state, that's the forever-loop again, visible as a Network tab filling up with matrix.json. React Lab 2 explains the dependency array properly, with values in it, and what an effect's clean-up is for; here, [] is all you need.

What the user sees, in order

// render 1 the 3×3 from START is on screen // effect fetch("/matrix.json") starts — React doesn't wait for it // (a moment) the answer arrives → setMatrix(data) // render 2 the 4×4 is on screen; the stats follow

So for a moment you see the old 3×3. That moment is where a real app shows "Loading…", and where it would show an error if the request failed. You're skipping both on purpose: they're React Lab 2's job. Notice too that Matrix drew a 4×4 without a single change — because it maps over whatever it's given, and the s06 tests made sure nothing assumed 3.

useEffect(async () => …) doesn't work

An async function always returns a promise, and React expects an effect to return nothing (or a clean-up function). It warns: useEffect must not return anything besides a function, which is used for clean-up. Use .then as above, or write an async function inside the effect and call it:

useEffect(() => { async function load() { const res = await fetch("/matrix.json"); setMatrix(await res.json()); } load(); }, []);

controlled inputAn input whose value comes from state, with an onChange that updates that state.
derived valueAnything computed from state — the sum, the max. Computed during render, never stored.
dependency arrayThe second argument of useEffect. []: run once, after the first render. React Lab 2 goes further.
dev serverA local server (Vite, at localhost:5173) that translates your files on request and updates the page as you save.
effectCode React runs after a render is on screen: useEffect(() => { … }, []). For things that aren't rendering, like fetching.
events upA child reporting something by calling a function its parent passed down as a prop.
fragment<> … </>: groups elements so a component can return them together, without adding an element to the page.
hookA function starting with use that works only while a component renders, at its top level: useState, useEffect.
immutable updateMaking a new value with the change in it, instead of changing the old one. Untouched parts stay the same objects.
JSXHTML-like syntax that compiles to function calls returning plain objects that describe elements.
keyA stable name for an item in a list, so React can match it between renders. On the element returned from map.
lifting state upMoving state to the closest common parent of every component that needs it, and passing it down.
node_modulesThe folder npm install fills with packages. Never edited, zipped or committed.
Object.isSame-object check. How React decides whether new state is different from the old.
propsThe one object a component is called with: the attributes written on its tag. Read-only; they flow down.
public/Vite serves this folder's files as they are: public/matrix.json is /matrix.json.
pureSame output for the same input, and no side effects. React expects components and updaters to be pure.
reconciliationReact comparing a render's output with the previous one and changing only the DOM that differs.
re-renderReact calling a component function again after its state (or its parent) changed.
stateData a component remembers between renders, held by useState. Changing it re-renders.
StrictModeA development-only checker that calls components, updaters and effects twice to expose impure code.
updater functionA function given to a setter, (prev) => next, run on the latest state.
ViteThe dev server and build tool: npm run dev, npm run build.

How to know you're ready

You're ready for the lab if you can do all of these without looking anything up:

  1. Draw App → Header, Matrix → Cell, Stats, and say what each one owns and what it receives.
  2. Trace a prop down: how the number 5 ends up as the text of one button.
  3. Trace an event up: from a click to setMatrix, naming every function on the way.
  4. Say why the numbers live in App, and not in Cell or Matrix.
  5. Write incrementAt from memory, with untouched rows kept as the same arrays.
  6. Say what React's useState does differently from the one you wrote in JS Lab 1, and why it can return a plain value.
  7. Say what a key is for, why the index is fine in this grid, and what key={value} would break.
  8. Say why the stats are computed, not stored.
  9. Say what happens between setMatrix(next) and the screen changing — and why the button keeps its focus.
  10. Explain the useEffect with [], and why the fetch can't go in the component's body.

React vs by hand

useState(START)By hand: useState(START, render) → [getState, setState] (JS Lab 1 §15). React needs no render argument and gives you the value.
return (JSX)By hand: render() calling region functions with createElement and textContent (JS Lab 2 §07). The component's return is the render.
reconciliationBy hand: previous.x !== state.x per region (JS Lab 2 §08). React compares per element.
key={id}By hand: data-id and Number(dataset.id). React matches list items by key.
onClick={() => …}By hand: one delegated listener and closest() (JS Lab 1 §13). React: a handler on each element; it delegates for you.
setX((prev) => …)Same as by hand: an updater, run on the latest value (JS Lab 1 §05).
computed in renderSame as by hand: derived data, never stored (JS Lab 2 §06).
useEffect(…, [])By hand: calling load() yourself at start-up (JS Lab 2 §07).
