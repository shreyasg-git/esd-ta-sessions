03

What an API contract is

Coretwo teams, one interface

A frontend and a backend are usually built by different people, at the same time. The frontend team can't write a single fetch until it knows what /api/courses returns: an array or an object? Is the field seatsLeft or seats_left? What comes back when the course doesn't exist — a 404 with JSON, or an HTML page?

A contract answers all of that before anyone writes code. It lists every endpoint, every request and response body, every status code and every error. Then both teams build against the contract, not against each other:

  • The frontend team builds against a mock that follows the contract, so it never waits for the backend. That's exactly how the React labs work.
  • The backend team builds to the contract, and tests against it, so it never waits for a finished frontend.
  • When the two meet, they fit. If they don't, the contract says who's wrong.

You've already been on the frontend side of this. In JS Lab 2, your app called a local course API whose responses you were told in advance; you checked res.ok and built URLs with URLSearchParams because of what that API promised (JS Lab 2 · §04 fetch, URLs and failures). Now you're on the other side: you make the promises.

OpenAPI

OpenAPI is the standard way to write such a contract: a YAML (or JSON) file that people and tools can both read. Because tools can read it, one file gives you documentation (Swagger UI renders it as a web page), mocks, generated client code, and tests. This course's contract is openapi.yaml, OpenAPI version 3.0.

Its first lines make a promise worth reading twice: any backend that conforms to this document works with the course's React app. "Conforms" isn't a matter of opinion; the conformance suite checks it.

In React, this becomes…

The React app calls fetch(`${BASE}/api/courses`), where BASE comes from VITE_API_URL. Empty means the mock; http://localhost:8080 means your backend. Nothing else in the app changes — which only works if your backend and the mock give the same answers.

Q1Your backend answers a missing course with {"error": "not found"} and status 404. The React app shows body.message. What does the user see, and whose bug is it?
Show answer

"undefined" (or nothing). It's the backend's bug: the contract says every error has a message, so the frontend was right to rely on it. That's the point of a contract — it settles the argument.

Paths and operations

Corewhat you can call

Open openapi.yaml in VS Code. It's long, but it has only seven top-level keys:

openapiThe first line: which version of OpenAPI the file is written in, 3.0.3.
infoTitle, version, and a long description: the rules that can't be written as schemas. Section 07.
serversWhere the API runs by default: http://localhost:8080.
tagsGroups for the docs: Auth, Users, Courses, Enrollments.
pathsEvery URL, and what each HTTP method does on it. This section.
componentsReusable pieces — schemas, parameters, responses — that paths refers to. Sections 05–06.
securityThe default: every operation needs a bearer token unless it says otherwise. Section 06.

A path, and its operations

Under paths, each key is a URL. Under each URL, each key is an HTTP method. One method on one path is an operation. Here's /api/courses, shortened:

/api/courses: get: operationId: listCourses summary: List courses, optionally filtered security: [] # public: no token needed parameters: - name: department in: query # ?department=... required: false schema: { type: string } - name: q in: query required: false schema: { type: string } responses: '200': description: Courses sorted by `code` ascending content: application/json: schema: type: array items: { $ref: '#/components/schemas/Course' } post: operationId: createCourse summary: Create a course (ADMIN) requestBody: required: true content: application/json: schema: { $ref: '#/components/schemas/CourseRequest' } responses: '201': ... '400': ...

Read it as a sentence. "GET /api/courses takes two optional query parameters, needs no token, and answers 200 with a JSON array of Course objects. POST /api/courses takes a CourseRequest body and answers 201, or 400…" The in: of a parameter says where it goes: query is after the ?, path is inside the URL, like the {id} in /api/courses/{id}.

In Spring, each operation is one controller method: @GetMapping on /api/courses with two @RequestParam(required = false) parameters. The operationId is a good name for the method.

05

Schemas and $ref

Corethe shape of the JSON

Following a $ref

$ref: '#/components/schemas/Course' means "the thing at that address in this same file": # is the top of the file, then components → schemas → Course. A $ref lets one definition be used in many places. In VS Code, search for Course: (four spaces, so you land on the definition):

Course: type: object required: [id, code, title, description, department, credits, capacity, seatsLeft] properties: id: { type: integer, format: int64, example: 7 } code: { type: string, example: CS501 } title: { type: string, example: Distributed Systems } description: { type: string, nullable: true } department: { type: string, example: Computer Science } credits: { type: integer, example: 4 } capacity: { type: integer, example: 60 } seatsLeft: type: integer minimum: 0 description: '`capacity` minus current enrollments; computed by the server'
  • required lists the fields that must be present. description is in it and is nullable: a course with no description still has "description": null in its JSON. Leaving the key out is a contract break.
  • type: integer, format: int64 is a Java Long. type: string, format: date-time (in other schemas) is an ISO-8601 timestamp, which in Java is an Instant.
  • seatsLeft is "computed by the server": it's not a column you store. Section 09.

Request schemas aren't response schemas

Compare CourseRequest, the body of POST and PUT, with Course, what comes back. The request has no id (the server assigns ids) and no seatsLeft (the server computes it). Two shapes for one entity: that's exactly why Spring Boot Lab 2 gave you request and response DTOs and a mapper. Here the contract decides the shapes, so your DTOs copy them field for field.

CourseRequest: type: object required: [code, title, department, credits, capacity] properties: code: { type: string, pattern: '^[A-Z]{2,4}[0-9]{3}$' } title: { type: string, minLength: 1, maxLength: 150, pattern: '[^\u0000- ]' } description: { type: string, maxLength: 1000, nullable: true } department: { type: string, minLength: 1, maxLength: 60, pattern: '[^\u0000- ]' } credits: { type: integer, minimum: 1, maximum: 6 } capacity: { type: integer, minimum: 1, maximum: 500 }

From schema keywords to Bean Validation

Every limit in a request schema becomes an annotation on your request DTO, and @Valid on the controller parameter enforces them all.

In the schemaOn the DTO field
in required@NotNull (a string that must not be blank: @NotBlank)
pattern: '[^\u0000- ]'@NotBlank — the contract's "not blank", see its Conventions
minLength / maxLength@Size(min = …, max = …)
pattern: '^[A-Z]…'@Pattern(regexp = "^[A-Z]{2,4}[0-9]{3}$")
minimum / maximum@Min / @Max (or @Positive for minimum 1)
format: email@Email
nullable: true, not requiredno @NotNull

A Java record makes a tidy DTO, and the annotations go straight on its components:

public record CourseRequest( @NotNull @Pattern(regexp = "^[A-Z]{2,4}[0-9]{3}$") String code, @NotBlank @Size(max = 150) String title, // … the other four fields, the same way ) {}
Q2A course has no description. Which of these responses conform? (a) {…, "description": null, …} (b) {…, "description": "", …} (c) no description key at all.
Show answer

(a) and (b). description is required, so the key must be there, and it's a nullable string, so null or any string is fine. (c) breaks the contract. Spring's default Jackson setup writes nulls, so a record or DTO with a null field gives you (a) — unless someone turned on NON_NULL.

06

Responses, errors and security

Corestatus codes, ApiError, bearer tokens

One status code, one meaning

Each operation's responses is keyed by status code, as a string. That list is the complete set of answers the operation may give. POST /api/enrollments, for example, lists 201, 400, 401, 404 and 409 — so a 500 or a 200 from it is a contract break, even if the data is right. Learn the codes the contract uses, because the React app reacts to each one differently:

StatusMeans, in this contract
200 OKHere's what you asked for.
201 CreatedCreated; the body is the new resource. Not 200.
204 No ContentDone, and there's no body: logout, drop, delete.
400 Bad RequestYour request is wrong: invalid fields, broken JSON, an id like abc.
401 UnauthorizedI don't know who you are: no token, or a bad, expired or logged-out one.
403 ForbiddenI know who you are, and you may not: a STUDENT creating a course.
404 Not FoundNo such course, enrollment or endpoint.
405 Method Not AllowedThe path exists, the method doesn't. An Allow header lists the ones that do.
409 ConflictValid request, but it breaks a rule: already enrolled, course full, code taken…

Shared responses, and the one error shape

Many operations say '400': { $ref: '#/components/responses/ValidationError' }. Under components/responses you find ValidationError, BadRequest, Unauthorized, Forbidden and NotFound — and every one of them has the same schema, ApiError:

{ "timestamp": "2026-01-15T09:30:00Z", "status": 400, "error": "Bad Request", "message": "Validation failed", "path": "/api/auth/signup", "fieldErrors": { "email": "must be a well-formed email address", "password": "size must be between 8 and 64" } }

Six fields, always all six. status repeats the HTTP status. error is the status's reason phrase. message is for the user. path is the request's path. fieldErrors maps each bad field to a reason for a validation error, and is null for every other error. One shape means the frontend needs one piece of code to show any error. Section 10 builds it.

Security

components: securitySchemes: bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT } security: - bearerAuth: [] # the default for every operation… # …unless the operation says security: [] (public)

So "needs a token" is the default, and the five public operations opt out. A client sends the token as a header: Authorization: Bearer eyJhbGciOi…. The schema can't say which tokens are good or what "ADMIN only" means; that's in the words of section 07.

07

The rules written in words

Coreinfo.description

A schema can say "credits is an integer from 1 to 6". It can't say "a student may not go over 24 credits", or "a logged-out token must stop working". Those rules are in the description at the top of the file, in plain English, under headings. Read it now, all of it. It's short, and the conformance suite checks almost every sentence.

ConventionsJSON everywhere; unknown request fields are ignored; timestamps in UTC; courses sorted by code, enrollments by enrolledAt; 201 carries the new resource; blank query parameters are ignored; what "not blank" means.
ErrorsEvery non-2xx is an ApiError — even 401 and 403 from the security layer. Which problems are 400, 404, 405, 500.
AuthenticationWhat's inside the token; 401 versus 403; authentication is checked before the body; what logout must do.
RolesSTUDENT for every signup; ADMIN is seeded only.
Business rulesEnrolled at most once; full courses take no one; 24 credits at most; codes unique; capacity never below enrollments; deleting a course deletes its enrollments; and the order the enroll rules are checked in.
Required seed dataThe users, courses and enrollments every backend starts with. Section 11.
CORSWhat a browser needs. React Lab 4's job (section 14).

Fixed messages

Clients show message and never parse it — except these, which the contract fixes word for word, so a client may compare them exactly. The suite checks them exactly too: same spelling, same capitals, no full stop.

messageWhen

Access deniedA 403: wrong role, or someone else's enrollment.

Other messages ("No course with id 7", "Email already registered") are yours to word; the suite only checks they exist.

Q3Riya is enrolled in CS201, which is full. She tries to enroll in CS201 again. Which 409 message does she get, and which line of the contract decides it?
Show answer

"Already enrolled in this course". Both rules are broken, and the last business rule says the first in this order wins: not found, already enrolled, full, credit limit. Your code must check them in that order.

09

Level A — the catalogue

CoreGET /api/courses, GET /api/courses/{id}

The entity and the response

Add description (nullable, up to 1000 characters), department and capacity to your Course entity, and make code unique. Don't add a seatsLeft column. A stored counter can drift away from the truth (the Spring Boot bug lab's half-write bug is exactly that). Compute it instead, each time you build the response:

// in the service, when mapping a course to its response DTO long enrolled = enrollmentRepository.countByCourseId(course.getId()); int seatsLeft = (int) Math.max(0, course.getCapacity() - enrolled);

That means level A already needs a minimal Enrollment entity (a user, a course, an enrolledAt) and a User entity, because the seed fills five courses with enrollments and the suite checks their seatsLeft is 0. The enrollment endpoints wait for level C.

Watch the query count

Counting per course inside a loop over 20 courses is 21 queries: the N+1 problem from the Spring Boot bug lab. Fine to start with. Stretch: one grouped query, select e.course.id, count(e) from Enrollment e group by e.course.id, then look counts up in a map.

Sorting and filtering

  • Sorted by code. findAllByOrderByCodeAsc(), or findAll(Sort.by("code")). Filtered lists are sorted too.
  • department: an exact match, ignoring case. ?department=data science %26 ai finds the Data Science & AI courses.
  • q: a substring of the code or the title, ignoring case. ?q=data finds CS201 Data Structures, CS305 Database Systems and DS101.
  • Both: both must match. Blank (?q=, ?q=%20): ignored, as if absent. No match: 200 [], not 404.

Take both as @RequestParam(required = false) String. Derived queries like findByDepartmentIgnoreCaseOrderByCodeAsc work. So does loading all courses sorted and filtering in Java: the catalogue is small, and the contract says so (no paging).

H2 and MySQL disagree about case

MySQL's default collation ignores case, so findByDepartment("data science & ai") matches on MySQL — and finds nothing on H2. Use IgnoreCase (or compare lowercased strings) so your code doesn't depend on the database.

The & in "Data Science & AI"

In a URL, & separates parameters, so a client must send it encoded: ?department=Data%20Science%20%26%20AI (JS Lab 2 · §04: URLSearchParams does it). Spring decodes it before your code sees it — there's nothing to do on the server, except not to break it. Try it with curl:

$ curl "http://localhost:8080/api/courses?department=Data%20Science%20%26%20AI"

On Windows PowerShell, type curl.exe instead of curl (plain curl there is a different command), and put a command that's split with \ on one line.

10

One error shape for everything

CoreApiError and @RestControllerAdvice

Spring Boot Lab 2 had an exception handler. Here it grows into the single place every error passes through. Start with the shape:

public record ApiError(Instant timestamp, int status, String error, String message, String path, Map<String, String> fieldErrors) { public static ApiError of(HttpStatus status, String message, String path, Map<String, String> fieldErrors) { return new ApiError(Instant.now(), status.value(), status.getReasonPhrase(), message, path, fieldErrors); } }

Three details the suite checks: Instant, not LocalDateTime, so the timestamp ends in Z (it's UTC); getReasonPhrase() ("Not Found"), not name() ("NOT_FOUND"); and path from request.getRequestURI().

One advice, one method per kind of error

A @RestControllerAdvice class catches exceptions thrown anywhere in your controllers and services, and turns each into a ResponseEntity<ApiError>. Here's the validation one — the method that builds fieldErrors:

@ExceptionHandler(MethodArgumentNotValidException.class) public ResponseEntity<ApiError> handleInvalid(MethodArgumentNotValidException ex, HttpServletRequest request) { Map<String, String> fieldErrors = new LinkedHashMap<>(); for (FieldError fe : ex.getBindingResult().getFieldErrors()) { // the first reason for each field wins fieldErrors.putIfAbsent(fe.getField(), fe.getDefaultMessage()); } ApiError body = ApiError.of(HttpStatus.BAD_REQUEST, "Validation failed", request.getRequestURI(), fieldErrors); return ResponseEntity.badRequest().body(body); }

The others follow the same pattern. This is the list the suite needs:

ExceptionAnswer
your own (not found, conflict, forbidden…)Its status and message. One exception class carrying an HttpStatus is enough; Lab 2 may already have one.
MethodArgumentNotValidException400, "Validation failed", fieldErrors (above).
HttpMessageNotReadableException400, fieldErrors: null: no body, or broken JSON.
MethodArgumentTypeMismatchException400: /api/courses/abc.
NoResourceFoundException404: no endpoint at that path (Spring Boot 3.2 and later).
HttpRequestMethodNotSupportedException405, with an Allow header: .allow(ex.getSupportedHttpMethods().toArray(HttpMethod[]::new)) on the ResponseEntity builder.
Exception500, "Unexpected server error". Log the exception; never send it.

Not everything reaches the advice

The advice only sees exceptions thrown while Spring MVC handles the request. A request with no token is turned away earlier, by the security filters, before any controller runs — so its 401 never passes through here. Section 12 handles those.

Q4You call /api/courses/abc and get a 500 with "message": "Failed to convert value of type 'java.lang.String' to required type 'long'…". Two things are wrong. What are they?
Show answer

The status: a bad id is the client's fault, so 400 — handle MethodArgumentTypeMismatchException. And the message leaks Java internals; the generic 500 handler should never echo ex.getMessage().

Loading the seed

Coreseed/seed.json, once

The contract says every backend starts with exactly the data in seed/seed.json: three users, twenty courses in five departments, and five enrollments that fill the five full courses. The React labs, the suite and the TAs all count on those logins and those courses.

LoginPasswordRole

seed/README.md walks you through loading it: copy the file into src/main/resources, and write an ApplicationRunner that reads it with Jackson and saves through your repositories — users (with hashed passwords), then courses, then enrollments.

Idempotent: seeding twice must change nothing

On MySQL your data survives a restart. A runner that always inserts would add a second admin and twenty more courses every time — or crash on a unique constraint. Seed only an empty database: if (userRepository.count() > 0) return; at the top of the runner. With H2 in memory every start is empty anyway, which hides the bug until the day you switch.

Do this now — seed, restart, check

Write the runner. Start your backend, stop it, start it again. Then npm run conformance -- --level A: A04 (all twenty courses, exactly as seeded) and A05 (the five full courses have seatsLeft 0) should pass, and GET /api/courses should still have twenty courses, not forty.

Level B — accounts on your JWT

Coresignup, login, me, logout, 401

Your Lab 2 scaffold already has a SecurityConfig and a JWT filter that checks tokens. Level B adds what turns that into accounts: a way to get a token, a way to ask "who am I?", and a way to give a token up. Read your scaffold's security code again first — you'll change it, so know what each line does.

Which endpoints are public

Exactly five: POST signup, login and google, and GET on /api/courses and /api/courses/*. Everything else needs a token. In SecurityConfig, permit those by method and path and end with .anyRequest().authenticated() — deny by default. That one line also gives you the rule "authentication before the body": the filters reject a request with no token before any controller reads the body, so a bad body with no token is a 401, never a 400.

Signup

  • A SignupRequest DTO with email, password, fullName — and no role field. Jackson in Spring Boot ignores unknown fields, so a "role": "ADMIN" in the JSON simply goes nowhere. Every account is a STUDENT.
  • Trim and lowercase the email before you store or compare it. A record's compact constructor does it before validation runs: public SignupRequest { email = email == null ? null : email.trim().toLowerCase(Locale.ROOT); }
  • Store a BCrypt hash, never the password. Email taken → 409. Success → 201 and a user DTO: id, email, fullName, role, createdAt, no password, no hash.

Login, and what goes in the token

Wrong password and unknown email get the same 401, "Invalid email or password", so nobody can find out which emails have accounts. Success → 200 { accessToken, tokenType: "Bearer", expiresIn: 3600 }. The token must carry five claims:

ClaimValue
subthe user's email
role"STUDENT" or "ADMIN"
jtia unique id for this token: UUID.randomUUID().toString(). Logout needs it.
iat, expissued and expires, in whole seconds; exp − iat = expiresIn

If your scaffold already issues tokens, add the missing claims. If it only verifies them, issue one with the same library and the same key it verifies with. With Spring's JwtEncoder the claims look like this (jjwt's builder has the same five pieces):

Instant now = Instant.now().truncatedTo(ChronoUnit.SECONDS); JwtClaimsSet claims = JwtClaimsSet.builder() .subject(user.getEmail()) .claim("role", user.getRole().name()) .id(UUID.randomUUID().toString()) // jti .issuedAt(now) .expiresAt(now.plusSeconds(3600)) .build();

Who am I

GET /api/users/me looks the user up by the token's sub. Identity comes from the verified token, never from the request — the lesson of Lab 2's audit.

Every 401 and 403 as an ApiError

When the security filters turn a request away, Spring Security answers with an empty body. The contract wants an ApiError with "Authentication required". Give Spring Security an AuthenticationEntryPoint (401) and an AccessDeniedHandler (403, "Access denied") that write one:

@Component public class ApiErrorEntryPoint implements AuthenticationEntryPoint { private final ObjectMapper objectMapper; // Spring's: writes Instant as "…Z" public ApiErrorEntryPoint(ObjectMapper objectMapper) { this.objectMapper = objectMapper; } @Override public void commence(HttpServletRequest request, HttpServletResponse response, AuthenticationException ex) throws IOException { response.setStatus(401); response.setContentType("application/json"); ApiError body = ApiError.of(HttpStatus.UNAUTHORIZED, "Authentication required", request.getRequestURI(), null); objectMapper.writeValue(response.getOutputStream(), body); } }

Register it in SecurityConfig with .exceptionHandling(e -> e.authenticationEntryPoint(…).accessDeniedHandler(…)). If your JWT filter writes its own 401 when a token is bad, make it write the same ApiError — or let it pass the request on unauthenticated and let the entry point answer.

Logout that means it

A JWT stays valid until it expires; deleting it in the browser doesn't stop a copy from working. So logout tells the server: remember this token's jti on a denylist, and refuse it from now on. A Map<String, Instant> from jti to expiry, in a @Component, is enough (drop entries once they'd have expired anyway). Then, in the filter, after the signature and expiry checks pass: a denylisted jti is a 401. Revoke by jti, not by user: the same user's other tokens — another browser, another device — keep working, and the suite checks that.

Do this now — level B

npm run conformance -- --level B. B24 and B25 also check that an unknown path is a 404 and a wrong method a 405 with Allow, sent with a valid token — the advice from section 10, reached through your security.

Level C — enrollments, admin and the 409 rules

Corethe one React Lab 4 needs

Enrollments replace your subscriptions

Your Lab 2 slice let a student subscribe to a course. An enrollment is the same idea with the contract's names and rules. The entity: a user, a course, an enrolledAt (Instant), and a unique constraint on (user, course).

OperationDoes
POST /api/enrollmentsBody { "courseId": 7 } — nothing else; the user is the token's. 201 and { id, course, enrolledAt }, where course is a full Course whose seatsLeft already counts this enrollment.
GET /api/users/me/enrollmentsMine, oldest first (ties by id), each with its full Course.
DELETE /api/enrollments/{id}204. No such enrollment → 404. Someone else's → 403 "Access denied".

The rules, in order

Enroll checks four things, and when several fail, the first one in this order decides the answer. Write them in this order, top to bottom, in your service:

// 1. the course exists → else 404 // 2. I'm not enrolled in it already → else 409 "Already enrolled in this course" // 3. its enrollments < its capacity → else 409 "Course is full" // 4. my credits + its credits <= 24 → else 409 "Credit limit of 24 exceeded" // then save, and return the enrollment with the course's new seatsLeft

Exactly 24 credits is allowed; 25 is not. Count only the user's current enrollments, so dropping a course frees its credits.

@Transactional, where it's earned

Enroll reads (is there a seat?) and then writes; two requests for the last seat must not both succeed. Deleting a course is two writes — its enrollments, then the course — that must happen together. Both are service methods with @Transactional. (For the last-seat race, a @Lock(LockModeType.PESSIMISTIC_WRITE) query that loads the course is the usual fix. Stretch.)

ADMIN course writes

  • POST /api/courses → 201 and the Course (seatsLeft = capacity). A code that exists → 409.
  • PUT /api/courses/{id} → a full replacement: every field is required except description, which becomes null when it's left out. Keeping the course's own code is fine; another course's code → 409; a capacity below its current enrollments → 409.
  • DELETE /api/courses/{id} → 204, and the course's enrollments go with it (delete them first: the foreign key won't let you delete a course that still has enrollments).

Put the role check in SecurityConfig: .requestMatchers(HttpMethod.POST, "/api/courses").hasRole("ADMIN"), and the same for PUT and DELETE on /api/courses/*. A URL rule runs in the filters, before the body is read — so a STUDENT gets 403 whatever they send. hasRole("ADMIN") looks for the authority ROLE_ADMIN, so the role you read from the token's role claim needs that ROLE_ prefix.

LazyInitializationException

A @ManyToOne is loaded eagerly unless you mark it fetch = FetchType.LAZY, and Spring Boot's open-in-view is on by default (it logs a warning at startup), so mapping an enrollment's course in the controller often just works. It throws "could not initialize proxy - no Session" when the relation is lazy and the session has already closed: open-in-view turned off, or code running outside a request. Don't depend on either: map it to the DTO inside the @Transactional service method, or load it with the enrollments (join fetch e.course).

Do this now — level C

npm run conformance (C is the default). The suite creates its own courses for these checks and deletes them at the end, so your seed stays as it was. When A, B and C all show ✓, the summary says Ready for React Lab 4 ✓ — add CORS there. That's the milestone this manual is for.

Reading the suite's output

Coreexpected, received, hint

Every check has an id (A07, C21…) and a one-line title saying what it wants. A failed check adds the request it sent, what the contract expected, what came back, and often a hint:

✗ A07 GET /api/courses/999999999 → 404 with the ApiError shape request GET /api/courses/999999999 expected "timestamp": ISO-8601 in UTC, like "2026-01-15T09:30:00Z" received HTTP 404 application/json {"timestamp":"2026-01-15T09:30:00.1234","status":404,…} hint Use java.time.Instant. A LocalDateTime has no zone, so it has no Z at the end.

Read it in that order: what was sent, what was wanted, what came back. Here the status is right and the timestamp has no Z — a LocalDateTime. One line to change.

A way of working

  1. Run one level at a time: --level A until it's green, then B, then C.
  2. Fix the first failure in the lowest level first. Later failures often follow from it: if login fails, most of B and C fail with it.
  3. Reproduce the request by hand — curl or Postman — and watch your backend's log while you do. The request and sent lines tell you exactly what to send. For a request that needs a token, get one with npm run -s token.
  4. Change one thing, rerun, and see the check go green.
$ curl -i http://localhost:8080/api/courses/999999999 $ curl -i -X POST http://localhost:8080/api/enrollments \ -H "Content-Type: application/json" -d "{}"

-i prints the status line and headers too, which is usually where the answer is.

If a run stops halfway

The suite cleans up after itself, even when checks fail. If you kill it mid-run, a few test courses (department "Conformance Testing") may stay behind. They don't break later runs; delete them as the admin, or restart H2.

Working with AI on this

Corerestrict, judge, own

AI is allowed for this, on the terms of Spring Boot Lab 2. The skill is the same one: restrict what it generates to a precise contract, and judge what comes back. Here the contract is already written, and a suite checks the result — but the suite can only tell you whether it conforms, not whether you understand it. You will be asked about your code.

Restrict

  • Give it the contract, not a wish. Paste the operation from openapi.yaml, the schemas it refers to, and the sentences from the description that apply. "Make enrollments work" is not a prompt.
  • One level, or one rule, at a time. Small asks are easy to check, and they save your free-tier prompts.
  • Name your constraints. Your packages and class names; Controller → Service → Repository; constructor injection; records for DTOs; no new dependencies; don't touch the security scaffold unless asked.
  • Paste a failing check. The expected/received block from the suite is a precise bug report.

A prompt that restricts

"Here is POST /api/enrollments and the EnrollmentRequest, Enrollment and ApiError schemas from my OpenAPI contract, and its business rules. My project has Course, User and Enrollment entities (pasted) and an ApiException(HttpStatus, message). Write only EnrollmentService.enroll(String email, long courseId): check the rules in the contract's order, throw ApiException with the exact messages, use constructor injection, and don't change any other class."

Judge

  • Read every line before you paste it. For each one, name the contract rule that earns it; cut what nothing earns. AI loves to add pagination, extra fields, caching, new libraries — none of which the contract asks for.
  • Run the suite. A change that turns one check green and two others red isn't progress.
  • Watch the classics: entities returned from controllers (a password hash in the JSON), permitAll() on everything, LocalDateTime, HttpStatus.name(), a stored seatsLeft, rules checked in the wrong order.

Never let it edit the judge

Don't let an AI change openapi.yaml, the seed or the suite to make a check pass — it will offer. A green run against an edited suite proves nothing, and React Lab 4 runs against the real one.

A second opinion: Schemathesis

Stretchhundreds of requests, generated from the schema

The conformance suite checks the rules the contract states in words: the 409 messages, the credit limit, logout revocation, the seed, auth before body, CORS. No tool can work those out from a schema. Schemathesis does the opposite job: it reads openapi.yaml, generates hundreds of requests — normal ones and very odd ones — and checks every response against the declared shapes and status codes. It is very good at finding the 500 you get from input you never imagined. Both green means your backend is ready.

# once — Python 3.9 or newer $ pip install schemathesis # or: pipx install schemathesis $ st --version

It changes and deletes data

Schemathesis runs as the admin, so it creates, edits and deletes courses — seeded ones included. Run it after the conformance suite, against a database you can throw away: restart H2, or reset MySQL afterwards.

# macOS / Linux — from esd-labs/api-contract, with your backend running $ st run openapi.yaml --url http://localhost:8080 --checks all \ --exclude-checks ensure_resource_availability \ -H "Authorization: Bearer $(npm run -s token)" \ --exclude-path /api/auth/logout --generation-codec ascii
# Windows (PowerShell): a backtick ` continues a line $ $t = npm run -s token $ st run openapi.yaml --url http://localhost:8080 --checks all ` --exclude-checks ensure_resource_availability ` -H "Authorization: Bearer $t" ` --exclude-path /api/auth/logout --generation-codec ascii
OptionWhy
-H "Authorization: Bearer …"Calls everything as admin@esd.local, so the protected operations are tested too. npm run -s token logs in and prints the token.
--exclude-path /api/auth/logoutOtherwise one of its requests logs that token out, and everything after it is a 401.
--generation-codec asciiThe contract counts string lengths in characters; Spring's @Size counts an emoji as two. ASCII-only input avoids reports about that difference.
--exclude-checks ensure_resource_availabilityThat check reports "created resource not found" when it enrolls, deletes the course, then can't find the enrollment. But deleting a course deletes its enrollments: the contract says so.

Each finding has a code (like ST202; st explain ST202 says what it means) and a curl command that reproduces it. The ones Spring backends usually show:

  • A 500 on odd input — an exception your advice doesn't map. The curl command shows the input; find what threw.
  • Schema-invalid data accepted — Jackson is lenient: "credits": "4" becomes 4, "credits": 4.5 becomes 4, "title": 7 becomes "7". The contract says integer and string. Turning off those coercions in Jackson makes them 400s.
  • A response that doesn't match its schema — a missing "description": null, a field with another name, a status the operation doesn't list.
  • 405 without Allow — section 10's last-but-one row.
