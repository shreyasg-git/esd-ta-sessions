M.Tech CSEESD React Bug Lab · AI after prediction

Predict the bug,
then prove it

You get a small React app you've never seen, a bug report from one of its users, and one planted bug. Before you run anything, you write down what's wrong, where it is, and what you'll see when you make it happen. Then you trigger it, fix it, and trigger it again. The written prediction is the point: it's what turns "I changed something and now it works" into "I knew why it broke, and I showed it".

Part 1 · The method
01

How this lab works

Coreone app, one bug, four steps

There are four small apps, all over the same course catalogue you've used since JS Lab 1: a semester planner, a seat watcher, a course comparer and a department explorer. Each comes in eight versions, and each version has exactly one planted bug. Everything else in it works. You get one of those 32 versions. Your neighbours get different ones.

What's in your zip

TRIGGER.mdThe bug report: what a user saw, in their words; the exact steps to make it happen; and what should have happened. It never says where the bug is.
PREDICTION.mdYour prediction. Parts 1–4 are written before you start the app; parts 5–9 after.
src/The app. Components, one or two custom hooks, a small API helper. A few hundred lines; you can read all of it.
mock/The course API from the React labs, served at /api by npm run dev. Don't edit it.
README.mdHow to run it.

The four steps

  1. Predict. Run npm install, and while it runs, read TRIGGER.md and the code. Write parts 1–4 of PREDICTION.md: what's wrong, where, what you'll see when you trigger it, and what your fix will be. Hand them in. No app, no AI.
  2. Trigger. npm run dev, DevTools open, and follow the steps. Did you see what you predicted?
  3. Fix. The smallest change that removes the cause. AI is allowed from here on.
  4. Re-trigger. The same steps, from a fresh page load. The failure is gone, and nothing else broke. Then finish PREDICTION.md.

A TA checks your fix by watching you re-trigger it and hearing you say why, in one sentence. Then the whole class debriefs together (section 10).

02

Why you predict first

Coreand why AI waits

Debugging by poking — change a line, reload, change another — sometimes works. You end up with a working app and no idea what was wrong, so the next time you meet the same bug, you poke again. A prediction changes that, because it's a claim you can check:

// a guess: "the header is broken" // a prediction: "Header reads props.count, but App passes the number as total, so count // is undefined. The header will say 'undefined courses', the console will // show no error, and adding a course won't change it."

The second one can be wrong. That's what makes it valuable. If it comes true, you understood the code. If it doesn't, you've just found the exact spot where your picture of React differs from React — and that's the thing you're here to fix, more than the bug.

It has to be written down, before you run anything. Once you've seen the failure, every explanation feels obvious ("of course it was that"), and you can't tell any more whether you knew or just recognised it. Written first, there's no arguing with it.

Why AI only after

An AI assistant will often name the bug in a few seconds. At work, that's useful. Here it would skip the one step this lab exists for: building the model in your own head. So the rule, the same as the Spring Boot bug lab: parts 1–4 of PREDICTION.md are yours, handed in before any AI tool is open. After that, AI is a second opinion — and you're now in a position to judge it, because you have an opinion of your own. Section 08 has good ways to use it.

A wrong prediction is a good result

The lab is ungraded, and there's no mark for being right. A specific prediction that turns out wrong teaches you more than a vague one that can't. In the debrief, "what fooled you?" is the most useful question in the room.

03

Reading a bug report

CoreTRIGGER.md

Every TRIGGER.md has the same three parts. Here's one for an app that isn't in the lab:

# Bug report — Course Shelf > I click Add on a course and nothing happens. ## Reproduce it 1. Wait for the list of courses. 2. Click Add next to CS101. What should happen: CS101 appears on your shelf.
  • The report is the symptom, in a user's words. Users don't open DevTools, so it's incomplete on purpose: it says what they saw on the screen, nothing about requests or the console.
  • The steps are exact. Follow them exactly — the order, the course codes, the menu settings. "Nearly the same steps" can miss the bug completely.
  • What should happen is the behaviour you're restoring. Your fix is done when the steps produce it.

The report never says where. The symptom is on the screen; the cause is usually somewhere else — in a hook, a helper, a parent component. Finding the path from one to the other is the work.

The Network menu

Every app has a Network menu in its header. It's a practice aid, not part of the app: it asks the mock API to misbehave on purpose, the way a real network does on a bad day.

SettingWhat the API does, from the next request on
NormalAnswers straight away.
SlowWaits 1.2 seconds before every answer.
RandomWaits between 0.1 and 1.5 seconds — so two requests can come back in either order.
FailingAnswers every request with a 500 error and the usual error body.

It's the mock's ?delay=… and ?fail=1 options, which you met in JS Lab 2 · §04, added to every request. Reloading the page sets it back to Normal.

"It doesn't happen every time"

Some reports say this. Believe it. Bugs that depend on timing show up in some runs and not others, so the steps tell you to repeat them. If you run them once and see nothing, you haven't shown there's no bug — run them five or six times.

Q1Your report says "the total is wrong after I remove a course". You run the steps and the total looks right. What do you do?
Show answer

Check that you followed the steps exactly — the same courses, in the same order, with the same Network setting, from a fresh page load. If it still looks right, repeat them a few times and tell your TA. Don't decide the bug isn't there after one try.

04

Writing a prediction

CorePREDICTION.md, parts 1–4

Parts 1–4 of PREDICTION.md ask four things. Here they are, answered twice for the Course Shelf report from section 03 — once weakly, once well. The code behind it:

function CourseRow({ course, onAdd }) { return ( <li> {course.code} {course.title} <button onclick={() => onAdd(course)}>Add</button> </li> ); }
PartWeakStrong
1. What's wrongThe Add button is broken.The button's click handler is never attached: it's written onclick, and React only knows onClick.
2. WhereSomewhere in the course list.CourseRow.jsx, the <button> line. onAdd in the parent is fine.
3. What I'll seeNothing happens when I click Add.Nothing happens, and no request is sent. The console will already show a warning when the page loads: Invalid event handler property `onclick`. Did you mean `onClick`?
4. My fix, and after itFix the button.Rename it to onClick. After it, clicking Add puts CS101 on the shelf, and the warning is gone.

The weak column restates the report. The strong column could be wrong in four different ways, and each one can be checked. That's what you're aiming for. Notice part 3: the strongest predictions say something the report doesn't — what the console, the Network tab, or one more click will show.

Questions that make a prediction specific

  • What does React do, step by step, when the user does the thing in the report? Which handler runs, which setter, which render, which effect?
  • What will the Network tab show: a request, no request, the wrong query string, a 500, a hundred requests?
  • What will the console show: an error, a React warning, nothing at all?
  • What happens if I then do one more thing — change a filter, reload, click again?
  • If I'm torn between two causes, what would I see that tells them apart?

You won't always find the line

If you can't find the exact line before handing in, write the best you have — "the effect in useCourses, I think its dependencies" — and say what you'd check first. A specific guess about the mechanism is worth more than a line number you found by luck.

Part 2 · The tools
05

Your debugging toolkit

Coreconsole, Network, React's warnings, a log

None of these are new. This section puts them in one place, with what each one is good for when the bug is in React code.

The console: errors and their stack

When code throws, the console shows the error and a stack trace: the chain of function calls it happened in, newest first, with file:line links you can click. With React, the top of the stack is often a component — and that's where the error happened, not necessarily where it was caused. If a component crashes on courses.map, the question is where courses came from.

An error thrown while React is rendering takes the whole app down: React removes everything from the page and logs the error, with a line naming the component it happened in. A blank page with an error in the console is that.

The Network tab: what really went to the server

DevTools → Network, filter to Fetch/XHR. Every request the app makes is a row. For bugs in data loading, this is the first place to look, because it shows what actually happened rather than what the code seems to say:

  • Count the rows. One per change of filter? None? Two at start-up? Hundreds?
  • Click a row. Headers shows the full URL — is the filter in the query string? Response shows the body — a list, or an error object?
  • The status column. 200, 404, 500.
  • The waterfall column. When each request started and when it finished. With several in flight, you can see which one finished last.

React's own warnings

In development, React checks a few common mistakes and prints a warning in the console — often before you've clicked anything. Read the console when the page loads. Some you've met:

Each child in a list should have a unique "key" prop. A component is changing an uncontrolled input to be controlled. Invalid event handler property `onclick`. Did you mean `onClick`? Too many re-renders. React limits the number of renders to prevent an infinite loop.

Just as useful is knowing what React doesn't warn about. It doesn't check that your effect's dependency array lists what the effect reads, that you never change state in place, that a key is the item's id and not its position, or that a response is still the one you're waiting for. Those bugs are silent, and they're most of what's worth practising.

A log in the right place

One console.log in the right spot answers the question "did this run, and with what?":

function Shelf({ department }) { const [shelf, setShelf] = useState([]); console.log("render Shelf", shelf); // once per render: did React re-render? useEffect(() => { console.log("effect: loading", department); // did the effect run, and for what? … }, [department]); function put(course) { console.log("put", course.code, shelf); // what does this handler see? … } }

A log at the top of a component runs every time React renders it. If you click and no "render" line appears, React didn't re-render — so the question becomes why not. Delete the logs once you're done.

StrictMode runs things twice — on purpose

Every app's main.jsx wraps <App /> in <StrictMode>. In development only, React then renders each component twice and runs each effect, cleans it up, and runs it again when a component first appears. It's checking that your components and effects survive it. So: a "render" log printed twice, and two identical requests when the page loads, are normal in development. Two is normal; a number that keeps growing isn't.

React DevTools

A browser extension (Chrome, Edge or Firefox) that adds a Components tab to DevTools. Pick a component and you see its props and its state, live, and you can edit them. Under its settings, Highlight updates when components render flashes every component that re-renders — handy for "did that click re-render anything?". It's optional: everything in this lab can be found with the console, the Network tab and a log.

Q1You open an app and the Network tab shows two identical /api/courses requests on load. Bug?
Show answer

Not by itself. In development, StrictMode runs each effect twice when the component first appears, so two requests is expected. Wait a few seconds: if it stays at two, fine. If it keeps going up, that's a real problem.

06

From symptom to suspect

Corewhat you see → where to look

A bug report gives you a symptom. This table gives you somewhere to start looking for each common one, and the question to ask there. It doesn't tell you the answer: several symptoms share a cause, and one symptom can have several. Use it to choose what to read first and what to check in the Network tab or the console — then come back to your prediction.

You seeLook at, and ask
You click, and the screen doesn't change — but it does later, when something else changes.The setter that click reaches. Is it given a new array or object, or the same one, changed? React compares references (JS Lab 1 · §09, §10; JS Lab 2 · §08).
Something you typed, ticked or opened in one row shows up in a different row after a row is removed or moved.The key on that list. Does it identify the item, or its position? Where does that row's state live? (React Lab 1 · §06)
Changing a filter doesn't change the list, and the Network tab shows no new request.The effect that loads the list. Does its dependency array name everything the effect reads? (React Lab 2 · §05)
The Network tab keeps filling with the same request; "Loading…" flickers; the fan spins.The same effect's dependencies. Is one of them a new object, array or function every render — or is the array missing? (React Lab 2 · §05, the dependency array; React Lab 1 · §11, Q2)

Start from the data, not from the line that looks odd

Reading code for a line that "looks wrong" works for typos. For most React bugs, the wrong line looks perfectly normal — the problem is what it does over time. Follow the data instead: where does the value on the screen come from, who sets it, and when?

07

What "fixed" means

Coretwo conditions, both required

A bug is fixed when the trigger no longer reproduces it, and you can say why. Either one alone isn't enough.

  1. The trigger no longer reproduces. Reload the page first, so the Network menu and the app start where the report starts. Then follow the same steps exactly. For a bug that "doesn't happen every time", repeat them as many times as it took to see it, and a few more.
  2. You can say why. One or two sentences: what was happening, and why your change stops it. "It works now" isn't why. "React only attaches a handler called onClick, so onclick was ignored and the click did nothing; renamed, React attaches it" is.
  3. Nothing else broke. Click through the rest of the app once: load, filter, add and remove, set the Network menu to Failing and check you still get a sensible message.

Changes that aren't fixes

Some changes make the trigger stop showing the symptom without touching the cause. They'll come up in the debrief.

  • Removing <StrictMode> to make the doubled request go away. The doubled request was never the bug.
  • A setTimeout "to wait for the state to update". State updates aren't late; the code is reading a value from the wrong render.
  • A try/catch that swallows the error. The page no longer goes blank, and now it shows nothing at all, with no message.
  • Reloading the page in code, or forcing a component to remount, so the stale thing disappears.

The test for each: can you explain the original bug, and does your change remove that? Prefer the smallest change at the cause.

Q1Your fix works, and you can explain it — but it's three times as long as the line you replaced. Is it fixed?
Show answer

By this section's definition, yes. Then look again: a long fix often means you're working around the cause instead of removing it. In the debrief, compare it with how others with the same kind of bug fixed theirs.

08

Using AI — after the prediction

Corea second opinion, not the first

Once parts 1–4 are handed in, you may use any AI tool. Use it to test your understanding, not to replace it. Free accounts run out quickly, so keep prompts small and specific.

Good uses

  • Check your explanation. Paste the report, the one file you think is wrong, and your part 1. "Is this explanation right? What would you check to confirm it?"
  • Ask about a mechanism. "Why does setX((prev) => …) fix this when setX(x + 1) doesn't?" — and then check the answer against the app.
  • Compare fixes. "Here are two fixes I'm considering. Which one removes the cause?"

Not useful here

  • Pasting the whole folder and asking "find the bug" — before or after. You'll get an answer you can't judge.
  • Accepting a fix you can't explain. If the AI's fix works and you don't know why, you're not done (section 07).
  • A fix that adds useMemo, useCallback, useRef or useReducer. They're still on the "not yet" list from React Lab 2. Every bug in this lab has a fix that uses only what you know.

Write down what you asked and what it said in part 9 of PREDICTION.md — especially where it was wrong. AI is confidently wrong about React bugs often enough that catching it is a skill.

09

In the lab

Corethe session, in order

The whole session is the method from section 01, done once, properly, with TAs walking the room. In order:

  1. Get your app. Your TA shares an assignment sheet. Find your row; it names one zip, like react-bug-planner-3.zip. Download that zip from the shared folder, unzip it anywhere, and run npm install inside it.
  2. Predict. While it installs, read TRIGGER.md and src/, and write parts 1–4 of PREDICTION.md. Hand them in the way your TA announces. No app, no AI, until you have.
  3. Trigger. npm run dev, open http://localhost:5173, DevTools open, and follow the steps. Write part 5.
  4. Fix, and re-trigger. AI is allowed now. Reload, run the steps again, click through the rest of the app.
  5. Show a TA. Raise your hand. Re-trigger it in front of them and say why it broke, in a sentence or two.
  6. Finish PREDICTION.md (parts 6–9) and hand it in.
  7. Debrief, all together (section 10).

One bug per student, done fully. Finished early? Ask your TA for a second zip — a different app and a different bug — and do it the same way, prediction first.

Bring

Your laptop with Node.js 20.19 or newer (the same as React Labs 1–3), this page read, and your React Lab folders so you can look things up. The packages are the same versions as those labs, so npm install is usually quick. Raise a hand when you're stuck — the TAs come to you.

10

The debrief

Corewho predicted this? what fooled you?

The lab ends with everyone together. There are only eight kinds of bug across the 32 apps, and the debrief goes through them one at a time. For each one, the TA asks:

  • Who had this one? Hands up. You'll find people whose app looked nothing like yours with the same bug underneath it.
  • Who predicted it? What did you write in part 1, and what made you think so?
  • What fooled you? If your prediction was wrong, what did you believe that wasn't true? This is the part everyone learns from.

Then the TA names the bug, shows it in two different apps side by side, and connects it to the lab where you first met the idea. The names come at the end on purpose: knowing what a bug is called is the least useful thing about it.

Bring your part 9

Have your PREDICTION.md open. If your prediction was wrong, you have the most interesting story in the room.

12

Practice run, unaided

Stretchpredict first, then open the answer

Four small bugs, none of them in the lab's apps. For each one, write your prediction in the same four parts — what's wrong, where, what you'd see, the fix — before you open the answer. If you want to check, paste the snippet into a React Lab app and run it.

P1A user says: "when my plan is empty, there's a lonely 0 on the page."
function PlanBadge({ plan }) { return <div>{plan.length && <span>{plan.length} planned</span>}</div>; }
Show answer

&& returns its left side when that side is falsy. With an empty plan, plan.length && … is 0, and React renders the number 0 (it skips false, null and undefined, but not 0). Fix: {plan.length > 0 && …}. A strong prediction adds: "with one course it's fine; only exactly zero shows it".

P2A user says: "the page doesn't load at all." The console says Too many re-renders.
function Counter() { const [n, setN] = useState(0); return <button onClick={setN(n + 1)}>Clicked {n} times</button>; }
Show answer

onClick={setN(n + 1)} calls setN while rendering, and passes its result (undefined) as the handler. Calling a setter during render asks for another render, which calls it again, forever — React stops it with that error. Fix: pass a function, onClick={() => setN(n + 1)}. Functions are values (JS Lab 1 · §04).

P3A user says: "I can't type in the search box. The cursor's there, but nothing appears."
function Search({ query }) { return <input value={query} placeholder="Search…" />; }
Show answer

A controlled input: React sets its value to query on every render, and nothing ever changes query, so every keystroke is undone. React warns about exactly this in the console: You provided a `value` prop to a form field without an `onChange` handler. Fix: lift the setter in too — <input value={query} onChange={(e) => onQuery(e.target.value)} /> — the controlled-input pattern from React Lab 2.

P4The list loads, and users are happy. But the console shows a warning as soon as the page loads.
useEffect(async () => { const res = await fetch("/api/courses"); setCourses(await res.json()); }, []);
Show answer

An async function always returns a promise, so this effect returns a promise — and React expects an effect to return either nothing or a cleanup function. React warns (useEffect must not return anything besides a function…) and ignores it — so this effect can never have a cleanup, and has nowhere to put one when it needs to ignore an old response. Fix: put the async work in a function inside the effect and call it: useEffect(() => { async function load() { … } load(); }, []) — the shape React Lab 2 uses, which also leaves room for a proper cleanup.

Handing in

Coreungraded — the prediction is what counts

This lab is ungraded, like the Spring Boot bug lab. There's no code to submit and no tests to pass. What you hand in is PREDICTION.md, twice:

  1. Parts 1–4, before you start the app and before any AI tool. Hand them in the way your TA announces at the start of the lab (usually: upload PREDICTION.md to the lab's submission slot, so it carries a timestamp). Then carry on.
  2. The whole file, parts 1–9, by the end of the lab, the same way. Don't edit parts 1–4 after handing them in: a wrong prediction is fine, a rewritten one defeats the point.

Keep your fixed app folder until the debrief is over; your TA may ask to see it or to run a check on it.

Glossary

come back to this
bug reportThe symptom, in a user's words, with steps to reproduce it. Says what, never where.
cleanup (effect)The function an effect returns. React runs it before the effect runs again, and when the component goes away.
closureA function together with the variables it could see when it was created — including the state values of that render.
dependency arrayThe second argument to useEffect: the values the effect reads. React re-runs the effect when one of them changes (by Object.is).
derived valueAnything you can compute from state, like a total. Computed during render, never stored separately.
functional updatesetX((prev) => next): React passes in the current value instead of the one your code captured.
ignore flaglet ignore = false in an effect, set to true in its cleanup, so a late response from an old run is thrown away.
keyHow React tells the items of a list apart between renders. Use the item's id.
mutationChanging an object or array in place (push, sort, arr[i] =). React can't see it, because the reference stays the same.
Object.isReact's "is it the same?" check, for state and dependencies. Two objects are the same only if they're the same reference.
predictionA written, checkable claim about a bug — its cause, its place, what you'll see, and what the fix will change — made before you look.
race conditionA bug where the result depends on which of several things finishes first.
re-triggerRunning the same steps again after a fix, from a fresh page load, to show the failure is gone.
stack traceThe chain of calls an error happened in, newest first, with file and line.
stale closureA function that runs later and still sees the state of the render that created it.
StrictModeA development-only wrapper that renders components and runs effects twice, to flush out code that isn't safe to repeat.
symptomWhat the failure looks like. Often far from the cause.
triggerThe exact steps that make a bug show itself.
