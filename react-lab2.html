How this lab works

Corepull, install, test, run

Same kind of folder as React Lab 1: a Vite app, tests that are the specification, one command to run them. Two things are new: a mock course API that npm run dev serves next to your app, and three Markdown files for the lab day.

Why a mock, and not your own Spring Boot backend? From the browser, a page on localhost:5173 calling a backend on localhost:8080 is a cross-origin call, which the browser blocks until the backend allows it with CORS — and CORS is added in React Lab 4 (The backend contract · §14); the mock is served from the app's own origin, so there's nothing to allow.

02

What you're building

Coretwo slices, one shape

One page, two slices — a slice being one feature, top to bottom: the screen, the logic, the call to the server.

Course searchPre-lab, by hand. A search box; type, and the courses whose code or title match appear. "Searching…", "Search failed.", "No courses match."
Courses — list + addLab day, with AI. Every course in the catalogue, and a form to add one. The new course appears in its place in the list; a duplicate code or a bad field shows the server's message.

The shape of a slice

Both slices are cut the same way. This is the one architectural idea this lab teaches — the seam between the part that shows things and the part that gets and changes them:

CourseSearch owns the query; wires the two below together ├─ useCourseSearch() useState + useEffect + apiFetch ← fetch and logic live here └─ SearchResults results, status → JSX ← only renders CoursesPage calls the hook; passes data down, passes addCourse down ├─ useCourses() useState + useEffect + apiFetch ← fetch and logic live here ├─ CoursesView courses, status, error → JSX ← only renders └─ AddCourseForm owns the half-typed form; onAdd ↑ ← raises "add this course" all of it talks to the server through src/api/client.js → /api

At the end of React Lab 1, one component did everything: it held the state, ran the effect, fetched, and returned the JSX. For a static file that was fine. Here, with loading, errors, a form and a server that says no, that one component becomes the thing nobody can read or test. So the fetching and the logic move into a custom hook, and the component that draws becomes dumb — a compliment, here: it does one thing, and you can test it with nothing but props.

You've done this split before

JS Lab 2 had view functions (state in, plain data out, no DOM, no fetch) and a separate load() that fetched and dispatched events. CoursesView is the view function, now returning JSX. useCourses is load() plus the state it fills, now as a hook.

Not in this lab

Several screens and URLs (routing), Context, a login screen and enrollments are React Lab 3. Pointing the app at your own Spring Boot backend, and CORS, are React Lab 4. Here the client logs in for you (section 03) and the mock API is the server.

Reading the contract for one slice

Coreopenapi.yaml · src/api/client.js

Refresher

fetch resolves for a 404 or a 500 — only "no response at all" rejects — so every call checks res.ok: JS Lab 2 · §04. The whole API specification, its conformance levels and how your own backend is checked against it are covered in the backend contract. This section reads just the two operations the Courses slice needs.

Every React lab talks to one API: the course catalogue. Its contract is a file called openapi.yaml — an OpenAPI document. It lists every endpoint: its path and method, what goes in (query parameters, a request body), and what comes back for each status code, with the shapes of the data written once under components.schemas. It is frozen. The mock in mock/ implements it; your Spring Boot backend grows into it.

Four questions for any endpoint

  1. Method and path — what do I call?
  2. What goes in — parameters, a body, a token?
  3. What comes back when it works — which status, which shape?
  4. What can go wrong — which statuses, and what should the screen do for each?

GET /api/courses — the list

/api/courses: get: security: [] public: no token needed parameters: - name: q optional: code or title contains q (any case) in: query - name: department optional: exact department name in: query responses: '200': description: Courses sorted by `code` ascending content: application/json: schema: type: array items: { $ref: '#/components/schemas/Course' }

Shortened, with notes on the right. The answers: GET /api/courses, optionally ?q=data; no body, no token; 200 and an array of Course, sorted by code. The contract also says "List order is part of the contract" — so if the screen adds a course, it has to keep that order too.

POST /api/courses — add one

post: no "security: []", so a token is required requestBody: required: true content: application/json: schema: { $ref: '#/components/schemas/CourseRequest' } responses: '201': Course the created course, with its new id '400': ValidationError message "Validation failed", plus fieldErrors '401': Unauthorized no token, or a bad one '403': Forbidden a token, but not an ADMIN's '409': ApiError "Course code already exists"

What you send, and what you get back

FieldCourseRequest — you sendCourse — you get back

Two shapes, because the client never invents an id or a seatsLeft. Notice the types: credits is an integer. Every value an <input> gives you is a string (section 06), so the screen has to convert it.

One error shape for everything

Every non-2xx answer, from any endpoint, has the same body — ApiError:

{ "timestamp": "2026-01-15T09:30:00Z", "status": 400, "error": "Bad Request", "message": "Validation failed", "path": "/api/courses", "fieldErrors": { "code": "must be 2–4 uppercase letters followed by 3 digits" } }

The contract's rule: clients display message; they never parse it. fieldErrors maps each bad field to a reason, only for a 400 validation error; otherwise it's null. So the screen needs no table of messages of its own — the server's words go straight onto it.

StatusWhat the Courses screen does
200 (the list)Show it.
201 (created)Insert the course from the body into the list, in code order. No need to fetch the list again — the body is the new course.
400 Validation failedShow the message, and each fieldErrors reason under its own input.
401, 403Show the message. (The client's stand-in login, below, means you shouldn't see these.)
409 Course code already existsShow the message; keep what was typed so the user can change the code.
500, or no responseLoading the list: "Couldn't load courses: …". Adding: the message, in the form.

The client — given

Nothing in the app calls fetch directly. Everything goes through src/api/client.js:

import { apiFetch, ApiError } from "../api/client.js"; const courses = await apiFetch("/api/courses"); // → Course[] const created = await apiFetch("/api/courses", { method: "POST", body: courseRequest }); // any non-2xx throws an ApiError, built from the contract's error body: error.status // 409 error.message // "Course code already exists" error.fieldErrors // null (or { code: "must be …" } for a 400)

Do this now — read the client

Open src/api/client.js. It's about 60 lines, and it's JS Lab 2's getJSON grown up: fetch, check res.ok, and on failure turn the error body into an ApiError with status, message and fieldErrors. "No response at all" isn't caught — fetch's own TypeError("Failed to fetch") reaches you unchanged. Find the line that does each of those things.

Two details. The base URL is import.meta.env.VITE_API_URL ?? "": empty means "the same origin as the app", which is where npm run dev serves the mock. And adding a course needs an ADMIN token, but logging in is React Lab 3's job — so, as a stand-in, the client logs in as the seeded admin the first time it needs a token, keeps it in a variable, and sends it on every request that isn't a GET. Real apps never hard-code a password; in this lab, you never touch a token at all.

Do this now — call the API from the console

With npm run dev running, open localhost:5173, then DevTools → Console, and the Network tab next to it.

await fetch("/api/courses?q=data").then((r) => r.json()) // [ { id: 2, code: "CS201", … }, { id: 3, code: "CS305", … }, { id: 14, code: "DS101", … } ] const res = await fetch("/api/courses", { method: "POST", headers: { "Content-Type": "application/json" }, body: "{}" }); res.status // 401 await res.json() // { status: 401, error: "Unauthorized", message: "Authentication required", … }

The empty body didn't get a 400: with no token, the contract says a protected endpoint answers 401 before it looks at the body. Click both requests in the Network tab and find the status and the response.

Why the contract is the leash on AI

Ask an AI chat for "a React page that lists and adds courses" and it has to invent everything you didn't say: a path (/courses? /api/v1/courses?), field names (courseName, courseCode), an error shape, a library to fetch with, maybe TypeScript. Every invention is a bug you then debug — with a free account's limited prompts. Give it the contract, and every name, shape and status is fixed. Better still, you can check its output against the contract, line by line. That's what CONTRACT.md is for: this section's endpoints and shapes, the behaviour of the screen, the client, and the rules about what the AI may use.

Q1The form sends credits: "4" — the string straight from the input. What comes back?
Show answer

400, message: "Validation failed", fieldErrors: { credits: "must be a whole number from 1 to 6" }. The contract says integer; a string isn't one, even if it looks like 4. Convert with Number(...) before sending.

Q2Adding CS501 fails, and so does adding cs501. Different statuses — which is which, and why?
Show answer

CS501 is a valid code that already exists: 409, "Course code already exists". cs501 isn't a valid code at all (lowercase): 400 with fieldErrors.code. A 400 is "your request is malformed"; a 409 is "your request is fine, but it conflicts with what's already there".

Q3After an add, the new course shows at the bottom of the list. Which sentence of the contract does the screen break?
Show answer

"List order is part of the contract: courses are sorted by code ascending." The server sends the list sorted; when the screen inserts a course itself, keeping that order is now the screen's job.

Part 3 · The pieces, by hand
04

Loading, error, empty — a view that only renders

Coresrc/search/SearchResults.jsx

Refresher

Components, props, and rendering a list with .map and a key: React Lab 1. One status field instead of several booleans, and why: JS Lab 2 · §05. View functions that only turn data into output: JS Lab 2 · §06.

The moment data comes from a server, a screen has more than one thing to show. While the request is on its way: loading. If it fails: an error. If it worked and there's nothing: empty. Otherwise: the data. A search box adds a fifth: idle, nothing typed yet. Forget one, and the user stares at a blank space, unable to tell "still loading" from "nothing matched" from "broken".

One status, not results.length

It's tempting to decide what to show from the data: results.length === 0 means "nothing". But an empty array is ambiguous: not loaded yet, loaded and empty, and failed all look the same. So the hook (next section) reports a status — one field, one of "idle", "loading", "ready", "error" — and the view picks its output from that.

Early returns

A component is a function, so it can return early. return null renders nothing at all.

export function SearchResults({ results, status }) { if (status === "idle") return null; if (status === "loading") return <p>Searching…</p>; // … "error", and "ready" with no results … return ( <ul className="results"> {results.map((course) => ( <li key={course.id}>…</li> ))} </ul> ); }

Exercise — SearchResults

PropsRenders
status "idle"nothing (null)
status "loading"<p>Searching…</p>
status "error"<p>Search failed.</p>
status "ready", no results<p>No courses match.</p>
status "ready"a <ul>, one <li key={course.id}> per course: CS101 · Programming Fundamentals

The key is the course's id — a stable identity from the data. Never the array index for a list that can change (React Lab 1): insert one course in the middle and every index after it now points at a different course.

Why "only renders" pays

Open test/search/SearchResults.test.jsx. Every test renders the component with an array and a string — no server, no waiting, no setup. The last one replaces fetch with a stub and checks it was never called. That's the property you'll demand of the AI's CoursesView in the lab, and the test for it there looks exactly the same.

Q1What should a search show while the user's second query is loading — the first query's results, or "Searching…"?
Show answer

Either can be right; it's a choice. This lab shows "Searching…", because the old results answer a question the user is no longer asking. What matters is that the choice is made in one place — the view, from status — and not by accident.

05

Effects that fetch: dependencies and cleanup

Coresrc/search/useCourseSearch.js

Refresher

React Lab 1 ended with useEffect(() => { … fetch … }, []): run this once, after the component first appears. And JS Lab 2 solved responses that arrive out of order with track(), a closure that knows whether it's still the latest call: JS Lab 2 · §09. This section joins the two.

What an effect is for

Rendering must be pure: from props and state, compute JSX, and nothing else — React may call your component more often than you expect. Talking to a server is a side effect: it reaches outside the component. So it goes in useEffect, which React runs after the screen has been updated. "After every render where something it depends on changed" — which is what the second argument says.

The dependency array

You writeReact runs the effect
useEffect(fn, [])Once, after the first render. Loading a list when a page appears.
useEffect(fn, [q])After the first render, and after any render where q changed — compared with Object.is, the same reference check as JS Lab 2 · §08.
useEffect(fn)After every render. With a setState inside: render → effect → fetch → setState → render → effect → … a request loop.

The rule: list every value from the component that the effect reads. Imports (apiFetch) and state setters (setResults) never change, so they don't count. For a search, that leaves the query.

One trap follows from Object.is. An object, array or function created during render — const params = { q }, [q], () => … — is a new value on every render, so as a dependency it never compares equal: the effect re-runs after every render, as if there were no array, and with a setState inside, that's the request loop again. Depend on primitives — the query string — and build any object you need inside the effect.

Cleanup, and the ignore flag

An effect may return a function: its cleanup. React calls it before running the effect again (the query changed) and when the component goes away. That's the exact moment JS Lab 2's track() needed: "a newer one has started". So the latest-only rule takes four lines:

useEffect(() => { let ignore = false; apiFetch(`/api/courses?${new URLSearchParams({ q })}`).then((courses) => { if (!ignore) setResults(courses); }); return () => { ignore = true; }; }, [q]);
type "data" effect A runs: request A ignoreA = false type "learn" cleanup A runs ignoreA = true effect B runs: request B ignoreB = false answer B ignoreB is false → setResults(B) the screen shows "learn" ✓ answer A ignoreA is true → dropped an old answer can't overwrite a new one ✓

Each run of the effect has its own ignore — a closure, like track's counter. Without the flag, whichever answer arrives last wins, and a slow "data" can land on top of "learn".

StrictMode runs your effects twice — on purpose

src/main.jsx wraps the app in <StrictMode>. In development, React then mounts each component, runs its effects, runs their cleanups, and runs the effects again — to flush out effects that don't clean up after themselves. That double run happens only when a component first appears. Your search won't show it: on the first render the query is blank, so the effect sends nothing, and after that it runs once per change as you type. You'll see it on lab day, when the Courses page loads its list: two GET /api/courses in the Network tab when the page loads. That's expected in development, and a production build (npm run build) runs it once. With an ignore flag, the first answer is dropped. Without one, both answers set state — harmless while they're identical, wrong the day they differ.

Exercise — useCourseSearch(query) → { results, status }

  1. Trim the query. A blank query sends no request and returns { results: [], status: "idle" }.
  2. Otherwise GET /api/courses?q=… with apiFetch, building the query string with URLSearchParams (JS Lab 2 · §04) so R&D can't break the URL.
  3. Status "loading" while it's on its way, "ready" with the results, "error" if it failed — set them with useState.
  4. Search again when the trimmed query changes, and only then. Think about what goes in the dependency array: "data" and " data " are the same search.
  5. Only the latest query's answer may reach the screen: the ignore flag, in the .then and the .catch.

The idle case needn't be stored in state: if the trimmed query is blank, just return { results: [], status: "idle" }. It's computed during render, like React Lab 1's stats — but it has to come after the hook calls. Section 07 says why.

Not useEffect(async () => …)

An async function always returns a promise, and React expects an effect to return either nothing or a cleanup function. Use .then/.catch as above, or define an async function inside the effect and call it.

Stretch — watch the race happen

Once section 06 puts the search on screen, start the dev server with a random delay on every request (stop the old one first):

$ MOCK_DELAY=random npm run dev # Windows (PowerShell): $ $env:MOCK_DELAY="random"; npm run dev

Each request now takes 0.1–1.5 s. Type data, then quickly select it and type learn. Now comment out your ignore check in .then and try a few more times: sometimes the "data" results end up under a box that says "learn". Put the check back. (To slow down only the search instead of every request, add &delay=random to the URL in your hook, temporarily.)

Q1Someone writes the search effect with no dependency array at all. What happens?
Show answer

It runs after every render. The answer calls setResults with a new array, which renders, which runs the effect, which fetches again — a loop of requests that never stops. You'd see the Network tab fill up.

Q2This effect declares let ignore = false and checks it in .then, but doesn't return anything. Does it protect against the race?
Show answer

No. Nothing ever sets ignore to true — that's the cleanup's job, and there is no cleanup. The flag looks like protection and does nothing. It's a classic thing to find in AI-written code.

06

Controlled inputs

Coresrc/search/CourseSearch.jsx

Refresher

<label> and <input>, and linking them with for/id: HTML & forms · §14. A form's submit, and event.preventDefault(): JS Lab 1 · §13. Computed keys, { [name]: value }: JS Lab 1 · §08.

The input shows the state

In JS Lab 2 the search box kept its own value and your code copied it into the state. In React you do it the other way round: the state is the one source of truth, and the input displays it. That's a controlled input:

const [query, setQuery] = useState(""); <input value={query} onChange={(event) => setQuery(event.target.value)} />

The loop: you press a key → onChange → setQuery → React re-renders → the input shows the new query. Reactivity, applied to a form field. Because the value lives in state, everything else can use it — here, the hook gets query as its argument. Leave out onChange and you can't type at all: the input keeps showing the state, which never changes (React warns about it in the console).

Labels

<label htmlFor="search-query">Search courses</label> <input id="search-query" type="search" value={query} onChange={…} />

In JSX it's htmlFor, because for is a JavaScript keyword. The pair makes a click on the label focus the input, lets a screen reader announce "Search courses", and lets the tests find the input the way a user does: getByLabelText("Search courses"). No label, no test.

Every value is a string

Even <input type="number"> gives you a string. The contract wants integers for credits and capacity, so the form converts when it sends:

Typed.valueNumber()parseInt()
4"4"44
(nothing)""0NaN
4.5"4.5"4.54
4abc"4abc"NaN4

Use Number and let the server judge: 0, 4.5 and NaN (which JSON.stringify sends as null) all come back as a 400 with a clear reason under the field. parseInt quietly "fixes" 4.5 and 4abc into 4 — the user's mistake disappears instead of being shown.

A form with many fields — what's coming on lab day

One field, one useState. Six fields: one object, and one handler that uses the input's name as a computed key:

const [form, setForm] = useState({ code: "", title: "", credits: "" /* … */ }); function handleChange(event) { const { name, value } = event.target; setForm((prev) => ({ ...prev, [name]: value })); // JS Lab 1 §08 } async function handleSubmit(event) { event.preventDefault(); // no page reload: JS Lab 1 §13 await onAdd({ // events up: React Lab 1 ...form, credits: Number(form.credits), // "4" → 4 capacity: Number(form.capacity), description: form.description === "" ? null : form.description, // empty → null }); } <input name="code" value={form.code} onChange={handleChange} />

Start every field at "", never undefined: an input whose value starts undefined is uncontrolled, and React warns when it switches.

Where the query lives

In CourseSearch, because nobody else needs it. React Lab 1's rule for state: as low as possible, as high as necessary. The course list on lab day is different — the View shows it and adding a course changes it — so it lives higher, in the hook the page calls. The half-typed form isn't shared, so it stays in the form.

Stretch — debounce the search

JS Lab 2's debounce stretch, as a hook. Write useDebounced(value, ms) in src/search/useDebounced.js: it returns value, but only once it has stopped changing for ms milliseconds. One useState for the settled value; one useEffect on [value, ms] that starts a setTimeout, and whose cleanup is clearTimeout — the cleanup runs whenever the value changes again, so the timer starts over. Then, in CourseSearch:

The input still shows every keystroke — it reads query — while the search waits for a pause. One request per word. npm run test:stretch.

Q1A test says Unable to find a label with the text of: Search courses, but the label is right there on screen. What's likely wrong?
Show answer

The label isn't linked to the input: htmlFor missing or not matching the input's id (or for written instead of htmlFor). Or the text differs — "Search course", "Search courses:". Wrapping the input inside the <label> also links them.

Q2Why does the stretch debounce the query before the hook, instead of putting a timer inside useCourseSearch?
Show answer

Each piece keeps one job: the hook fetches for whatever query it's given; useDebounced decides when a value has settled; the component wires them. Debouncing is then reusable for anything, and the hook stays as simple — and as testable — as before.

07

Custom hooks — and why the view gets dumb

Corewhat you just built, and why it's shaped that way

A custom hook is just a function

A custom hook is a function whose name starts with use and that calls other hooks. That's all — nothing to register, no class. useCourseSearch is one: it calls useState twice and useEffect once, and returns what the component needs. The use prefix tells React (and the reader) that the rules of hooks apply inside.

A hook shares logic, not state. Each component that calls it gets its own: put two <CourseSearch /> on a page and you get two queries and two sets of requests. To share state, call the hook once, in the parent, and pass the values down — lifting state, from React Lab 1. (React Lab 3's Context is the other way.)

The rules of hooks

Call hooks only at the top level of a component or a custom hook: not inside an if, a loop, a callback, or after an early return. React tells your useState calls apart by their order — the first call is "state 1", the second "state 2" — so the order has to be the same on every render.

// ✗ when q becomes blank, the hooks below stop being called: the order changes if (q === "") return { results: [], status: "idle" }; const [results, setResults] = useState([]); // ✓ every hook first, every render; decisions after const [results, setResults] = useState([]); const [status, setStatus] = useState("idle"); useEffect(() => { … }, [q]); if (q === "") return { results: [], status: "idle" };

What the split buys you

  1. The view is testable with nothing but props. SearchResults' tests need no server.
  2. The logic is testable with no screen. Open test/search/useCourseSearch.test.jsx: renderHook(() => useCourseSearch("data")) runs the hook inside a tiny test component, result.current is what it returned on the latest render, and rerender({ q: "learn" }) is "the user typed something else". The race test there holds two answers back and releases them in the wrong order.
  3. The component reads in five seconds. CourseSearch is wiring: one state, one hook, one view.

P1Optimistic add: show the new course in the list the moment the user submits, replace it with the server's version on success, and take it out again on failure.
Show answer
async function addCourse(request) { const temp = { ...request, id: `pending-${request.code}`, seatsLeft: request.capacity }; setCourses((prev) => [...prev, temp].sort(byCode)); try { const created = await apiFetch("/api/courses", { method: "POST", body: request }); setCourses((prev) => prev.map((c) => (c.id === temp.id ? created : c))); return created; } catch (error) { setCourses((prev) => prev.filter((c) => c.id !== temp.id)); throw error; } }

Every update is an updater function, because by the time the answer arrives the list may have changed. The trade-off: it feels instant, but on a 409 the course appears and then vanishes. Worth it when failures are rare; with a form the server often rejects, the plain version is the better default.

Show answer

useCourses(department): the effect builds the URL with URLSearchParams (so "Data Science & AI" survives), depends on [department], and keeps its ignore flag — it's now useCourseSearch's shape exactly. The page owns department in a useState and renders a controlled <select>; the View doesn't know filtering exists.

P4Find both bugs: useEffect(async () => { const data = await apiFetch("/api/courses"); setCourses(data); });
Show answer

One: the effect function is async, so it returns a promise where React expects nothing or a cleanup (React warns). Two: no dependency array, so it runs after every render, and setCourses with a new array causes the next render — requests forever. And with no cleanup there's no ignore flag either.
